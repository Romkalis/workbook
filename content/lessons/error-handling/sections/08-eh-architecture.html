Обработка ошибок в приложении

Последняя часть лекции отвечает на вопрос «как организовать всё это в настоящем приложении». Ответ лектора — граница ошибок плюс свои классы ошибок.

Граница ошибок

Граница ошибок (error boundary) — место, через которое ошибки не проходят дальше: там их ловят, записывают и превращают в понятное состояние интерфейса. Лектор оговаривается, что в React (популярная библиотека для интерфейсов) есть компонент с таким названием, но имеет в виду общую идею. Самая внешняя граница — try...catch вокруг точки входа приложения (функции main): всё, что не поймали глубже, попадёт сюда.

Исправленная версия кода лекции (классы из раздела о своих ошибках):

class GoogleApiError extends AppError {
  constructor(message, { status, code, cause } = {}) {
    super(message, { cause });
    this.status = status;
    this.code = code;
  }
}
class DatabaseError extends AppError {
  constructor(message, { code, cause } = {}) {
    super(message, { cause });
    this.code = code;
  }
}

async function callGoogleApi() {
  try {
    return await googleApi();
  } catch (error) {
    throw new GoogleApiError('Google API недоступен', {
      status: error.statusCode, code: error.code, cause: error,
    });
  }
}

async function main() {
  try {
    await callGoogleApi();
  } catch (error) {
    if (error instanceof GoogleApiError) {
      showMessage('Сервис карт временно недоступен');
    } else if (error instanceof DatabaseError) {
      showMessage('Не удалось сохранить данные');
    } else {
      showMessage('Что-то пошло не так');
    }
    logError(error);
  }
}

Код запущен в Node.js 22 с заглушками (простыми функциями-подставками, которые только печатают в консоль) showMessage и logError: main пошла по ветке GoogleApiError, у ошибки были status: 404, code: 'NOT_FOUND' и исходный объект в cause. В лекции ветвление сделано через return console.log(...) — короче, но смешивает возврат значения и вывод; цепочка if...else читается проще.

Одна граница на всё приложение — минимум. В интерфейсе удобнее несколько: у каждого независимого блока (лента, корзина, виджет погоды) своя обработка, и сбой одного не ломает остальные. Синхронный try в main не поймает ошибки в обработчиках событий и таймерах, которые сработают позже, поэтому к нему добавляют глобальные error и unhandledrejection.

Что показать пользователю

  • Говорите, что случилось и что делать: «Нет соединения. Проверьте интернет и нажмите «Повторить»», а не «Error: Failed to fetch».
  • Не показывайте стек, коды и технические подробности: пользователю они не помогут, а злоумышленнику подскажут устройство системы.
  • Сохраняйте введённое: ошибка при отправке формы не должна стирать текст.
  • Не оставляйте вечный индикатор загрузки: снимайте его в finally.
  • Различайте временные сбои (сеть, 503 — можно повторить) и постоянные (404, ошибка валидации — повтор не поможет).

Логирование

Программа модуля называет логирование отдельной целью. Минимум — console.error(error): в отличие от console.log, он помечает запись как ошибку и показывает стек. Но консоль пользователя вы не видите. В продакшене (рабочей версии сайта, которой пользуются люди) ошибки отправляют в сервис мониторинга (Sentry, Rollbar, Datadog; например, документация Sentry для JavaScript — из общих знаний): он собирает их из глобальных обработчиков и границ, группирует одинаковые и показывает стек, браузер и действия пользователя перед сбоем. Пишите в журнал объект ошибки целиком, с name, message, stack, своим кодом и cause, а не только текст.

Чек-лист

Выбрасываю только Error и наследников. У своих классов задан name. catch обрабатывает свои ошибки и пробрасывает чужие. В асинхронном коде есть await или .catch. Статус fetch проверяется. Есть граница с понятным сообщением и глобальные error и unhandledrejection. Ошибки попадают в журнал со стеком.
