throw и try...catch...finally

throw

throw прерывает выполнение текущей функции. Дальше движок поднимается по стеку вызовов — к функции, которая вызвала эту, потом к её вызывающей и так далее — пока не найдёт подходящий catch. Если не нашёл, ошибка становится неперехваченной (uncaught): в консоли появляется красное «Uncaught TypeError...», текущий скрипт или обработчик события останавливается.

function divide(a, b) {
  if (b === 0) {
    throw new RangeError('Делить на ноль нельзя');
  }
  return a / b;
}

Выбрасывать ошибку стоит, когда функция не может выполнить своё обещание и не должна молча вернуть мусор. Это лучше, чем вернуть null и надеяться, что вызывающий проверит.

try...catch

try...catch выполняет код в блоке try. Если там (или в функциях, которые он вызывает) выброшена ошибка, выполнение try обрывается и управление переходит в catch, куда передаётся выброшенное значение. Если ошибки не было, catch пропускается.

try {
  const settings = JSON.parse(localStorage.getItem('settings'));
  applySettings(settings);
} catch (error) {
  console.error('Настройки повреждены, берём стандартные', error);
  applySettings(DEFAULT_SETTINGS);
}

Если объект ошибки не нужен, скобки можно опустить: try { ... } catch { ... }. Это возможно с ES2019 (версия стандарта 2019 года); лектор упоминает, что «раньше было обязательно».

Переменная error видна только внутри catch, а переменные, объявленные внутри try через let и const, — только внутри try. Нужный результат объявляйте снаружи.

finally

Блок finally выполняется всегда: после успешного try, после catch и даже если внутри был return или ошибка выброшена дальше. Его используют для «уборки»: спрятать индикатор загрузки, закрыть файл, снять блокировку кнопки.

button.disabled = true;
try {
  await sendForm(data);
  showMessage('Отправлено');
} catch (error) {
  showMessage('Не получилось, попробуйте ещё раз');
} finally {
  button.disabled = false;
}

Две проверенные в Node.js 22 тонкости. Функция try { return 'try' } finally { console.log(...) } сначала напечатала сообщение из finally, а потом вернула 'try'. А если в finally тоже есть return, он перекрывает результат try: функция вернула 'finally'. Так же return в finally «съедает» выброшенную ошибку, поэтому return в finally не пишут.

Задача 3. Индикатор загрузки всегда выключается ★★☆ практика

Напишите withLoading(setLoading, task): включает индикатор, выполняет асинхронную task, выключает индикатор при любом исходе и возвращает результат задачи (или пробрасывает её ошибку).

Зачем: вечный спиннер после ошибки сети — классический баг. Выключение, написанное только в ветке успеха, срабатывает в 99% случаев и ломается именно тогда, когда пользователю и так плохо.

Решение и разбор
export async function withLoading<T>(setLoading: (on: boolean) => void, task: () => Promise<T>): Promise<T> {
  setLoading(true);
  try {
    return await task();
  } finally {
    setLoading(false);
  }
}

finally выполняется и после return, и после исключения. Ошибка при этом продолжает путь наверх. await внутри try обязателен: без него функция вернула бы промис сразу, finally выключил бы индикатор до окончания задачи, а ошибку задачи try бы не увидел.

Задача 4. Что вернёт функция ★★★ с подвохом

Не запуская код, скажите, что вернут a(), b() и c(). Потом проверьте.

function a() { try { return 'try'; } finally { console.log('finally'); } }
function b() { try { return 'try'; } finally { return 'finally'; } }
function c() { try { throw new Error('потерялась'); } finally { return 'ok'; } }
// fns.ts
export function a() { try { return 'try'; } finally { void 0; } }
// eslint-disable-next-line no-unsafe-finally
export function b() { try { return 'try'; } finally { return 'finally'; } }
// eslint-disable-next-line no-unsafe-finally
export function c() { try { throw new Error('потерялась'); } finally { return 'ok'; } }

Зачем: return в finally молча отменяет и результат, и ошибку из try. Функция c «съедает» исключение без единого catch. Это ловушка, которую линтер ловит правилом no-unsafe-finally.

Решение и разбор
// ответ.txt
a() → 'try' (а в консоли «finally»)
b() → 'finally'
c() → 'ok', ошибка пропала

finally выполняется всегда, и если в нём есть свой return, он побеждает. Поэтому правило простое: в finally только уборка (закрыть файл, снять индикатор), без return и throw. Скрытая проверка прогоняет эти функции и подтверждает ответ.

Ловить только то, что умеете обработать

Пустой catch — главная ошибка новичков. Он прячет не только ожидаемую проблему, но и любой баг рядом: опечатку в имени функции вы будете искать часами. Правило из главы javascript.info (на русском): catch должен обрабатывать только те ошибки, которые он знает, и пробрасывать остальные.

try {
  user = parseUser(json);
} catch (error) {
  if (error instanceof SyntaxError) {
    showMessage('Сервер прислал повреждённые данные');
  } else {
    throw error; // не наш случай — пусть ловят выше
  }
}

Проверять тип через instanceof надёжнее, чем через error.name === '...' или текст сообщения: тексты отличаются в разных браузерах.

Задача 5. Ловить только своё ★★☆ практика

Функция loadSettings(read) читает строку настроек через read() и разбирает JSON. Если JSON испорчен, вернуть настройки по умолчанию { theme: "light" }. Любую другую ошибку (например, read упал из-за прав доступа) — пробросить дальше, а не скрыть.

Зачем: catch, который ловит всё подряд, прячет настоящие поломки: вместо «нет прав на файл» пользователь молча получает настройки по умолчанию и не понимает, почему его тема сбрасывается. Ловите то, что умеете исправить.

Решение и разбор
export interface Settings {
  theme: 'light' | 'dark';
}
const DEFAULTS: Settings = { theme: 'light' };

export function loadSettings(read: () => string): Settings {
  const raw = read();
  try {
    return JSON.parse(raw) as Settings;
  } catch (err) {
    if (err instanceof SyntaxError) return DEFAULTS;
    throw err;
  }
}

Самое надёжное — сузить сам try: read() вынесен из него, поэтому его ошибки до catch даже не доходят. Проверка instanceof SyntaxError внутри — второй рубеж, на случай если блок разрастётся. Проверку формы настроек здесь опустили. В реальном коде после JSON.parse её стоит сделать, как в уроке Состояние и отрисовка.

Когда try не нужен

  • Ожидаемые ситуации лучше проверять заранее: пустое поле формы — это if, а не исключение.
  • Не оборачивайте каждую строку в отдельный try. Обычно достаточно ловить ошибки на границах: обработчик клика, загрузка данных, точка входа приложения — функция, с которой оно запускается (раздел об архитектуре).
  • try...catch работает синхронно: он не поймает ошибку, которая произойдёт позже, в колбэке таймера или события. Об этом — раздел про асинхронный код.

Задача 6. Результат вместо исключения ★★☆ практика

Напишите attempt(fn) и attemptAsync(fn): выполняют функцию и возвращают [null, value] или [error, null], где error всегда экземпляр Error (бросить могли и строку). Перепишите с их помощью цепочку из двух шагов без вложенных try.

Зачем: вложенные try на каждом шаге читаются тяжело, а забытый try роняет программу. Кортеж «ошибка или значение» (как в Go) делает обработку явной и линейной. Важно понимать, когда этот подход уместен, а когда исключение честнее.

Решение и разбор
export type Attempt<T> = [Error, null] | [null, T];

const toError = (e: unknown) => (e instanceof Error ? e : new Error(String(e)));

export function attempt<T>(fn: () => T): Attempt<T> {
  try {
    return [null, fn()];
  } catch (e) {
    return [toError(e), null];
  }
}

export async function attemptAsync<T>(fn: () => Promise<T>): Promise<Attempt<T>> {
  try {
    return [null, await fn()];
  } catch (e) {
    return [toError(e), null];
  }
}

export async function loadProfile(fetchUser: () => Promise<{ id: string }>, fetchOrders: (id: string) => Promise<string[]>) {
  const [userErr, user] = await attemptAsync(fetchUser);
  if (userErr) return { error: `Профиль: ${userErr.message}` };
  const [ordersErr, orders] = await attemptAsync(() => fetchOrders(user.id));
  return { user, orders: ordersErr ? [] : orders };
}

Тип [Error, null] | [null, T] — размеченное объединение по первому элементу. После if (userErr) return TypeScript знает, что user не null. Видно и разное отношение к ошибкам: без пользователя экран не имеет смысла, а без заказов показываем пустой список. Когда это неуместно: если ошибку обрабатывают на много уровней выше (общий обработчик сервера), исключение пройдёт туда само, а кортеж пришлось бы передавать вручную через каждый слой.
