Свои классы ошибок

Встроенных типов мало, чтобы описать проблемы приложения. Сервер вернул 404, пользователь ввёл неправильный email, кончился лимит запросов — всё это Error, но реагировать на них нужно по-разному. Лектор показывает пример: нужно передать вместе с ошибкой код HTTP-статуса, а new Error('...', 404) его просто проигнорирует. Решение — свой класс, наследник Error (глава javascript.info «Custom errors», на русском).

class AppError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = this.constructor.name;
  }
}

class HttpError extends AppError {
  constructor(status, message) {
    super(message ?? `HTTP ${status}`);
    this.status = status;
  }
}

class ValidationError extends AppError {
  constructor(field, message) {
    super(message);
    this.field = field;
  }
}

const error = new HttpError(404);
error.name;                    // 'HttpError'
error.message;                 // 'HTTP 404'
error.status;                  // 404
error instanceof HttpError;    // true
error instanceof AppError;     // true
error instanceof Error;        // true

Что здесь важно:

  • super(message, options) передаёт сообщение и cause в конструктор Error. Он же заполняет stack.
  • this.name = this.constructor.name записывает имя класса. Один раз в базовом классе — и у всех наследников будет правильное имя. Без этой строки name останется 'Error', и в консоли все ваши ошибки будут выглядеть одинаково.
  • Иерархия даёт гибкость проверок: instanceof AppError — «любая наша, ожидаемая ошибка», instanceof HttpError — конкретно сетевая.
Поправка к коду лекции

В лекции и на слайдах классы написаны так: super(); this.message = message; this.statusCode = statusCode;. Это работает, но с двумя недостатками. Сообщение не передано в super, поэтому присваивается вручную. И не задан name: проверка в Node.js 22 показала, что new CustomError('x', 500).name равно 'Error'. В классе GoogleApiError присваивания повторяются ещё раз вместо передачи аргументов в super(message, statusCode). Версия выше делает то же короче и правильнее.

Коды ошибок

Лектор обращает внимание: серьёзные библиотеки и API сопровождают ошибки кодами — числовыми (234, PD3212) или словесными (NOT_FOUND, AuthorisationFailed). Код не меняется при переводе сообщения, по нему удобно ветвиться в коде и искать описание в документации. Его стоит хранить в своём классе ошибки и писать в лог. Например, у ошибок Node.js есть свойство code: 'ENOENT' — файл не найден (из общих знаний).

Оборачивание ошибок: cause

Низкоуровневая ошибка («Unexpected token } in JSON») мало что говорит тому, кто вызывал вашу функцию. Её оборачивают в понятную, сохраняя исходную в cause:

function parseConfig(text) {
  try {
    return JSON.parse(text);
  } catch (error) {
    throw new AppError('Конфиг повреждён', { cause: error });
  }
}

try {
  parseConfig('{');
} catch (error) {
  console.log(error.name, error.message, error.cause.name);
  // AppError Конфиг повреждён SyntaxError
}

В лекции эта же идея реализована вручную: callGoogleApi ловит «сырую» ошибку API и выбрасывает GoogleApiError. С cause исходная ошибка со своим стеком не теряется, и DevTools показывает обе.
