Свои классы ошибок

Встроенных типов мало, чтобы описать проблемы приложения. Сервер вернул 404, пользователь ввёл неправильный email, кончился лимит запросов — всё это Error, но реагировать на них нужно по-разному. Лектор показывает пример: нужно передать вместе с ошибкой код HTTP-статуса, а new Error('...', 404) его просто проигнорирует. Решение — свой класс, наследник Error (глава javascript.info «Custom errors», на русском).

class AppError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = this.constructor.name;
  }
}

class HttpError extends AppError {
  constructor(status, message) {
    super(message ?? `HTTP ${status}`);
    this.status = status;
  }
}

class ValidationError extends AppError {
  constructor(field, message) {
    super(message);
    this.field = field;
  }
}

const error = new HttpError(404);
error.name;                    // 'HttpError'
error.message;                 // 'HTTP 404'
error.status;                  // 404
error instanceof HttpError;    // true
error instanceof AppError;     // true
error instanceof Error;        // true

Что здесь важно:

  • super(...) вызывает конструктор родительского класса. Здесь super(message, options) передаёт сообщение и cause в конструктор Error. Он же заполняет stack.
  • this.constructor — класс, которым создан объект, а .name — его имя в виде строки. Строка this.name = this.constructor.name записывает имя класса в ошибку. Один раз в базовом классе — и у всех наследников будет правильное имя. Без этой строки name останется 'Error', и в консоли все ваши ошибки будут выглядеть одинаково.
  • Запись message ?? `HTTP ${status}` использует оператор ??: если сообщение не передали (undefined), берётся текст по умолчанию.
  • Иерархия даёт гибкость проверок: instanceof AppError — «любая наша, ожидаемая ошибка», instanceof HttpError — конкретно сетевая.
Поправка к коду лекции

В лекции и на слайдах классы написаны так: super(); this.message = message; this.statusCode = statusCode;. Это работает, но с двумя недостатками. Сообщение не передано в super, поэтому присваивается вручную. И не задан name: проверка в Node.js 22 показала, что new CustomError('x', 500).name равно 'Error'. В классе GoogleApiError присваивания повторяются ещё раз вместо передачи аргументов в super(message, statusCode). Версия выше делает то же короче и правильнее.

Коды ошибок

Лектор обращает внимание: серьёзные библиотеки и API сопровождают ошибки кодами — числовыми (234, PD3212) или словесными (NOT_FOUND, AuthorisationFailed). Код не меняется при переводе сообщения, по нему удобно ветвиться в коде и искать описание в документации. Его стоит хранить в своём классе ошибки и писать в лог. Например, у ошибок Node.js есть свойство code: 'ENOENT' — файл не найден (из общих знаний).

Задача 8. Коды ошибок и сообщения для людей ★☆☆ разминка

Сервер возвращает ошибки с кодами: EMAIL_TAKEN, WEAK_PASSWORD, RATE_LIMITED. Напишите messageFor(code, lang) со словарём сообщений на русском и английском. Неизвестный код или язык → общее сообщение на этом языке (или на русском). Тип кода опишите так, чтобы новый код нельзя было забыть перевести.

Зачем: коды стабильны, а тексты меняются и переводятся. Код решает, что делать (подсветить поле, показать таймер), текст — что сказать человеку. Record по union кодов превращает «забыли перевод» в ошибку компиляции.

Решение и разбор
export type ErrorCode = 'EMAIL_TAKEN' | 'WEAK_PASSWORD' | 'RATE_LIMITED';
type Lang = 'ru' | 'en';

const MESSAGES: Record<Lang, Record<ErrorCode, string> & { UNKNOWN: string }> = {
  ru: {
    EMAIL_TAKEN: 'Этот email уже зарегистрирован',
    WEAK_PASSWORD: 'Пароль слишком простой',
    RATE_LIMITED: 'Слишком много попыток, подождите минуту',
    UNKNOWN: 'Что-то пошло не так, попробуйте ещё раз',
  },
  en: {
    EMAIL_TAKEN: 'This email is already registered',
    WEAK_PASSWORD: 'Password is too weak',
    RATE_LIMITED: 'Too many attempts, wait a minute',
    UNKNOWN: 'Something went wrong, please try again',
  },
};

export function messageFor(code: string, lang: string = 'ru'): string {
  const dict = MESSAGES[lang as Lang] ?? MESSAGES.ru;
  return dict[code as ErrorCode] ?? dict.UNKNOWN;
}

Параметры функции — string, а не узкие типы: код и язык приходят с сервера и из настроек браузера, и там может быть что угодно. Узкий тип стоит на словаре: при добавлении кода в ErrorCode компилятор потребует перевод в обоих языках. as при чтении безопасен, потому что отсутствие ключа обработано через ??.

Оборачивание ошибок: cause

Низкоуровневая ошибка («Unexpected token } in JSON») мало что говорит тому, кто вызывал вашу функцию. Её оборачивают в понятную, сохраняя исходную в cause:

function parseConfig(text) {
  try {
    return JSON.parse(text);
  } catch (error) {
    throw new AppError('Конфиг повреждён', { cause: error });
  }
}

try {
  parseConfig('{');
} catch (error) {
  console.log(error.name, error.message, error.cause.name);
  // AppError Конфиг повреждён SyntaxError
}

В лекции эта же идея реализована вручную: callGoogleApi ловит «сырую» ошибку API и выбрасывает GoogleApiError. С cause исходная ошибка со своим стеком не теряется, и DevTools показывает обе.

Задача 7. Свои классы ошибок и HTTP-ответ ★★☆ практика

Создайте базовый AppError и два наследника: ValidationError (с полем field) и NotFoundError (с полями resource и id, сообщение собирается само). У каждого правильное name. Напишите toHttp(err): ValidationError → 400 с полем, NotFoundError → 404, любая другая ошибка → 500 с общим текстом.

Зачем: свои классы превращают «что-то пошло не так» в данные, по которым код принимает решения. Обработчик ошибок сервера и интерфейс различают их через instanceof, а не через разбор текста сообщения, который однажды поменяют.

Решение и разбор
export class AppError extends Error {
  constructor(message: string, options?: ErrorOptions) {
    super(message, options);
    this.name = new.target.name;
  }
}

export class ValidationError extends AppError {
  constructor(
    readonly field: string,
    message: string,
  ) {
    super(message);
  }
}

export class NotFoundError extends AppError {
  constructor(
    readonly resource: string,
    readonly id: string,
  ) {
    super(`${resource} с id ${id} не найден`);
  }
}

export function toHttp(err: unknown): { status: number; body: Record<string, string> } {
  if (err instanceof ValidationError) return { status: 400, body: { message: err.message, field: err.field } };
  if (err instanceof NotFoundError) return { status: 404, body: { message: err.message } };
  return { status: 500, body: { message: 'Внутренняя ошибка' } };
}

new.target.name в базовом классе ставит имя того класса, который реально создают. Не нужно повторять this.name = '...' в каждом наследнике, и имя не разойдётся с классом. Порядок проверок в toHttp важен, если иерархия глубже: сначала частные классы, потом общие. Неизвестные ошибки получают общий текст: подробности — в логи, а не клиенту (урок Web Security).

Задача 9. Цепочка причин ★★☆ практика

Напишите causeChain(err), которая возвращает массив сообщений от внешней ошибки к самой глубокой причине по полю cause. Защититесь от циклической ссылки (ошибка, которая указывает сама на себя) и от cause, который не является ошибкой (тогда добавьте его как строку и остановитесь).

Зачем: когда каждый слой оборачивает ошибку своей (new Error('Не удалось загрузить профиль', { cause })), в логе важна вся цепочка: «профиль → запрос к API → ECONNRESET». Функция, которая её разворачивает, — обычный инструмент логирования.

Решение и разбор
export function causeChain(err: unknown): string[] {
  const chain: string[] = [];
  const seen = new Set<unknown>();
  let current: unknown = err;
  while (current !== undefined && !seen.has(current)) {
    seen.add(current);
    if (!(current instanceof Error)) {
      chain.push(String(current));
      break;
    }
    chain.push(current.message);
    current = current.cause;
  }
  return chain;
}

Set посещённых объектов — стандартная защита обхода от циклов. Цикл кажется надуманным, но достаточно одного неудачного err.cause = err в чужой библиотеке, чтобы логгер ушёл в бесконечный цикл и уронил сервер. cause бывает чем угодно (строка, объект ответа), поэтому неошибки превращаются в строку, и обход останавливается.
