Заголовки, сжатие, кеш и куки

Заголовки — метаданные сообщения: кто спрашивает, что он умеет принимать, в каком формате тело, можно ли его кешировать. Имена заголовков не зависят от регистра (в HTTP/2 их всегда пишут строчными).

Основные заголовки

Свои заголовки можно придумывать. Раньше их называли с префиксом X- (X-Forwarded-For, X-Request-Id), как говорится в вебинаре. Учтите, что с 2012 года (RFC 6648) префикс X- для новых заголовков не рекомендуется, хотя старые так и остались. Ещё одна ловушка: браузер даёт JavaScript прочитать из ответа на кросс-доменный запрос только несколько «безопасных» заголовков, остальные сервер должен явно открыть через Access-Control-Expose-Headers.

Сжатие: encoding — не encryption

Текст (HTML, CSS, JS, JSON) хорошо сжимается, потому что в нём много повторов. Клиент сообщает, что умеет: Accept-Encoding: gzip, br. Сервер сжимает и помечает: Content-Encoding: br. Браузер распаковывает сам, и в response.json() приходят уже обычные данные — делать ничего не нужно.

Проверка на Node.js 22: массив из 200 объектов пользователей в JSON занял 12 181 байт, после gzip — 1 082, после Brotli — 523. Это уменьшение в 11 и 23 раза; на реальных данных выигрыш обычно меньше, но всё равно кратный. Сжатие без потерь (lossless) восстанавливает данные бит в бит; в вебинаре его объясняют на примере замены повторяющихся букв числом повторов.

Вебинар подчёркивает: кодирование (encoding) не защищает данные, его цель — удобство или экономия. Статья Auth0 «Encoding, Encryption and Hashing» разводит три понятия:

КодированиеШифрованиеХеширование
ЦельПредставить данные в другом форматеСкрыть данные от постороннихПолучить «отпечаток» данных
Обратимо?Да, любым, кто знает форматДа, только с ключомНет
ПримерыBase64, UTF-8, gzip, URL-кодированиеAES, RSA, TLSSHA-256, bcrypt для паролей

Частая ошибка новичков — считать Base64 защитой. Строку YWRtaW46MTIz любой раскодирует командой atob и получит admin:123.

Кеширование

Самый быстрый запрос — тот, которого не было. Сервер подсказывает браузеру, как обращаться с ответом:

  • Cache-Control: max-age=31536000, immutable — хранить год и не проверять. Так отдают файлы с хешем в имени (app.3f9a1c.js): при изменении меняется имя.
  • Cache-Control: no-cache — хранить можно, но перед использованием спросить сервер. Несмотря на название, это не запрет кеша.
  • Cache-Control: no-store — не хранить вообще (банковские данные).

Проверка актуальности работает через условные запросы. Сервер присылает ETag: "abc123" (отпечаток версии) или Last-Modified. В следующий раз браузер спрашивает If-None-Match: "abc123", и если ресурс не изменился, сервер отвечает 304 Not Modified без тела. В лекции по HTTP это показано на картинках, которые «не загружаются заново». Принцип REST «кешируемость» (раздел о REST) опирается именно на эти заголовки.

Куки

Кука — небольшая пара «имя=значение», которую браузер хранит для конкретного сайта и автоматически прикладывает к каждому запросу на этот сайт в заголовке Cookie. Так поверх протокола без состояния строится «память»: при входе сервер создаёт сессию в базе, кладёт её идентификатор в куку, и по нему узнаёт пользователя в следующих запросах.

HTTP/1.1 200 OK
Set-Cookie: sessionId=a3fWa; Max-Age=604800; Path=/; Secure; HttpOnly; SameSite=Lax
Сеансовая (session)
Без Expires и Max-Age. Удаляется, когда заканчивается сеанс браузера.
Постоянная (persistent)
Живёт до даты Expires или Max-Age секунд, даже после закрытия браузера.
HttpOnly
Кука недоступна из JavaScript (document.cookie её не покажет). Защищает сессию от кражи через XSS. В DevTools её видно, но изменить её может только сервер.
Secure
Отправляется только по HTTPS (исключение — localhost).
SameSite
Strict — только запросы со своего сайта; Lax — плюс переход по ссылке с чужого сайта; None — всегда, но обязательно вместе с Secure. Защищает от CSRF. Если атрибут не указан, Chrome с 2020 года считает его Lax.
Domain, Path
Для каких поддоменов и путей отправлять куку.

Как установить куку:

  • Сервер присылает Set-Cookie — основной способ, единственный для HttpOnly.
  • JavaScript: document.cookie = 'lang=ru; max-age=86400; path=/'. Присваивание добавляет или обновляет одну куку, а не перезаписывает все. Читать неудобно: document.cookie возвращает одну строку вида "lang=ru; theme=dark", которую надо разбирать.
  • Вручную в DevTools → Application → Cookies.
Поправки к вебинару

1. В вебинаре упомянут способ через <meta http-equiv="set-cookie">. Современные браузеры его игнорируют: Chrome перестал его выполнять в начале 2018 года (версия 65), использовать его нельзя.
2. На вебинаре видно ошибку из домашних работ: document.cookie = 'ru'. Кука должна быть парой имя=значение: document.cookie = 'lang=ru'.
3. Во второй части лектор разбирается, почему сеансовая кука не удалилась после закрытия Chrome. Причина в настройке «Продолжить работу с того же места» (восстановление вкладок): браузер считает сеанс не завершённым и сохраняет сеансовые куки. Safari с другой настройкой удаляет их, как и ожидалось. Полагаться на то, что сеансовая кука пропадёт при закрытии окна, нельзя.

Куки уходят с каждым запросом к сайту, включая картинки и стили, поэтому хранить в них что-то большое невыгодно. Для данных, нужных только на клиенте, есть localStorage (около 5 МБ, не отправляется на сервер). Лимит одной куки около 4 КБ.
