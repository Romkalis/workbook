HTTPS и TLS

Обычный HTTP передаёт всё открытым текстом. Любой, кто находится на пути пакетов (владелец публичного Wi-Fi, провайдер, взломанный роутер), может прочитать пароль и номер карты или подменить ответ. HTTPS — тот же HTTP, но внутри зашифрованного канала TLS (Transport Layer Security). Это не новый протокол, а «обёртка»: методы, заголовки и статусы остаются прежними. Порт по умолчанию — 443 вместо 80.

Статья freeCodeCamp «HTTP vs HTTPS» перечисляет, что даёт HTTPS:

  • Конфиденциальность — перехваченные данные выглядят как мусор.
  • Целостность — данные нельзя незаметно изменить по дороге (вставить рекламу, подменить скрипт).
  • Подлинность — сертификат подтверждает, что вы говорите именно с github.com, а не с поддельным сервером.

Плюс практические причины: браузеры помечают HTTP-сайты как «Не защищено», Google учитывает HTTPS в ранжировании, а HTTP/2, HTTP/3, Service Worker, геолокация, камера и куки с Secure работают только на HTTPS. Замок в адресной строке означает защищённое соединение, но не то, что сайт честный: у фишингового сайта тоже может быть сертификат.

SSL — старое название предшественника TLS. Все версии SSL давно небезопасны и отключены; когда говорят «SSL-сертификат», имеют в виду сертификат для TLS. Актуальны TLS 1.2 и 1.3.

Симметричное и асимметричное шифрование

Симметричное шифрование (AES, ChaCha20) использует один ключ для шифрования и расшифровки. Оно очень быстрое, но как передать ключ собеседнику через открытую сеть так, чтобы его не перехватили?

Асимметричное шифрование (RSA, эллиптические кривые) использует пару ключей. Открытый (public) ключ можно раздавать всем: зашифрованное им расшифровывается только закрытым (private) ключом, который хранится у владельца. Оно решает задачу передачи ключа, но в сотни раз медленнее симметричного.

TLS берёт лучшее от обоих: асимметричная криптография используется в начале, чтобы безопасно договориться об общем сеансовом ключе, а дальше все данные шифруются им симметрично.

Две оговорки из того же видео. Во-первых, в TLS 1.3 рукопожатие сокращено до одного RTT. Во-вторых, обмен ключом через RSA в TLS 1.3 вообще убран. Используется алгоритм Диффи — Хеллмана (обычно на эллиптических кривых, ECDHE): стороны обмениваются открытыми параметрами, и каждая из них вычисляет один и тот же сеансовый ключ, который никогда не передаётся по сети. Плюс такого подхода — прямая секретность (forward secrecy): даже если закрытый ключ сервера украдут потом, записанный раньше трафик расшифровать не получится (из общих знаний). Сертификат при этом всё равно нужен — чтобы убедиться, что на той стороне тот, за кого себя выдаёт.

Поправки ко второму вебинару

1. В вебинаре сказано, что ключ «генерируется на стороне клиента и на стороне сервера, они должны совпасть, и если совпали, значит всё в порядке». На деле ключи не сравниваются: стороны получают одинаковый ключ, потому что вычисляют его по протоколу (или клиент передаёт его зашифрованным). Проверку подлинности выполняет сертификат, а целостность рукопожатия — завершающие сообщения Finished.
2. Метод назван «асинхронным». Правильно — асимметричный; асинхронность здесь ни при чём.
3. В лекции по HTTP сказано, что сервер выдаёт каждому клиенту «свой открытый ключ». Открытый ключ у сервера один и лежит в сертификате; разные для каждого соединения — сеансовые ключи.

Сертификаты и центры сертификации

Как браузер понимает, что открытый ключ действительно принадлежит github.com, а не злоумышленнику посередине? Через сертификат: документ с доменом, открытым ключом, сроком действия и подписью центра сертификации (CA, Certificate Authority). В браузеры и операционные системы встроен список корневых сертификатов доверенных CA. Браузер проверяет цепочку подписей до одного из них, срок действия и совпадение домена — всё локально, без запроса в CA на каждое соединение.

Если проверка не прошла (самоподписанный сертификат, истёк срок, чужой домен), браузер показывает полноэкранное предупреждение «Подключение не защищено». Один из вопросов на вебинаре — почему сайты не открываются при неправильных системных часах. Ответ: браузер сверяет срок действия сертификата с текущей датой; если часы отстают на годы, валидный сертификат выглядит «ещё не начавшим действовать» или «истёкшим».

В вебинаре показан прайс-лист платного CA. Важное дополнение: с 2015 года есть Let's Encrypt — бесплатный автоматический CA; большинство хостингов (Vercel, Netlify, GitHub Pages) выдают сертификаты сами. Платные сертификаты сегодня нужны для особых случаев.

Локальный HTTPS

Во втором вебинаре лектор генерирует самоподписанный сертификат командой OpenSSL и запускает HTTPS-сервер на Node.js:

openssl req -x509 -newkey rsa:2048 -nodes -sha256 -days 365 \
  -keyout key.pem -out cert.pem -subj '/CN=localhost'
import https from 'node:https';
import { readFileSync } from 'node:fs';

https.createServer(
  { key: readFileSync('key.pem'), cert: readFileSync('cert.pem') },
  (req, res) => {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ ok: true }));
  },
).listen(8001);

Проверено в Node.js 22: curl https://localhost:8001/ отказывается соединяться (код выхода 60, «сертификат не проверен»), а curl -k, который пропускает проверку, получает {"ok":true}. Браузер точно так же ругается на такой сертификат — его подписал не доверенный CA, а сам разработчик. Лектор включает флаг Chrome chrome://flags/#allow-insecure-localhost; удобнее утилита mkcert, которая создаёт локальный CA и добавляет его в доверенные системой. Фронтендеру обычно достаточно знать, поддерживает ли сервер HTTPS; генерация сертификатов — задача бэкенда и DevOps.
