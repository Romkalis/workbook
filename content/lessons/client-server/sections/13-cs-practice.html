Практика и вопросы для самопроверки

Упражнения

  1. Откройте любой сайт, DevTools → Network, включите Disable cache и перезагрузите страницу. Найдите первый документ, посмотрите его Timing: сколько ушло на DNS, соединение, TLS, ожидание сервера? Включите столбец Protocol и найдите ресурсы по h2 и h3.
  2. Перезагрузите страницу без Disable cache. Какие ресурсы пришли с кодом 304, какие из кеша (memory cache, disk cache)?
  3. Выполните curl -I https://example.com и curl -v https://example.com -o /dev/null. Найдите в выводе версию протокола, TLS-рукопожатие и заголовки.
  4. Напишите функцию поиска пользователей GitHub из раздела о запросах. Проверьте, что будет при пустой строке поиска, без сети (режим Offline в Network) и при опечатке в домене.
  5. Запустите CORS-сервер из соответствующего раздела и откройте страницу на другом порту (например, npx serve -l 1234). Сделайте fetch GET-запросом, затем DELETE. Посмотрите в Network, когда появляется OPTIONS. Удалите строку с Allow-Origin и посмотрите на ошибку.
  6. В консоли выполните document.cookie = 'lang=ru; max-age=60', найдите куку в Application → Cookies, подождите минуту и проверьте снова.

Вопросы

Почему «в Postman работает, а в браузере ошибка CORS»?

CORS — правило браузера. Он защищает пользователя: не даёт чужой странице читать ответы с его куками. Postman не браузер, политики одного источника у него нет. Запрос из браузера тоже доходит до сервера, но ответ без Access-Control-Allow-Origin браузер не отдаёт скрипту.

fetch вернул ответ 500. Сработает .catch?

Нет. Промис fetch отклоняется только при сетевой ошибке или отмене. На 4xx и 5xx он выполняется, а response.ok будет false. Статус нужно проверять вручную и бросать ошибку самому.

Чем 401 отличается от 403?

401 — сервер не знает, кто вы: нет токена или он истёк. Нужно войти. 403 — сервер знает, кто вы, но действие запрещено. Повторный вход не поможет.

Зачем HTTP/2, если HTTP/1.1 уже переиспользует соединения?

В HTTP/1.1 по соединению одновременно идёт один запрос, а соединений к хосту не больше шести, поэтому ресурсы стоят в очереди. HTTP/2 мультиплексирует много запросов в одном соединении и сжимает заголовки.

Почему HTTP/3 работает поверх UDP, если UDP ненадёжный?

Надёжность реализована внутри QUIC, над UDP. UDP выбрали, потому что его пропускают все сети, а новый транспортный протокол на уровне ОС и роутеров внедрять пришлось бы десятилетиями. QUIC при этом знает о потоках и не блокирует все запросы из-за одного потерянного пакета.

Почему TLS не шифрует всё асимметрично?

Асимметричное шифрование слишком медленное для больших объёмов. Его (или алгоритм Диффи — Хеллмана) используют только в рукопожатии, чтобы получить общий сеансовый ключ, а данные шифруют быстрым симметричным алгоритмом.

Как сервер узнаёт пользователя, если HTTP не хранит состояние?

Клиент передаёт идентификатор в каждом запросе: куку с ID сессии (браузер прикладывает её сам) или токен в заголовке Authorization.

Помогает ли mode: 'no-cors' от ошибки CORS?

Нет. Запрос уйдёт, но ответ станет непрозрачным: статус 0, пустое тело. Прочитать данные нельзя.
