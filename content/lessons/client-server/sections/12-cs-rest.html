API и REST

API (Application Programming Interface) — договорённость о том, как одна программа может пользоваться другой. В вебе под API обычно понимают сервер, который по HTTP отдаёт данные (чаще в JSON) и принимает команды: GitHub API отдаёт пользователей и репозитории, API погоды — прогноз. Какие адреса, параметры и ответы у API, описано в его документации.

Что такое REST

REST (Representational State Transfer) — архитектурный стиль, описанный Роем Филдингом в диссертации 2000 года. Это не протокол и не стандарт, а набор ограничений. Если API их соблюдает, его называют RESTful, и он получает масштабируемость, простоту и надёжность. Вторая часть вебинара разбирает шесть ограничений.

  1. Клиент — сервер. Интерфейс и хранение данных разделены. Сервер ничего не знает о том, как данные показываются, поэтому к одному API можно подключить сайт, мобильное и десктопное приложения.
  2. Без состояния. Сервер не хранит контекст клиента между запросами; каждый запрос несёт всё нужное для обработки, включая токен. Пользователь только что вошёл, но если следующий запрос пришёл без токена, сервер ответит 401.
  3. Кешируемость. Ответ должен явно говорить, можно ли его кешировать и сколько (Cache-Control, ETag). Простое на словах ограничение, по замечанию лектора, на практике реализуется сложнее всего.
  4. Многоуровневая система. Клиент не знает и не должен знать, что за API: один сервер, балансировщик, кеш, CDN или цепочка микросервисов. За этим «занавесом» можно что угодно перестраивать.
  5. Код по требованию (необязательное). Сервер может передать клиенту исполняемый код. Единственное необязательное ограничение, на практике его обычно не обсуждают.
  6. Единообразный интерфейс, из четырёх частей:
    • Идентификация ресурсов: каждый ресурс имеет свой URI (/users/5). Как ресурс хранится на сервере (таблица, файл), клиенту неважно — он получает представление, например JSON.
    • Управление ресурсами через представления: в полученном представлении достаточно данных (например, id), чтобы изменить или удалить ресурс.
    • Самоописывающие сообщения: сообщение несёт всё для своей обработки — метод, Content-Type, кодировку.
    • HATEOAS (hypermedia as the engine of application state): ответ содержит ссылки на возможные действия — у банковского счёта ссылки «пополнить», «снять», «перевести», «закрыть». Признаёт и лектор: большинство API, называющих себя REST, этого не делают.

Как выглядит REST-API на практике

ЗапросДействиеТипичный ответ
GET /usersсписок пользователей200 + массив
GET /users/5один пользователь200 или 404
POST /usersсоздать201 + новый объект
PUT /users/5заменить200 или 204
PATCH /users/5изменить часть200
DELETE /users/5удалить204

Ресурсы называют существительными во множественном числе, действие выражают методом: не /getUsers и /deleteUser?id=5, а GET /users и DELETE /users/5. Эти соглашения и таблица — из общих знаний, в вебинаре их нет.

Альтернативы

Лектор упоминает более старый SOAP — протокол со строгим форматом сообщений в XML, до сих пор живущий в банках и госсистемах. Из общих знаний: GraphQL (клиент одним запросом описывает, какие поля ему нужны), gRPC (двоичный протокол поверх HTTP/2, популярен между микросервисами), WebSocket (постоянный двусторонний канал для чатов и игр). REST не обязателен: API, нарушающий какое-то ограничение, тоже работает, просто его труднее масштабировать.

Пара слов об авторизации

В конце вебинара слушатели просят рассказать об авторизации, и лектор кратко упоминает JWT — токен из трёх частей, который клиент передаёт с каждым запросом, чтобы сервер понял, можно ли выполнить действие. Аутентификация — проверка, кто вы; авторизация — проверка, что вам можно. Подробно токены разобраны в уроке «JWT-авторизация» этого учебника.
