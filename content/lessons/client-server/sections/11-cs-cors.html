CORS

Типичная сцена из обеих лекций: фронтенд на http://localhost:1234 делает fetch('http://localhost:8001/api'), в Network видно, что сервер ответил 200 и даже прислал данные, а в консоли красное сообщение «blocked by CORS policy», и в JavaScript ничего не попадает. Полный справочник — MDN: CORS. Чтобы понимать, что происходит, нужно начать с политики одного источника.

Origin и политика одного источника

Origin — схема, хост и порт. Два URL имеют один origin, только если совпадают все три части.

Политика одного источника (same-origin policy) появилась в Netscape 2 в 1995 году вместе с JavaScript. Скрипт страницы может свободно читать ответы только своего origin. Статья Джейка Арчибальда «How to win at CORS» (там есть интерактивная песочница) объясняет, зачем. Браузер прикладывает к запросу куки того сайта, куда идёт запрос. Если бы любой открытый вами сайт мог сделать fetch('https://your-bank.com/accounts') и прочитать ответ, он получил бы ваши счета, ведь запрос ушёл бы с вашей банковской кукой. Ещё есть ресурсы, защищённые не куками, а сетью: корпоративный интранет (внутренние сайты компании, доступные только из её сети), админка домашнего роутера. Чужой сайт, открытый у вас дома, мог бы их сканировать.

Арчибальд различает origin и site: https://help.bank.com и https://profile.bank.com — разные origin, но один site (сайт определяется по списку публичных суффиксов — доменов вроде .com или github.io, поддомены которых принадлежат разным владельцам). Куки и SameSite работают на уровне site, CORS — на уровне origin.

Старые теги <img>, <script src>, <link rel="stylesheet">, <iframe> грузят ресурсы с любых доменов без разрешения, но страница не может прочитать их содержимое как данные. Арчибальд называет это ошибкой раннего дизайна веба, которую с тех пор латают.

Как CORS разрешает доступ

CORS (Cross-Origin Resource Sharing) — механизм, через который сервер сам говорит браузеру: «этому origin можно читать мои ответы». Браузер добавляет к кросс-доменному запросу заголовок Origin: http://localhost:1234, а сервер отвечает заголовками Access-Control-*. Если разрешения нет, браузер не отдаёт ответ JavaScript.

Ключевая мысль, которую стоит запомнить: запрос до сервера доходит, и сервер отвечает. Блокирует браузер, и только чтение ответа. Поэтому из Postman, curl или Node.js тот же запрос работает: там нет политики одного источника и нет ваших чужих кук, которые нужно защищать.

Поправка к вебинару

Во второй части сказано, что CORS «направлен не столько на защиту клиента, сколько на защиту сервера» — чтобы сервер отдавал данные только «своему» приложению. Это частая путаница. CORS защищает пользователя и его данные от чужих страниц в его же браузере. Сервер он не защищает: любой может отправить запрос с любым заголовком Origin из curl. Доступ к API ограничивают аутентификацией (токены, куки), а не CORS.

Простые запросы

Запрос считается простым, если метод GET, HEAD или POST, заголовки только из «безопасного» списка (Accept, Accept-Language, Content-Language, Content-Type), а Content-Type — один из text/plain, application/x-www-form-urlencoded, multipart/form-data. Такие запросы могла отправить и обычная HTML-форма до появления CORS, поэтому браузер отправляет их сразу и только потом смотрит на ответ: есть ли Access-Control-Allow-Origin с вашим origin или *.

Предварительный запрос

Всё остальное (PUT, DELETE, PATCH, Content-Type: application/json, заголовок Authorization) требует предварительного запроса (preflight). Перед настоящим запросом браузер сам отправляет OPTIONS и спрашивает разрешения. Без preflight такой запрос мог бы что-то изменить на сервере, который о CORS ничего не знает.

Заголовки CORS

Access-Control-Allow-Origin
Какой origin может читать ответ: один конкретный или * (любой). Перечислить несколько через запятую нельзя, хотя в вебинаре сказано обратное: сервер должен сверить пришедший Origin со своим списком и вернуть его одного. При этом добавляют Vary: Origin, чтобы кеши не перепутали ответы для разных origin.
Access-Control-Allow-Methods
Разрешённые методы (в ответе на preflight).
Access-Control-Allow-Headers
Разрешённые нестандартные заголовки запроса, например Content-Type, Authorization.
Access-Control-Allow-Credentials: true
Разрешить запросы с куками. Тогда Allow-Origin не может быть *.
Access-Control-Expose-Headers
Какие заголовки ответа можно прочитать из JS сверх безопасного минимума.
Access-Control-Max-Age
На сколько секунд кешировать ответ на preflight.

Сервер с CORS на Node.js

import http from 'node:http';

const ALLOWED = new Set(['http://localhost:1234']);

http.createServer((req, res) => {
  const origin = req.headers.origin;
  if (ALLOWED.has(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
    res.setHeader('Vary', 'Origin');
  }
  if (req.method === 'OPTIONS') {
    res.setHeader('Access-Control-Allow-Methods', 'GET, POST, DELETE');
    res.setHeader('Access-Control-Allow-Headers', 'Content-Type');
    res.setHeader('Access-Control-Max-Age', '600');
    res.writeHead(204);
    return res.end();
  }
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ ok: true }));
}).listen(8001);

Проверка через curl: с Origin: http://localhost:1234 ответ пришёл с Access-Control-Allow-Origin: http://localhost:1234, preflight OPTIONS вернул 204 со всеми разрешающими заголовками. С Origin: http://evil.example сервер всё равно ответил 200 и телом, просто без CORS-заголовков. Браузер в этом случае скрыл бы ответ от скрипта, а curl спокойно его показал — наглядная иллюстрация того, что CORS работает только в браузере.

Куки в кросс-доменных запросах

По умолчанию fetch на другой origin куки не отправляет и Set-Cookie из ответа игнорирует. Чтобы отправлял, нужно fetch(url, { credentials: 'include' }) на клиенте и Access-Control-Allow-Credentials: true плюс конкретный origin на сервере. Кроме того, кука должна разрешать кросс-сайтовую отправку (SameSite=None; Secure). Статья javascript.info «Fetch: Cross-Origin Requests» (есть перевод на русский) разбирает все эти случаи.

Режимы fetch

Параметр mode у fetch по умолчанию равен 'cors', так что писать его не нужно — лектор во втором вебинаре это и заметил. mode: 'no-cors' ошибку не чинит: запрос уйдёт, но ответ станет «непрозрачным» (opaque) — статус 0, тело пустое, прочитать ничего нельзя. Он нужен только для особых случаев вроде кеширования чужих ресурсов в Service Worker.

Как правильно исправить ошибку CORS

  1. Настроить заголовки на сервере. Правильный способ, если сервер ваш или вашей команды. * допустим для публичного API без авторизации, но не для API с куками.
  2. Прокси на своём origin. Запрос идёт на свой сервер, а тот уже обращается к чужому API — между серверами CORS нет. В разработке это встроено в dev-серверы: опция server.proxy в Vite, rewrites в Next.js. Заодно прокси скрывает секретный ключ API от браузера.
  3. Публичные CORS-прокси вроде cors-anywhere, которые советует лекция по HTTP, годятся только для экспериментов: все ваши данные проходят через чужой сервер. Демо-экземпляр cors-anywhere давно требует ручной активации и для работы не годится.
  4. JSONP из той же лекции — исторический трюк: данные загружаются через <script src>, который не подчиняется политике одного источника, а сервер оборачивает JSON в вызов вашей функции. Работает только для GET и позволяет чужому серверу выполнить любой код на вашей странице. Сегодня его не используют.

Чего делать не нужно: отключать CORS в браузере флагами или расширениями «Allow CORS». У вас заработает, а у пользователей нет, и заодно вы отключите защиту для всех сайтов.
