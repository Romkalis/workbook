Версии HTTP: от 0.9 до 3

MDN в «Evolution of HTTP» прослеживает историю протокола. Важно понимать не даты, а какую проблему решала каждая версия.

HTTP/0.9 и HTTP/1.0

HTTP/0.9 (1991) — протокол в одну строку: GET /page.html. Ни версии, ни заголовков, ни кодов состояния; в ответ приходит только HTML, после чего соединение закрывается.

HTTP/1.0 (1996, RFC 1945) добавил версию в строку запроса, коды состояния, заголовки и Content-Type — теперь можно передавать не только HTML. Но каждый запрос по-прежнему открывал новое TCP-соединение и закрывал его после ответа: страница с тремя стилями и десятью картинками — четырнадцать рукопожатий.

HTTP/1.1

HTTP/1.1 (1997, затем RFC 2616 и RFC 9112) стал основным стандартом веба на почти двадцать лет и до сих пор широко используется. Главное:

  • Постоянные соединения (keep-alive) по умолчанию: одно TCP-соединение обслуживает много запросов подряд, рукопожатие одно.
  • Обязательный заголовок Host — несколько сайтов на одном IP.
  • Передача по частям (Transfer-Encoding: chunked), когда размер заранее неизвестен.
  • Согласование содержимого, кеширование, условные запросы.
  • Конвейеризация (pipelining): отправить несколько запросов, не дожидаясь ответов. Ответы всё равно должны идти строго по порядку, и один медленный ответ задерживает остальные. Из-за этого и багов в прокси браузеры её так и не включили.
Поправка к лекции по HTTP

На слайдах и в лекции интернет-стандартом назван HTTP/1.0, а keep-alive показан как его возможность. Стандартом стал HTTP/1.1, и именно в нём постоянные соединения работают по умолчанию. В 1.0 keep-alive был нестандартным расширением.

Ограничения HTTP/1.1

По одному соединению в каждый момент идёт только один запрос-ответ. Чтобы грузить ресурсы параллельно, браузер открывает несколько соединений к одному хосту, но не больше шести. Вторая часть вебинара показывает демо: сетка из 180 картинок 32×32. По HTTP/1.1 они идут пачками по шесть, последние запросы ждут очереди больше секунды, а при задержке 200 мс вся картинка грузится около 10 секунд, хотя весит всего 184 КБ.

Отсюда целый набор старых трюков: спрайты (все иконки в одной картинке, нужная часть показывается через background-position), склейка всех JS в один файл, раздача статики с нескольких поддоменов (domain sharding), встраивание картинок в CSS как data URI (картинка, закодированная прямо в строку).

Вторая проблема — заголовки не сжимаются. Тело можно сжать gzip, а килобайты кук, User-Agent и Content-Security-Policy едут в каждом запросе как есть.

HTTP/2

HTTP/2 (2015) вырос из экспериментального протокола Google SPDY. Смысл запросов (методы, статусы, заголовки) не изменился, изменилась упаковка:

  • Двоичный формат. Сообщения разбиты на кадры (frames) — небольшие порции, помеченные номером запроса: отдельно кадры заголовков, отдельно кадры данных. Читать руками уже нельзя, DevTools показывает их как обычно.
  • Мультиплексирование. Одно TCP-соединение, по нему одновременно идёт много потоков (streams), кадры разных запросов перемешиваются и собираются обратно по номеру потока. Лимит в шесть соединений больше не мешает. В том же демо все 180 картинок загрузились примерно за 0,6 с даже с задержкой 200 мс.
  • Сжатие заголовков HPACK. Повторяющиеся заголовки передаются ссылкой на таблицу, а не целиком.
  • Приоритеты потоков: CSS важнее картинки внизу страницы.
  • Server Push: сервер мог прислать ресурсы, о которых клиент ещё не спросил (запросили HTML — сразу отправить CSS и JS).
Server Push больше нет

Во втором вебинаре Server Push подан как одна из главных возможностей HTTP/2. На практике он оказался неудобным и часто вредным (сервер пушил то, что уже лежит в кеше браузера). Chrome отключил его в 2022 году (версия 106), Firefox — в 2024-м. Вместо него используют <link rel="preload"> и ответ 103 Early Hints.

Для фронтенда переход на HTTP/2 бесплатный: код не меняется, протокол настраивается на сервере. Браузеры поддерживают HTTP/2 только поверх HTTPS. Спрайты и склейка всего в один файл при HTTP/2 теряют смысл и даже мешают кешированию: изменилась одна иконка — заново качается весь спрайт.

Блокировка начала очереди

HTTP/2 решил блокировку на уровне HTTP, но не на уровне TCP. TCP доставляет байты строго по порядку: если потерялся один пакет, все следующие ждут его повторной отправки, даже если относятся к другим, независимым потокам. Это head-of-line blocking — блокировка начала очереди. Похоже на кассу в магазине: один покупатель ищет кошелёк, и стоит вся очередь, хотя у остальных всё готово. На плохой мобильной сети с потерями HTTP/2 по одному соединению может работать хуже, чем HTTP/1.1 по шести.

HTTP/3 и QUIC

Статьи Smashing Magazine «HTTP/3 From A To Z» и Cloudflare «The Road to QUIC» объясняют: на самом деле нужен был не HTTP/3, а «TCP/2». Обновить TCP невозможно — он зашит в операционные системы и миллионы роутеров. Поэтому новый транспорт QUIC построили поверх UDP, а всю надёжность (подтверждения, повторы, порядок, контроль перегрузки, чтобы не забить сеть) реализовали внутри QUIC. HTTP/3 (RFC 9114, 2022) — это HTTP поверх QUIC.

  • Шифрование встроено. TLS 1.3 — часть QUIC, без шифрования он не работает. Транспортное и TLS-рукопожатие объединены: новое соединение за 1 RTT вместо 2–3, повторное — иногда за 0 RTT.
  • Потоки на уровне транспорта. QUIC знает о потоках, потеря пакета задерживает только свой поток.
  • Миграция соединения. TCP-соединение определяется четвёркой IP и портов; при переходе с Wi-Fi на мобильную сеть оно рвётся. QUIC использует идентификатор соединения, и загрузка продолжается.
  • Развиваемость. Почти всё зашифровано, промежуточные устройства не могут на него опираться, поэтому новые версии выкатываются обновлением браузеров и серверов.

Smashing предупреждает: HTTP/3 не быстрее «по волшебству» из-за UDP. Выигрыш заметен на мобильных и нестабильных сетях; на хорошем канале разница с HTTP/2 небольшая. Вместо HPACK используется QPACK, адаптированный к тому, что потоки приходят не по порядку. Браузер узнаёт о поддержке HTTP/3 из заголовка Alt-Svc или DNS-записи HTTPS и переключается на него.
