Live coding: тесты на записи

Самый весомый блок, 100 баллов. Его оценивают по ходу рассуждений, а не только по зелёным галочкам. Функцию и настройку тестов можно подготовить заранее. Сами тесты пишутся на записи.

План на 7–10 минут

  1. Покажите функцию (1 мин): что принимает, что возвращает, какие правила реализует. Например, calculateCart(cart, promo) возвращает сумму, скидку и итог; SALE10 даёт 10%; неизвестный код скидки не даёт.
  2. Перечислите сценарии вслух (1–2 мин), лучше комментариями или через it.todo (о todo и each). Выбирайте по классам эквивалентности и границам (как): обычный случай, пустая корзина, верный код, неверный код, регистр, повторный расчёт, округление.
  3. Напишите 3–5 тестов (4–5 мин) по схеме подготовить, выполнить, проверить (AAA).
  4. Запустите и разберите (1–2 мин): что проверено, что нет, что добавили бы.

Пример готового набора — tests/cart.test.ts из урока Express на TypeScript: та же функция, пять сценариев. Для функции фильтрации удобен it.each, одна таблица на много случаев:

it.each([
  ['', 'about'],
  ['#/', 'about'],
  ['#/cart', 'cart'],
  ['#catalog', 'catalog'],
  ['#/admin', 'about'],
])('%j → %s', (hash, route) => {
  expect(parseRoute(hash)).toBe(route);
});

Когда тест упал

Задание прямо говорит: удачно найденная и объяснённая ошибка — часть работы. Вот реальный пример. Пишем тест на округление и ожидаем, что 10% от 99 999 копеек — это 9 999 (дробную часть отбросим):

import { expect, it } from 'vitest';
import { calculateCart } from '../src/domain/cart.js';

it('скидка с нецелого результата', () => {
  // 99 999 копеек × 10% = 9 999,9 копейки
  expect(calculateCart([{ productId: 'x', price: 99999, quantity: 1 }], 'SALE10').discount).toBe(9999);
});
FAIL  tests/live.test.ts > скидка с нецелого результата
AssertionError: expected 10000 to be 9999 // Object.is equality
- Expected
+ Received
- 9999
+ 10000

Как рассуждать вслух:

  1. Прочитать сообщение. Ожидали 9999, получили 10000. Разница — одна копейка, значит, дело в округлении, а не в формуле.
  2. Найти место в коде. В calculateCart стоит Math.round: 9999,9 округляется до 10000.
  3. Решить, кто прав, тест или код. Это вопрос правила, а не JavaScript. Если магазин округляет скидку по математическим правилам, неверен тест и ожидание исправляем на 10000. Если скидка должна быть не больше 10%, неверен код, нужен Math.floor.
  4. Зафиксировать решение. Исправить одно из двух, перезапустить, убедиться, что зелёный. Сказать, что правило стоит записать в README.

Такая минута рассуждений показывает больше, чем пять тестов, которые прошли с первого раза. Не бойтесь, если тест упал на записи. Плохо только молча стирать его.

Если тесты на эту функцию уже есть, их не удаляют, а добавляют новые сценарии: границы, неверный ввод, неизменность исходных данных.
