Командная работа: договорённости, доска, ветки, ревью

Первая встреча: о чём договориться

Полчаса созвона в начале сэкономят дни. Запишите итог в README или в первую задачу на доске:

  • Проект, минимум и «если останется время» (предыдущий раздел).
  • Канал связи и время ответа. Например: Discord, отвечаем в течение суток, созвон по вторникам и пятницам в 20:00.
  • Что делаем, если кто-то пропал или не успевает. Например: предупредить заранее; если задача стоит больше трёх дней, её забирает другой. По условию, если напарник пропал совсем, нужно заранее сообщить организаторам.
  • Правила кода: названия веток, формат коммитов, кто и как быстро ревьюит.
  • Дата, когда фичи заморожены и начинаем готовиться к интервью.

Как разделить задачи

Плохой вариант: «я делаю вёрстку, ты логику». Тогда один не сможет рассказать о тестах, а другой — об интерфейсе, и оба ждут друг друга. Лучше резать по фичам сверху донизу: каждый делает свою функцию от логики и тестов до кнопки на экране.

Деплой и страница «О нас»ревьюитделает
Каталог: данные, карточки, фильтры, сортировкаделаетревьюит

Сохранение корзины, маршрутизацияделаетревьюит

Так у каждого есть своя чистая функция для live coding, у каждого есть опыт и автора, и ревьюера, и есть о чём рассказать на вопрос «какие задачи выполняли лично вы».

Доска задач

GitHub Projects удобнее всего: задачи (issues) живут в том же репозитории, а PR закрывает задачу словами Closes #12 в описании. Пошаговая настройка есть в гайде задания, раздел 3. Что важно для оценки:

  • У каждой задачи есть исполнитель и короткий критерий «готово». Например: «повторное добавление товара увеличивает количество, новая строка не появляется; есть тест».
  • Статусы двигаются по-настоящему: In Progress — когда начали, In Review — когда открыли PR, Done — после слияния. На интервью вы показываете доску, и пустой Todo с горой Done, перенесённых в последний вечер, видно сразу.
  • Если план изменился, это отражено на доске: задача переназначена, разбита или перенесена в «если останется время». Это хороший материал для вопроса «что происходило, если планы менялись».
  • Доска может быть закрытой, но тогда покажите её на записи. Доступ к доске настраивается отдельно от доступа к репозиторию.

Ветки, коммиты и PR

git switch main
git pull origin main
git switch -c feat/cart-total     # тип/кратко-о-задаче
# ...работа, npm test...
git add .
git commit -m "feat: calculate cart total with promo code"
git push -u origin feat/cart-total
  • Ветка на одну задачу, от свежего main. Чем короче живёт ветка, тем меньше конфликтов.
  • Коммиты по конвенции RS School (feat:, fix:, test:, refactor:, docs:, chore:).
  • В описании PR: что сделано, как проверить, какую задачу закрывает. Шаблон — в уроке Code Review.
  • Конфликт — не повод перезаписывать чужой код. Откройте конфликтующий файл вдвоём и решите вместе. Как устроены ветки и отмена изменений — в Git: углубляемся.
  • Запретите прямые пуши в main: Settings → Branches → правило для main с обязательным PR и одобрением (из общих знаний; для приватных репозиториев на бесплатном тарифе правило может быть недоступно). Тогда правило «всё через PR» соблюдается само.

Ревью, о котором можно рассказать

Одно из вопросов интервьюера: «расскажите о замечании на code review». Чтобы ответ был, ревью должно быть настоящим, а не «LGTM» («looks good to me», «мне нравится») за пять секунд. Как читать PR и писать замечания, разобрано в уроке Code Review. Хорошие поводы для замечаний в этом проекте:

  • Сумма считается в обработчике клика, а не в функции, и её нельзя протестировать.
  • Дробные цены: перевод 4.35 * 100 в копейки даёт 434.99999999999994.
  • Функция меняет исходный массив товаров (sort без копии), и после сортировки «исходный порядок» уже не восстановить.
  • Нет теста на пустую корзину или на неизвестный промокод.

Отмечайте в заметках удачные обсуждения со ссылкой на PR. Перед интервью эти ссылки сэкономят время.
