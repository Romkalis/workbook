Что показывают лекции RS School

В программе модуля три видео. Они разобраны по расшифровкам: что в каждом показано, какие паттерны добавлены сверх списка refactoring.guru и где лекторы ошибаются.

Observer и Singleton на TypeScript (2023Q1)

В лекции 2023Q1 лектор Михаил строит небольшое приложение: логин пользователя вводится в одном компоненте и должен сразу появиться в шапке и в другом поле. Сначала задача решена классическим наблюдателем: интерфейс IObserver с методом update, интерфейс ISubject с subscribe, unsubscribe и notify, а компонент-издатель хранит массив подписчиков и вызывает notify на событие keyup. Синглтон показан в классическом виде: приватное статическое поле, закрытый конструктор и статический метод getInstance.

Затем лектор честно показывает минусы получившегося наблюдателя:

  • в компонентах интерфейса появляется много чужой им логики подписок;
  • компоненты сильно связаны: каждого нужно «познакомить» с каждым вручную, и изменение одного тянет цепочку правок;
  • компонент, созданный позже (в лекции — через setTimeout), пропускает уже случившиеся изменения и не знает, где взять текущее значение;
  • один метод update на все события: подписчику приходится разбираться, что именно изменилось.

Решение из лекции — отдельное хранилище: оно держит значения в Map (ключи — из перечисления, чтобы не опечататься в строке), а подписчиков — в Map из ключа в Set функций. Подписываются не объектом с update, а конкретной функцией на конкретный ключ. Лектор называет это «чем-то очень близким к EventEmitter». Упрощённая версия, проверенная в Node.js 22:

class Store {
  #values = new Map();
  #listeners = new Map();

  subscribe(key, fn) {
    if (!this.#listeners.has(key)) this.#listeners.set(key, new Set());
    this.#listeners.get(key).add(fn);
    return () => this.#listeners.get(key).delete(fn); // функция отписки
  }
  set(key, value) {
    this.#values.set(key, value);
    this.#listeners.get(key)?.forEach((fn) => fn(value));
  }
  get(key) {
    return this.#values.get(key);
  }
}

const store = new Store();
const off = store.subscribe('login', (v) => console.log('шапка:', v));
store.subscribe('login', (v) => console.log('кабинет:', v));
store.set('login', 'anya');  // шапка: anya, кабинет: anya
off();
store.set('login', 'anya2'); // кабинет: anya2
store.get('login');          // 'anya2' — компонент, созданный позже, читает текущее значение

Компоненты теперь знают только хранилище, а не друг друга, — это уже шаг к посреднику и к менеджерам состояния вроде zustand и Redux. Хранилище обычно существует в одном экземпляре на приложение, так в лекции встречаются оба паттерна. Расшифровка этого видео обрывается на середине реализации хранилища; связка с синглтоном восстановлена по плану лекции.

Design Patterns: функциональная реализация

Во второй лекции паттерны реализованы на функциях и прототипах, без классов: лектор объясняет это тем, что классы в JavaScript — надстройка над прототипами, и понимать «старый» способ полезно. Главный источник, который он советует, — книга Адди Османи «Learning JavaScript Design Patterns» (бесплатная онлайн-версия есть на patterns.dev). Разобраны четыре паттерна:

  • Singleton — IIFE с переменной instance и методом getInstance, который создаёт объект при первом вызове и дальше возвращает тот же. На вопрос из чата «почему просто не экспортировать один экземпляр из модуля» лектор отвечает: тогда ничто не мешает коллеге создать второй экземпляр из того же конструктора. Справедливо и обратное: экспорт готового объекта из ES-модуля — самый простой синглтон в JavaScript, потому что модуль выполняется один раз (урок «Модули в JavaScript»).
  • Factory — функция-фабрика VehicleFactory, у которой в prototype лежит класс по умолчанию, а createVehicle(options) по полю vehicleType выбирает конструктор Car или Truck. Результат проверяется через instanceof. Это упрощённая «простая фабрика», а не фабричный метод из GoF.
  • Observer — ObserverList (массив с методами добавления, поиска и удаления), Subject с notify и пример: главный чекбокс, а кнопка добавляет новые чекбоксы-наблюдатели, которые повторяют его состояние. Лектор приводит практические примеры: события DOM, HTTP-запросы в RxJS (библиотеке для работы с потоками событий) и Angular.
  • Decorator — сначала просто добавление свойств готовому объекту, затем пример с MacBook: функция-декоратор подменяет метод cost, прибавляя 250 за страховку (997 → 1247). Объект после этого остаётся экземпляром своего конструктора.
Поправки ко второй лекции

1. Лектор говорит, что «применение паттерна практически всегда оправданно» и «если сделать правильно, автоматически станет успешным». Это противоречит его же словам об антипаттернах: паттерн, применённый без нужды, только усложняет код (раздел «Когда обойтись без паттерна»).
2. «Паттернов больше 30» — смотря где считать. В книге «банды четырёх» (GoF) их 23, у Османи и на patterns.dev добавлены паттерны, характерные для JavaScript (Module, Mixin и другие).
3. «Классы — просто синтаксический сахар» — в основном верно, но не полностью: приватные поля #, обязательный new и строгий режим в классах на функциях так просто не воспроизвести.

Patterns: обзор трёх групп (RS School Poland)

Англоязычная лекция проходит по трём группам GoF с примерами из учебного репозитория лектора (по мотивам книги Османи). Важная мысль в начале: паттерны — это ещё и общий словарь команды («используем State?» понятнее, чем объяснение на полстраницы), но опасно применять их «просто потому что знаешь» вместо того, чтобы решать задачу.

Кроме паттернов из основной программы урока, лектор показывает ещё пять. Короткие примеры ниже проверены в Node.js 22.

Prototype (порождающий)
Новый объект создаётся копированием или на основе готового образца, а не через класс. В JavaScript это встроено: Object.create(carProto) создаёт объект, который наследует методы образца, а structuredClone(obj) делает глубокую копию.
Module (структурный)
IIFE с замыканием прячет приватное и возвращает публичный интерфейс. Подробно — в уроке «Модули в JavaScript».
Mixin (структурный)
Набор методов, которые «подмешивают» в класс без наследования: Object.assign(Duck.prototype, canFly, canSwim) — и утка умеет и летать, и плавать. Замена множественного наследования, которого в JavaScript нет.
Flyweight, «Легковес» (структурный)
Общие неизменяемые данные хранятся один раз и разделяются между множеством объектов. В проверке 100 000 маркеров карты ссылались всего на 2 объекта-иконки из кеша вместо 100 000 копий.
Memento, «Снимок» (поведенческий)
Объект сохраняет снимок своего состояния и умеет к нему вернуться, не раскрывая внутренностей. Классический пример — отмена действия: редактор с приватным полем #text возвращает замороженный снимок через save(), история хранит снимки, restore() откатывает текст к «Привет, мир», а затем к «Привет».

Хорошие примеры из жизни, которые приводит лектор: Redux построен на идее команды (action — объект «что сделать» с данными), Passport.js — на стратегии (способ входа через Google, GitHub или Facebook подключается как стратегия), чат — классический посредник, оплата «сначала картой, потом PayPal» — цепочка обязанностей, светофор — состояние.

Поправки к третьей лекции

1. Builder назван «constructor/builder pattern» и объяснён как наследование: «если видите extends и super, это builder». Это неверно. Строитель собирает сложный объект по шагам (раздел о строителе), наследование к нему отношения не имеет.
2. Abstract Factory объяснена как «фабрика фабрик». У GoF это фабрика семейства связанных объектов: например, кнопки и поля одной темы оформления, которые должны сочетаться (раздел об абстрактной фабрике).
3. State описан как «умение хранить что-то в экземпляре», как state в React. Хранить данные — не паттерн. State у GoF — это смена поведения объекта через смену объекта-состояния; пример со светофором в лекции как раз такой, а сравнение с state в React — нет.
4. Memento назван «общим хранилищем между экземплярами», с аналогией «база данных — это memento». Суть паттерна — снимок состояния одного объекта для отката, без нарушения инкапсуляции (принципа, по которому внутренние данные объекта скрыты от внешнего кода).
5. MVC упомянут как структурный паттерн. MVC — архитектурный паттерн уровня приложения, в 23 паттерна GoF он не входит.
