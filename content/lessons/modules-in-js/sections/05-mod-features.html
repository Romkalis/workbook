Как ведут себя ES-модули

Своя область видимости и строгий режим

Переменные модуля не попадают в глобальную область: другие модули их не видят, пока они не экспортированы. Код модуля всегда выполняется в строгом режиме ('use strict'): например, присваивание необъявленной переменной вызовет ошибку. На верхнем уровне модуля this равен undefined (проверено), а не глобальному объекту. В модуле можно писать await вне функции.

Модуль выполняется один раз

Сколько бы раз и из скольких файлов модуль ни импортировали, его код выполняется один раз, при первом импорте. Все получают один и тот же экземпляр. Проверено: файл с console.log, импортированный дважды статически и один раз через import(), напечатал сообщение один раз. Поэтому модуль удобно использовать как единственный общий объект — настройки, соединение, хранилище.

Живые привязки

Импорт — не копия значения, а живая привязка (live binding) к переменной в модуле-источнике. Если модуль сам изменил свою переменную, все импортёры увидят новое значение. Но импортёр не может её переприсвоить:

import reset, { count, increment, settings as config } from './counter.js';
import { setDark } from './a.js'; // a.js меняет settings.theme на 'dark'

console.log(count);   // 0
increment(); increment();
console.log(count);   // 2 — значение обновилось само
setDark();
console.log(config.theme); // 'dark' — объект общий для всех модулей
count = 10;           // TypeError: Assignment to constant variable.
reset();
console.log(count);   // 0

В CommonJS иначе: module.exports = { count } кладёт в объект копию числа. Тот же счётчик на CommonJS после двух вызовов increment() показал снаружи count = 0.

Поправка к лекции RS School

В лекции сказано, что модули — «синглтоны», поэтому изменения импортированного объекта «локальны» и не видны в других файлах. Первая половина верна, вторая — нет, и одно противоречит другому: раз экземпляр один, изменение объекта видно всем. Проверка выше это показывает: модуль a.js поменял settings.theme, и main.js увидел 'dark'. Запрещено только переприсваивать импортированную переменную. Лектор прав в главном выводе: делить изменяемое состояние через модули рискованно, для этого есть менеджеры состояния (например, zustand или Redux).

Циклические зависимости

Если c1.js импортирует из c2.js, а c2.js — из c1.js, это циклическая зависимость. ES-модули её допускают, но порядок выполнения может удивить:

// c1.js
import { b } from './c2.js';
export const a = 'A';
console.log('c1 видит b =', b);

// c2.js
import { a } from './c1.js';
export const b = 'B';
console.log('c2 видит a =', a);

Запуск node c1.js: сначала выполнился c2.js и упал с ReferenceError: Cannot access 'a' before initialization — c1.js ещё не дошёл до объявления a. Затем c1.js напечатал «c1 видит b = B». Лектор говорит, что сборщик «обычно умеет с этим справиться»; на деле сборщик лишь сохраняет такой же порядок, и ошибка остаётся. Циклы лучше устранять: вынести общий код в третий модуль, от которого зависят оба.

Импорты всплывают

Все статические import обрабатываются до выполнения кода модуля, где бы они ни стояли в файле. Поэтому они должны быть на верхнем уровне (не внутри if или функции), а путь — строкой, а не выражением. Это позволяет инструментам заранее, не запуская код, построить дерево зависимостей и выбросить неиспользуемый код (tree shaking — «встряхивание дерева»).
