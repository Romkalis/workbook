Формы

Слушайте submit, а не click по кнопке

Форма отправляется кликом по кнопке, Enter в текстовом поле, программно. Событие submit на форме ловит все способы сразу; обработчик click на кнопке пропустит Enter. Поэтому логика отправки живёт в submit:

export interface ReviewInput {
  author: string;
  rating: number;
  text: string;
}

export type ParseResult = { ok: true; value: ReviewInput } | { ok: false; errors: Partial<Record<keyof ReviewInput, string>> };

export function parseReviewForm(data: FormData): ParseResult {
  const author = String(data.get('author') ?? '').trim();
  const rating = Number(data.get('rating'));
  const text = String(data.get('text') ?? '').trim();
  const errors: Partial<Record<keyof ReviewInput, string>> = {};
  if (author === '') errors.author = 'Укажите имя';
  if (!Number.isInteger(rating) || rating < 1 || rating > 5) errors.rating = 'Оценка от 1 до 5';
  if (text.length < 10) errors.text = 'Отзыв — хотя бы 10 символов';
  return Object.keys(errors).length === 0 ? { ok: true, value: { author, rating, text } } : { ok: false, errors };
}

export function listenReviewForm(form: HTMLFormElement, onSubmit: (review: ReviewInput) => void, onErrors: (errors: Partial<Record<keyof ReviewInput, string>>) => void): void {
  form.addEventListener('submit', (event) => {
    event.preventDefault();
    const result = parseReviewForm(new FormData(form));
    if (result.ok) onSubmit(result.value);
    else onErrors(result.errors);
  });
}

new FormData(form) собирает значения всех полей формы по атрибуту name. Значения — строки (или файлы), поэтому разбор и проверка вынесены в чистую функцию parseReviewForm: её тестируют без DOM, на объекте FormData, а обработчик остаётся тонким. Это тот же приём «функция-результат», что и в серверной проверке в уроке Express на TypeScript.

Задача 8. Форма в объект ★☆☆ разминка

Форма поиска с полями q (текст), category (select) и чекбоксом inStock. Напишите readSearchForm(form), которая возвращает { q: string; category: string | null; inStock: boolean }: строка обрезана, пустая категория — null.

Зачем: FormData отдаёт строки или null, а неотмеченный чекбокс вообще отсутствует. Функция-разбор переводит это в аккуратный объект с типами, и остальной код больше не думает о форме.

Решение и разбор
// search-form.ts
export interface SearchQuery {
  q: string;
  category: string | null;
  inStock: boolean;
}

export function readSearchForm(form: HTMLFormElement): SearchQuery {
  const data = new FormData(form);
  const category = String(data.get('category') ?? '');
  return {
    q: String(data.get('q') ?? '').trim(),
    category: category === '' ? null : category,
    inStock: data.has('inStock'),
  };
}

Отмеченный чекбокс без value даёт строку "on", неотмеченный не попадает в FormData совсем. Поэтому has, а не сравнение значения. String(x ?? '') превращает null и файл в строку без ошибки. В этой форме файлов нет, но тип FormDataEntryValue их допускает.

Задача 9. Отправка без перезагрузки ★★☆ практика

Подключите readSearchForm из прошлой задачи к событию submit: отмените перезагрузку и вызовите onSearch(query). Проверьте, что отправка Enter (программно — form.requestSubmit()) тоже срабатывает.

Зачем: одна точка входа для всех способов отправки: пользователю не важно, как он отправил форму, и коду тоже не должно быть важно.

Решение и разбор
// submit.ts
import { readSearchForm, type SearchQuery } from './search-form.js';

export function listenSearch(form: HTMLFormElement, onSearch: (q: SearchQuery) => void): void {
  form.addEventListener('submit', (event) => {
    event.preventDefault();
    onSearch(readSearchForm(form));
  });
}
// search-form.ts
export interface SearchQuery {
  q: string;
  category: string | null;
  inStock: boolean;
}
export function readSearchForm(form: HTMLFormElement): SearchQuery {
  const data = new FormData(form);
  const category = String(data.get('category') ?? '');
  return { q: String(data.get('q') ?? '').trim(), category: category === '' ? null : category, inStock: data.has('inStock') };
}

requestSubmit() ведёт себя как настоящая отправка: проходит встроенную проверку полей и генерирует submit. Старый form.submit() отправляет форму в обход и того и другого, и ваш обработчик его не увидит. Это частая ловушка в тестах и при программной отправке.

Задача 10. Проверка формы заказа ★★☆ практика

Напишите чистую функцию parseOrderForm(data: FormData) для полей name (непустое), phone (только цифры после удаления пробелов, скобок, дефисов и плюса, длина 11), delivery (courier или pickup) и address (обязателен только для курьера). Результат: { ok: true, value } или { ok: false, errors } с сообщением на каждое поле.

Зачем: правила формы — бизнес-логика, и она должна тестироваться без браузера. Условное правило («адрес нужен только для курьера») — типичное место ошибок, и в чистой функции его проверка стоит одну строку теста.

Решение и разбор
// order-form.ts
export interface Order {
  name: string;
  phone: string;
  delivery: 'courier' | 'pickup';
  address: string | null;
}
type Errors = Partial<Record<keyof Order, string>>;

export function parseOrderForm(data: FormData): { ok: true; value: Order } | { ok: false; errors: Errors } {
  const get = (key: string) => String(data.get(key) ?? '').trim();
  const errors: Errors = {};

  const name = get('name');
  if (name === '') errors.name = 'Укажите имя';

  const phone = get('phone').replace(/[\s()+-]/g, '');
  if (!/^\d{11}$/.test(phone)) errors.phone = 'Телефон — 11 цифр';

  const delivery = get('delivery');
  if (delivery !== 'courier' && delivery !== 'pickup') errors.delivery = 'Выберите способ получения';

  const address = get('address');
  if (delivery === 'courier' && address === '') errors.address = 'Для курьера нужен адрес';

  if (Object.keys(errors).length > 0) return { ok: false, errors };
  return {
    ok: true,
    value: { name, phone, delivery: delivery as Order['delivery'], address: delivery === 'courier' ? address : null },
  };
}

Все ошибки собираются сразу, а не до первой: пользователь исправит всё за один раз. Для самовывоза адрес не сохраняется, даже если его ввели: в заказе не должно быть данных, которые ничего не значат. Утверждение as Order['delivery'] безопасно: выше значение проверено, а если были ошибки, функция до этой строки не дошла.

input или change

input срабатывает на каждое изменение значения: каждую букву, вставку, удаление. change — когда изменение «завершено»: для текстового поля при потере фокуса, для select и чекбокса — сразу при выборе. Живой поиск слушает input (обычно с debounce, как в Country Search), а change удобен для фильтров-переключателей.

Задача 11. Живой поиск с задержкой ★★☆ практика

Напишите liveSearch(input, onQuery, delay = 300): на каждое событие input откладывает вызов onQuery(значение); новый ввод отменяет предыдущий отложенный вызов. Одинаковое значение подряд не отправляется повторно (например, пользователь напечатал букву и стёр её).

Зачем: запрос на каждую букву перегружает сервер и вызывает гонку ответов. Задержка и отсев повторов — два простых правила, после которых поиск становится и быстрым, и экономным.

Решение и разбор
// live.ts
export function liveSearch(input: HTMLInputElement, onQuery: (q: string) => void, delay = 300): void {
  let timer: ReturnType<typeof setTimeout> | undefined;
  let last: string | undefined;
  input.addEventListener('input', () => {
    clearTimeout(timer);
    timer = setTimeout(() => {
      const q = input.value.trim();
      if (q === last) return;
      last = q;
      onQuery(q);
    }, delay);
  });
}

Значение читается в момент срабатывания таймера, а не в момент ввода, поэтому уходит последнее. ReturnType<typeof setTimeout> подходит и для браузера (число), и для Node (объект): тип не привязан к среде. Тест использует управляемые таймеры Vitest (vi.useFakeTimers), то же, что mock.timers из урока о тестировании. Отмена устаревших ответов — следующая ступень, она разобрана в Country Search.

Задача 12. Фильтр по select ★☆☆ разминка

Подпишитесь на изменение select категории так, чтобы onCategory вызывался один раз при каждом выборе, с null для пункта «Все категории» (пустое значение).

Зачем: для выпадающего списка выбор и есть законченное действие, поэтому подходит change. Пустое значение превращается в null на границе, чтобы дальше в коде не было «магической» пустой строки.

Решение и разбор
// category.ts
export function listenCategory(select: HTMLSelectElement, onCategory: (c: string | null) => void): void {
  select.addEventListener('change', () => {
    onCategory(select.value === '' ? null : select.value);
  });
}

У select события input и change срабатывают одновременно при выборе, но change точнее выражает намерение и единообразен с чекбоксами. Для текстового поля разница огромная: там change ждёт потери фокуса.

Встроенная проверка и свои сообщения

Атрибуты required, min, max, minlength, pattern, type="email" браузер проверяет сам и не даст отправить форму с нарушением, показав свою подсказку. form.checkValidity() проверяет программно, input.validity объясняет, что не так, input.setCustomValidity('текст') задаёт своё сообщение (пустая строка — «ошибки нет»). Встроенная проверка — хорошая первая линия, но её тексты и вид у каждого браузера свои, поэтому часто ставят novalidate на форму и показывают ошибки сами.

Свою ошибку связывают с полем: поле получает aria-invalid="true" и aria-describedby="id-сообщения", а сообщение — элемент с этим id. Тогда программа чтения с экрана, переходя на поле, прочитает и ошибку (из общих знаний о WAI-ARIA).

Проверка в браузере — удобство для пользователя, а не защита. Её обходят отключением JavaScript или запросом из Postman. Сервер проверяет данные всегда (урок Express на TypeScript).

Задача 13. Показать ошибки у полей ★★☆ практика

Напишите showErrors(form, errors): для каждого поля из errors ставит aria-invalid="true" и выводит текст в элемент #<name>-error, связанный через aria-describedby. У полей без ошибки снимает и атрибут, и текст. Фокус переводит на первое поле с ошибкой.

Зачем: ошибки должны быть видны, связаны с полем для программ чтения с экрана и исчезать, когда поле исправлено. Фокус на первой ошибке экономит пользователю поиск, особенно на длинной форме и на телефоне.

Решение и разбор
// show-errors.ts
export function showErrors(form: HTMLFormElement, errors: Partial<Record<string, string>>): void {
  let first: HTMLElement | null = null;
  for (const field of form.querySelectorAll<HTMLInputElement | HTMLSelectElement | HTMLTextAreaElement>('[name]')) {
    const message = errors[field.name];
    const box = form.querySelector(`#${field.name}-error`);
    if (box) box.textContent = message ?? '';
    if (message) {
      field.setAttribute('aria-invalid', 'true');
      if (box) field.setAttribute('aria-describedby', box.id);
      first ??= field;
    } else {
      field.removeAttribute('aria-invalid');
    }
  }
  first?.focus();
}

Функция проходит по всем полям, а не только по тем, где есть ошибка. Так снимаются старые ошибки исправленных полей, и вызов с пустым объектом «очищает» форму. ??= запоминает только первое поле с ошибкой. Здесь id собирается из name — имена полей задаёте вы сами в разметке, а не пользователь, поэтому подстановка в селектор безопасна. Сравните с задачами про data-id, где значения приходят из данных.

Задача 14. Своё сообщение во встроенной проверке ★★☆ практика

Поле подтверждения пароля должно совпадать с паролем. Используя setCustomValidity, сделайте так, чтобы при несовпадении form.checkValidity() возвращал false, а у поля было сообщение «Пароли не совпадают». Проверка запускается на каждый input в любом из двух полей.

Зачем: встроенная проверка не умеет сравнивать два поля, но позволяет добавить своё правило. Тогда checkValidity, псевдокласс :invalid в CSS и блокировка отправки работают единообразно для встроенных и своих правил.

Решение и разбор
// confirm.ts
export function linkPasswords(password: HTMLInputElement, confirm: HTMLInputElement): void {
  const check = () => {
    confirm.setCustomValidity(confirm.value !== password.value ? 'Пароли не совпадают' : '');
  };
  password.addEventListener('input', check);
  confirm.addEventListener('input', check);
  check();
}

Пустая строка в setCustomValidity означает «ошибки нет». Её обязательно нужно передать, иначе поле останется невалидным навсегда. Проверка подписана на оба поля: пользователь может исправить и первое поле, а не только подтверждение. Первый вызов check() синхронизирует состояние сразу при подключении.

Пока форма отправляется

Пока запрос идёт, кнопку отправки блокируют (button.disabled = true) и снимают блокировку в finally, чтобы она не осталась заблокированной после ошибки. Иначе нетерпеливый пользователь нажмёт трижды и создаст три заказа.

Задача 15. Защита от двойной отправки ★★☆ практика

Напишите submitOnce(form, send): на submit блокирует кнопку отправки, вызывает асинхронную send(formData) и снимает блокировку после завершения — и при успехе, и при ошибке. Повторный submit, пока запрос идёт, игнорируется. Ошибку передайте в onError.

Зачем: двойная отправка — это два заказа и два списания денег. Блокировка кнопки — подсказка пользователю, а флаг «уже отправляем» — настоящая защита: Enter в поле отправит форму и при заблокированной кнопке.

Решение и разбор
// once.ts
export function submitOnce(form: HTMLFormElement, send: (data: FormData) => Promise<void>, onError: (e: unknown) => void): void {
  let busy = false;
  form.addEventListener('submit', async (event) => {
    event.preventDefault();
    if (busy) return;
    busy = true;
    const button = form.querySelector<HTMLButtonElement>('[type=submit], button:not([type])');
    if (button) button.disabled = true;
    try {
      await send(new FormData(form));
    } catch (error) {
      onError(error);
    } finally {
      busy = false;
      if (button) button.disabled = false;
    }
  });
}

finally выполняется и после успеха, и после ошибки, поэтому кнопка не останется заблокированной навсегда. Флаг busy ставится синхронно, до первого await: второе событие, пришедшее, пока ждём сеть, уже увидит true. Селектор button:not([type]) нужен потому, что кнопка без type внутри формы — это кнопка отправки.
