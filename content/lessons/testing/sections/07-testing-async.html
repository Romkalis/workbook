Асинхронность: дождитесь результата

Runner должен знать, когда закончилась проверка. Возвращайте Promise из теста или используйте async/await. Иначе тест может завершиться раньше, чем выполнится утверждение; позже возникнет необработанная ошибка или ложный успех.

Успех и отклонение Promise

import test from 'node:test';
import assert from 'node:assert/strict';

async function loadTitle(id, fetchMovie) {
  const movie = await fetchMovie(id);
  if (typeof movie.title !== 'string') {
    throw new TypeError('Ответ не содержит название');
  }
  return movie.title;
}
test('возвращает название загруженного фильма', async () => {
  const fetchMovie = async id => ({ id, title: 'Солярис' });
  const title = await loadTitle(7, fetchMovie);
  assert.equal(title, 'Солярис');
});
test('передаёт ошибку загрузки вызывающему коду', async () => {
  const error = new Error('Нет сети');
  const fetchMovie = async () => { throw error; };
  await assert.rejects(() => loadTitle(7, fetchMovie), error);
});
test('отклоняет ответ без названия', async () => {
  await assert.rejects(() => loadTitle(7, async () => ({})), TypeError);
});

Настоящая сеть здесь не используется: мы проверяем реакцию loadTitle на управляемую зависимость. Ошибку асинхронной функции проверяет rejects, а не throws. Перед await не забывайте, что сама проверка тоже возвращает Promise.

Задача 9. Загрузка каталога: успех и отказ ★★☆ практика

Функция loadCatalog(fetchJson) получает функцию загрузки и возвращает массив товаров. Если ответ не массив — TypeError, если загрузка упала — ошибка уходит дальше без изменений. Напишите три асинхронных теста с управляемой fetchJson.

// catalog.mjs
export async function loadCatalog(fetchJson) {
  const data = await fetchJson('/api/products');
  if (!Array.isArray(data)) throw new TypeError('Ожидался массив товаров');
  return data;
}

Зачем: асинхронный код ошибается не в том, что он считает, а в том, как реагирует на внешний мир: пустой ответ, мусор, отказ сети. Управляемая зависимость позволяет проверить все эти ситуации за миллисекунды и без интернета.

Решение и разбор
// catalog.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { loadCatalog } from './catalog.mjs';

test('возвращает товары из ответа', async () => {
  const products = await loadCatalog(async () => [{ id: 1 }]);
  assert.deepEqual(products, [{ id: 1 }]);
});

test('ответ не массив — TypeError', async () => {
  await assert.rejects(() => loadCatalog(async () => ({ error: 'oops' })), TypeError);
});

test('ошибка сети уходит вызывающему без изменений', async () => {
  const network = new Error('Нет сети');
  await assert.rejects(() => loadCatalog(async () => { throw network; }), network);
});

Мутант «на всякий случай» глотает ошибки и возвращает пустой массив. Интерфейс тогда покажет «товаров нет» вместо «нет сети, повторите». Наши тесты ловят это сразу. assert.rejects с объектом ошибки проверяет, что дошла именно та самая ошибка, а не какая-то другая.

Задача 10. Тест, который «прошёл» ★★★ с подвохом

В отчёте тест ниже помечен ok, хотя проверяемая функция работает неправильно. Найдите ошибку в тесте и исправьте её. Затем запустите исправленный тест на сломанной функции и убедитесь, что он теперь красный.

// starter.mjs
test('отклоняет пустой ответ', () => {
  assert.rejects(() => loadTitle(async () => ({})), TypeError);
});
// title.mjs
export async function loadTitle(fetchMovie) {
  const movie = await fetchMovie();
  if (typeof movie.title !== 'string') throw new TypeError('Нет названия');
  return movie.title;
}

Зачем: асинхронная проверка без await выполняется уже после того, как runner посчитал тест пройденным. Это классическая причина «зелёных» тестов, которые ничего не проверяют.

Решение и разбор
// title.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { loadTitle } from './title.mjs';

test('отклоняет пустой ответ', async () => {
  await assert.rejects(() => loadTitle(async () => ({})), TypeError);
});

assert.rejects возвращает Promise. Без await тест-функция завершается синхронно, и runner ставит ok. Мы проверили, что делает Node 22 со сломанной функцией: тест помечен ok 1, но ниже печатается «generated asynchronous activity after the test ended», и весь файл считается упавшим. Сообщение легко пропустить в длинном отчёте. В других runner'ах такая ошибка может пройти совсем тихо. Правило: тест с асинхронной проверкой — async, а каждая асинхронная проверка — с await.

Время и ожидание — из общих знаний

Не делайте фиксированную паузу «на всякий случай»: на быстрой машине она тратит время, на медленной всё равно может оказаться короткой. Ждите конкретное событие или проверяемое состояние. Для debounce и таймеров можно использовать управляемые часы runner, но их API зависит от инструмента; после теста часы нужно восстанавливать.

В node:test это mock.timers. После enable функции setTimeout и clearTimeout больше не ждут настоящего времени: оно идёт, только когда тест вызывает tick(мс). Пример проверен в Node.js 22:

import { describe, it, beforeEach, afterEach, mock } from 'node:test';
import assert from 'node:assert/strict';

function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

describe('debounce', () => {
  beforeEach(() => mock.timers.enable({ apis: ['setTimeout'] }));
  afterEach(() => mock.timers.reset()); // вернуть настоящие таймеры

  it('вызывает один раз после паузы', () => {
    const fn = mock.fn();
    const search = debounce(fn, 300);
    search('a');
    search('ab');
    mock.timers.tick(299);
    assert.equal(fn.mock.callCount(), 0);
    mock.timers.tick(1);
    assert.deepEqual(fn.mock.calls[0].arguments, ['ab']);
  });
});

В Jest и Vitest та же идея называется fake timers (jest.useFakeTimers(), vi.useFakeTimers()), но названия методов отличаются.

В браузерных тестах автоматическое ожидание элементов помогает синхронизации, но не исправляет гонки приложения. Если два запроса могут завершиться в обратном порядке, отдельно проверьте, что UI показывает актуальный результат.

Задача 11. Debounce без ожидания ★★★ с подвохом

Напишите тесты для debounce(fn, ms) с управляемыми таймерами mock.timers: функция не вызывается раньше паузы; после паузы вызывается один раз с последними аргументами; новый вызов во время паузы сдвигает её. Настоящего ожидания в тестах быть не должно.

// debounce.mjs
export function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

Зачем: тест с await sleep(300) медленный и всё равно ненадёжный на загруженной машине. Управляемые часы делают время частью Arrange: «прошло 299 мс» — и это ровно 299 мс, каждый раз (Repeatable из FIRST).

Решение и разбор
// debounce.test.mjs
import { describe, it, beforeEach, afterEach, mock } from 'node:test';
import assert from 'node:assert/strict';
import { debounce } from './debounce.mjs';

describe('debounce', () => {
  beforeEach(() => mock.timers.enable({ apis: ['setTimeout'] }));
  afterEach(() => mock.timers.reset());

  it('не вызывает раньше паузы', () => {
    const fn = mock.fn();
    debounce(fn, 300)('a');
    mock.timers.tick(299);
    assert.equal(fn.mock.callCount(), 0);
  });

  it('после паузы вызывает один раз с последними аргументами', () => {
    const fn = mock.fn();
    const search = debounce(fn, 300);
    search('a');
    search('ab');
    mock.timers.tick(300);
    assert.equal(fn.mock.callCount(), 1);
    assert.deepEqual(fn.mock.calls[0].arguments, ['ab']);
  });

  it('новый вызов сдвигает паузу', () => {
    const fn = mock.fn();
    const search = debounce(fn, 300);
    search('a');
    mock.timers.tick(200);
    search('ab');
    mock.timers.tick(200);
    assert.equal(fn.mock.callCount(), 0);
    mock.timers.tick(100);
    assert.equal(fn.mock.callCount(), 1);
  });
});

Мутант — это на самом деле throttle с первым аргументом: он игнорирует вызовы во время паузы. Он проходит первый тест, но вызывает функцию с 'a' вместо 'ab' и не сдвигает паузу. afterEach с reset() возвращает настоящие таймеры, иначе следующий файл или тест получит «замороженное» время.
