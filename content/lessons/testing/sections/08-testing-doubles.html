Подмены: stub, spy, mock и fake

Из общих знаний: тестовая подмена заменяет зависимость, чтобы управлять условиями или наблюдать взаимодействие. Термины у библиотек пересекаются, поэтому важнее объяснить, что именно заменено и что проверяется.

Stub
Возвращает заранее выбранные данные или ошибку.
Spy
Записывает вызовы: аргументы и число обращений; иногда оборачивает настоящую функцию.
Mock
Подмена с проверяемыми ожиданиями взаимодействия; в runner этим словом часто называют и более общие функции-подмены.
Fake
Упрощённая работающая реализация, например хранилище в памяти вместо базы.

Если коротко: stub задаёт состояние — «пусть сервер вернёт пустой список» или «пусть запрос упадёт с ошибкой 500», чтобы проверить, как код поведёт себя в такой ситуации. Spy наблюдает — сколько раз и с чем вызвали функцию. Mock заранее знает, какие вызовы должны произойти, и сам проверяет это.

Чистые функции проще всего тестировать

Чистая функция — функция, результат которой зависит только от её аргументов, и которая ничего не меняет снаружи: не пишет в глобальные переменные, не ходит в сеть, не трогает DOM. На результат чистой функции не влияют ни переменные окружения, ни глобальные переменные, ни текущее время. Те же аргументы — всегда тот же ответ. Поэтому ей не нужны подмены: подготовили аргументы, вызвали, сравнили.

let rate = 0.2;
const priceWithTax = (price) => price * (1 + rate); // читает внешнюю переменную — не чистая
const priceWithTaxPure = (price, taxRate) => price * (1 + taxRate); // только аргументы — чистая

const first = priceWithTax(100);
rate = 0.1;
console.log(priceWithTax(100) === first); // false — аргумент тот же, ответ другой
console.log(priceWithTaxPure(100, 0.2) === priceWithTaxPure(100, 0.2)); // true

Отсюда практический совет: выносите расчёты в чистые функции, а работу с сетью, временем и DOM оставляйте в тонком внешнем слое. Тогда большую часть логики покроют простые unit-тесты, а подмены понадобятся только на краях. Пример выполнен как тест в Node.js 22.

Задача 12. Сделайте функцию чистой ★☆☆ разминка

Функция ниже читает внешнюю переменную, и её результат меняется «сам». Перепишите её в чистую: ставка налога — параметр. Напишите тест, который был бы невозможен для исходной версии без изменения глобальной переменной.

let rate = 0.2;
export const priceWithTax = (price) => Math.round(price * (1 + rate));

Зачем: чистой функции не нужны подмены, очистка и порядок тестов: подготовили аргументы, вызвали, сравнили. Чем больше логики в чистых функциях, тем дешевле весь набор тестов.

Решение и разбор
// tax.mjs
export const priceWithTax = (price, taxRate) => Math.round(price * (1 + taxRate));
// tax.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { priceWithTax } from './tax.mjs';

test('разные ставки в соседних тестах не мешают друг другу', () => {
  assert.equal(priceWithTax(1000, 0.2), 1200);
  assert.equal(priceWithTax(1000, 0.1), 1100);
  assert.equal(priceWithTax(1000, 0), 1000);
});

Где тогда хранить ставку? Там, где она известна: в настройках приложения, которые читает тонкий внешний слой и передаёт в функцию. Для исходной версии такой тест потребовал бы менять rate, а значит, и восстанавливать его потом. Ровно эту боль мы разбирали в задаче про окружение.

Передайте зависимость явно

Вместо настоящей отправки письма передадим функцию send. Это делает тест быстрым и позволяет проверить публично значимый эффект: кому отправлено уведомление. Почтовый сервер этот тест не проверяет.

Массив calls ниже — самодельный шпион. В node:test есть готовый: mock.fn(реализация) возвращает функцию, которая выполняет реализацию и записывает каждый вызов. Число вызовов — fn.mock.callCount(), аргументы вызова — fn.mock.calls[i].arguments. Аналоги — jest.fn() и vi.fn().

import test from 'node:test';
import assert from 'node:assert/strict';

async function notify(email, send) {
  await send({ to: email, subject: 'Заказ принят' });
  return 'sent';
}
test('отправляет одно подтверждение нужному получателю', async () => {
  const calls = [];
  const send = async message => { calls.push(message); };
  const result = await notify('student@example.com', send);
  assert.equal(result, 'sent');
  assert.deepEqual(calls, [
    { to: 'student@example.com', subject: 'Заказ принят' }
  ]);
});

Задача 13. Шпион: письмо отправлено один раз ★★☆ практика

Функция confirmOrder(order, send) отправляет письмо, только если заказ оплачен. Используя mock.fn() из node:test, проверьте: для оплаченного заказа send вызвана ровно один раз с нужным адресом и темой; для неоплаченного не вызвана вовсе.

// confirm.mjs
export async function confirmOrder(order, send) {
  if (order.status !== 'paid') return false;
  await send({ to: order.email, subject: `Заказ №${order.id} оплачен` });
  return true;
}

Зачем: здесь взаимодействие и есть контракт: письмо о неоплаченном заказе — реальная ошибка, которую увидит покупатель. Шпион записывает вызовы, и тест проверяет, что именно ушло наружу, без настоящего почтового сервера.

Решение и разбор
// confirm.test.mjs
import { test, mock } from 'node:test';
import assert from 'node:assert/strict';
import { confirmOrder } from './confirm.mjs';

test('оплаченный заказ: одно письмо нужному получателю', async () => {
  const send = mock.fn(async () => {});
  await confirmOrder({ id: 7, email: 'buyer@example.com', status: 'paid' }, send);
  assert.equal(send.mock.callCount(), 1);
  assert.deepEqual(send.mock.calls[0].arguments, [{ to: 'buyer@example.com', subject: 'Заказ №7 оплачен' }]);
});

test('неоплаченный заказ: письма нет', async () => {
  const send = mock.fn(async () => {});
  const result = await confirmOrder({ id: 8, email: 'buyer@example.com', status: 'new' }, send);
  assert.equal(result, false);
  assert.equal(send.mock.callCount(), 0);
});

mock.fn(impl) создаёт функцию, которая выполняет impl и записывает каждый вызов в .mock.calls. Мутант отправляет письмо до проверки статуса, но возвращает правильный false. Тест, который смотрит только на результат, его бы пропустил, а проверка «вызовов 0» ловит. Это тот случай, когда проверять взаимодействие правильно.

Задача 14. Заглушка: сервер ответил ошибкой ★★☆ практика

submitOrder(order, api) отправляет заказ и возвращает { ok: true, id } или, если api.post отклонился, { ok: false, message: 'Не удалось оформить заказ, попробуйте ещё раз' }. Напишите тесты для обоих исходов с объектами-заглушками вместо api.

// submit.mjs
export async function submitOrder(order, api) {
  try {
    const { id } = await api.post('/orders', order);
    return { ok: true, id };
  } catch {
    return { ok: false, message: 'Не удалось оформить заказ, попробуйте ещё раз' };
  }
}

Зачем: воспроизвести настоящую ошибку сервера по запросу трудно, а заглушка делает это одной строкой. Ветку ошибки чаще всего не проверяют, и именно в ней пользователь видит белый экран.

Решение и разбор
// submit.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { submitOrder } from './submit.mjs';

test('успех: возвращает id заказа', async () => {
  const api = { post: async () => ({ id: 42 }) };
  assert.deepEqual(await submitOrder({ items: [] }, api), { ok: true, id: 42 });
});

test('сервер упал: понятное сообщение вместо исключения', async () => {
  const api = { post: async () => { throw new Error('500'); } };
  assert.deepEqual(await submitOrder({ items: [] }, api), {
    ok: false,
    message: 'Не удалось оформить заказ, попробуйте ещё раз',
  });
});

Заглушке не нужен mock.fn: обычный объект с методом нужной формы. Нам не важно, как её вызвали, важно, что она вернула, поэтому это stub, а не spy. Мутант без try/catch пропускает исключение наружу, и второй тест падает.

Задача 15. Fake: хранилище в памяти ★★☆ практика

registerUser(repo, email) регистрирует пользователя, если такого email ещё нет (без учёта регистра), иначе бросает Error('Email занят'). Напишите fake-репозиторий на Map с методами findByEmail и save и тесты: регистрация, повтор, повтор в другом регистре.

// register.mjs
export async function registerUser(repo, email) {
  const normalized = email.trim().toLowerCase();
  if (await repo.findByEmail(normalized)) throw new Error('Email занят');
  return repo.save({ email: normalized });
}

Зачем: fake — это настоящая, только упрощённая реализация. Она помнит состояние между вызовами, поэтому проверяет сценарий «сохранили — потом нашли», который заглушка с заранее заданным ответом не воспроизведёт.

Решение и разбор
// register.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { registerUser } from './register.mjs';

function createFakeRepo() {
  const users = new Map();
  let nextId = 1;
  return {
    async findByEmail(email) {
      return users.get(email) ?? null;
    },
    async save(user) {
      const saved = { id: nextId++, ...user };
      users.set(user.email, saved);
      return saved;
    },
  };
}

test('регистрирует нового пользователя', async () => {
  const user = await registerUser(createFakeRepo(), 'Anna@Example.com');
  assert.deepEqual(user, { id: 1, email: 'anna@example.com' });
});

test('повторный email отклоняется', async () => {
  const repo = createFakeRepo();
  await registerUser(repo, 'anna@example.com');
  await assert.rejects(() => registerUser(repo, 'anna@example.com'), /Email занят/);
});

test('повтор в другом регистре тоже отклоняется', async () => {
  const repo = createFakeRepo();
  await registerUser(repo, 'anna@example.com');
  await assert.rejects(() => registerUser(repo, ' ANNA@example.com '), /Email занят/);
});

Каждый тест создаёт свой репозиторий через фабрику, так что данные не пересекаются. Мутант без нормализации пускает ANNA@example.com как нового пользователя, и ловит его последний тест. Подсказка на будущее: на сервере тот же fake пригодится, чтобы тестировать маршруты без настоящей базы.

Где подмена перестаёт помогать

У подмен две типичные ошибки. Первая — подменить саму проверяемую функцию. Тогда тест проверяет только то, что подмена вернула заданный вами ответ, а настоящий код не выполняется вовсе. Вторая — проверять каждый внутренний вызов: «сначала вызвали format, потом round». Такой тест упадёт, как только вы перепишете код по-другому, даже если результат остался верным. Подменяйте только внешнее (сеть, время, базу) и проверяйте результат, а не порядок шагов внутри.

Подменяйте внешнюю границу, когда её реальная работа не является целью теста. Взаимодействие проверяйте, когда оно само часть контракта: например, не отправить письмо дважды. Совместимость с настоящим сервисом проверяйте отдельно интеграционным тестом или тестом контракта.

Задача 16. От проверки шагов к проверке результата ★★☆ практика

Тест ниже проверяет, в каком порядке функция вызывает свои внутренние помощники. Он упадёт при любом рефакторинге, даже если результат верен. Перепишите его так, чтобы он проверял только результат: строку цены.

// starter.mjs
test('formatPrice', () => {
  const calls = [];
  const helpers = {
    toRubles: (k) => { calls.push('toRubles'); return k / 100; },
    fix: (r) => { calls.push('fix'); return r.toFixed(2); },
  };
  formatPrice(150050, helpers);
  assert.deepEqual(calls, ['toRubles', 'fix']);
});
// price.mjs
export function formatPrice(kopecks) {
  const rubles = Math.trunc(kopecks / 100);
  const rest = String(kopecks % 100).padStart(2, '0');
  return `${rubles}.${rest} ₽`;
}

Зачем: тест — это договор о поведении, а не о реализации. Проверка внутренних шагов мешает улучшать код: функцию переписали без деления на дробные рубли, результат тот же, а тест красный. В итоге команда перестаёт доверять тестам.

Решение и разбор
// price.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { formatPrice } from './price.mjs';

for (const [kopecks, expected] of [
  [150050, '1500.50 ₽'],
  [5, '0.05 ₽'],
  [100000, '1000.00 ₽'],
]) {
  test(`${kopecks} копеек → ${expected}`, () => {
    assert.equal(formatPrice(kopecks), expected);
  });
}

Реализация в given уже переписана без помощников: она работает с целыми числами. Старый тест к ней уже не применить: функция не принимает помощников, хотя результат прежний. Новый тест проходит. Мутант с наивным делением даёт 1500.5 ₽ и 0.05 ₽: тест 150050 его ловит, хотя 0.05 случайно совпал бы. Поэтому в таблице несколько разных случаев.
