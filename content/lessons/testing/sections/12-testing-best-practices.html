Лучшие практики: по сборнику Йони Гольдберга

В программе есть большой сборник javascript-testing-best-practices. Его «золотое правило»: тестовый код должен быть коротким, простым и читаться с одного взгляда. Тест, который стоит дороже пользы, лучше удалить. Ниже правила, которые больше всего пригодятся фронтенд-студенту.

Анатомия теста

  • Имя из трёх частей: что тестируем, при каком условии и чего ждём. Например, «parsePrice: отрицательная цена → RangeError». Упавший тест сразу объясняет проблему.
  • AAA: подготовка, действие, проверка — три визуально отделённых блока (подробнее в разделе «Первый тест»).
  • Чёрный ящик: проверяйте публичное поведение, а не приватные методы. Тогда рефакторинг не ломает тесты.
  • Реалистичные данные: не 'foo', а похожие на настоящие. Строка «199,90» с запятой найдёт ошибку, которую «100» пропустит.
  • Ошибки ожидают, а не ловят: вместо try/catch внутри теста используйте assert.throws или expect(...).toThrow().
  • Два уровня группировки: describe по модулю, внутри него по сценарию. Отчёт читается как оглавление.
  • Тест на каждый найденный баг до его исправления: так он больше не вернётся.
  • Короткие снимки: если используете snapshot, делайте его маленьким и встроенным в тест.

Тестирование свойств

Вместо пяти вручную выбранных входов можно сгенерировать тысячу и проверить свойство, которое верно для любого из них. В сборнике для этого советуют библиотеку fast-check. Ниже идея показана без библиотек. Пример выполнен через node --test в Node.js 22, все три теста проходят.

import { test } from 'node:test';
import assert from 'node:assert/strict';

function parsePrice(text) {
  const value = Number(text.replace(',', '.'));
  if (!Number.isFinite(value) || value < 0) throw new RangeError(`Некорректная цена: ${text}`);
  return Math.round(value * 100);
}

test('parsePrice: строка с запятой → цена в копейках', () => {
  assert.equal(parsePrice('199,90'), 19990);
});

test('parsePrice: отрицательная цена → RangeError', () => {
  assert.throws(() => parsePrice('-5'), RangeError);
});

test('parsePrice: свойство — копейки считаются точно для любой цены', () => {
  for (let i = 0; i < 1000; i++) {
    const rubles = Math.floor(Math.random() * 100000);
    const kopeks = Math.floor(Math.random() * 100);
    const text = `${rubles},${String(kopeks).padStart(2, '0')}`;
    assert.equal(parsePrice(text), rubles * 100 + kopeks, text);
  }
});

Почему здесь Math.round: 199.9 * 100 в JavaScript даёт 19989.999999999996, а не 19990. Тест свойства на тысяче случайных цен поймал бы такую ошибку, если убрать округление. Минус случайных входов — их трудно воспроизвести, поэтому в сообщение передаётся сам вход (text). fast-check к тому же умеет уменьшать найденный вход до минимального примера.

Ещё несколько правил

  • Подменяйте осторожно: заглушки (stub) и шпионы (spy), проверяющие наблюдаемый результат, надёжнее моков, которые проверяют внутренние вызовы (см. «Подмены»).
  • Никаких общих данных: каждый тест создаёт свои данные. Общие «посевные» записи связывают тесты между собой.
  • Граничные случаи интеграции: медленный ответ, таймаут, повторная попытка, а не только код 500.
  • Метки: помечайте быстрые и медленные тесты, чтобы во время разработки запускать только быстрые.
  • Не только пирамида: выбирайте вид теста по рискам конкретного приложения. Для небольшого сервиса тест всего компонента через его API часто полезнее сотни unit-тестов.
