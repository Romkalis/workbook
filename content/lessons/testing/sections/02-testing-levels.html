Уровни и цели: не складывайте всё в один список

Уровень теста отвечает на вопрос «какую часть системы проверяем вместе?». Цель отвечает на вопрос «какое свойство проверяем?». Автоматизация — ещё одна ось: проверка может выполняться человеком или программой.

Unit, integration и E2E

УровеньГраницаПример для поиска фильмов
Unit, модульный (module testing)Небольшая единица поведенияПустая строка не проходит нормализацию запроса
Integration, интеграционныйСовместная работа нескольких частейКлиент посылает запрос тестовому серверу и разбирает ответ
E2E, сквознойПользовательский путь через выбранную границу системыОткрыть страницу, ввести запрос, увидеть результаты от тестового backend

Границы терминов у команд различаются. Тест двух настоящих модулей уже проверяет их интеграцию, но тест клиента с полностью подменённой сетью не доказывает совместимость с настоящим сервером. Браузерный сценарий с замоканным API тоже не проверяет весь путь до базы данных. Указывайте, какие части реальные, а какие заменены.

Задача 1. Unit-тест нормализации запроса ★☆☆ разминка

Напишите unit-тесты для normalizeQuery: обрезает пробелы, приводит к нижнему регистру, а пустой результат превращает в null (такой запрос не отправляем). Минимум четыре теста. Файл — query.test.mjs, запуск — node --test.

// query.mjs
export function normalizeQuery(raw) {
  const q = raw.trim().toLowerCase();
  return q === '' ? null : q;
}

Зачем: это нижний этаж пирамиды: самая дешёвая проверка самой частой логики. Если здесь ошибка, никакой E2E-тест не скажет, где именно, а unit-тест укажет на функцию.

Решение и разбор
// query.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { normalizeQuery } from './query.mjs';

test('обрезает пробелы по краям', () => {
  assert.equal(normalizeQuery('  matrix '), 'matrix');
});

test('приводит к нижнему регистру', () => {
  assert.equal(normalizeQuery('MaTrIx'), 'matrix');
});

test('пустая строка — null', () => {
  assert.equal(normalizeQuery(''), null);
});

test('строка из пробелов и табуляции — null', () => {
  assert.equal(normalizeQuery(' \t\n '), null);
});

Тест на «только пробелы» — главный: именно он ловит версию без trim(). Она отправляла бы на сервер запрос из пробелов и показывала «ничего не найдено». Мы проверили: мутант без trim падает на двух тестах из четырёх.

Функциональные и нефункциональные проверки

Функциональные проверяют результат: отправляется ли заявка, отображается ли ошибка. Производительность оценивает задержки, пропускную способность и поведение под нагрузкой. Безопасность проверяет, например, ограничения доступа и обработку недоверенного ввода. Доступность оценивает возможность пользоваться интерфейсом разными способами.

Из общих знаний: регрессионная проверка помогает не вернуть исправленный дефект, smoke-проверка быстро подтверждает жизнеспособность основных сценариев, исследовательское тестирование ищет неожиданные проблемы через изучение продукта. Они не являются конкурирующими уровнями вместо unit/integration/E2E.

Безопасность и производительность подробнее — из общих знаний

Тестирование безопасности ищет способы получить то, что не положено. Во фронтенде это прежде всего проверки, что пользовательский текст не превращается в HTML (XSS), что скрытая кнопка не заменяет серверную проверку прав и что токены и ключи не попадают в код бандла. Часть проверок автоматизирована: npm audit сообщает об уязвимых зависимостях, статический анализ находит опасные конструкции вроде innerHTML с данными пользователя. Глубокий аудит и пентест проводят специалисты.

Тестирование производительности измеряет, а не угадывает. Нагрузочный тест проверяет поведение под ожидаемым числом пользователей, стресс-тест ищет точку отказа. Для фронтенда главные инструменты — Lighthouse и вкладка Performance в DevTools: время до первого содержимого, длинные задачи, размер бандла. Порог («страница интерактивна быстрее 3 секунд на среднем телефоне») можно проверять в CI, чтобы не ухудшить его незаметно.

Скриншотные тесты: регрессии во внешнем виде

Регрессия — это когда работавшее раньше сломалось после новой правки. Логику ловят unit-тесты, а вот «кнопка уехала на 20 пикселей» или «текст стал белым на белом» они не увидят: функция по-прежнему возвращает правильное значение. Для внешнего вида есть скриншотные тесты (screenshot testing, visual regression testing). Тест открывает страницу или компонент в браузере, делает снимок и сравнивает его попиксельно с эталоном — снимком, который команда однажды проверила глазами и сохранила в репозиторий.

Из общих знаний: такие проверки умеют Playwright (toHaveScreenshot), Storybook с дополнениями, сервисы вроде Chromatic и Percy. Главная трудность — стабильность: шрифты, сглаживание и анимации отличаются между машинами, поэтому снимки делают в одинаковом окружении и задают допустимый порог отличий. Не путайте их со snapshot-тестами: snapshot сравнивает текстовое представление (например, разметку), а не картинку.

Пишут ли тесты безопасности для фронтенда

Обычно нет. Безопасность в первую очередь обеспечивает сервер: проверку прав, валидацию, хранение секретов. Код фронтенда целиком лежит у пользователя в браузере, и любую его проверку можно обойти. Поэтому специальные тесты безопасности, как правило, пишут для бэкенда, а проводят их отдельные специалисты (пентест — попытка взломать систему по договорённости с её владельцем). Но для фронтенда такие проверки можно добавить, если создать условия: например, тест, что пользовательский текст <img onerror=…> выводится как текст, а не исполняется (защита от XSS), или проверку зависимостей через npm audit в CI (из общих знаний).

Задача 2. Тест: текст пользователя не становится HTML ★★☆ практика

Функция escapeHtml готовит пользовательский текст к вставке через innerHTML. Напишите тесты, которые докажут, что строка <img src=x onerror=alert(1)> превращается в безопасный текст, и что экранируются &, " и '.

// escape.mjs
const MAP = { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' };
export function escapeHtml(text) {
  return text.replace(/[&<>"']/g, (ch) => MAP[ch]);
}

Зачем: это один из немногих тестов безопасности, которые реально писать во фронтенде. Экранирование легко «упростить» при рефакторинге, а тест сразу поднимет тревогу. Кавычки важны для атрибутов: title="${text}" с кавычкой внутри ломает разметку.

Подсказка

Проверьте ожидание целиком (assert.equal с готовой строкой), а не «не содержит <»: так вы поймаете и лишнее, и недостающее.

Решение и разбор
// escape.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { escapeHtml } from './escape.mjs';

test('тег с обработчиком превращается в текст', () => {
  assert.equal(escapeHtml('<img src=x onerror=alert(1)>'), '&lt;img src=x onerror=alert(1)&gt;');
});

test('экранирует амперсанд первым, без двойного экранирования', () => {
  assert.equal(escapeHtml('Tom & Jerry <3'), 'Tom &amp; Jerry &lt;3');
});

test('экранирует кавычки для атрибутов', () => {
  assert.equal(escapeHtml(`"Солярис" и 'Сталкер'`), '&quot;Солярис&quot; и &#39;Сталкер&#39;');
});

Каждый тест сравнивает с конкретной строкой, посчитанной вручную. Мутант, который экранирует только угловые скобки, проходит первый тест и падает на остальных. Учтите границы такой проверки: она доказывает свойства функции, а не то, что её везде вызывают. Надёжнее вообще не использовать innerHTML для текста и писать textContent.

Тестирование в инженерном процессе

Фраза Engineering Processes в программе относится к процессам разработки, а не к отдельному уровню теста. Требования обсуждают до реализации, быстрые проверки запускают при правках, необходимые проверки — в CI перед слиянием. После выпуска мониторинг помогает заметить реальные сбои, но не заменяет проверки до выпуска.
