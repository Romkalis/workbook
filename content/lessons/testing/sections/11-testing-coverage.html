Покрытие и поддержка тестов

Из общих знаний: coverage показывает, какие части программы были выполнены во время тестов. Это полезная карта пробелов, а не процент доказанной правильности.

Строки, функции и ветви

Покрытие строк отмечает выполненные строки, функций — вызванные функции, ветвей — пройденные варианты условий. Даже если одна строка с условием выполнялась, обе ветви могли не проверяться. А выполнение ветви без сильного утверждения не гарантирует верный результат.

Тест, который вызывает функцию и ничего не проверяет, может увеличить покрытие. Поэтому 100% не означает отсутствие дефектов. Смотрите на непокрытые правила и возможные ошибки, а не добавляйте бессмысленные вызовы ради числа.

Задача 20. Непокрытая ветка в отчёте Node ★★☆ практика

Запустите node --test --experimental-test-coverage для файлов ниже. Найдите в отчёте функцию с непокрытой веткой (колонка branch %) и допишите тест, который её проходит и проверяет результат.

// shipping.mjs
export function shippingLabel(order) {
  if (order.pickup) {
    return 'Самовывоз';
  }
  if (order.total >= 500000) {
    return 'Бесплатная доставка';
  }
  return 'Доставка 300 ₽';
}
// shipping.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { shippingLabel } from './shipping.mjs';
test('самовывоз', () => assert.equal(shippingLabel({ pickup: true, total: 0 }), 'Самовывоз'));
test('платная доставка', () => assert.equal(shippingLabel({ pickup: false, total: 1000 }), 'Доставка 300 ₽'));

Зачем: отчёт покрытия показывает, какие правила никто не проверял. Здесь непроверенным оказалось правило о деньгах (бесплатная доставка), и его можно сломать незаметно.

Решение и разбор
// shipping.free.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { shippingLabel } from './shipping.mjs';

test('бесплатная доставка ровно от 5 000 ₽', () => {
  assert.equal(shippingLabel({ pickup: false, total: 500000 }), 'Бесплатная доставка');
});

До нового теста в строке shipping.mjs отчёт показывает меньше 100% по строкам и веткам, а в колонке непокрытых строк — строки с бесплатной доставкой. Тест берёт значение ровно на границе, поэтому заодно ловит замену >= на >. Мутант, который удалил правило целиком, тоже падает.

Как считают покрытие

Покрытие — это всегда доля: сколько проверено от того, что вообще есть, умноженная на 100. Разница только в том, что считать.

  • Покрытие кода = строки (функции, ветви), выполненные тестами ÷ все строки × 100. Его считает инструмент: node --test --experimental-test-coverage, jest --coverage.
  • Покрытие требований = требования, отобранные для проверки ÷ все заявленные требования × 100. Его считают по списку требований, а не по коду: например, в таблице «требование — тесты, которые его проверяют».

Нужно ли 100% и как покрытие связано с качеством

100% покрытия не обязательно и обычно не нужно. Последние проценты — это тривиальные геттеры, обработка невозможных ошибок, служебный код, а стоят они дорого. Команды обычно ставят разумный порог (часто 70–80%, из общих знаний) и важнее смотрят, покрыты ли рискованные места: расчёт денег, права доступа, обработка ошибок.

Покрытие влияет на качество, но не прямо пропорционально. Рост покрытия на 20% не делает продукт на 20% лучше: тест может выполнить строку и ничего не проверить. Но и связи «никакой» нет: код, который ни разу не запускался в тестах, точно не проверен. Покрытие показывает, где тестов нет, а не насколько хороши те, что есть.

Мысленно сломайте реализацию

Попробуйте заменить >= на >, убрать обработку ошибки, вернуть постоянное значение. Упадёт ли тест? Такой вопрос помогает оценить качество проверок. Инструменты mutation testing автоматизируют похожую идею, но не обязательны для первого учебного набора.

Задача 21. Убейте трёх мутантов ★★☆ практика

Ниже правильная applyDiscount(price, percent) и три её сломанные версии: без округления, без проверки верхней границы, с percent > 0 вместо >= 0. Напишите минимальный набор тестов, который проходит на правильной версии и падает на каждом мутанте.

// discount.mjs
export function applyDiscount(price, percent) {
  if (!Number.isFinite(percent) || percent < 0 || percent > 100) {
    throw new RangeError('Скидка от 0 до 100');
  }
  return Math.round(price * (1 - percent / 100));
}

Зачем: так работает мутационное тестирование, только вручную: качество набора — это то, сколько правдоподобных ошибок он ловит. Каждый тест в итоговом наборе должен иметь причину существования.

Решение и разбор
// discount.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { applyDiscount } from './discount.mjs';

test('округляет до целых копеек', () => {
  assert.equal(applyDiscount(999, 10), 899); // 899.1 → 899
});

test('скидка 0% разрешена', () => {
  assert.equal(applyDiscount(1000, 0), 1000);
});

test('скидка больше 100% отклоняется', () => {
  assert.throws(() => applyDiscount(1000, 101), RangeError);
});

Три теста — три мутанта. Без округления 999 × 0,9 даёт 899.1. Без верхней границы 101% вернёт отрицательную цену вместо ошибки. С > 0 ноль бросит исключение. Цена 999, а не 1000, выбрана намеренно: 10% от 1000 — целое число, и мутант без округления бы выжил. Проверка запуском: каждый из трёх мутантов падает ровно на своём тесте.

Снимки и поведение

Snapshot фиксирует представление результата и обнаруживает его изменение. Большой снимок, который без чтения обновляют после каждого падения, почти не защищает. Для конкретного правила полезнее явное утверждение: есть сообщение об ошибке, сумма равна ожидаемой, действие недоступно.

При падении сначала прочитайте название, ожидаемое и фактическое значение. Запустите нужный тест, воспроизведите дефект, исправьте причину и затем прогоните подходящий набор. Если поменялось требование, обновляйте тест осознанно, а не подгоняйте ожидание под любой текущий результат.
