TDD и BDD: подходы к разработке

TDD строит реализацию короткими шагами через проверку ожидаемого поведения. Это больше, чем «написать тесты до сдачи»: каждый цикл должен дать обратную связь о следующем маленьком требовании.

Red → Green → Refactor

  1. Red: добавьте тест следующего поведения и убедитесь, что он падает по нужной причине.
  2. Green: напишите достаточный код, чтобы тест прошёл.
  3. Refactor: улучшите структуру, сохраняя поведение и успешный прогон.

Названия фаз взяты из цветов, которыми runner показывает результат: красный — тест упал, зелёный — прошёл. У третьей фазы, Refactor, своего цвета в runner нет: тесты остаются зелёными. На схемах цикла её обычно рисуют синим или серым, единого правила нет (из общих знаний). Жёлтый к TDD отношения не имеет.

Ниже самостоятельный файл для фазы Red. Он намеренно завершается с ошибкой: isEmpty всегда возвращает false, хотя для [] ожидается true. Ошибка синтаксиса или отсутствующий импорт не подтверждали бы нужное требование.

import test from 'node:test';
import assert from 'node:assert/strict';
const isEmpty = items => false;
test('пустой массив распознаётся', () => {
  assert.equal(isEmpty([]), true);
});

Фаза Green: замените заглушку на проверку длины, затем добавьте случай непустого массива. Ниже полный проходящий файл. После этого можно проверить, нужно ли упрощать реализацию: для такой короткой функции рефакторинг может и не понадобиться.

import test from 'node:test';
import assert from 'node:assert/strict';
const isEmpty = items => items.length === 0;
test('пустой массив распознаётся', () => {
  assert.equal(isEmpty([]), true);
});
test('массив с элементом не пуст', () => {
  assert.equal(isEmpty([0]), false);
});

Статья CircleCI из программы перечисляет плюсы TDD: требования понятны до реализации, ошибки находятся рано, дизайн складывается под тесты, а сами тесты служат документацией и позволяют уверенно менять код. Из минусов там упомянуто только, что TDD требует больше усилий в начале. Это однобоко. Из общих знаний: TDD плохо ложится на исследовательскую работу, когда интерфейс ещё неясен, на вёрстку и на прототипы, которые завтра выбросят. Там тесты пишут после того, как поведение устоялось.

BDD: согласовать поведение на примерах

BDD помогает разработчикам, тестировщикам и людям со стороны продукта договориться о поведении. Сначала обсуждают конкретные случаи, затем формулируют их так, чтобы можно было проверить. Синтаксис Given/When/Then удобен, но сам по себе не делает процесс BDD.

Пример сценария

Дано: корзина пуста. Когда: пользователь открывает оформление заказа. Тогда: кнопка подтверждения недоступна и есть объяснение, что нужно добавить товар.

Этот сценарий — текстовое описание, не исполняемый файл Gherkin. Его можно автоматизировать разными инструментами. BDD и TDD совместимы: согласованный пользовательский пример направляет разработку, а TDD помогает шаг за шагом построить нужную логику. Названия describe/it не определяют методологию.
