TDD и BDD: подходы к разработке

TDD строит реализацию короткими шагами через проверку ожидаемого поведения. Это больше, чем «написать тесты до сдачи»: каждый цикл должен дать обратную связь о следующем маленьком требовании.

Red → Green → Refactor

  1. Red: добавьте тест следующего поведения и убедитесь, что он падает по нужной причине.
  2. Green: напишите достаточный код, чтобы тест прошёл.
  3. Refactor: улучшите структуру, сохраняя поведение и успешный прогон.

Названия фаз взяты из цветов, которыми runner показывает результат: красный — тест упал, зелёный — прошёл. У третьей фазы, Refactor, своего цвета в runner нет: тесты остаются зелёными. На схемах цикла её обычно рисуют синим или серым, единого правила нет (из общих знаний). Жёлтый к TDD отношения не имеет.

Ниже самостоятельный файл для фазы Red. Он намеренно завершается с ошибкой: isEmpty всегда возвращает false, хотя для [] ожидается true. Ошибка синтаксиса или отсутствующий импорт не подтверждали бы нужное требование.

import test from 'node:test';
import assert from 'node:assert/strict';
const isEmpty = items => false;
test('пустой массив распознаётся', () => {
  assert.equal(isEmpty([]), true);
});

Фаза Green: замените заглушку на проверку длины, затем добавьте случай непустого массива. Ниже полный проходящий файл. После этого можно проверить, нужно ли упрощать реализацию: для такой короткой функции рефакторинг может и не понадобиться.

import test from 'node:test';
import assert from 'node:assert/strict';
const isEmpty = items => items.length === 0;
test('пустой массив распознаётся', () => {
  assert.equal(isEmpty([]), true);
});
test('массив с элементом не пуст', () => {
  assert.equal(isEmpty([0]), false);
});

Статья CircleCI из программы перечисляет плюсы TDD: требования понятны до реализации, ошибки находятся рано, дизайн складывается под тесты, а сами тесты служат документацией и позволяют уверенно менять код. Из минусов там упомянуто только, что TDD требует больше усилий в начале. Это однобоко. Из общих знаний: TDD плохо ложится на исследовательскую работу, когда интерфейс ещё неясен, на вёрстку и на прототипы, которые завтра выбросят. Там тесты пишут после того, как поведение устоялось.

Задача 17. TDD: разбор параметра сортировки ★★☆ практика

Сделайте по TDD функцию parseSort(value): 'price-asc' → { field: 'price', dir: 'asc' }; 'title-desc' → { field: 'title', dir: 'desc' }; любое другое значение (null, 'price', 'cost-asc') → null. Начните с одного падающего теста, двигайтесь маленькими шагами.

Зачем: каждый новый тест в TDD — маленькое требование, и код растёт ровно настолько, насколько нужно. В конце у вас и функция, и её спецификация, а каждый случай «а что если…» уже записан.

Подсказка

Шаги: 1) 'price-asc' (минимальный код может вернуть константу!), 2) 'title-desc' заставит разбирать строку, 3) неизвестное поле, 4) нет направления, 5) null.

Решение и разбор
// sort.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { parseSort } from './sort.mjs';

test('price-asc', () => assert.deepEqual(parseSort('price-asc'), { field: 'price', dir: 'asc' }));
test('title-desc', () => assert.deepEqual(parseSort('title-desc'), { field: 'title', dir: 'desc' }));
test('неизвестное поле — null', () => assert.equal(parseSort('cost-asc'), null));
test('без направления — null', () => assert.equal(parseSort('price'), null));
test('лишняя часть — null', () => assert.equal(parseSort('price-asc-x'), null));
test('null — null', () => assert.equal(parseSort(null), null));
// sort.mjs
const FIELDS = ['price', 'title'];
const DIRS = ['asc', 'desc'];

export function parseSort(value) {
  if (typeof value !== 'string') return null;
  const [field, dir, ...rest] = value.split('-');
  if (rest.length > 0 || !FIELDS.includes(field) || !DIRS.includes(dir)) return null;
  return { field, dir };
}

После первого теста «зелёная» реализация может быть return { field: 'price', dir: 'asc' }. Звучит глупо, но это честный шаг: второй тест заставляет её обобщить. Тест «лишняя часть» появился, когда на шаге рефакторинга стало видно, что деструктуризация молча отбросит хвост. Белые списки FIELDS и DIRS — это ещё и безопасность: значение из адреса страницы не попадёт в запрос как есть.

BDD: согласовать поведение на примерах

BDD помогает разработчикам, тестировщикам и людям со стороны продукта договориться о поведении. Сначала обсуждают конкретные случаи, затем формулируют их так, чтобы можно было проверить. Синтаксис Given/When/Then удобен, но сам по себе не делает процесс BDD.

Пример сценария

Дано: корзина пуста. Когда: пользователь открывает оформление заказа. Тогда: кнопка подтверждения недоступна и есть объяснение, что нужно добавить товар.

Этот сценарий — текстовое описание, не исполняемый файл Gherkin. Его можно автоматизировать разными инструментами. BDD и TDD совместимы: согласованный пользовательский пример направляет разработку, а TDD помогает шаг за шагом построить нужную логику. Названия describe/it не определяют методологию.

Задача 18. Сценарий Given/When/Then в тестах ★☆☆ разминка

Превратите сценарий из раздела в тесты для checkoutState(cart). Функция возвращает { enabled, reason }: для пустой корзины кнопка недоступна, а причина — «Добавьте товар в корзину»; для непустой — доступна, причины нет. Названия describe/it должны читаться как сценарий.

// checkout.mjs
export function checkoutState(cart) {
  if (cart.length === 0) return { enabled: false, reason: 'Добавьте товар в корзину' };
  return { enabled: true, reason: null };
}

Зачем: сценарий, согласованный с продуктом, становится исполняемой проверкой. Изменят требование — упадёт тест с понятным всем названием, а не загадочный test 12.

Решение и разбор
// checkout.test.mjs
import { describe, it } from 'node:test';
import assert from 'node:assert/strict';
import { checkoutState } from './checkout.mjs';

describe('Оформление заказа', () => {
  describe('Дано: корзина пуста. Когда: пользователь открывает оформление', () => {
    it('Тогда: кнопка подтверждения недоступна и объяснено почему', () => {
      assert.deepEqual(checkoutState([]), { enabled: false, reason: 'Добавьте товар в корзину' });
    });
  });

  describe('Дано: в корзине есть товар', () => {
    it('Тогда: кнопка доступна, объяснение не нужно', () => {
      assert.deepEqual(checkoutState([{ id: 1, quantity: 1 }]), { enabled: true, reason: null });
    });
  });
});

Важная часть сценария — объяснение. Мутант делает кнопку недоступной, но молча, и пользователь не понимает почему. Проверка deepEqual всего объекта ловит это. Сама функция ничего не знает о кнопке: она описывает состояние, а интерфейс решает, как его показать.
