Коммиты по правилам RS School

По Git convention RS School сообщение имеет вид type(scope): description; scope необязателен. После двоеточия нужен пробел. Тип пишите строчными буквами, описание — кратким действием в настоящем времени и повелительном наклонении: add, fix, migrate.

ТипКогда использовать
featНовая возможность
fixИсправление ошибки
refactorИзменение устройства кода без смены поведения
docsДокументация
styleФорматирование кода; не оформление интерфейса
testТесты
buildСборка и зависимости
ciАвтоматические проверки
perfПроизводительность
choreСлужебные изменения
revertОтмена предыдущего изменения

Отдельный init сейчас не рекомендуется; его использование по старым материалам школа не считает ошибкой. Обычных типов достаточно с первого коммита.

Авторские примеры для News API из общих знаний: build: configure TypeScript loader, refactor(api): migrate loader to TypeScript, fix(news): ignore stale responses, feat(ui): add loading indicator, docs: describe deployment steps. Выбирайте тип по фактическому изменению. Запись style: add responsive cards вводит в заблуждение: адаптивность меняет интерфейс, а style относится к форматированию кода.

Делайте коммиты по завершённым шагам, проверяя diff перед фиксацией. Не выдумывайте минимальное число коммитов: в присланном условии News API оно не задано. Нужна история разработки, а не искусственное дробление готовой работы.
