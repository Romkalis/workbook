Этап 1. Fork, ветка и исходное поведение

Откройте оригинальное приложение и создайте свой публичный fork. Клонируйте именно свой fork. От основной ветки создайте ветку задачи, например news-api; дальнейшая работа и PR должны оставаться внутри вашего репозитория.

Сначала исследуйте проект

  1. Прочитайте README, package.json и конфигурацию Webpack. Определите версию Node.js, команды запуска и сборки, точку входа и каталог результата. Если есть lockfile, используйте совместимую с ним установку зависимостей.
  2. Запустите приложение по его инструкции. Проверьте загрузку списка источников, выбор источника и появление новостей. Сохраните список наблюдений и снимок интерфейса для сравнения.
  3. Проследите один запрос: от клика до построения URL, сетевого ответа и изменения DOM. Найдите классы загрузчика, контроллера и представления, даже если они называются иначе.
  4. Зафиксируйте исходные неисправности отдельно: неверный ключ API, недоступность сервера и ошибка TypeScript — разные проблемы.

Нарисуйте для себя цепочку «событие → контроллер → загрузчик → ответ → представление». Для каждого перехода запишите вход и выход: элемент события, идентификатор источника, параметры запроса, список статей. Эти записи станут будущими типами.

Ниже нет обещания конкретной структуры файлов исходника: содержимое его файлов в этой работе не разобрано. Сначала сопоставьте план со своей версией fork, затем меняйте код.

Готово, когда: вы можете показать исходный сценарий или точно объяснить, какой внешний сбой мешает запуску, и назвать места, через которые проходят данные.
