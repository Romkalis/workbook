Этап 2. Подключаем TypeScript, Webpack и ESLint

Настраивайте инструменты в fork приложения, а не в репозитории этого учебника. Сохраните существующие плагины для HTML, CSS и изображений: перенос языка не должен сломать загрузку ресурсов.

Строгая конфигурация

Добавьте локальный TypeScript и создайте tsconfig.json по разобранному примеру, согласовав include с исходниками. В финальной конфигурации явно укажите strict: true и noImplicitAny: true. Второй флаг входит в strict, но в задании требуется показать оба.

Подберите target, module, moduleResolution и lib для браузерного проекта и используемой версии TypeScript. DOM-типы должны быть доступны. На время поэтапного переноса можно оставить allowJs, но это промежуточный приём: к сдаче весь прикладной код должен быть перенесён в TS. JS-конфигурация сборщика сама по себе не означает, что миграция приложения не завершена.

Сборка и отдельная проверка типов

По уроку о Webpack подключите ts-loader совместимой версии, добавьте правило для TS, исключите node_modules, обновите entry и разрешение расширений .ts и .js. Проверьте импорты и существующие правила: два загрузчика не должны случайно обрабатывать один файл несовместимыми способами.

Добавьте отдельную npm-команду typecheck для tsc с noEmit. Если noEmit стоит непосредственно в tsconfig, учтите, что ts-loader обычно нуждается в выпуске JS: разделите конфигурации или переопределите эту настройку для загрузчика. Успешная транспиляция с отключённой проверкой типов ещё не доказывает корректность типов.

Линтер без подавления ошибок

Выберите конфигурацию по версии ESLint в fork. Для современного проекта используйте eslint.config.mjs: пример flat config. Для сопровождения старого исходника доступен полный пример .eslintrc.json с установкой пакетов и запуском. В обоих случаях нужны recommended и правило @typescript-eslint/no-explicit-any со значением error.

Если вы сохраняете legacy на совместимой версии, переписывать его только ради имени файла не требуется. Проверьте охват TS-файлов и запуск линтера. Если обновляете проект до ESLint 10, выполните миграцию ниже. В сравнении форматов показано, куда переносится каждая настройка.

Если в исходнике есть .eslintrc.json

Это старый формат. В ESLint 9 flat config стал форматом по умолчанию, а в ESLint 10 поддержка .eslintrc полностью удалена. При переходе на flat config создайте eslint.config.mjs; одного переименования JSON недостаточно. Сверьте изменения с руководством ESLint 10.

  1. Проверьте локальную версию ESLint и совместимость Node.js и плагинов перед обновлением зависимостей.
  2. Перенесите строковые extends в импорты наборов правил; подключите tseslint.configs.recommended по typescript-eslint Quickstart.
  3. Укажите files для всех TS-исходников, rules для правил, languageOptions.globals для глобальных имён браузера. Старое env: browser не переносится буквально.
  4. Перенесите шаблоны из .eslintignore в отдельный объект ignores, проверьте их область действия. Flat config не читает .eslintignore автоматически.
  5. После переноса удалите устаревшую .eslintrc.json и ненужную .eslintignore, обновите lint-скрипт. Не оставляйте два противоречащих источника настроек.

Это план миграции из официального руководства. В условии задачи требование к recommended и no-explicit-any относится к действующим правилам проверки, а не к обязательному имени .eslintrc.json.

Добавьте npm-команду lint, которая действительно захватывает все TS-исходники. Временно внесите явный запрещённый тип в учебную строку, убедитесь, что линтер падает, затем удалите её. Аналогично проверьте, что typecheck замечает несовместимое присваивание. Не сдавайте эти намеренные ошибки.

Готово, когда: первый TS-модуль входит в сборку, проверка типов и линтер запускаются отдельно и обнаруживают ошибки. Все зависимости инструментов добавляются в fork приложения; учебнику новые зависимости не нужны.
