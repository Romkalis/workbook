Экраны и их жизненный цикл

Экран в SPA живёт дольше, чем кажется: он подписался на события стора, запустил таймер, начал загрузку. Когда пользователь ушёл на другой экран, всё это должно остановиться. Иначе подписки копятся, старые экраны продолжают реагировать на события, а ответ запоздавшего запроса рисуется поверх нового экрана.

export interface View {
  mount(root: HTMLElement): void;
  unmount(): void;
}

export function createClockView(): View {
  let timer: ReturnType<typeof setInterval> | undefined;
  return {
    mount(root) {
      const p = document.createElement('p');
      root.replaceChildren(p);
      const tick = () => (p.textContent = new Date().toLocaleTimeString('ru-RU'));
      tick();
      timer = setInterval(tick, 1000);
    },
    unmount() {
      clearInterval(timer);
    },
  };
}

Роутер при переходе вызывает unmount текущего экрана и только потом mount нового. Для отмены сразу всего, что экран запустил (обработчики, запросы), удобен один AbortController на экран: его signal передают в addEventListener и fetch, а в unmount вызывают abort().

Состояние между экранами

Данные, которые нужны нескольким экранам, хранятся вне экранов — в сторе. Экран при mount подписывается и рисует текущее состояние, при unmount отписывается. Что именно положить в адрес, а что в стор: всё, чем пользователь хочет поделиться ссылкой (страница, фильтры, открытый товар), — в адрес; временное (открыт ли выпадающий список, введённый, но не отправленный текст) — в состояние экрана.

Задача 8. Экран, который убирает за собой ★★☆ практика

Напишите экран createCartView(store, api): при mount подписывается на стор и рисует число товаров, запускает загрузку рекомендаций (api.recommendations(signal)) и вешает обработчик на кнопку «Очистить». При unmount всё отменяется одним AbortController: подписка, обработчик и запрос. Ответ, пришедший после unmount, не должен ничего рисовать.

Зачем: это самая частая утечка в SPA: пользователь ушёл со страницы, а её подписка продолжает перерисовывать удалённые элементы, и запоздавший ответ показывает рекомендации на чужом экране. Один контроллер на экран — простое правило, которое закрывает все три случая.

Решение и разбор
export interface Store {
  get(): { count: number };
  subscribe(fn: () => void): () => void;
  clear(): void;
}
export interface Api {
  recommendations(signal: AbortSignal): Promise<string[]>;
}

export function createCartView(store: Store, api: Api) {
  let controller: AbortController | null = null;
  return {
    mount(root: HTMLElement) {
      controller = new AbortController();
      const { signal } = controller;
      const count = document.createElement('p');
      const button = document.createElement('button');
      button.textContent = 'Очистить';
      const recs = document.createElement('ul');
      root.replaceChildren(count, button, recs);

      const draw = () => (count.textContent = `Товаров: ${store.get().count}`);
      draw();
      const unsubscribe = store.subscribe(draw);
      signal.addEventListener('abort', unsubscribe);
      button.addEventListener('click', () => store.clear(), { signal });

      api
        .recommendations(signal)
        .then((items) => {
          if (signal.aborted) return;
          recs.replaceChildren(...items.map((t) => Object.assign(document.createElement('li'), { textContent: t })));
        })
        .catch(() => {});
    },
    unmount() {
      controller?.abort();
      controller = null;
    },
  };
}

Подписка стора не умеет принимать signal, поэтому её отписка вешается на событие abort самого сигнала. Так все виды уборки собираются в одном месте. Проверка signal.aborted в then нужна, даже если API честно отменяет запрос: ответ мог прийти за мгновение до отмены. catch глотает ошибку отмены. В рабочем коде настоящие ошибки сети стоит отличать и показывать.

Задача 9. Фильтры каталога в адресе ★★☆ практика

Напишите readFilters(search) и writeFilters(filters) для фильтров { q: string; sort: "new" | "price"; page: number }. Значения по умолчанию ("", "new", 1) в адрес не пишутся. Неверные значения из адреса заменяются значениями по умолчанию. Затем applyFilters(filters): при смене q или sort страница сбрасывается на 1, адрес обновляется через replaceState для поиска и pushState для смены страницы.

Зачем: адрес — публичный интерфейс экрана: им делятся и его сохраняют в закладки. Короткие адреса без значений по умолчанию читаются лучше, а выбор между push и replace решает, сколько раз пользователю жать «Назад»: никто не хочет откатывать поиск по одной букве.

Решение и разбор
export interface Filters {
  q: string;
  sort: 'new' | 'price';
  page: number;
}
const DEFAULTS: Filters = { q: '', sort: 'new', page: 1 };

export function readFilters(search: string): Filters {
  const p = new URLSearchParams(search);
  const sort = p.get('sort');
  const page = Number(p.get('page'));
  return {
    q: p.get('q')?.trim() ?? DEFAULTS.q,
    sort: sort === 'new' || sort === 'price' ? sort : DEFAULTS.sort,
    page: Number.isInteger(page) && page >= 1 ? page : DEFAULTS.page,
  };
}

export function writeFilters(f: Filters): string {
  const p = new URLSearchParams();
  if (f.q !== DEFAULTS.q) p.set('q', f.q);
  if (f.sort !== DEFAULTS.sort) p.set('sort', f.sort);
  if (f.page !== DEFAULTS.page) p.set('page', String(f.page));
  const s = p.toString();
  return s ? `?${s}` : '';
}

export function applyFilters(next: Filters): Filters {
  const prev = readFilters(location.search);
  const resetPage = next.q !== prev.q || next.sort !== prev.sort;
  const final = resetPage ? { ...next, page: 1 } : next;
  const url = location.pathname + writeFilters(final);
  if (resetPage) history.replaceState(null, '', url);
  else if (final.page !== prev.page) history.pushState(null, '', url);
  return final;
}

Чтение прощает всё: ?page=abc или ?sort=hack превращаются в значения по умолчанию, а не в ошибку экрана. Сброс страницы при новом поиске обязателен: на десятой странице результатов нового запроса может не быть. replaceState для поиска означает, что «Назад» вернёт на предыдущий экран, а не на предыдущую букву запроса.
