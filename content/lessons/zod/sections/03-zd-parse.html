parse и safeParse

import { z } from 'zod';
import { Product } from './intro.js';

export function readProduct(input: unknown) {
  const result = Product.safeParse(input);
  if (!result.success) {
    return { ok: false as const, errors: z.flattenError(result.error).fieldErrors };
  }
  return { ok: true as const, product: result.data }; // result.data: Product
}

schema.parse(x) возвращает проверенные данные или бросает ZodError. schema.safeParse(x) не бросает, а возвращает { success: true, data } или { success: false, error } — размеченное объединение, которое TypeScript сужает по success. Правило выбора: parse — когда неверные данные это авария (конфигурация при старте), safeParse — когда это нормальная ситуация (ввод пользователя, запрос клиента).

Важно: возвращается новый объект — проверенный, с применёнными trim, default и без лишних полей. Работайте с result.data, а не с исходным input.

Ошибки: issues и формы

error.issues — массив проблем. У каждой есть path (путь к полю, например ['items', 0, 'quantity']), code (вид ошибки) и message. Для формы удобнее z.flattenError(error): { formErrors: [...], fieldErrors: { title: ['...'], price: ['...'] } } — ошибки по полям верхнего уровня. Для логов есть z.prettifyError(error) — читаемый текст. В Zod 3 вместо этих функций был метод error.flatten().

Свои тексты задаются прямо в схеме: z.string().min(3, 'Минимум 3 символа') или z.string({ error: 'Нужна строка' }). Стандартные сообщения Zod английские, поэтому для интерфейса на русском свои тексты нужны почти всегда.

Задача 5. Конфигурация: parse при старте ★★☆ практика

Перепишите loadConfig из урока о Node.js на Zod: PORT — целое 1–65535, по умолчанию 3000; NODE_ENV — development, production или test, по умолчанию development; API_KEY обязателен при production. Используйте parse: при неверной конфигурации сервер не должен стартовать. Сообщение ошибки — z.prettifyError.

Зачем: неверная конфигурация — авария, а не обычная ситуация: продолжать работу с неизвестным портом или без ключа бессмысленно. Это как раз случай для parse, который бросает. Читаемый текст ошибки сразу говорит, какая переменная не так.

Решение и разбор
// config.ts
import { z } from 'zod';

const Env = z
  .object({
    PORT: z.coerce.number().int().min(1).max(65535).default(3000),
    NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
    API_KEY: z.string().min(1).optional(),
  })
  .refine((env) => env.NODE_ENV !== 'production' || env.API_KEY !== undefined, {
    message: 'API_KEY обязателен в production',
    path: ['API_KEY'],
  });

export type Config = z.infer<typeof Env>;

export function loadConfig(env: Record<string, string | undefined> = process.env): Config {
  const result = Env.safeParse(env);
  if (!result.success) throw new Error(`Неверная конфигурация:\n${z.prettifyError(result.error)}`);
  return result.data;
}

Используется safeParse, но ошибка всё равно бросается: так в сообщение можно добавить заголовок и читаемый текст prettifyError вместо сырого JSON ZodError. Поведение то же, что у parse. z.object отбросит все остальные переменные окружения (их сотни), и в Config останутся только нужные. Сравните с ручной версией из урока о Node.js: правила те же, а кода вдвое меньше.

Задача 6. Результат safeParse ★☆☆ разминка

Напишите parseQuantityInput(value: unknown) на safeParse: возвращает { ok: true, quantity } или { ok: false, message }, где сообщение — первое из ошибок схемы. Схема: целое от 1 до 99, свои русские тексты.

Зачем: ввод пользователя ошибается постоянно, это не исключительная ситуация. safeParse возвращает результат, который можно разобрать без try/catch, а TypeScript сужает тип по полю success.

Решение и разбор
// quantity.ts
import { z } from 'zod';

const Quantity = z
  .number({ error: 'Введите число' })
  .int('Только целое количество')
  .min(1, 'Минимум 1 штука')
  .max(99, 'Не больше 99 штук');

export function parseQuantityInput(value: unknown): { ok: true; quantity: number } | { ok: false; message: string } {
  const result = Quantity.safeParse(value);
  if (result.success) return { ok: true, quantity: result.data };
  return { ok: false, message: result.error.issues[0]?.message ?? 'Неверное количество' };
}

После if (result.success) TypeScript знает, что result.data — число, а в другой ветке есть result.error. issues[0]?.message с запасным текстом: компилятор с noUncheckedIndexedAccess требует учесть, что массив теоретически пуст. Тексты ошибок заданы прямо в цепочке вторым аргументом.

Задача 7. Ошибки формы по полям ★★☆ практика

Схема формы регистрации: имя (непустое), email (формат z.email()), возраст (целое от 14). Все сообщения по-русски. Напишите validateSignup(data), которая возвращает либо данные, либо объект { поле: первое сообщение }, готовый для функции показа ошибок у полей.

Зачем: форма показывает одну ошибку у поля, а не список. Преобразовать flattenError в «поле → строка» нужно в одном месте, и тогда любая схема подключается к любой форме одинаково.

Решение и разбор
// signup.ts
import { z } from 'zod';

export const Signup = z.object({
  name: z.string().trim().min(1, 'Укажите имя'),
  email: z.email('Нужен адрес почты вида name@example.com'),
  age: z.number({ error: 'Укажите возраст числом' }).int().min(14, 'Регистрация с 14 лет'),
});

export function firstErrors(error: z.ZodError): Record<string, string> {
  const fields = z.flattenError(error).fieldErrors as Record<string, string[] | undefined>;
  return Object.fromEntries(
    Object.entries(fields).flatMap(([field, messages]) => (messages?.[0] ? [[field, messages[0]]] : [])),
  );
}

export function validateSignup(data: unknown) {
  const result = Signup.safeParse(data);
  return result.success ? { ok: true as const, value: result.data } : { ok: false as const, errors: firstErrors(result.error) };
}

firstErrors не привязана к Signup и подходит для любой схемы. Её можно вынести в общий модуль. Почта anna@example.com пройдёт, а a@b.c — нет: в Zod 4 часть после последней точки должна быть не короче двух букв (проверено запуском). Об этом стоит помнить, тестируя формы.

Задача 8. Ошибки во вложенных данных ★★☆ практика

Для схемы заказа из задачи «Заказ: непустой массив строк» напишите describeIssues(error): превращает issues в понятные строки вида «Строка 2, количество: …» для ошибок в items и «промокод: …» для промокода. Номер строки начинается с 1.

// order.ts
import { z } from 'zod';
export const Order = z.object({
  items: z.array(z.object({ productId: z.string().min(1), quantity: z.number().int().min(1).max(99) })).min(1).max(50),
  promo: z.string().trim().toUpperCase().optional(),
});

Зачем: flattenError собирает ошибки только верхнего уровня, а у вложенных важен путь: ['items', 1, 'quantity']. Перевести путь на человеческий язык — работа интерфейса, и issues дают для этого всё нужное.

Решение и разбор
// describe.ts
import type { z } from 'zod';

const FIELD_NAMES: Record<string, string> = { productId: 'товар', quantity: 'количество', promo: 'промокод', items: 'состав заказа' };

export function describeIssues(error: z.ZodError): string[] {
  return error.issues.map((issue) => {
    const [first, index, field] = issue.path;
    if (first === 'items' && typeof index === 'number' && typeof field === 'string') {
      return `Строка ${index + 1}, ${FIELD_NAMES[field] ?? field}: ${issue.message}`;
    }
    return `${FIELD_NAMES[String(first)] ?? String(first)}: ${issue.message}`;
  });
}

Путь — массив из ключей объекта (строки) и индексов массива (числа). По typeof различаем «элемент массива» и «поле». Индекс +1, потому что пользователи считают строки с единицы. Словарь названий полей отделяет технические имена от слов интерфейса: переименуете поле в коде — словарь подскажет, где поправить подпись.
