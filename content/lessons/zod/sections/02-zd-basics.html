Схемы: из чего собирать

СхемаЧто принимает
z.string(), z.number(), z.boolean()значение этого типа
z.literal('ok')ровно это значение
z.enum(['a', 'b'])одно из перечисленного
z.array(схема)массив, каждый элемент по схеме
z.object({ ... })объект с полями по схемам
.optional()поле может отсутствовать (`T \undefined`)
.nullable()значение может быть null
.default(значение)при отсутствии подставит значение

Уточнения цепочкой: z.string().min(3).max(200), z.number().int().positive(), z.string().trim() (обрежет пробелы до остальных проверок). Форматы строк в Zod 4 — отдельные функции: z.email(), z.url(), z.uuid(). Запись z.string().email() из Zod 3 ещё работает, но помечена устаревшей.

Лишние поля

z.object по умолчанию молча отбрасывает поля, которых нет в схеме: из { id: 'a', isAdmin: true } получится { id: 'a' }. Это защита: клиент не протащит в базу поле, о котором вы не думали. Если лишнее поле — признак ошибки клиента и о нём надо сказать, есть z.strictObject(...): он отклонит такие данные.

Задача 2. optional, nullable и default ★☆☆ разминка

Опишите схему профиля: name обязательное; phone может отсутствовать; avatarUrl обязателен, но может быть null (аватар удалён); newsletter — boolean, по умолчанию false. Проверьте, какой тип выведет z.infer и что вернёт parse({ name: 'Аня', avatarUrl: null }).

Зачем: «поле не передали», «поле передали пустым» и «подставь значение по умолчанию» — три разных смысла. Схема выражает их явно, и интерфейс не перепутает «аватара нет» с «аватар не загрузили».

Решение и разбор
// profile.ts
import { z } from 'zod';

export const Profile = z.object({
  name: z.string().min(1),
  phone: z.string().optional(),
  avatarUrl: z.url().nullable(),
  newsletter: z.boolean().default(false),
});

export type Profile = z.infer<typeof Profile>;
// { name: string; phone?: string | undefined; avatarUrl: string | null; newsletter: boolean }

parse({ name: 'Аня', avatarUrl: null }) вернёт { name: 'Аня', avatarUrl: null, newsletter: false }. Значение по умолчанию подставлено, и в выходном типе newsletter обязателен. Входной тип (z.input<typeof Profile>) при этом разрешает его не передавать. Для URL используется формат Zod 4 z.url().

Задача 3. Заказ: непустой массив строк ★☆☆ разминка

Схема заказа: items — массив от 1 до 50 строк { productId: строка, quantity: целое от 1 до 99 }; promo — необязательная строка, которая приводится к верхнему регистру после обрезки пробелов.

Зачем: пустой заказ и заказ на тысячу строк — оба ошибки, которые проще отсечь схемой на входе, чем ловить в логике. Верхний регистр промокода тоже правило формата, и его место в схеме, а не в обработчике.

Решение и разбор
// order.ts
import { z } from 'zod';

export const OrderItem = z.object({
  productId: z.string().min(1),
  quantity: z.number().int().min(1).max(99),
});

export const Order = z.object({
  items: z.array(OrderItem).min(1).max(50),
  promo: z.string().trim().toUpperCase().optional(),
});

export type Order = z.infer<typeof Order>;

min/max у массива ограничивают число элементов, а у элемента — его собственные поля. Ограничение сверху — защита от злоупотребления: заказ на 100 000 строк сервер посчитает, но зачем позволять. toUpperCase() — встроенное преобразование строки в Zod. После проверки promo уже готов к сравнению с 'SALE10'.

Задача 4. Лишние поля: отбросить или отклонить ★★☆ практика

Для PATCH товара сделайте схему, которая отклоняет лишние поля (клиент прислал id или isAdmin — это ошибка, о ней надо сказать), а для приёма товара от партнёра — схему, которая молча отбрасывает лишние поля (у партнёра в ответе много своего). Покажите разницу на одном и том же объекте.

Зачем: это решение о поведении API, а не о синтаксисе. Строгая схема сообщает клиенту об опечатке в имени поля (prise вместо price): иначе поле молча пропадёт, и клиент не поймёт, почему цена не меняется.

Решение и разбор
// strict.ts
import { z } from 'zod';

export const ProductPatch = z.strictObject({
  title: z.string().trim().min(1).optional(),
  price: z.number().int().nonnegative().optional(),
});

export const PartnerProduct = z.object({
  title: z.string(),
  price: z.number().int().nonnegative(),
});

На объекте { price: 100, prise: 90 } строгая схема даёт ошибку с кодом unrecognized_keys и названием лишнего поля, а обычная возвращает { price: 100 }. Для данных извне, которые вы не контролируете, обычная схема удобнее. Для запросов к вашему API строгая помогает клиентам найти свои ошибки.
