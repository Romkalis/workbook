Составные схемы

Схемы собираются из схем — так же, как типы через утилиты (Partial, Pick, Omit):

  • Product.pick({ id: true, title: true }), Product.omit({ id: true }) — выбрать или убрать поля;
  • Product.partial() — все поля необязательны (патч);
  • Product.extend({ stock: z.number() }) — добавить поля;
  • z.discriminatedUnion('status', [...]) — размеченное объединение, как RemoteData.

Схема создания товара — это схема товара без id; схема патча — она же, но частичная. Меняется товар — меняется всё, что из него выведено.

Одна схема для сервера и фронтенда

Схему тела запроса можно положить в общий модуль и импортировать и на сервере (проверка запроса), и во фронтенде (проверка формы до отправки и разбор ответа). Тогда договор «что принимает API» описан один раз. В монорепозитории это отдельный пакет; в учебных проектах — общий файл. Проверка на фронтенде при этом остаётся удобством для пользователя: сервер проверяет всегда.

Задача 13. Схемы создания и патча из одной ★★☆ практика

Из схемы товара { id, title, price, category, stock } выведите: CreateProduct (без id, stock по умолчанию 0), PatchProduct (всё, кроме id, необязательно, хотя бы одно поле обязательно) и ProductCard (только id, title, price).

Зачем: четыре схемы одной сущности, написанные вручную, разъедутся при первом же изменении. Выведенные из одной, они меняются вместе: добавили поле в товар — оно появилось в создании и патче.

Решение и разбор
// compose.ts
import { z } from 'zod';

export const Product = z.object({
  id: z.string(),
  title: z.string().trim().min(1),
  price: z.number().int().nonnegative(),
  category: z.enum(['books', 'games', 'home']),
  stock: z.number().int().nonnegative(),
});

export const CreateProduct = Product.omit({ id: true }).extend({
  stock: z.number().int().nonnegative().default(0),
});

export const PatchProduct = Product.omit({ id: true })
  .partial()
  .refine((p) => Object.keys(p).length > 0, { message: 'Нужно хотя бы одно поле' });

export const ProductCard = Product.pick({ id: true, title: true, price: true });

extend с уже существующим полем заменяет его схему, так задаётся значение по умолчанию только для создания. Пустой патч отклонён через refine: запрос «ничего не менять» почти всегда ошибка клиента. ProductCard пригодится на фронтенде, где для карточки не нужны остаток и категория.

Задача 14. Доставка: размеченное объединение ★★☆ практика

Опишите способ получения через z.discriminatedUnion('type', ...): курьер — с адресом и временем (morning или evening), самовывоз — с id пункта, почта — с индексом из 6 цифр. Напишите deliveryLabel(d) со switch по type и проверкой полноты.

Зачем: у каждого способа свои поля, и объединение делает их обязательными ровно там, где они нужны. С одним объектом и десятью необязательными полями пропущенный индекс почты обнаружится только у курьера.

Решение и разбор
// delivery.ts
import { z } from 'zod';

export const Delivery = z.discriminatedUnion('type', [
  z.object({ type: z.literal('courier'), address: z.string().min(5), slot: z.enum(['morning', 'evening']) }),
  z.object({ type: z.literal('pickup'), pointId: z.string() }),
  z.object({ type: z.literal('post'), zip: z.string().regex(/^\d{6}$/, 'Индекс — 6 цифр') }),
]);
export type Delivery = z.infer<typeof Delivery>;

export function deliveryLabel(d: Delivery): string {
  switch (d.type) {
    case 'courier':
      return `Курьер, ${d.slot === 'morning' ? 'утром' : 'вечером'}: ${d.address}`;
    case 'pickup':
      return `Самовывоз из пункта ${d.pointId}`;
    case 'post':
      return `Почта, индекс ${d.zip}`;
    default: {
      const unreachable: never = d;
      return unreachable;
    }
  }
}

Выведенный тип — то самое размеченное объединение из уроков TypeScript, только теперь оно ещё и проверяет данные. discriminatedUnion сначала смотрит на type и проверяет только подходящий вариант, поэтому ошибка для почты будет про индекс, а не перечисление всех трёх вариантов сразу.

Задача 15. Одна схема на сервере и в клиенте ★★★ с подвохом

Сделайте модуль shared/review.ts со схемой создания отзыва. Сервер (POST /api/reviews) проверяет ею тело запроса, а клиент createReviewClient(baseUrl, fetchFn) проверяет ею данные до отправки (неверные не отправляет) и проверяет ответ схемой сохранённого отзыва (с id). Тест поднимает сервер и вызывает клиента с настоящим fetch.

Зачем: договор API описан один раз. Поменяли правило (минимальная длина отзыва) — изменилось и на сервере, и в форме, и типы обеих сторон. Ручную синхронизацию «а на фронте мы проверяем так же?» больше не нужно делать.

Решение и разбор
// shared/review.ts
import { z } from 'zod';

export const NewReview = z.object({
  productId: z.string().min(1),
  rating: z.number().int().min(1).max(5),
  text: z.string().trim().min(10),
});
export const SavedReview = NewReview.extend({ id: z.string() });

export type NewReview = z.infer<typeof NewReview>;
export type SavedReview = z.infer<typeof SavedReview>;
// server.ts
import express from 'express';
import { z } from 'zod';
import { NewReview } from './shared/review.js';

export function createApp() {
  const app = express();
  app.use(express.json());
  let nextId = 1;
  app.post('/api/reviews', (req, res) => {
    const result = NewReview.safeParse(req.body);
    if (!result.success) return res.status(400).json({ error: 'Неверные данные', details: z.flattenError(result.error).fieldErrors });
    res.status(201).json({ id: String(nextId++), ...result.data });
  });
  return app;
}
// client.ts
import { z } from 'zod';
import { NewReview, SavedReview } from './shared/review.js';

export function createReviewClient(baseUrl: string, fetchFn: typeof fetch = fetch) {
  return {
    async create(input: unknown): Promise<{ ok: true; review: SavedReview } | { ok: false; errors: Record<string, string[] | undefined> }> {
      const checked = NewReview.safeParse(input);
      if (!checked.success) return { ok: false, errors: z.flattenError(checked.error).fieldErrors };
      const res = await fetchFn(new URL('/api/reviews', baseUrl), {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(checked.data),
      });
      if (!res.ok) throw new Error(`Сервер ответил ${res.status}`);
      return { ok: true, review: SavedReview.parse(await res.json()) };
    },
  };
}

Клиент не отправляет заведомо неверные данные: пользователь сразу видит ошибку у поля, а сервер не тратит запрос. Сервер всё равно проверяет: запрос можно отправить и в обход клиента. Ответ сервера проверяется схемой SavedReview, выведенной из той же NewReview, так что клиент и сервер согласованы и в обратную сторону. В настоящем проекте shared/ — отдельный пакет или папка, которую подключают обе сборки.
