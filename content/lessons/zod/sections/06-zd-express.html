Zod в Express

Ручная проверка из урока Express на TypeScript превращается в схему и одну универсальную middleware:

import type { NextFunction, Request, Response } from 'express';
import { z } from 'zod';

export function validateBody<S extends z.ZodType>(schema: S) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({ error: 'Неверные данные', details: z.flattenError(result.error).fieldErrors });
    }
    req.body = result.data; // дальше — проверенные и очищенные данные
    next();
  };
}

Маршрут подключает её перед обработчиком: router.post('/quote', validateBody(QuoteBody), handler). Обработчик получает уже проверенное тело, а формат ошибки 400 одинаков во всём API. Запись req.body = result.data важна: так обработчик видит данные после trim, default и без лишних полей.

Тип req.body внутри обработчика Express сам не узнает. Его указывают явно: Request<{}, unknown, z.infer<typeof QuoteBody>>. Это честно, потому что middleware перед ним уже проверила данные.

Задача 16. validateBody для расчёта корзины ★★☆ практика

Замените ручной isQuoteBody из урока Express на TypeScript схемой и middleware validateBody из раздела. Маршрут POST /api/cart/quote получает уже проверенное тело и типизирован через z.infer. Ответ 400 содержит details по полям.

// validate.ts
import type { NextFunction, Request, Response } from 'express';
import { z } from 'zod';
export function validateBody<S extends z.ZodType>(schema: S) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({ error: 'Неверные данные', details: z.flattenError(result.error).fieldErrors });
    }
    req.body = result.data;
    next();
  };
}

Зачем: двенадцать строк ручной проверки превращаются в объявление формы данных, а ответ 400 становится одинаковым для всего API. Обработчик маршрута снова занимается только своим делом — расчётом.

Решение и разбор
// app.ts
import express, { type Request, type Response } from 'express';
import { z } from 'zod';
import { validateBody } from './validate.js';

const PRICES: Record<string, number> = { b1: 150000, b2: 99000 };

export const QuoteBody = z.object({
  items: z.array(z.object({ productId: z.string(), quantity: z.number().int().min(1) })).min(1),
  promo: z.string().trim().toUpperCase().optional(),
});
type QuoteBody = z.infer<typeof QuoteBody>;

export function createApp() {
  const app = express();
  app.use(express.json());
  app.post('/api/cart/quote', validateBody(QuoteBody), (req: Request<{}, unknown, QuoteBody>, res: Response) => {
    let subtotal = 0;
    for (const { productId, quantity } of req.body.items) {
      const price = PRICES[productId];
      if (price === undefined) return res.status(400).json({ error: `Нет товара ${productId}` });
      subtotal += price * quantity;
    }
    const discount = req.body.promo === 'SALE10' ? Math.round(subtotal / 10) : 0;
    res.json({ subtotal, discount, total: subtotal - discount });
  });
  return app;
}

Проверка «товар существует» осталась в обработчике: это не форма данных, а знание о каталоге, и схеме его брать неоткуда. Граница проходит так: схема проверяет форму, логика — смысл. Request<{}, unknown, QuoteBody> честно описывает тело, потому что middleware перед обработчиком уже его проверила и заменила.

Задача 17. Проверка query в Express 5 ★★★ с подвохом

Напишите validateQuery(schema): проверяет req.query схемой и при успехе кладёт результат в res.locals.query, при ошибке отвечает 400. Подключите к GET /api/products со схемой CatalogQuery из задачи про параметры адреса. Почему результат не записывают обратно в req.query?

Зачем: в Express 5 req.query — свойство только для чтения (геттер), и присваивание ему выбрасывает ошибку. Это отличие от Express 4, на котором написаны многие статьи с req.query = parsed. res.locals — официальное место для данных, которые middleware передаёт дальше по цепочке.

Решение и разбор
// query-mw.ts
import express, { type NextFunction, type Request, type Response } from 'express';
import { z } from 'zod';

export function validateQuery<S extends z.ZodType>(schema: S) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.query);
    if (!result.success) {
      return res.status(400).json({ error: 'Неверные параметры', details: z.flattenError(result.error).fieldErrors });
    }
    res.locals.query = result.data;
    next();
  };
}

const emptyToUndefined = (v: unknown) => (v === '' ? undefined : v);
export const CatalogQuery = z.object({
  page: z.preprocess(emptyToUndefined, z.coerce.number().int().min(1).default(1)),
  maxPrice: z.preprocess(emptyToUndefined, z.coerce.number().int().min(0).optional()),
});

export function createApp() {
  const app = express();
  app.get('/api/products', validateQuery(CatalogQuery), (_req, res) => {
    const query = res.locals.query as z.infer<typeof CatalogQuery>;
    res.json({ query });
  });
  return app;
}

Мы проверили запуском: в Express 5.3 req.query = {} внутри middleware бросает TypeError («Cannot set property query … which has only a getter»). res.locals живёт столько же, сколько запрос, и доступен всем следующим обработчикам. Тип там any, поэтому в обработчике нужно утверждение. Оно оправдано: middleware перед ним гарантирует форму.
