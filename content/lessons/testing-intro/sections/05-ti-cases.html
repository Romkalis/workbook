Как придумывать тесты

Самый трудный вопрос новичка — не «как написать тест», а «какие тесты писать». Помогает простой список: для каждой функции подумайте о трёх группах случаев.

  1. Обычный случай — то, ради чего функция существует. Категория 'books' возвращает книги.
  2. Граничный случай — края допустимого: пустой массив, ноль, одна штука, максимальное количество на складе, сумма ровно 20 000 копеек.
  3. Неправильный ввод — то, чего «не должно быть», но будет: несуществующая категория, ID строкой '1' вместо числа, NaN, пробелы вместо запроса.

Задание Testing Intro построено ровно так: для каждой функции три сценария по три кейса. Посмотрите на таблицу для getProductById: товар существует (обычный), числовой ID отсутствует (граница), ID неверного типа (неправильный ввод).

Структура теста: Arrange, Act, Assert

Хороший тест читается в три шага:

test('не меняет исходный массив', () => {
  // Arrange — подготовка данных
  const catalog = [{ id: 1, stock: 2 }, { id: 2, stock: 0 }];

  // Act — вызов проверяемой функции
  getAvailableProducts(catalog);

  // Assert — проверка результата
  expect(catalog).toEqual([{ id: 1, stock: 2 }, { id: 2, stock: 0 }]);
});

Комментарии писать не обязательно, но мысленно делить тест на эти части полезно. Подробнее — в разделе AAA основного урока.

Задача 15. Тест «не меняет входные данные» ★☆☆ разминка

Напишите в стиле AAA тест, который доказывает, что sortByPrice не меняет переданный массив. Отметьте комментариями три части теста.

// sort.js
function sortByPrice(products) {
  return [...products].sort((a, b) => a.price - b.price);
}
module.exports = { sortByPrice };

Зачем: функции, которые тайком меняют аргументы, — источник самых трудных багов: данные «портятся» далеко от места, где их испортили. Такой тест — дешёвая страховка.

Решение и разбор
// sort.test.js
const { sortByPrice } = require('./sort');

test('не меняет исходный массив', () => {
  // Arrange
  const products = [{ id: 1, price: 300 }, { id: 2, price: 100 }];
  // Act
  sortByPrice(products);
  // Assert
  expect(products.map((p) => p.id)).toEqual([1, 2]);
});

Данные созданы внутри теста, а не взяты из общего файла: если мутант всё же испортит массив, это не повлияет на другие тесты. Проверяется порядок id до и после. Убедились: версия функции без копии (products.sort(...)) этот тест роняет.

Признаки хорошего теста

  • Одна мысль на тест. Если тест упал, по названию сразу понятно, какое правило нарушено.
  • Понятное название. «возвращает пустой массив для пустого каталога» вместо «test 5».
  • Конкретные ожидания. Сравнивайте с готовым значением ([1, 2]), а не пересчитывайте его в тесте той же логикой, что в коде: иначе тест повторит ошибку кода.
  • Независимость. Тесты не должны зависеть друг от друга и от порядка запуска. Если один тест меняет общие данные, другой может внезапно упасть.
  • Повторяемость. Никаких случайных чисел, текущего времени и сети в проверках: результат должен быть одинаковым при каждом запуске.

Последние пункты вместе с быстротой называют принципами FIRST — подробно в разделе FIRST.

Какие случаи вы бы проверили у функции removeFromCart(cart, productId)?

Обычный: удаляет нужный товар, остальные остаются. Граничный: удаление единственного товара даёт пустую корзину. Неправильный ввод: ID товара, которого нет, — корзина не меняется. Ровно эти три теста есть в задании.

Задача 14. Три группы случаев для фильтра цены ★★☆ практика

Для filterByPrice(products, min, max) (границы включаются, пустая граница не применяется) сначала выпишите случаи по трём группам: обычные, граничные, неправильный ввод. Затем напишите тесты: минимум по два на группу.

// price.js
// min и max включительно; undefined — граница не применяется
function filterByPrice(products, min, max) {
  return products.filter(
    (p) => (min === undefined || p.price >= min) && (max === undefined || p.price <= max),
  );
}
module.exports = { filterByPrice };

Зачем: ошибки чаще всего прячутся на краях: < вместо <=, пустой массив, отсутствующий параметр. Список трёх групп превращает «а что бы проверить?» в механическую процедуру.

Подсказка

Граничные: товар с ценой ровно min, ровно max, min === max, пустой каталог. Неправильный ввод: min > max.

Решение и разбор
// price.test.js
const { filterByPrice } = require('./price');

const products = [
  { id: 1, price: 100 },
  { id: 2, price: 200 },
  { id: 3, price: 300 },
];
const ids = (list) => list.map((p) => p.id);

describe('обычные случаи', () => {
  test('диапазон 150–250 оставляет товар 2', () => {
    expect(ids(filterByPrice(products, 150, 250))).toEqual([2]);
  });
  test('только min оставляет всё дороже', () => {
    expect(ids(filterByPrice(products, 200, undefined))).toEqual([2, 3]);
  });
});

describe('границы', () => {
  test('цена ровно на min и max включается', () => {
    expect(ids(filterByPrice(products, 100, 300))).toEqual([1, 2, 3]);
  });
  test('min равен max — один товар', () => {
    expect(ids(filterByPrice(products, 200, 200))).toEqual([2]);
  });
  test('пустой каталог — пустой результат', () => {
    expect(filterByPrice([], 0, 1000)).toEqual([]);
  });
});

describe('неправильный ввод', () => {
  test('без границ возвращает всё', () => {
    expect(ids(filterByPrice(products))).toEqual([1, 2, 3]);
  });
  test('min больше max — ничего', () => {
    expect(filterByPrice(products, 300, 100)).toEqual([]);
  });
});

Мутант с > и < вместо >= и <= проходит «обычные» тесты, а ловят его только граничные: «ровно на min и max» и «min равен max». Тест «min больше max — ничего» фиксирует поведение, которое стоит обсудить: может, интерфейс должен менять границы местами? Тест делает это решение видимым.

Задача 16. Почините плохие тесты ★★☆ практика

Тесты ниже проходят, но нарушают правила из раздела выше. Найдите три нарушения и перепишите тесты.

// starter.js
const cart = [];

test('добавляет товар', () => {
  cart.push({ id: 1, price: 100, quantity: 2 });
  expect(cart).toHaveLength(1);
});

test('считает сумму', () => {
  // работает, только если первый тест уже выполнился
  const expected = cart.reduce((s, i) => s + i.price * i.quantity, 0);
  expect(subtotal(cart)).toBe(expected);
});
// subtotal.js
const subtotal = (cart) => cart.reduce((s, i) => s + i.price * i.quantity, 0);
module.exports = { subtotal };

Зачем: тест, зависящий от соседа, падает «случайно» при запуске одного файла или в другом порядке. А ожидание, посчитанное той же формулой, что и в коде, повторит ошибку кода и всегда будет зелёным.

Решение и разбор
// subtotal.test.js
const { subtotal } = require('./subtotal');

test('сумма учитывает количество', () => {
  const cart = [{ id: 1, price: 100, quantity: 2 }, { id: 2, price: 50, quantity: 1 }];
  expect(subtotal(cart)).toBe(250);
});

test('пустая корзина даёт 0', () => {
  expect(subtotal([])).toBe(0);
});

Три нарушения. Общее изменяемое состояние: массив cart на уровне файла, второй тест зависит от первого. Ожидание той же формулой: если в subtotal забыть quantity, в тесте его можно «забыть» так же, и тест останется зелёным. Мутант без quantity исходный тест действительно проходит. Первый тест проверяет не наш код, а Array.prototype.push. В новой версии у каждого теста свои данные и ожидание, посчитанное вручную: 100 × 2 + 50 = 250.

Задача 17. Время — параметром ★★☆ практика

Функция ниже зависит от текущего времени, поэтому её нельзя надёжно протестировать. Перепишите её так, чтобы дата передавалась параметром (по умолчанию — new Date()), и напишите тесты: акция ещё не началась, идёт и уже закончилась (граница «последний день включительно»).

function isSaleActive() {
  const now = new Date();
  return now >= new Date('2026-11-20') && now < new Date('2026-11-30');
}

Зачем: повторяемость: тест, зависящий от сегодняшней даты, сегодня зелёный, а через неделю красный, хотя код никто не трогал. Внешнюю зависимость (часы, сеть, случайность) выносят в параметр, и функция становится чистой.

Решение и разбор
// sale.js
const SALE_START = new Date('2026-11-20T00:00:00Z');
const SALE_END = new Date('2026-11-30T00:00:00Z'); // не включительно: 29-е — последний день

function isSaleActive(now = new Date()) {
  return now >= SALE_START && now < SALE_END;
}
module.exports = { isSaleActive };
// sale.test.js
const { isSaleActive } = require('./sale');

test.each([
  ['2026-11-19T23:59:59Z', false],
  ['2026-11-20T00:00:00Z', true],
  ['2026-11-29T23:59:59Z', true],
  ['2026-11-30T00:00:00Z', false],
])('%s → %s', (iso, expected) => {
  expect(isSaleActive(new Date(iso))).toBe(expected);
});

Значение по умолчанию сохраняет удобный вызов isSaleActive() в приложении, а тест передаёт любую дату. Тестовые точки стоят по обе стороны каждой границы с точностью до секунды. Даты указаны в UTC (Z): без этого результат зависел бы от часового пояса компьютера, и тест вёл бы себя по-разному у вас и в CI.
