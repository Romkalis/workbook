Jest: как устроен тест

Установка и запуск

Jest ставится в проект как dev-зависимость — пакет, который нужен только при разработке, а не пользователю сайта:

npm install --save-dev jest

В package.json добавляют скрипт:

{
  "scripts": {
    "test": "jest"
  }
}

Теперь npm test запускает Jest, а тот находит все файлы, которые заканчиваются на .test.js (или лежат в папке __tests__), и выполняет их. Можно запустить только часть: npx jest tests/catalog выполнит тесты из одной папки.

Задача 5. Проект с Jest с нуля ★☆☆ разминка

Создайте пустую папку, установите Jest как dev-зависимость и добавьте скрипт test. Напишите sum.js и sum.test.js с одним тестом. Запустите сначала все тесты, затем только этот файл командой npx jest sum.

Зачем: проект, в котором тесты запускаются одной стандартной командой npm test, понятен любому разработчику и любому CI. Запуск одного файла ускоряет работу, когда тестов становятся сотни.

Решение и разбор
// package.json
{
  "name": "jest-start",
  "private": true,
  "scripts": {
    "test": "jest"
  },
  "devDependencies": {
    "jest": "^30.0.0"
  }
}
// sum.js
function sum(a, b) {
  return a + b;
}
module.exports = { sum };
// sum.test.js
const { sum } = require('./sum');

test('складывает два числа', () => {
  expect(sum(2, 3)).toBe(5);
});

Jest в devDependencies: пользователю сайта он не нужен. Скрипт называется именно test: у npm для него есть сокращение npm test без run. Аргумент npx jest sum — это шаблон пути: запустятся файлы, в пути которых есть sum.

Анатомия тестового файла

Вот готовый пример из задания Testing Intro (сокращён):

const products = require('../../src/data/products');
const { getAvailableProducts } = require('../../src/catalog');

describe('getAvailableProducts', () => {
  test('исключает товары с нулевым остатком', () => {
    const catalog = [{ id: 1, stock: 2 }, { id: 2, stock: 0 }, { id: 3, stock: 5 }];
    expect(getAvailableProducts(catalog)).toEqual([{ id: 1, stock: 2 }, { id: 3, stock: 5 }]);
  });

  test('возвращает пустой массив для пустого каталога', () => {
    expect(getAvailableProducts([])).toEqual([]);
  });
});

Разберём каждую часть:

  • require('../../src/catalog') — подключение кода из другого файла. Это синтаксис CommonJS, старый стандарт модулей Node; в проекте задания используется он. Аналог в современных модулях — import { getAvailableProducts } from '../../src/catalog.js'. Путь ../../ значит «подняться на две папки вверх».
  • describe('название', () => { ... }) — группа тестов. Обычно одна группа на одну функцию. Группы можно вкладывать друг в друга.
  • test('название', () => { ... }) — один тест, одна проверяемая мысль. Вместо test можно писать it, это синоним. Название пишут так, чтобы оно читалось как правило: «исключает товары с нулевым остатком».
  • expect(фактическое).toEqual(ожидаемое) — проверка. expect принимает то, что вернула функция, а метод после точки — матчер — говорит, как сравнивать.

describe, test и expect не нужно импортировать: Jest сам делает их доступными во всех тестовых файлах.

Задача 6. Переведите проверки на Jest ★☆☆ разминка

Перепишите проверки из задачи «Первый тест без библиотек» на Jest: файл discount.test.js, одна группа describe на функцию, по test на каждый случай.

// discount.js
function calculateDiscount(subtotal) {
  return subtotal >= 20000 ? Math.round(subtotal * 0.1) : 0;
}
module.exports = { calculateDiscount };

Зачем: тот же смысл, но теперь упавший тест не остановит остальные, отчёт покажет, что и где сломалось, а код выхода поймёт CI.

Решение и разбор
// discount.test.js
const { calculateDiscount } = require('./discount');

describe('calculateDiscount', () => {
  test('без скидки при сумме меньше 20 000', () => {
    expect(calculateDiscount(19999)).toBe(0);
  });

  test('10% ровно на пороге 20 000', () => {
    expect(calculateDiscount(20000)).toBe(2000);
  });

  test('10% при сумме больше порога', () => {
    expect(calculateDiscount(35000)).toBe(3500);
  });
});

Названия тестов теперь читаются как правила, а describe собирает их под именем функции. Попробуйте заменить в функции >= на >: упадёт ровно один тест, «10% ровно на пороге». Название сразу говорит, какое правило нарушено. Мы проверили это: такая версия функции действительно роняет этот набор.

Задача 7. Названия, которые объясняют правило ★☆☆ разминка

Переименуйте тесты так, чтобы по названию было понятно правило, без чтения кода. Сами проверки не меняйте.

// starter.js
const { isFreeDelivery } = require('./delivery');
describe('isFreeDelivery', () => {
  test('test 1', () => expect(isFreeDelivery(50000)).toBe(true));
  test('works', () => expect(isFreeDelivery(49999)).toBe(false));
  test('edge', () => expect(isFreeDelivery(0)).toBe(false));
});
// delivery.js
const FREE_DELIVERY_FROM = 50000;
function isFreeDelivery(subtotal) {
  return subtotal >= FREE_DELIVERY_FROM;
}
module.exports = { isFreeDelivery };

Зачем: через полгода упавший тест прочитает человек, который не писал код, возможно, вы сами. «test 1 failed» не говорит ничего, а «доставка бесплатна ровно от 50 000» сразу показывает, какое правило сломано.

Решение и разбор
// delivery.test.js
const { isFreeDelivery } = require('./delivery');

describe('isFreeDelivery', () => {
  test('бесплатна ровно от 50 000 копеек', () => expect(isFreeDelivery(50000)).toBe(true));
  test('платная, если не хватает одной копейки', () => expect(isFreeDelivery(49999)).toBe(false));
  test('платная для пустой корзины', () => expect(isFreeDelivery(0)).toBe(false));
});

Удобный шаблон: «[результат] при/для [условие]». Название вместе с describe читается как предложение: isFreeDelivery бесплатна ровно от 50 000 копеек. В названии есть конкретное значение границы: если её поменяют, станет видно, что тест устарел.

Как читать результат

Если все тесты прошли, Jest печатает зелёные галочки и сводку вида Tests: 9 passed, 9 total. Если какой-то упал, вы увидите его название красным и разницу (diff):

✕ исключает товары с нулевым остатком

  expect(received).toEqual(expected)

  - Expected  - 0
  + Received  + 4

  @@ ... @@
  +   Object {
  +     "id": 2,
  +     "stock": 0,
  +   },

Строки с - есть в ожидаемом, но нет в фактическом. Строки с + — наоборот, лишние. Здесь функция вернула товар с stock: 0, которого быть не должно. Ниже Jest показывает номер строки в тестовом файле. (Вывод приведён по общим знаниям о формате Jest и может немного отличаться в вашей версии.)

Если тест упал, сначала поймите, кто прав: код или тест. Тест тоже может быть написан с ошибкой. Но в задании Testing Intro тесты корзины трогать нельзя — там правы они.

Задача 8. Кто прав: тест или код? ★★☆ практика

Тест ниже падает с таким выводом. Определите по diff, что вернула функция, найдите ошибку и исправьте код, а не тест.

// starter.txt
✕ возвращает только товары в наличии
  expect(received).toEqual(expected)
  - Expected  - 0
  + Received  + 4
  +   Object {
  +     "id": 2,
  +     "stock": 0,
  +   },
// available.test.js
const { getAvailableProducts } = require('./available');
test('возвращает только товары в наличии', () => {
  const catalog = [{ id: 1, stock: 2 }, { id: 2, stock: 0 }, { id: 3, stock: 5 }];
  expect(getAvailableProducts(catalog)).toEqual([{ id: 1, stock: 2 }, { id: 3, stock: 5 }]);
});

Зачем: красный тест — не приговор коду и не приговор тесту, это вопрос: «кто из нас неправ?». Умение читать diff экономит часы: он прямо показывает, чего не хватает и что лишнее.

Подсказка

Строки с + — лишнее в фактическом результате. В результат попал товар с stock: 0. Посмотрите на условие фильтра.

Решение и разбор
// available.js
// Было: products.filter((p) => p.stock >= 0)
function getAvailableProducts(products) {
  return products.filter((p) => p.stock > 0);
}
module.exports = { getAvailableProducts };

Diff показал лишний объект с stock: 0. Значит, функция пропускает нулевой остаток, и виновато условие >= 0. Почему прав тест: его название — правило из требований («только в наличии»), а товар с нулевым остатком купить нельзя. Если бы тест противоречил требованиям, исправлять пришлось бы его. Решение «кто прав» всегда принимается по требованиям, а не по тому, что проще поменять.

test.todo и test.each

test.todo('название') — тест-заметка «надо написать». Он не выполняется и показывается в отчёте как todo. В задании все тесты каталога заданы именно так: вам нужно превратить каждый todo в настоящий тест.

test.each запускает один и тот же тест на нескольких наборах данных. Подробно — в разделе с решением.

Задача 9. План тестов через test.todo ★☆☆ разминка

Для функции applyPromo(subtotal, code) из прошлых задач (SAVE10 даёт 10% от 20 000 копеек) сначала запишите план: 5 тестов через test.todo с понятными названиями. Затем превратите два из них в настоящие тесты и запустите: в отчёте должно быть 2 passed и 3 todo.

// promo.js
function applyPromo(subtotal, code) {
  if (code !== 'SAVE10' || subtotal < 20000) return subtotal;
  return subtotal - Math.round(subtotal * 0.1);
}
module.exports = { applyPromo };

Зачем: список todo — это чек-лист требований, который живёт рядом с кодом и виден в отчёте. Пока он не пуст, работа явно не закончена. Так удобно разбивать задачу на маленькие шаги.

Решение и разбор
// promo.test.js
const { applyPromo } = require('./promo');

describe('applyPromo', () => {
  test('SAVE10 уменьшает сумму на 10% от 20 000', () => {
    expect(applyPromo(30000, 'SAVE10')).toBe(27000);
  });

  test('без промокода сумма не меняется', () => {
    expect(applyPromo(30000, undefined)).toBe(30000);
  });

  test.todo('SAVE10 не действует на сумму меньше 20 000');
  test.todo('неизвестный промокод не даёт скидки');
  test.todo('промокод чувствителен к регистру: save10 не работает');
});

Последний todo — решение, которое надо принять осознанно: работает ли save10? Сейчас функция сравнивает строго, и тест зафиксирует это поведение. Записав такой вопрос в todo, вы не забудете обсудить его с командой.

Задача 10. Уберите копипасту через test.each ★★☆ практика

Четыре теста ниже отличаются только данными. Перепишите их одним test.each с таблицей и названием, в котором подставляются значения.

// starter.js
test('1 → 1 товар', () => expect(pluralize(1)).toBe('1 товар'));
test('2 → 2 товара', () => expect(pluralize(2)).toBe('2 товара'));
test('5 → 5 товаров', () => expect(pluralize(5)).toBe('5 товаров'));
test('11 → 11 товаров', () => expect(pluralize(11)).toBe('11 товаров'));
// pluralize.js
function pluralize(n) {
  const mod10 = n % 10;
  const mod100 = n % 100;
  if (mod10 === 1 && mod100 !== 11) return `${n} товар`;
  if (mod10 >= 2 && mod10 <= 4 && (mod100 < 12 || mod100 > 14)) return `${n} товара`;
  return `${n} товаров`;
}
module.exports = { pluralize };

Зачем: когда правило проверяется на многих примерах, таблица читается лучше пяти копий. Добавить случай — одна строка, и сразу видно, какие значения уже проверены, а какие нет (здесь не хватает 12, 21, 22…).

Решение и разбор
// pluralize.test.js
const { pluralize } = require('./pluralize');

test.each([
  [1, '1 товар'],
  [2, '2 товара'],
  [5, '5 товаров'],
  [11, '11 товаров'],
  [12, '12 товаров'],
  [21, '21 товар'],
  [22, '22 товара'],
])('%s → %s', (n, expected) => {
  expect(pluralize(n)).toBe(expected);
});

В таблицу сразу добавлены 12, 21 и 22: когда данные лежат в столбик, пробелы в покрытии видны. Версия функции, которая помнит про 11, но забыла про 12–14, проходит все четыре исходных теста и возвращает «12 товара». Ловит её только строка с 12: мы проверили это запуском. %s в названии подставляет значения строки по порядку.
