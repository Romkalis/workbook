Первый тест своими руками

Прежде чем ставить библиотеку, полезно понять, что она делает внутри. Возьмём вариант из прошлого раздела и улучшим его.

Функция-проверка

Писать if (...) throw каждый раз неудобно. Вынесем сравнение в функцию. Такую функцию принято называть assert (англ. «утверждать»): мы утверждаем, что результат такой-то, и если это не так — ошибка.

function assertEqual(actual, expected, name) {
  if (actual === expected) {
    console.log(`✓ ${name}`);
  } else {
    console.log(`✗ ${name}: ожидали ${expected}, получили ${actual}`);
  }
}

assertEqual(calculateCartSubtotal([]), 0, 'пустая корзина');
assertEqual(calculateCartSubtotal([{ price: 27900, quantity: 2 }]), 55800, 'две лампы');
assertEqual(
  calculateCartSubtotal([{ price: 49900, quantity: 1 }, { price: 27900, quantity: 2 }]),
  105700,
  'наушники и две лампы',
);

Здесь есть два важных слова. actual — фактический результат, то, что вернула функция. expected — ожидаемый, то, что должно было получиться. Эти слова встретятся в любом тестовом инструменте.

Задача 1. Первый тест без библиотек ★☆☆ разминка

Функция ниже считает скидку. Напишите файл discount.check.js без библиотек: три вызова assertEqual из раздела выше. Случаи: сумма меньше порога, ровно на пороге, больше порога. Запустите его через node discount.check.js.

// discount.js
// Скидка 10% при сумме от 20 000 копеек, иначе 0
function calculateDiscount(subtotal) {
  return subtotal >= 20000 ? Math.round(subtotal * 0.1) : 0;
}
module.exports = { calculateDiscount };

Зачем: даже самый простой тест — это код, который вы запускаете вместо ручной проверки. Написав его руками, вы увидите, что делает любой тестовый фреймворк, и не будете считать его магией.

Подсказка

Самые полезные значения — по обе стороны от порога: 19999 и 20000. Ошибки чаще всего живут на границах.

Решение и разбор
// discount.check.js
const { calculateDiscount } = require('./discount');

function assertEqual(actual, expected, name) {
  if (actual === expected) console.log(`✓ ${name}`);
  else console.log(`✗ ${name}: ожидали ${expected}, получили ${actual}`);
}

assertEqual(calculateDiscount(19999), 0, 'меньше порога — без скидки');
assertEqual(calculateDiscount(20000), 2000, 'ровно на пороге — скидка есть');
assertEqual(calculateDiscount(35000), 3500, 'больше порога — 10%');

Порог проверен с двух сторон: если кто-то заменит >= на >, второй случай это покажет. Ожидаемые числа посчитаны руками, а не той же формулой: иначе тест повторил бы ошибку кода. Недостатки самодельного варианта видны уже здесь: упавший тест не меняет код выхода программы, и CI его не заметит. Это одна из причин взять фреймворк.

Задача 2. Падение, которое видит CI ★★☆ практика

Доработайте assertEqual из прошлой задачи: при провале она по-прежнему печатает строку с ✗ и ставит process.exitCode = 1. Тогда команда завершится с ошибкой, но остальные проверки всё равно выполнятся.

Зачем: CI и git-хуки понимают только код выхода программы: 0 — успех, всё остальное — провал. Тест, который печатает «✗», но выходит с 0, для автоматики считается пройденным.

Подсказка

Не бросайте исключение: оно остановит файл на первой ошибке. process.exitCode задаёт код, с которым Node завершится сам, когда всё выполнит.

Решение и разбор
// assert.js
function assertEqual(actual, expected, name) {
  if (actual === expected) {
    console.log(`✓ ${name}`);
    return;
  }
  console.log(`✗ ${name}: ожидали ${expected}, получили ${actual}`);
  process.exitCode = 1;
}
module.exports = { assertEqual };

process.exitCode, а не process.exit(1): второй вариант прервёт программу сразу, и вы не узнаете о других провалах. Именно так ведёт себя Jest: выполняет всё, показывает все ошибки и в конце выходит с кодом 1. Проверьте в терминале: node file.js; echo $? (в PowerShell — $LASTEXITCODE).

Почему === не хватает

const cart = [{ id: 1, quantity: 2 }];
console.log(cart === [{ id: 1, quantity: 2 }]); // false!

Массивы и объекты в JavaScript сравниваются по ссылке: === отвечает на вопрос «это один и тот же объект в памяти?», а не «у них одинаковое содержимое?». Два разных массива с одинаковыми элементами не равны (см. значения и ссылки). Значит, для объектов нужно сравнивать содержимое по всем полям — глубокое сравнение. Писать его самому долго, и это первая причина взять готовый инструмент.

Задача 3. Своё сравнение массивов ★★☆ практика

Напишите arraysEqual(a, b) для массивов примитивов: длины совпадают и все элементы попарно равны (===). Покажите, что arraysEqual([1, 2], [1, 2]) — true, хотя [1, 2] === [1, 2] — false.

Зачем: понимать разницу между «тот же объект» и «то же содержимое» нужно не только в тестах. На этом же построены зависимости useEffect в React и сравнение состояния. Написав сравнение сами, вы поймёте, что делает toEqual.

Решение и разбор
// arrays-equal.js
function arraysEqual(a, b) {
  if (a.length !== b.length) return false;
  return a.every((item, i) => item === b[i]);
}
module.exports = { arraysEqual };

Проверка длины идёт первой: без неё [1, 2] и [1, 2, 3] оказались бы «равными», ведь every проходит только по первому массиву. Функция работает лишь на один уровень: для вложенных массивов и объектов нужна рекурсия по всем полям. Именно это и делает toEqual в Jest, поэтому писать такое руками каждый раз не стоит.

Задача 4. Ловушка JSON.stringify ★★☆ практика

Популярный «быстрый» способ сравнить объекты: JSON.stringify(a) === JSON.stringify(b). Напишите два теста на Jest. Первый показывает, что для { id: 1, qty: 2 } и { qty: 2, id: 1 } такое сравнение даёт false, а toEqual считает их равными. Второй показывает, что поле со значением undefined исчезает при сериализации.

Зачем: самодельное «глубокое сравнение» через JSON ломается на порядке ключей, undefined, датах и NaN. Тесты, построенные на нём, падают без причины или, что хуже, проходят там, где должны упасть.

Решение и разбор
// json.test.js
test('порядок ключей ломает сравнение через JSON', () => {
  const a = { id: 1, qty: 2 };
  const b = { qty: 2, id: 1 };
  expect(JSON.stringify(a) === JSON.stringify(b)).toBe(false);
  expect(a).toEqual(b);
});

test('undefined-поле исчезает при JSON.stringify', () => {
  expect(JSON.stringify({ id: 1, note: undefined })).toBe('{"id":1}');
});

Строка JSON хранит ключи в порядке их добавления, поэтому два одинаковых по смыслу объекта дают разные строки. Поле со значением undefined вообще пропадает. Матчер toEqual тоже его игнорирует, а toStrictEqual различает. Вывод: для сравнения содержимого используйте матчеры фреймворка, они продуманы под эти случаи.

Зачем нужен тестовый фреймворк

Наш самодельный вариант быстро упрётся в ограничения. Тестовый фреймворк (Jest, Vitest, встроенный в Node node:test) берёт на себя всё скучное:

  • сам находит файлы с тестами по имени (*.test.js) и запускает их одной командой;
  • умеет сравнивать объекты, массивы, ошибки и многое другое;
  • если один тест упал, остальные всё равно выполняются;
  • показывает понятный отчёт: что прошло, что нет, и чем отличается результат от ожидаемого;
  • считает покрытие кода (об этом ниже).

В задании RS School используется Jest — один из самых популярных фреймворков для JavaScript.
