TDD: сначала тест, потом код

Обычно код пишут, а потом (если хватит времени) тестируют. TDD (Test-Driven Development, разработка через тестирование) переворачивает порядок: сначала пишем тест для того, чего ещё нет, и только потом код. Звучит странно, но вторая часть задания Testing Intro устроена именно так: тесты корзины уже написаны, а функции — пустые заглушки.

Цикл красный — зелёный — рефакторинг

Зачем видеть красный тест? Чтобы убедиться, что тест вообще что-то проверяет. Тест, который зелёный ещё до появления кода, бесполезен: он пройдёт и с ошибкой.

Задача 19. TDD: стоимость доставки ★★☆ практика

Правило: доставка стоит 300 ₽ (30 000 копеек), от 3 000 ₽ — 150 ₽, от 5 000 ₽ — бесплатно; пустая корзина — 0. Сделайте функцию deliveryCost(subtotal) по TDD. На каждое правило сначала напишите тест, увидьте красный, затем минимальный код до зелёного. Закоммитьте пары «тест → код».

Зачем: красный тест доказывает, что тест вообще что-то проверяет. Короткие шаги «тест → минимальный код» не дают написать лишнего: каждая строка кода появилась ради конкретного требования.

Подсказка

Порядок шагов: пустая корзина → базовая цена → первый порог → второй порог. На каждом шаге код должен проходить все тесты, написанные до этого.

Решение и разбор
// delivery.test.js
const { deliveryCost } = require('./delivery');

describe('deliveryCost', () => {
  test('пустая корзина — 0', () => expect(deliveryCost(0)).toBe(0));
  test('до 3 000 ₽ — 300 ₽', () => expect(deliveryCost(299999)).toBe(30000));
  test('ровно 3 000 ₽ — 150 ₽', () => expect(deliveryCost(300000)).toBe(15000));
  test('ровно 5 000 ₽ — бесплатно', () => expect(deliveryCost(500000)).toBe(0));
  test('чуть меньше 5 000 ₽ — 150 ₽', () => expect(deliveryCost(499999)).toBe(15000));
});
// delivery.js
const STEPS = [
  { from: 500000, cost: 0 },
  { from: 300000, cost: 15000 },
  { from: 1, cost: 30000 },
];

function deliveryCost(subtotal) {
  return STEPS.find((s) => subtotal >= s.from)?.cost ?? 0;
}
module.exports = { deliveryCost };

История коммитов для этой задачи может выглядеть так: test: empty cart delivery → feat: ... → test: base delivery price → … На шаге рефакторинга цепочка if превратилась в таблицу STEPS: правила видны как данные, а новый порог — одна строка. Тесты на этом шаге не менялись и остались зелёными, в этом и смысл рефакторинга под защитой тестов. Мутант со строгими > ловят тесты «ровно 3 000» и «ровно 5 000».

Задача 20. Тест, который не может упасть ★☆☆ разминка

Тест ниже зелёный даже тогда, когда функции removeFromCart ещё нет (она пустая заглушка). Объясните почему и перепишите тест так, чтобы на заглушке он был красным.

// starter.js
// заглушка: function removeFromCart(cart, id) { return cart; }
test('удаляет товар', () => {
  const cart = [{ id: 1 }, { id: 2 }];
  const result = removeFromCart(cart, 1);
  expect(result).toBeTruthy();
});
// cart.js
function removeFromCart(cart, id) {
  return cart.filter((item) => item.id !== id);
}
module.exports = { removeFromCart };

Зачем: шаг «красный» в TDD нужен именно для этого: увидеть, что тест способен упасть. Слабая проверка вроде toBeTruthy пройдёт почти с любым результатом, и тест превращается в декорацию.

Решение и разбор
// cart.test.js
const { removeFromCart } = require('./cart');

test('удаляет товар с указанным id и оставляет остальные', () => {
  const cart = [{ id: 1 }, { id: 2 }];
  expect(removeFromCart(cart, 1)).toEqual([{ id: 2 }]);
});

Любой массив, даже пустой, — truthy, поэтому исходный тест проходил с заглушкой, которая ничего не удаляет. Конкретное ожидание [{ id: 2 }] проверяет и что удалено нужное, и что остальное на месте. Заглушка-мутант return cart новый тест роняет.

Пример на removeFromCart

Красный. Тест из задания уже есть, функция — заглушка:

// tests/cart/cart.test.js
test('удаляет выбранный товар', () => {
  const cart = [{ ...headphones, quantity: 1 }, { ...lamp, quantity: 2 }];
  expect(removeFromCart(cart, 1)).toEqual([{ ...lamp, quantity: 2 }]);
});

// src/cart.js
function removeFromCart() { return notImplemented(); }

Запускаем npm run test:cart — тест красный с ошибкой «Корзина ещё не реализована».

Зелёный. Читаем тест как требование: «вернуть корзину без товара с этим ID». Пишем минимум:

function removeFromCart(cart, productId) {
  return cart.filter((item) => item.id !== productId);
}

Запускаем снова — зелёный. Заодно проходят и два других теста на removeFromCart: пустая корзина и отсутствующий ID. filter их уже покрывает.

Рефакторинг. Здесь улучшать нечего. В функциях побольше на этом шаге выносят повторяющийся код и придумывают понятные имена, проверяя тестами, что ничего не сломалось.

Плюсы и минусы

  • Плюсы: тесты точно есть; вы заранее продумываете, как функцией будут пользоваться; рефакторить не страшно.
  • Минусы: поначалу медленнее; тяжело применять, когда сами требования ещё не понятны (например, в прототипе интерфейса).

Рядом с TDD часто упоминают BDD (Behavior-Driven Development): тесты описывают поведение языком, понятным не только программисту, — «когда покупатель вводит SAVE10 при заказе от 200 ₽, он получает скидку 10%». Названия тестов в задании Testing Intro написаны как раз в этом духе. Подробнее — TDD и BDD.
