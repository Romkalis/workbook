Архитектура браузера web.dev «How browsers work», Chrome «Inside look» часть 1

Процесс — отдельная работающая программа с собственной областью памяти; поток — последовательность работы внутри процесса. Движок рендеринга обрабатывает разметку и стили, JavaScript-движок исполняет JS. Renderer process — процесс для содержимого страницы, browser process — часть браузера, координирующая окна, навигацию и другие службы.

Основные компоненты

Любой браузер можно разложить на одинаковый набор частей. Это общая схема из статьи Тали Гарсиэль:

КомпонентЗа что отвечает
Пользовательский интерфейсВсё, кроме окна с самой страницей: адресная строка, кнопки назад и вперёд, закладки.
Browser engineПосредник между UI и движком рендеринга.
Rendering engineПревращает HTML и CSS в картинку на экране.
СетьHTTP-запросы. Единый интерфейс над разными платформенными реализациями.
UI backendРисует базовые виджеты (окна, выпадающие списки) через средства ОС.
JavaScript-интерпретаторРазбирает и выполняет JS.
Хранилище данныхCookies, localStorage, IndexedDB и подобное.

Движки рендеринга

В статье 2011 года перечислены Trident (Internet Explorer), Gecko (Firefox), WebKit (Safari) и Blink, форк WebKit в Chrome и Opera. Сегодня живы Blink, Gecko и WebKit. Терминология у них немного разная: то, что WebKit называет render tree и layout, у Gecko называется frame tree и reflow. Поток при этом по сути один и тот же. Про WebKit отдельный раздел ниже.

Как устроено железо и процессы

Чтобы понять архитектуру Chrome, нужны четыре понятия.

  • CPU. «Мозг» компьютера. Ядро выполняет самые разные задачи по очереди.
  • GPU. Много простых ядер, которые параллельно делают однотипную работу. Поэтому графика, которая «на GPU», быстрая и плавная.
  • Процесс. Работающая программа со своим приватным куском памяти. Если процессам нужно общаться, они используют IPC (inter-process communication).
  • Поток. Исполнитель внутри процесса. Потоки одного процесса делят его память.

Мультипроцессная архитектура Chrome

Единого стандарта на устройство браузера нет, это деталь реализации. Chrome выбрал схему «много процессов, внутри каждого немного потоков».

ПроцессЧто контролирует
Browser«Хром» приложения: адресная строка, закладки, кнопки. Плюс невидимые привилегированные вещи: сеть и доступ к файлам.
RendererВсё, что внутри вкладки: HTML, CSS, JS страницы.
GPUЗадачи на GPU, изолированно от остальных. GPU обслуживает много приложений и рисует в одну поверхность.
Plugin / Extension / utilityПлагины, расширения и вспомогательные задачи.

Посмотреть живые процессы можно в Диспетчере задач Chrome (Дополнительные инструменты → Диспетчер задач).

Зачем столько процессов

  • Устойчивость. Зависла одна вкладка, закрыли её, остальные живут.
  • Безопасность и песочница. ОС умеет ограничивать права процесса. Renderer, который обрабатывает недоверенный контент, не получает произвольный доступ к файлам.
  • Цена. У каждого процесса своя память и своя копия инфраструктуры вроде V8, поэтому памяти уходит больше. Chrome ограничивает число процессов в зависимости от ресурсов устройства. Упёрся в лимит, начинает запускать несколько вкладок одного сайта в одном процессе.

Servicification и Site Isolation

Servicification. Части браузерной программы оформляются как сервисы. На мощном железе их можно разнести по разным процессам ради стабильности, на слабом объединить в один, чтобы сэкономить память.

Site Isolation. Раньше был один renderer на вкладку, и кросс-доменные iframe жили в нём вместе с основной страницей. С Site Isolation (включена на десктопе с Chrome 67) каждый кросс-сайтовый iframe получает отдельный renderer. Причина в безопасности. Правило одного источника (Same Origin Policy) и раньше запрещало чужому сайту читать данные вашего. Но в 2018 году нашли уязвимости процессоров Meltdown и Spectre: через них код мог подсмотреть чужую память внутри того же процесса. Единственная надёжная защита — держать разные сайты в разных процессах, у которых память не общая.

Запомнить

Browser process отвечает за всё вне вкладки и за сеть. Renderer process отвечает за всё внутри вкладки. Рендеринг страницы происходит в renderer.
