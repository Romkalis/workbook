Навигация: от Enter до начала рендеринга Chrome «Inside look» часть 2

Навигация — переход к документу по адресу. DNS помогает найти сетевой адрес сервера по доменному имени; HTTP описывает обмен запросом и ответом. Кэш — сохранённый результат, который иногда можно использовать повторно. IPC означает обмен сообщениями между процессами браузера.

Навигацией называется всё, что браузер делает, пока не передаст полученный HTML на рендеринг. Начинается она в browser process.

Простая навигация по шагам

  1. Обработка ввода. UI-поток решает, это поисковый запрос или URL, и куда идти: в поисковик или на сайт.
  2. Старт навигации. UI-поток отдаёт запрос сетевому потоку. Тот делает DNS-запрос и устанавливает TLS-соединение. Если сервер отвечает редиректом (например, 301), сетевой поток сообщает об этом UI-потоку и запускается новый запрос.
  3. Чтение ответа. По первым байтам и заголовку Content-Type определяется тип данных. Заголовок может быть неверным или отсутствовать, поэтому делается MIME sniffing. HTML уходит на рендеринг, архив или другой файл уходит в менеджер загрузок. Здесь же проходят проверка Safe Browsing (не известный ли это вредоносный сайт) и CORB (чтобы чувствительные кросс-сайтовые данные не попали в renderer).
  4. Поиск renderer-процесса. Чтобы не терять время, UI-поток ещё на втором шаге начинает искать или запускать renderer параллельно с сетевым запросом. К приходу данных процесс уже ждёт. Если случился кросс-сайтовый редирект, подготовленный процесс может не пригодиться.
  5. Commit navigation. Browser process по IPC говорит renderer-у зафиксировать навигацию и передаёт поток данных. После подтверждения обновляются адресная строка, индикатор безопасности и история сессии, и начинается загрузка документа.

Завершение загрузки. Renderer продолжает грузить ресурсы и рисовать страницу. Когда на всех фреймах отработали обработчики onload, он шлёт IPC в browser process, и спиннер на вкладке останавливается. «Завершил» здесь условно: клиентский JS может подгружать что-то ещё и после этого.

Переход на другой сайт

Перед новой навигацией browser process спрашивает текущий renderer, нет ли обработчика beforeunload (это тот самый диалог «Покинуть сайт?»). Раз JS-код живёт в renderer, браузеру может потребоваться обработать это событие перед переходом; обработчик не даёт странице безусловного права запретить уход.

Ловушка

Не вешайте beforeunload безусловно. Обработчик должен отработать до начала навигации, и это прямая задержка. Нужен он только когда пользователь может потерять введённые данные.

Если уходим на другой сайт, для него берётся новый renderer, а старый остаётся жить, чтобы обработать unload.

Service Worker и Navigation Preload

Service worker — ваш JS-код, который стоит между страницей и сетью, как посредник. На каждый запрос он решает: отдать ответ из кэша или сходить в сеть. Так работают сайты, которые открываются без интернета. Сам воркер выполняется в renderer-процессе. Откуда браузер знает, что у сайта есть воркер? При регистрации запоминается его область — scope, набор адресов, за которые он отвечает. При каждом переходе сетевой поток сверяет адрес со scope и, если воркер есть, запускает его.

Если воркер всё равно решит идти в сеть, получится лишний круг browser ↔ renderer. Navigation Preload убирает эту задержку: сетевой запрос стартует параллельно с запуском воркера, а сервер видит специальный заголовок и может, например, отдать только свежие данные вместо целого документа.
