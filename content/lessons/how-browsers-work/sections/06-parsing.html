Что такое парсинг

Парсинг, или разбор, превращает текст в структуру данных. Токенизация выделяет части записи — например, тег и его атрибуты; построение дерева связывает их в узлы. Правила зависят от языка: HTML сохраняет значимые пробелы и умеет исправлять многие ошибки, поэтому модель «выбросить пробелы и остановиться на первой ошибке» для него не подходит.

От байтов к DOM

Сеть отдаёт документ кусками (в старой статье упоминаются 8 КБ). Цепочка такая: байты → символы → токены → узлы → DOM. Токены это открывающие и закрывающие теги, имена и значения атрибутов, текст. Некоторые узлы создаются по тегам, другие — по тексту; существуют также элементы без закрывающего тега. Построение дерева следует правилам HTML, а не просто подсчёту пар скобок. Вложенные пары тегов дают вложенные узлы, так получается иерархия.

DOM это одновременно внутреннее представление страницы в браузере и API, через которое с ней работает JavaScript. Корень дерева объект Document.

Строится DOM инкрементально. Это важно: узлы появляются по мере прихода HTML. Чем больше узлов, тем дороже все следующие стадии, поэтому гигантский DOM ударяет и по layout, и по стилям.

Как устроен HTML-парсер

Алгоритм описан в спецификации HTML5 и состоит из двух стадий: токенизация и построение дерева.

  • Токенизатор это конечный автомат. У него есть состояния («Data state», «Tag open state», «Tag name state» и т. д.), и один и тот же символ в разных состояниях даёт разный результат. Встретили <, перешли в Tag open, встретили букву, начали токен тега и так далее до >.
  • Построение дерева тоже автомат, его состояния называются «режимами вставки» (insertion modes). Конструктор получает токены, создаёт нужные элементы и добавляет в дерево и в стек открытых элементов. Стек нужен, чтобы исправлять неправильную вложенность и незакрытые теги. Если в HTML нет <head>, он будет создан неявно.

Почему HTML нельзя разобрать обычным парсером

Обычные парсеры (сверху вниз или снизу вверх) работают с контекстно-свободными грамматиками, их можно записать в форме BNF. HTML такой грамматикой не описывается. Причины:

  1. Язык «прощающий»: можно опускать теги, не закрывать их.
  2. У браузеров есть традиционная терпимость к ошибкам для известных случаев кривой разметки.
  3. Парсинг реентерабельный: скрипт с document.write() может во время разбора добавить новые токены, то есть изменить сам вход.

Поэтому браузеры пишут собственные HTML-парсеры. А вот CSS как раз контекстно-свободный язык, и его разбирают обычными методами.

Терпимость к ошибкам

HTML не выдаёт «Invalid syntax». Браузер молча чинит разметку и идёт дальше. Пример из серии Chrome: разметка Hi! <b>I'm <i>Chrome</b>!</i> (тег b закрыт раньше i) будет истолкована как Hi! <b>I'm <i>Chrome</i></b><i>!</i>. Из статьи 2011 года: вложенный form внутри form игнорируется, «бесхозная» таблица внутри таблицы вытаскивается в соседнюю, слишком глубокая вложенность одинаковых тегов обрезается. Правила исправления сегодня описаны в спецификации HTML5. Вывод для разработчика: браузер простит, но писать валидную разметку всё равно стоит.

Что после парсинга

Документ помечается как interactive, выполняются скрипты с defer, затем состояние становится complete и срабатывает событие load.

Парсинг CSS и CSSOM

CSS разбирается в CSSOM, объектную модель стилей. Она похожа на DOM, но с принципиальным отличием: CSSOM не строится инкрементально, а CSS блокирует рендеринг. Причина в каскаде: любое следующее правило может переопределить предыдущее, поэтому пока весь CSS не получен и не разобран, рисовать что-либо нельзя, иначе пользователь увидит неправильные стили.

Скрипты блокируют парсинг

Встретив <script>, HTML-парсер останавливается: надо скачать (если файл внешний), разобрать и выполнить код. Причина в том, что скрипт может изменить документ, например через document.write(). Это классическая синхронная модель веба.

Скрипты и стили связаны ещё и друг с другом. Скрипт может запросить стиль элемента, а если нужные CSS ещё не загрузились, он получит неверный ответ. Поэтому браузеры заставляют скрипт ждать загрузки предшествующих стилей (в старой статье описано, что Firefox блокировал все скрипты, а WebKit только те, что обращаются к затронутым свойствам).

Как подсказать браузеру, что и когда грузить

ПриёмЧто делает
deferСкрипт скачивается параллельно с парсингом и выполняется после того, как документ разобран.
asyncСкрипт скачивается параллельно и выполняется, как только загрузился, не дожидаясь парсера.
type="module"Модульные скрипты по умолчанию откладываются, как defer.
<link rel="preload">Сообщает, что ресурс точно нужен текущей странице, и просит начать загрузку как можно раньше.

async и defer можно использовать, только если скрипт не вызывает document.write().

Preload scanner и спекулятивный парсинг

Пока основной поток занят, например ждёт выполнения скрипта, параллельно работает preload scanner. Он просматривает токены, находит <img>, <link>, <script> и заранее отправляет запросы сетевому потоку. DOM он не меняет, этим занимается только основной парсер. Благодаря этому ресурсы грузятся по параллельным соединениям, и общее время падает.

Запомнить

JS блокирует парсинг HTML, CSS блокирует рендеринг. Скрипт, стоящий после стилей, ждёт эти стили. Отсюда советы: тяжёлый JS в конец или с defer/async, критичный CSS как можно раньше и как можно меньше.
