Вычисление стилей web.dev, Chrome часть 3, web.dev Rendering performance

Вычисленный стиль (computed style) — итог выбора значений CSS-свойств элемента после применения правил каскада. Каскад определяет, каким правилам отдать приоритет; специфичность сравнивает селекторы лишь внутри соответствующего уровня. Поэтому «более длинный селектор всегда выигрывает» — неверное правило.

Одного DOM мало, чтобы знать, как выглядит страница. На этой стадии для каждого узла вычисляется computed style: какие именно значения свойств он получил с учётом всех правил. Результат виден во вкладке Computed в DevTools.

Computed style есть даже у страницы совсем без CSS. Заголовок h1 крупнее h2, у элементов есть отступы, всё благодаря таблице стилей браузера по умолчанию.

Каскад: кто победит

Свойство может быть задано в нескольких местах. Порядок приоритета по CSS2, от низшего к высшему:

  1. стили браузера;
  2. обычные стили пользователя;
  3. обычные стили автора (вашей страницы);
  4. стили автора с !important;
  5. стили пользователя с !important.

Внутри одного уровня сравнивается специфичность селектора, а при равенстве выигрывает правило, указанное позже («последнее побеждает»). Специфичность считают как четвёрку чисел a-b-c-d: a это inline-стиль, b число id, c число классов, атрибутов и псевдоклассов, d число тегов и псевдоэлементов.

li            /* 0-0-0-1 */
ul li         /* 0-0-0-2 */
li.red        /* 0-0-1-1 */
#x34y         /* 0-1-0-0 */
style="..."   /* 1-0-0-0 */

Как браузер быстро находит подходящие правила

Перебирать все правила для каждого элемента слишком дорого. Поэтому после разбора правила раскладываются по хэш-таблицам: по id, по классу, по тегу и общая для остального. Ключом служит самая правая часть селектора. Для элемента сначала берутся кандидаты из этих таблиц, а затем проверяется остаток селектора. Так отсекается больше 95% правил. Кроме того, WebKit умеет делить объекты стилей между похожими соседними узлами, а Firefox хранит дерево правил, чтобы не пересчитывать одни и те же значения.

Не переоценивайте

MDN прямо говорит: менее специфичные селекторы быстрее более специфичных (.foo быстрее .bar .foo), но выигрыш измеряется микросекундами. Оптимизировать селекторы стоит только когда профайлер показал, что проблема именно в них. Сначала измерять.
