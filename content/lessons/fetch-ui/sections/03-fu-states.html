Четыре состояния данных

Пока данные загружаются, их нет. Загрузка может упасть. Данные могут прийти пустыми. Каждое из этих состояний пользователь должен увидеть, а не гадать, почему страница пустая. Описываем их размеченным объединением:

export type RemoteData<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string };

Почему не три поля isLoading, error, data: они допускают бессмысленные сочетания («загрузка и ошибка одновременно», «данные есть, но и ошибка есть»). Объединение разрешает только возможные состояния, а switch с проверкой never не даст забыть нарисовать одно из них. Это тот же приём, что в задаче про состояние каталога в TypeScript Basic.

Задача 6. switch по состоянию ★☆☆ разминка

Напишите statusMessage(state: RemoteData<unknown[]>): текст для строки статуса над списком. idle — пусто, loading — «Загрузка…», success — «Найдено N» или «Ничего не найдено», error — «Ошибка: …». В default — проверка полноты.

Зачем: строка статуса с aria-live объявляет программе чтения с экрана, что происходит. Это часть доступности, а не украшение. А never гарантирует, что новое состояние не останется без текста.

Решение и разбор
// status.ts
export type RemoteData<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string };

export function statusMessage(state: RemoteData<unknown[]>): string {
  switch (state.status) {
    case 'idle':
      return '';
    case 'loading':
      return 'Загрузка…';
    case 'success':
      return state.data.length === 0 ? 'Ничего не найдено' : `Найдено: ${state.data.length}`;
    case 'error':
      return `Ошибка: ${state.message}`;
    default: {
      const unreachable: never = state;
      return unreachable;
    }
  }
}

В ветке success TypeScript знает про data, в error — про message, без единой проверки на undefined. Число выведено после двоеточия, «Найдено: 3», чтобы не склонять слово «товар» (как это делать, разобрано в задаче «Объявить результат поиска»).

Задача 7. Загрузить и пройти по состояниям ★★☆ практика

Напишите load(fetcher, onState): сообщает loading, вызывает асинхронный fetcher(), затем сообщает success с данными или error с текстом ошибки (error.message или «Неизвестная ошибка», если брошено не Error). Функция сама никогда не отклоняется.

Зачем: это мост между промисом и состояниями интерфейса. Написанный один раз, он гарантирует, что ни одна загрузка в приложении не забудет показать ошибку или снять индикатор.

Решение и разбор
// load.ts
export type RemoteData<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string };

export async function load<T>(fetcher: () => Promise<T>, onState: (s: RemoteData<T>) => void): Promise<void> {
  onState({ status: 'loading' });
  try {
    onState({ status: 'success', data: await fetcher() });
  } catch (error) {
    onState({ status: 'error', message: error instanceof Error ? error.message : 'Неизвестная ошибка' });
  }
}

throw 'строка' в JavaScript разрешён, поэтому в catch лежит unknown, и проверка instanceof Error обязательна. Функция «не отклоняется никогда»: вызывающему коду не нужен свой try/catch, а ошибка всё равно доходит до пользователя через состояние.

Задача 9. Повтор с паузой ★★★ с подвохом

Напишите withRetry(fn, { retries, delayMs }, shouldRetry): вызывает асинхронную fn, при ошибке повторяет до retries раз с паузой, которая удваивается (delayMs, 2×delayMs, …). Повторяет только если shouldRetry(error) истинно. Например, для сетевых ошибок и 5xx, но не для 400 и не для отмены.

Зачем: кратковременный сбой сети не должен превращаться в ошибку для пользователя. Но повторять имеет смысл не всё: 400 («неверные данные») повторится так же, а отменённый запрос повторять нельзя вовсе. Решение «что повторять» — инженерное, и оно вынесено в параметр.

Решение и разбор
// retry.ts
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

export async function withRetry<T>(
  fn: () => Promise<T>,
  { retries, delayMs }: { retries: number; delayMs: number },
  shouldRetry: (error: unknown) => boolean,
): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (attempt >= retries || !shouldRetry(error)) throw error;
      await sleep(delayMs * 2 ** attempt);
    }
  }
}

Удвоение паузы (экспоненциальная задержка) не даёт тысяче клиентов разом добивать упавший сервер одинаковыми частыми повторами. В реальных системах к паузе ещё добавляют случайный разброс (jitter), чтобы повторы не совпадали по времени (из общих знаний). После последней попытки бросается исходная ошибка, а не «попытки кончились»: в ней настоящая причина. Повторять POST, который меняет данные, опасно: сервер мог выполнить первый запрос, а сломался только ответ.
