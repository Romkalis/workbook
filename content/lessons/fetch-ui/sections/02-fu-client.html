Слой API-клиента

Вызовы fetch не разбрасывают по обработчикам кнопок. Их собирают в один модуль — API-клиент: функции «получить товары», «посчитать корзину» с типизированным результатом. Остальной код не знает адресов, заголовков и формата ошибок сервера.

export interface Product {
  id: string;
  title: string;
  price: number;
}

export class HttpError extends Error {
  constructor(
    readonly status: number,
    message: string,
  ) {
    super(message);
    this.name = 'HttpError';
  }
}

function isProduct(x: unknown): x is Product {
  return (
    typeof x === 'object' && x !== null &&
    'id' in x && typeof x.id === 'string' &&
    'title' in x && typeof x.title === 'string' &&
    'price' in x && Number.isInteger(x.price)
  );
}

export function createApi(baseUrl: string, fetchFn: typeof fetch = fetch) {
  return {
    async getProducts(search = '', signal?: AbortSignal): Promise<Product[]> {
      const url = new URL('/api/products', baseUrl);
      if (search) url.searchParams.set('search', search);
      const res = await fetchFn(url, { signal });
      if (!res.ok) throw new HttpError(res.status, `Сервер ответил ${res.status}`);
      const data: unknown = await res.json();
      if (!Array.isArray(data) || !data.every(isProduct)) throw new TypeError('Неожиданный ответ сервера');
      return data;
    },
  };
}

Четыре решения, которые стоит уметь объяснить:

  • new URL(path, base) вместо склейки строк: не будет двойного или потерянного слэша, а параметры searchParams закодируются сами (пробелы, русские буквы).
  • res.ok: fetch не бросает ошибку на 404 и 500, ответ сервера с ошибкой — тоже «успешный» ответ на уровне сети (подробнее). Статус проверяем сами и превращаем в HttpError.
  • Ответ — unknown, пока не проверен. Тип Promise<Product[]> без проверки был бы обещанием, которое никто не выполняет: сервер обновили, поле переименовали — и интерфейс падает в неожиданном месте с undefined. Проверка на входе даёт понятную ошибку сразу. Вручную писать такие проверки утомительно; в следующем уроке их заменит библиотека Zod.
  • fetchFn параметром. В приложении это обычный fetch, в тестах — подмена, которая отвечает что угодно: успех, 500, кривой JSON. Это то же внедрение зависимости, что в уроке о тестировании.

Задача 1. Адрес запроса без склейки строк ★☆☆ разминка

Напишите buildUrl(base, path, params): собирает адрес через new URL, добавляет непустые параметры (пустые строки, undefined и null пропускает). Должно работать при base со слэшем в конце и без.

Зачем: склейка ${base}/api?search=${q} ломается на слэшах, пробелах, амперсандах и русских буквах. URL решает всё это и делает адрес таким, каким его ждёт сервер.

Решение и разбор
// url.ts
export function buildUrl(base: string, path: string, params: Record<string, string | number | null | undefined> = {}): URL {
  const url = new URL(path, base);
  for (const [key, value] of Object.entries(params)) {
    if (value !== undefined && value !== null && value !== '') url.searchParams.set(key, String(value));
  }
  return url;
}

Путь начинается со слэша ('/api/products'), поэтому он заменяет путь базы целиком. С базой http://host/v1/ и путём 'api' без слэша получился бы /v1/api. Это особенность new URL, и её стоит знать. Значение 0 сохраняется: это реальное число, а не «пусто».

Задача 2. Текст ошибки от сервера ★★☆ практика

Сервер в случае ошибки отвечает JSON { error: "текст" }, но прокси или хостинг могут вернуть HTML-страницу ошибки. Напишите readErrorMessage(res): возвращает текст из поля error, если он есть, иначе «Сервер ответил <статус>». Функция не должна бросать ни при каком теле.

Зачем: пользователь должен увидеть понятную причину («Нет товара zz»), если сервер её сообщил. А разбор тела ошибки, который сам падает с SyntaxError, подменяет настоящую проблему новой.

Решение и разбор
// error-text.ts
export async function readErrorMessage(res: Response): Promise<string> {
  try {
    const body: unknown = await res.json();
    if (typeof body === 'object' && body !== null && 'error' in body && typeof body.error === 'string') {
      return body.error;
    }
  } catch {
    // тело не JSON
  }
  return `Сервер ответил ${res.status}`;
}

Тело ответа читается один раз: после res.json() вызвать res.text() уже нельзя. Если нужен и текст, и JSON, сначала читают text(), потом JSON.parse. Проверка typeof body.error === 'string' не даёт показать пользователю [object Object], если сервер прислал объект ошибки.

Задача 3. Универсальный getJson с проверкой ★★☆ практика

Напишите обобщённую getJson<T>(url, isT, fetchFn = fetch): делает GET, при статусе не 2xx бросает HttpError, а ответ проверяет переданным предикатом isT (не подошёл — TypeError). Тип результата — Promise<T>, без as.

Зачем: одна функция с правильной обработкой статуса и проверкой вместо копий в каждом запросе. Предикат параметром связывает проверку и тип: TypeScript выведет T из предиката, и обещанный тип не разойдётся с проверкой.

Решение и разбор
// get-json.ts
export class HttpError extends Error {
  constructor(
    readonly status: number,
    message: string,
  ) {
    super(message);
    this.name = 'HttpError';
  }
}

export async function getJson<T>(url: string | URL, isT: (x: unknown) => x is T, fetchFn: typeof fetch = fetch): Promise<T> {
  const res = await fetchFn(url);
  if (!res.ok) throw new HttpError(res.status, `Сервер ответил ${res.status}`);
  const data: unknown = await res.json();
  if (!isT(data)) throw new TypeError(`Неожиданный ответ от ${String(url)}`);
  return data;
}

Тип T выводится из предиката: getJson(url, isProductList) вернёт Promise<Product[]>. После if (!isT(data)) throw компилятор сам сужает data до T, поэтому as не нужен. В сообщении ошибки есть адрес: в логе сразу видно, какой запрос вернул неожиданное.

Задача 4. Таймаут и отмена вместе ★★☆ практика

Добавьте к запросу таймаут: fetchWithTimeout(url, { signal, timeoutMs }, fetchFn) отменяет запрос, если он идёт дольше timeoutMs, или если сработал внешний signal. Различите причины: таймаут — ошибка с именем TimeoutError, внешняя отмена — AbortError.

Зачем: сервер, который не отвечает, хуже сервера, который ответил ошибкой: интерфейс висит в «загрузке» вечно. Таймаут превращает зависание в понятную ошибку, а внешняя отмена остаётся для гонки запросов.

Подсказка

AbortSignal.timeout(ms) и AbortSignal.any([a, b]) разобраны в Country Search.

Решение и разбор
// timeout.ts
export function fetchWithTimeout(
  url: string | URL,
  { signal, timeoutMs }: { signal?: AbortSignal; timeoutMs: number },
  fetchFn: typeof fetch = fetch,
): Promise<Response> {
  const timeout = AbortSignal.timeout(timeoutMs);
  return fetchFn(url, { signal: signal ? AbortSignal.any([signal, timeout]) : timeout });
}

AbortSignal.any срабатывает от первого из сигналов, а причина (reason) берётся от сработавшего. Поэтому fetch отклоняется с TimeoutError или AbortError, и вызывающий код различает «сервер не ответил» (показать ошибку) и «мы сами отменили» (молча проигнорировать). Тест имитирует fetch, который честно слушает сигнал и отклоняется его причиной, как настоящий.

Зачем: клиент — граница между приложением и сетью. Всё, что дальше по коду, работает с проверенными Product[] и понятными ошибками. Ошибки этого слоя дороже всего: их последствия расползаются по всему интерфейсу.

Решение и разбор
// src/api.ts
async getProducts(filters: ProductFilters = {}, signal?: AbortSignal): Promise<Product[]> {
  const url = new URL('/api/products', baseUrl);
  for (const [key, value] of Object.entries(filters)) {
    if (value) url.searchParams.set(key, value);
  }
  const res = await fetchFn(url, { signal });
  if (!res.ok) throw new HttpError(res.status, await readError(res));
  const data: unknown = await res.json();
  if (!Array.isArray(data) || !data.every(isProduct)) throw new TypeError('Неожиданный ответ сервера');
  return data;
},

readError — функция из задачи «Текст ошибки от сервера», она лежит рядом в api.ts решения. every(isProduct) проверяет каждый элемент. Достаточно одного кривого товара, чтобы отклонить ответ целиком: частично верные данные хуже явной ошибки, потому что прячут проблему. Полный файл — в папке 02-start.
