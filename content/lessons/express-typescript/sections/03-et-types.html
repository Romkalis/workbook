Типы запроса и ответа

Обработчик Express получает req и res. Если написать обработчик прямо внутри app.get(...), TypeScript выведет их типы сам (контекстная типизация, о ней здесь). Но по умолчанию req.body имеет тип any, а req.query — «что угодно из строки запроса». Это надо уточнять.

Четыре параметра Request

Request — обобщённый тип (generic) с четырьмя параметрами по порядку:

Request<Params, ResBody, ReqBody, Query>
//      :id      что     что пришло  ?search=...
//               отвечаем в теле

Пример из нашего API: параметр пути :id и ответ — товар.

// src/routes/products.ts
productsRouter.get('/:id', (req: Request<{ id: string }>, res: Response<Product>) => {
  const product = PRODUCTS.find((p) => p.id === req.params.id);
  if (!product) throw new HttpError(404, 'Товар не найден');
  res.json(product);
});

Response<Product> — обещание компилятору: res.json() примет только Product. Попробуйте написать res.json({ title: 1 }), и редактор подчеркнёт ошибку. Это защищает от случайного изменения формы ответа, на которую рассчитывает фронтенд.

Задача 5. Типизированный PATCH ★★☆ практика

Напишите маршрут PATCH /api/products/:id, который меняет цену и/или название. Типизируйте все позиции Request: параметры пути, тело ответа (товар или { error }), тело запроса (unknown до проверки). Неверное тело — 400, нет товара — 404, иначе 200 с обновлённым товаром. Данные храните в Map, переданном в фабрику.

Зачем: Request<Params, ResBody, ReqBody, Query> описывает весь контракт маршрута в одной строке. Тело запроса — unknown, потому что это обещание проверить данные, а не поверить им.

Решение и разбор
// app.ts
import express, { type Request, type Response } from 'express';

export interface Product {
  id: string;
  title: string;
  price: number;
}
type ErrorBody = { error: string };
type ProductPatch = Partial<Pick<Product, 'title' | 'price'>>;

function isProductPatch(body: unknown): body is ProductPatch {
  if (typeof body !== 'object' || body === null) return false;
  const keys = Object.keys(body);
  if (keys.length === 0 || keys.some((k) => k !== 'title' && k !== 'price')) return false;
  if ('title' in body && (typeof body.title !== 'string' || body.title.trim() === '')) return false;
  if ('price' in body && !(typeof body.price === 'number' && Number.isInteger(body.price) && body.price >= 0)) return false;
  return true;
}

export function createApp(store: Map<string, Product>) {
  const app = express();
  app.use(express.json());

  app.patch(
    '/api/products/:id',
    (req: Request<{ id: string }, Product | ErrorBody, unknown>, res: Response<Product | ErrorBody>) => {
      if (!isProductPatch(req.body)) return res.status(400).json({ error: 'Неверное тело запроса' });
      const current = store.get(req.params.id);
      if (!current) return res.status(404).json({ error: 'Товар не найден' });
      const updated: Product = { ...current, ...req.body };
      store.set(updated.id, updated);
      res.json(updated);
    },
  );
  return app;
}

Тип патча собран из Product, а не написан заново: появится поле description, и добавить его в разрешённые — одна правка. Пустой объект и лишние ключи (например, id) отклоняются, чтобы клиент не мог «случайно» поменять идентификатор. Проверка тела идёт до поиска товара. Какой из двух ответов (400 или 404) отдать первым — вопрос договорённости, главное, что поведение одинаково для всех маршрутов.

Строка запроса: всегда строки

В адресе /api/products?minPrice=1000 значение minPrice приходит строкой "1000", а не числом. HTTP передаёт текст, и Express ничего не угадывает. Поэтому тип Query честно описан строками, а перевод в число с проверкой — отдельная функция:

// src/routes/products.ts
import { Router, type Request, type Response } from 'express';
import { filterProducts, PRODUCTS, type Product, type ProductFilters } from '../domain/products.js';
import { HttpError } from '../http-error.js';

export const productsRouter = Router();

type ProductsQuery = { search?: string; category?: string; minPrice?: string; maxPrice?: string };

function toNumber(value: string | undefined, name: string): number | undefined {
  if (value === undefined || value === '') return undefined;
  const n = Number(value);
  if (!Number.isInteger(n) || n < 0) throw new HttpError(400, `${name} должен быть целым числом ≥ 0`);
  return n;
}

productsRouter.get('/', (req: Request<{}, Product[], unknown, ProductsQuery>, res: Response<Product[]>) => {
  const filters: ProductFilters = {
    search: req.query.search,
    category: req.query.category,
    minPrice: toNumber(req.query.minPrice, 'minPrice'),
    maxPrice: toNumber(req.query.maxPrice, 'maxPrice'),
  };
  res.json(filterProducts(PRODUCTS, filters));
});

Тип ProductsQuery со строками — это допущение, а не проверка. По адресу ?search=a&search=b Express отдаст массив. Для учебного API это допустимо, а в серьёзном проекте строку запроса проверяют так же, как тело (следующий раздел).

Обратите внимание на {} в позиции Params: у маршрута / параметров пути нет. А unknown в позиции тела — у GET-запроса тела нет, и мы не обещаем, что оно есть.

Задача 6. Параметр сортировки как union ★★☆ практика

Добавьте к списку товаров параметр sort со значениями price-asc, price-desc, title. Тип — union литералов, проверка — предикат isSort(value): value is Sort на основе массива as const. Неизвестное значение — 400 с перечнем допустимых.

Зачем: строка из адреса превращается в узкий тип после проверки. Дальше switch по ней проверяется компилятором на полноту, а новое значение сортировки добавляется в одном месте, в массиве.

Решение и разбор
// sort.ts
export const SORTS = ['price-asc', 'price-desc', 'title'] as const;
export type Sort = (typeof SORTS)[number];

export function isSort(value: string): value is Sort {
  return (SORTS as readonly string[]).includes(value);
}

export function sortProducts<T extends { price: number; title: string }>(items: readonly T[], sort: Sort): T[] {
  const copy = [...items];
  switch (sort) {
    case 'price-asc':
      return copy.sort((a, b) => a.price - b.price);
    case 'price-desc':
      return copy.sort((a, b) => b.price - a.price);
    case 'title':
      return copy.sort((a, b) => a.title.localeCompare(b.title, 'ru'));
    default: {
      const unreachable: never = sort;
      return unreachable;
    }
  }
}
// app.ts
import express, { type Request } from 'express';
import { isSort, sortProducts, SORTS } from './sort.js';

const PRODUCTS = [
  { id: 'b1', title: 'Чистый код', price: 150000 },
  { id: 'b2', title: 'Грокаем алгоритмы', price: 99000 },
];

export function createApp() {
  const app = express();
  app.get('/api/products', (req: Request<{}, unknown, unknown, { sort?: string }>, res) => {
    const { sort } = req.query;
    if (sort === undefined) return res.json(PRODUCTS);
    if (!isSort(sort)) return res.status(400).json({ error: `sort: одно из ${SORTS.join(', ')}` });
    res.json(sortProducts(PRODUCTS, sort));
  });
  return app;
}

Тот же приём, что с категориями в задачах TypeScript Basic: массив as const — источник правды и для проверки, и для текста ошибки, и для типа. localeCompare(..., 'ru') сортирует русские названия по алфавиту, а не по кодам символов. Сообщение 400 перечисляет допустимые значения: клиенту не надо идти в документацию.

Решение и разбор
// src/domain/products.ts
import type { Product } from '../data/products.js';

export interface ProductFilters {
  search?: string;
  category?: string;
  minPrice?: number;
  maxPrice?: number;
}

export function filterProducts(products: readonly Product[], f: ProductFilters): Product[] {
  const query = f.search?.trim().toLowerCase() ?? '';
  return products.filter(
    (p) =>
      (query === '' || p.title.toLowerCase().includes(query)) &&
      (f.category === undefined || p.category === f.category) &&
      (f.minPrice === undefined || p.price >= f.minPrice) &&
      (f.maxPrice === undefined || p.price <= f.maxPrice),
  );
}

Разбор цены (toPrice в маршруте) бросает HttpError(400), а общий обработчик из шага 2 превращает её в ответ. Маршрут остаётся коротким. Полный код маршрута — в разделе урока и в папке следующего шага.

Деньги — в целых копейках

В Product цена хранится в копейках: 150000 вместо 1500.00. В JavaScript 0.1 + 0.2 равно 0.30000000000000004, потому что дробные числа хранятся в двоичном виде приблизительно. Сумма корзины из десятка позиций может разойтись на копейку с тем, что посчитал фронтенд. С целыми числами такого нет, а рубли с копейками показывают только при выводе ((price / 100).toFixed(2)). Это из общих знаний, но на интервью такой вопрос задают часто.
