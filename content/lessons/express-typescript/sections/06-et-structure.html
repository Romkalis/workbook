Структура: app отдельно от server

src/
  domain/        чистая логика без Express: товары, корзина
    products.ts
    cart.ts
  routes/        HTTP-слой: разбирает запрос, вызывает domain, отвечает
    products.ts
    cart.ts
  http-error.ts
  app.ts         createApp(): собирает приложение, но НЕ слушает порт
  server.ts      читает env и вызывает listen
tests/
  cart.test.ts   unit-тесты domain
  api.test.ts    тесты HTTP через supertest
// src/server.ts
import { createApp } from './app.js';

const port = Number(process.env.PORT ?? 3000);
const app = createApp(process.env.CLIENT_ORIGIN);

app.listen(port, () => {
  console.log(`API: http://localhost:${port}`);
});

Почему так

  • Тесты не занимают порт. Тест импортирует createApp() и отдаёт его supertest. Если бы app.ts сам вызывал listen(3000), два тестовых файла поспорили бы за порт, а запущенный npm run dev ломал бы тесты.
  • Логика не знает про HTTP. calculateCart принимает массив и возвращает объект. Её можно тестировать без сервера и даже скопировать во фронтенд, чтобы показывать сумму мгновенно. Сервер остаётся источником истины.
  • Настройки через окружение. Порт и адрес фронтенда берутся из process.env (о переменных окружения), потому что на хостинге они другие.

Это тот же принцип единственной ответственности из Clean Code, применённый к папкам.

Задача 14. Хранилище через интерфейс ★★★ с подвохом

Опишите интерфейс ProductRepo (list, findById, create) и реализуйте InMemoryProductRepo. Передайте репозиторий в createApp(repo). Тесты создают свой новый репозиторий в каждом тесте. Покажите, что маршруты не знают, где лежат данные.

Зачем: зависимость от интерфейса, а не от конкретной базы, — главное архитектурное решение маленького бэкенда. Тесты получают быстрый и изолированный fake, а переход на настоящую базу касается одного нового класса, а не всех маршрутов.

Решение и разбор
// repo.ts
export interface Product {
  id: string;
  title: string;
  price: number;
}

export interface ProductRepo {
  list(): Promise<Product[]>;
  findById(id: string): Promise<Product | null>;
  create(data: Omit<Product, 'id'>): Promise<Product>;
}

export class InMemoryProductRepo implements ProductRepo {
  #items = new Map<string, Product>();
  #nextId = 1;

  async list() {
    return [...this.#items.values()];
  }
  async findById(id: string) {
    return this.#items.get(id) ?? null;
  }
  async create(data: Omit<Product, 'id'>) {
    const product = { id: String(this.#nextId++), ...data };
    this.#items.set(product.id, product);
    return product;
  }
}
// app.ts
import express from 'express';
import type { ProductRepo } from './repo.js';

export function createApp(repo: ProductRepo) {
  const app = express();
  app.use(express.json());
  app.get('/api/products', async (_req, res) => {
    res.json(await repo.list());
  });
  app.get('/api/products/:id', async (req, res) => {
    const product = await repo.findById(req.params.id);
    if (!product) return res.status(404).json({ error: 'Товар не найден' });
    res.json(product);
  });
  app.post('/api/products', async (req, res) => {
    const { title, price } = req.body ?? {};
    if (typeof title !== 'string' || !Number.isInteger(price)) return res.status(400).json({ error: 'Неверные данные' });
    res.status(201).json(await repo.create({ title, price }));
  });
  return app;
}

Методы асинхронные, хотя Map отвечает сразу. Интерфейс описывает любую реализацию, а настоящей базе нужно время. Если сделать его синхронным, переход на базу заставит переписать все маршруты. В app.ts только import type: приложение зависит от формы хранилища, а не от кода реализации. Где создаётся InMemoryProductRepo? В server.ts, единственном месте, которое знает, «на чём мы работаем». Этот приём называется внедрением зависимостей (dependency injection).
