Ошибки: свой класс, 404 и общий обработчик

Класс HttpError

// src/http-error.ts
export class HttpError extends Error {
  constructor(
    readonly status: number,
    message: string,
  ) {
    super(message);
    this.name = 'HttpError';
  }
}

Ошибка несёт HTTP-статус. Маршрут не думает, как отформатировать ответ: он бросает new HttpError(404, 'Товар не найден'), а всё остальное делает общий обработчик. Приём «свой класс ошибки» подробно разобран в уроке Обработка ошибок.

Задача 10. Свой класс ошибки: 409 ★☆☆ разминка

Добавьте к HttpError наследника ConflictError (статус 409, сообщение задаётся). Используйте его в функции addCategory(store, name): повтор существующей категории без учёта регистра — конфликт.

// http-error.ts
export class HttpError extends Error {
  constructor(
    readonly status: number,
    message: string,
  ) {
    super(message);
    this.name = 'HttpError';
  }
}

Зачем: именованные ошибки читаются как предложения: throw new ConflictError('Категория уже есть') понятнее, чем new HttpError(409, ...), и меньше шанс перепутать коды. А общий обработчик продолжает работать, потому что наследник — тоже HttpError.

Решение и разбор
// conflict.ts
import { HttpError } from './http-error.js';

export class ConflictError extends HttpError {
  constructor(message: string) {
    super(409, message);
    this.name = 'ConflictError';
  }
}

export function addCategory(store: Set<string>, name: string): string {
  const normalized = name.trim().toLowerCase();
  if (store.has(normalized)) throw new ConflictError(`Категория «${normalized}» уже есть`);
  store.add(normalized);
  return normalized;
}

409 Conflict — «запрос корректный, но противоречит текущему состоянию». Не 400: с данными всё в порядке, просто такая категория уже есть. Обработчик ошибок из урока проверяет err instanceof HttpError, и ConflictError проходит эту проверку без единой правки обработчика. Это принцип открытости/закрытости из ООП на практике.

Сборка приложения

// src/app.ts
import express, { type ErrorRequestHandler } from 'express';
import cors from 'cors';
import { productsRouter } from './routes/products.js';
import { cartRouter } from './routes/cart.js';
import { HttpError } from './http-error.js';

export function createApp(allowedOrigin = 'http://localhost:5173') {
  const app = express();
  app.use(cors({ origin: allowedOrigin }));
  app.use(express.json());

  app.get('/api/health', (_req, res) => {
    res.json({ ok: true });
  });
  app.use('/api/products', productsRouter);
  app.use('/api/cart', cartRouter);

  app.use((_req, _res, next) => next(new HttpError(404, 'Маршрут не найден')));

  const onError: ErrorRequestHandler = (err, _req, res, _next) => {
    const status = err instanceof HttpError ? err.status : (err.status ?? 500);
    if (status >= 500) console.error(err);
    res.status(status).json({ error: status >= 500 ? 'Внутренняя ошибка сервера' : err.message });
  };
  app.use(onError);
  return app;
}

Порядок app.use — порядок обработки, сверху вниз:

  1. cors и express.json() срабатывают на каждый запрос. Второй превращает JSON-тело в объект req.body.
  2. Маршруты.
  3. Middleware без пути после всех маршрутов ловит то, что никто не обработал, и создаёт 404.
  4. Обработчик ошибок. Express узнаёт его по четырём параметрам (err, req, res, next). Тип ErrorRequestHandler подставляет типы всех четырёх, а неиспользуемые параметры начинаются с _.

Ветка err.status ?? 500 нужна для ошибок, которые создал не наш код. Когда express.json() получает битый JSON, он бросает ошибку со status: 400. Без этой ветки клиент получил бы 500, будто упал сервер. Это проверено тестом в разделе о тестах.

Для 5xx клиенту уходит общий текст, а подробности — в лог (console.error). Текст внутренней ошибки может раскрыть путь к файлам, запрос к базе или ключ. Это из общих знаний, но правило стоит запомнить сразу.

Задача 12. Ошибка проверки с подробностями ★★☆ практика

Сделайте ValidationError extends HttpError (статус 400) с полем details: string[]. Доработайте обработчик ошибок: для неё ответ { error, details }, для остальных — как раньше. Проверьте маршрутом, который бросает ValidationError.

Зачем: формат ответа об ошибке — часть API. Если одни маршруты отдают details, а другие строку, фронтенд обрастает условиями. Единый обработчик гарантирует один формат.

Решение и разбор
// app.ts
import express, { type ErrorRequestHandler } from 'express';

export class HttpError extends Error {
  constructor(
    readonly status: number,
    message: string,
  ) {
    super(message);
  }
}

export class ValidationError extends HttpError {
  constructor(readonly details: string[]) {
    super(400, 'Неверные данные');
  }
}

export function createApp() {
  const app = express();
  app.use(express.json());
  app.post('/api/check', (req, res) => {
    const errors: string[] = [];
    if (typeof req.body?.email !== 'string' || !req.body.email.includes('@')) errors.push('email: нужен адрес почты');
    if (errors.length) throw new ValidationError(errors);
    res.json({ ok: true });
  });

  const onError: ErrorRequestHandler = (err, _req, res, _next) => {
    if (err instanceof ValidationError) return res.status(400).json({ error: err.message, details: err.details });
    const status = err instanceof HttpError ? err.status : (err.status ?? 500);
    res.status(status).json({ error: status >= 500 ? 'Внутренняя ошибка сервера' : err.message });
  };
  app.use(onError);
  return app;
}

Проверка ValidationError стоит перед общей проверкой HttpError: наследник тоже instanceof HttpError, и в обратном порядке ветка с details никогда бы не сработала. Порядок от частного к общему — то же правило, что для catch в других языках.

Express 5 и async-обработчики

В Express 4 исключение внутри async-обработчика терялось: промис отклонялся, а запрос висел, пока не истечёт время ожидания. Приходилось оборачивать каждый обработчик в try/catch с next(err). В Express 5 отклонённый промис сам уходит в обработчик ошибок. Мы проверили: app.get('/a', async () => { throw new Error('boom') }) отвечает 500 через наш обработчик. Если в интернете видите express-async-errors или обёртки asyncHandler, скорее всего, материал написан под Express 4.

Задача 13. Асинхронный репозиторий без try/catch ★☆☆ разминка

Сделайте маршрут GET /api/products/:id асинхронным: товар берётся из await repo.findById(id). Ни одного try/catch в маршруте. Проверьте, что отказ репозитория даёт 500 с общим текстом, а отсутствие товара — 404.

Зачем: в Express 5 отклонённый промис сам уходит в обработчик ошибок. Маршрут описывает только счастливый путь и бизнес-ошибки, а инфраструктурные сбои обрабатываются централизованно.

Решение и разбор
// app.ts
import express, { type ErrorRequestHandler } from 'express';

export interface Product {
  id: string;
  title: string;
}
export interface ProductRepo {
  findById(id: string): Promise<Product | null>;
}

class NotFound extends Error {}

export function createApp(repo: ProductRepo) {
  const app = express();
  app.get('/api/products/:id', async (req, res) => {
    const product = await repo.findById(req.params.id);
    if (!product) throw new NotFound('Товар не найден');
    res.json(product);
  });
  const onError: ErrorRequestHandler = (err, _req, res, _next) => {
    if (err instanceof NotFound) return res.status(404).json({ error: err.message });
    res.status(500).json({ error: 'Внутренняя ошибка сервера' });
  };
  app.use(onError);
  return app;
}

Тип ProductRepo описывает, что маршруту нужно от хранилища, и ничего больше. Сегодня это массив, завтра Mongo или PostgreSQL, а маршрут не меняется. Это и есть следующая задача.
