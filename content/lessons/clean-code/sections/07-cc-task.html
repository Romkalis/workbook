Задание Clean Code S1E1: план работы

Дано маленькое TODO-приложение: index.html, style.css, app.js. Нужно отрефакторить его по гайду так, чтобы приложение работало и выглядело как раньше. Максимум 45 баллов: 15 правил начального уровня по 2 балла и 3 продвинутых по 5.

Ноль баллов, если нарушено хоть одно требование
  • Личный публичный репозиторий clean-code-s1e1: форк или новый репозиторий с копией файлов. Во втором случае первый коммит — init: ….
  • Работа в ветке clean-code-s1e1, созданной от main. Сама main не меняется.
  • Один коммит — одно правило гайда, сообщение называет его. Совмещать можно, только если выполнение одного правила автоматически выполняет другое и их не разделить. Тогда в сообщении перечислены оба.
  • Никакого Prettier и других автоформаттеров.
  • Функциональность сохранена (или исправлена, если была сломана).
  • PR из clean-code-s1e1 в main вашего репозитория, открыт, оформлен по правилам. Сдаётся ссылка на PR.

Ловушка форка

Если вы сделали форк, GitHub при создании PR по умолчанию предложит влить его в main исходного репозитория rolling-scopes-school. Обязательно переключите base repository на свой. PR в чужой репозиторий — ошибка, которую видят все.

Пошагово

  1. Форк или новый репозиторий, затем git clone, затем git switch -c clean-code-s1e1.
  2. Откройте index.html в браузере и пройдите весь список функций (ниже). Сделайте скриншот «до», чтобы потом сравнить внешний вид.
  3. Берите правила по одному. Правка, проверка в браузере, коммит. Не копите десять правил, чтобы потом раскладывать их по коммитам.
  4. После каждого переименования классов или id ищите старое имя во всех трёх файлах, включая app.js.
  5. В конце — финальная проверка функциональности, деплой на gh-pages (необязательно, но проверяющим удобнее), PR с описанием и самооценкой.

Пример последовательности коммитов

Гайд разрешает два стиля сообщений, оба на английском. Выберите один и держитесь его:

fix(basic-2.2): add html5 doctype
refactor(basic-1.2): use lowercase for tags, attributes and colors
refactor(basic-1.3): use double quotes in html and css
refactor(basic-2.4): remove type attribute from link and script
refactor(basic-2.3): replace named character reference with symbol
refactor(basic-1.1): use two spaces for indentation
refactor(basic-2.1): put block and list elements on new lines
refactor(basic-3.5): indent rules inside media query
refactor(basic-3.6): add space after colon in css properties
refactor(basic-3.7): add semicolon after each css property
refactor(basic-3.8): put each selector and property on new line
refactor(extended-1.1): use semantic tags for page layout
fix(extended-1.2): add alt text to images
refactor(extended-2.1, basic-3.1): rename classes according to bem
refactor(basic-3.2, basic-3.3): use meaningful and concise ids
refactor(basic-3.4): replace tag selectors with classes

Второй стиль: fix: add html5 doctype according to rule 2.2 in html-and-css.md. Порядок выбран так, чтобы механические правки шли раньше переименований: когда вы дойдёте до БЭМ, код уже отформатирован, и diff переименования не утонет в пробелах.

Что сломается при переименовании

app.js завязан на имена из разметки. Разберитесь с ними до того, как менять HTML и CSS:

  • getElementById("new-task"), "incompleteTasks", "completed-tasks" — id в разном стиле, после переименования их надо поменять и здесь.
  • querySelector(".edit"), "button.edit", "button.delete" — классы кнопок.
  • classList.contains("editMode") и classList.toggle("editMode") — режим редактирования. В CSS от него зависит ul li.editMode label. Пропустите одно место — режим редактирования перестанет работать.
  • className = 'task', "edit", "delete" в createNewTaskElement. Новые задачи создаются из JS, и если не обновить классы здесь, новые элементы будут выглядеть иначе, чем исходные.
  • getElementsByTagName("button")[0] — кнопка «Add» найдена как «первая кнопка на странице». Если при переделке семантики перед ней появится другая кнопка, привязка молча уедет. Надёжнее дать кнопке класс и искать по нему.

Любопытная деталь: обработчик addTask навешан дважды, через onclick и через addEventListener. Задача не дублируется только потому, что первый вызов очищает поле, а второй выходит на проверке if (!taskInput.value) return. Это скрытая связь, которая сломается от безобидной правки. Можно исправить отдельным коммитом fix: remove duplicate click handler: правки JS заданием не запрещены, функциональность разрешено чинить.

Чек-лист функциональности

  • Добавить задачу в «Todo».
  • Отредактировать задачу в «Todo» и в «Completed» (Edit → Save).
  • Удалить задачу из обоих списков.
  • Отметить чекбокс — задача переезжает в «Completed»; снять — возвращается в «Todo».
  • Внешний вид не изменился (мелкие сдвиги отступов из-за замены тегов не штрафуются, PerfectPixel не нужен).
  • У всех нужных картинок есть alt; анимация кнопки удаления работает.

Шрифт fantasy из приложения в Linux может выглядеть иначе. Критерии прямо разрешают заменить его на похожий без штрафа. И главное правило проверки из задания: «Будьте снисходительны. Все спорные вопросы решаются в пользу большего балла».
