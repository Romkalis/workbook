Как проектировать REST-API

Статья Codecademy «What is REST?» предлагает начинать с моделей: какие сущности есть в системе и какие у них поля. Для магазина одежды это, например, клиенты (customers) и заказы (orders). Затем для каждой модели описывают запросы и ответы. Отсюда несколько правил, которые разделяют и статья dev.to «Fundamentals of REST API», и практика большинства публичных API.

Ресурсы — существительные, действия — методы

ПлохоХорошо
GET /getUsersGET /users
POST /createUserPOST /users
GET /deleteUser?id=5DELETE /users/5
GET /user/5/getArticlesGET /users/5/articles
  • Коллекции называют существительными во множественном числе: /users, /orders.
  • Один элемент — по идентификатору: /users/5.
  • Связанные ресурсы — вложенностью: /users/5/articles. Глубже двух уровней обычно не идут: /articles?userId=5 читается проще, чем /users/5/articles/12/comments.
  • Адреса в нижнем регистре, слова через дефис: /order-items.
  • GET никогда не меняет данные: поисковые роботы и предзагрузка браузера могут вызвать его сами.

Фильтры, сортировка, пагинация

Выборку из коллекции уточняют строкой запроса, а не новыми адресами:

GET /employees?role=developer          фильтр
GET /employees?_sort=-salary           сортировка по убыванию
GET /employees?_page=2&_per_page=10    вторая страница по 10

Имена параметров каждый API выбирает сам — они описаны в его документации. Подчёркивание в _page и _sort — соглашение json-server, чтобы служебные параметры не путались с полями данных. Клиенту для пагинации нужно знать общее число записей или страниц: сервер сообщает его в теле ответа или заголовком (раздел о json-server).

Версии API

API меняется, а старые клиенты (мобильные приложения, которые пользователи не обновили) должны продолжать работать. Статья restfulapi.net о версиях советует повышать версию только при ломающих изменениях: поменялся формат ответа, тип поля (целое стало дробным), удалена часть API. Добавление нового адреса или нового поля в ответ ничего не ломает. Три способа указать версию:

  • В адресе: /v1/users. Самый простой и распространённый способ (так делает, например, Stripe: api.stripe.com/v1/charges), хотя он нарушает идею «один ресурс — один адрес».
  • Своим заголовком: Accept-Version: v1 или X-API-Version: 1.
  • Через Accept: Accept: application/vnd.example.v1+json — адреса чистые, но клиент должен знать нужный заголовок.

Статья приводит в пример версию в адресе api.github.com/v3/repos. Это неточно: GitHub не пишет версию в путь, а принимает её заголовком X-GitHub-Api-Version (из общих знаний). Хорошая практика — объявлять об устаревании версии заранее и отключать её постепенно.

Альтернативы

Статья tutsplus сравнивает REST с SOAP — протоколом со строгим форматом XML-сообщений, который до сих пор живёт в банках и госсистемах, — и с GraphQL: клиент одним запросом к одному адресу описывает, какие поля ему нужны, и получает ровно их. REST проще и лучше кешируется, GraphQL удобнее, когда экранам нужны данные из многих ресурсов сразу.
