Как проектировать REST-API

Статья Codecademy «What is REST?» предлагает начинать с моделей: какие сущности есть в системе и какие у них поля. Для магазина одежды это, например, клиенты (customers) и заказы (orders). Затем для каждой модели описывают запросы и ответы. Отсюда несколько правил, которые разделяют и статья dev.to «Fundamentals of REST API», и практика большинства публичных API.

Ресурсы — существительные, действия — методы

ПлохоХорошо
GET /getUsersGET /users
POST /createUserPOST /users
GET /deleteUser?id=5DELETE /users/5
GET /user/5/getArticlesGET /users/5/articles
  • Коллекции называют существительными во множественном числе: /users, /orders.
  • Один элемент — по идентификатору: /users/5.
  • Связанные ресурсы — вложенностью: /users/5/articles. Глубже двух уровней обычно не идут: /articles?userId=5 читается проще, чем /users/5/articles/12/comments.
  • Адреса в нижнем регистре, слова через дефис: /order-items.
  • GET никогда не меняет данные: поисковые роботы и предзагрузка браузера могут вызвать его сами.

Задача 7. Переименуйте маршруты ★☆☆ разминка

Перепишите маршруты в стиле REST: ресурсы — существительные во множественном числе, действие — метод. Отметьте маршрут, который опасен независимо от названия.

app.get('/getAllOrders', list);
app.post('/createOrder', create);
app.get('/order/:id/cancel', cancel);
app.post('/updateOrderStatus', updateStatus); // { id, status } в теле
app.get('/deleteOrder', remove);              // ?id=5
app.get('/user/:id/getOrders', userOrders);

Зачем: единые правила адресов делают API предсказуемым: зная один ресурс, можно угадать остальные. Опасность GET, который меняет данные, вполне реальна: браузер, поисковый робот или предзагрузка ссылок могут вызвать его без участия пользователя.

Решение и разбор
// routes.ts
app.get('/orders', list);
app.post('/orders', create);
app.patch('/orders/:id', updateStatus);  // { status: 'cancelled' } — отмена это смена статуса
app.delete('/orders/:id', remove);
app.get('/users/:id/orders', userOrders);

Опасны GET /order/:id/cancel и GET /deleteOrder: они меняют данные через GET. Отмена — не отдельный «глагол», а изменение поля status, поэтому она уходит в PATCH. Если у отмены сложная логика (возврат денег, письмо), допустим и POST /orders/:id/cancellation: создаётся «запрос на отмену». Это тоже существительное. id переехал из тела и строки запроса в путь: он указывает, какой ресурс, а тело описывает, что с ним сделать.

Фильтры, сортировка, пагинация

Выборку из коллекции уточняют строкой запроса, а не новыми адресами:

GET /employees?role=developer          фильтр
GET /employees?_sort=-salary           сортировка по убыванию
GET /employees?_page=2&_per_page=10    вторая страница по 10

Имена параметров каждый API выбирает сам — они описаны в его документации. Подчёркивание в _page и _sort — соглашение json-server, чтобы служебные параметры не путались с полями данных. Клиенту для пагинации нужно знать общее число записей или страниц: сервер сообщает его в теле ответа или заголовком (раздел о json-server).

Задача 8. Параметры списка: проверить и нормализовать ★★☆ практика

Напишите parseListQuery(params: URLSearchParams) для GET /employees. Результат: { role?: string; sort: { field: "name" | "salary"; dir: "asc" | "desc" }; page: number; perPage: number }. Правила:

  • sort=-salary — по убыванию, без минуса — по возрастанию, по умолчанию name;
  • page — целое от 1, по умолчанию 1;
  • perPage — от 1 до 100, по умолчанию 10, больше 100 обрезается до 100;
  • неизвестное поле сортировки или нечисловая страница — ошибка RangeError с понятным текстом.

Зачем: строка запроса — это пользовательский ввод: её можно набрать руками. Без верхней границы perPage=1000000 заставит сервер выгрузить всю таблицу. А разбор в одном месте даёт обработчику уже проверенные данные нужных типов.

Решение и разбор
const FIELDS = ['name', 'salary'] as const;
type Field = (typeof FIELDS)[number];
export interface ListQuery {
  role?: string;
  sort: { field: Field; dir: 'asc' | 'desc' };
  page: number;
  perPage: number;
}

function int(raw: string | null, name: string, fallback: number): number {
  if (raw === null || raw === '') return fallback;
  const n = Number(raw);
  if (!Number.isInteger(n) || n < 1) throw new RangeError(`${name}: ожидалось целое число от 1`);
  return n;
}

export function parseListQuery(params: URLSearchParams): ListQuery {
  const rawSort = params.get('sort') ?? 'name';
  const dir = rawSort.startsWith('-') ? 'desc' : 'asc';
  const field = rawSort.replace(/^-/, '');
  if (!(FIELDS as readonly string[]).includes(field)) {
    throw new RangeError(`sort: допустимо ${FIELDS.join(', ')}`);
  }
  const query: ListQuery = {
    sort: { field: field as Field, dir },
    page: int(params.get('page'), 'page', 1),
    perPage: Math.min(int(params.get('perPage'), 'perPage', 10), 100),
  };
  const role = params.get('role');
  if (role) query.role = role;
  return query;
}

Почему слишком большой perPage обрезается, а неверная страница — ошибка? perPage=500 выражает понятное желание «побольше», и его можно выполнить в разумных пределах. А page=abc — явная ошибка клиента, и угадывать за него опасно. Текст ошибки перечисляет допустимые значения: тот, кто пишет клиент, исправит запрос, не открывая документацию. В Express такой RangeError превращается в ответ 400. Ту же работу короче делает схема Zod.

Задача 9. Применить фильтр, сортировку и страницу ★★☆ практика

Напишите applyQuery(items, query), где query — результат прошлой задачи. Порядок: отфильтровать по role, отсортировать, отрезать страницу. Ответ: { data, total, page, pages }, где total — число записей после фильтра. Исходный массив не меняется.

Зачем: порядок операций важен. Сначала отрезать страницу, а потом сортировать — значит отсортировать десять случайных записей вместо всей выборки. Это частая ошибка, когда пагинацию добавляют позже остального.

Решение и разбор
export interface Employee {
  id: string;
  name: string;
  role: string;
  salary: number;
}
export interface ListQuery {
  role?: string;
  sort: { field: 'name' | 'salary'; dir: 'asc' | 'desc' };
  page: number;
  perPage: number;
}

export function applyQuery(items: readonly Employee[], q: ListQuery) {
  const filtered = q.role === undefined ? [...items] : items.filter((e) => e.role === q.role);
  const sign = q.sort.dir === 'asc' ? 1 : -1;
  filtered.sort((a, b) =>
    sign * (q.sort.field === 'name' ? a.name.localeCompare(b.name, 'ru') : a.salary - b.salary),
  );
  const start = (q.page - 1) * q.perPage;
  return {
    data: filtered.slice(start, start + q.perPage),
    total: filtered.length,
    page: q.page,
    pages: Math.ceil(filtered.length / q.perPage),
  };
}

filter уже возвращает новый массив, а в ветке без фильтра копию делает [...items]. Поэтому sort на месте никого не задевает. В настоящей базе данных тот же порядок задают в запросе: WHERE → ORDER BY → LIMIT/OFFSET. Делать это в памяти можно только для небольших учебных наборов.

Версии API

API меняется, а старые клиенты (мобильные приложения, которые пользователи не обновили) должны продолжать работать. Статья restfulapi.net о версиях советует повышать версию только при ломающих изменениях: поменялся формат ответа, тип поля (целое стало дробным), удалена часть API. Добавление нового адреса или нового поля в ответ ничего не ломает. Три способа указать версию:

  • В адресе: /v1/users. Самый простой и распространённый способ (так делает, например, Stripe: api.stripe.com/v1/charges), хотя он нарушает идею «один ресурс — один адрес».
  • Своим заголовком: Accept-Version: v1 или X-API-Version: 1.
  • Через Accept: Accept: application/vnd.example.v1+json — адреса чистые, но клиент должен знать нужный заголовок.

Статья приводит в пример версию в адресе api.github.com/v3/repos. Это неточно: GitHub не пишет версию в путь, а принимает её заголовком X-GitHub-Api-Version (из общих знаний). Хорошая практика — объявлять об устаревании версии заранее и отключать её постепенно.

Задача 10. Две версии API на одних данных ★★☆ практика

В версии 1 сотрудник отдаётся как { id, name }. В версии 2 имя разделили: { id, firstName, lastName }. Сделайте Express-приложение, где /api/v1/employees и /api/v2/employees работают одновременно на одних данных. Каждую версию оформите отдельным Router.

Зачем: мобильное приложение, которое пользователь не обновил, продолжит ходить в v1. Если поменять формат без версии, оно сломается у реальных людей. Отдельные роутеры поверх общих данных позволяют поддерживать обе версии, не копируя логику хранения.

Решение и разбор
// app.ts
import express, { Router } from 'express';

interface Employee {
  id: string;
  firstName: string;
  lastName: string;
}
const employees: Employee[] = [{ id: '1', firstName: 'Анна', lastName: 'Смирнова' }];

const v1 = Router();
v1.get('/employees', (_req, res) => {
  res.json(employees.map((e) => ({ id: e.id, name: `${e.firstName} ${e.lastName}` })));
});

const v2 = Router();
v2.get('/employees', (_req, res) => {
  res.json(employees);
});

export function createApp() {
  const app = express();
  app.use('/api/v1', v1);
  app.use('/api/v2', v2);
  return app;
}

Данные хранятся в новом, более точном формате, а v1 — это представление для старых клиентов. Обратный путь (хранить name и пытаться резать его на имя и фамилию) ненадёжен: «Анна Мария Смирнова» разрежется неправильно. Роутер монтируется на префикс, поэтому внутри маршруты пишутся без версии, и перенос в /v3 — одна строка.

Альтернативы

Статья tutsplus сравнивает REST с SOAP — протоколом со строгим форматом XML-сообщений, который до сих пор живёт в банках и госсистемах, — и с GraphQL: клиент одним запросом к одному адресу описывает, какие поля ему нужны, и получает ровно их. REST проще и лучше кешируется, GraphQL удобнее, когда экранам нужны данные из многих ресурсов сразу.
