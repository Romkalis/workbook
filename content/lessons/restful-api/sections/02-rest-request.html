Анатомия запроса

На слайдах лекции запрос состоит из четырёх частей: адрес (endpoint), метод, заголовки и данные. Подробно HTTP разобран в уроке «Клиент-серверное взаимодействие», здесь — то, что важно именно для REST.

Адрес (endpoint)

https://domain.com/user/1/articles?page=3&published=true
└──────┬─────────┘└──────┬───────┘└──────────┬──────────┘
   домен (+ порт)       путь           строка запроса

Путь указывает ресурс: «статьи пользователя 1». Строка запроса после ? уточняет выборку: третья страница, только опубликованные. Пары разделяются &. Порт по умолчанию — 443 для HTTPS и 80 для HTTP; при локальной разработке его пишут явно: localhost:3000.

Задача 1. Разобрать адрес на части ★☆☆ разминка

Напишите parseEndpoint(url), которая возвращает { origin, segments, query }. Для https://domain.com/user/1/articles?page=3&published=true получится origin: "https://domain.com", segments: ["user", "1", "articles"], query: { page: "3", published: "true" }. Разбирайте встроенным классом URL, без регулярных выражений.

Зачем: адрес — это структура, а не строка. Ручной разбор через split("?") ломается на кодированных символах (%20), на # и на портах. URL есть и в браузере, и в Node, и уже знает все эти правила.

Решение и разбор
export function parseEndpoint(url: string) {
  const u = new URL(url);
  return {
    origin: u.origin,
    segments: u.pathname.split('/').filter(Boolean),
    query: Object.fromEntries(u.searchParams),
  };
}

searchParams сам декодирует значения: ?q=%D1%82%D1%81 превратится в "тс". Обратите внимание, что все значения — строки: page равно "3", а не 3. Привести их к нужному типу и проверить — работа сервера, этим займётся задача про параметры списка ниже. filter(Boolean) убирает пустые части от ведущего и конечного слеша.

Методы и CRUD

Почти любое действие с данными сводится к четырём операциям — CRUD: Create, Read, Update, Delete. В REST каждой соответствует метод HTTP:

ОперацияМетодПримерУспешный ответ
Read — прочитать списокGETGET /employees200 + массив
Read — прочитать одинGETGET /employees/2200 или 404
Create — создатьPOSTPOST /employees + JSON201 + созданный объект
Update — заменитьPUTPUT /employees/2 + полный объект200
Update — изменить частьPATCHPATCH /employees/2 + изменённые поля200
Delete — удалитьDELETEDELETE /employees/2200 или 204

Лектор признаётся, что «особой разницы между PUT и PATCH не видит», и тут же на демо показывает её: PUT с телом {"role": "developer"} стёр все остальные поля пользователя. Проверено на json-server: после PUT /employees/1 с {"role":"lead"} от записи осталось только {"role":"lead","id":"1"}, а PATCH /employees/2 с {"salary":3000} поменял только зарплату. PUT — замена ресурса целиком, PATCH — частичное изменение.

Важное свойство — идемпотентность: повтор запроса даёт тот же итог. GET, PUT и DELETE идемпотентны (удалить уже удалённое — всё равно «удалено»), POST нет: три одинаковых POST создадут три записи. Поэтому при обрыве связи повторить PUT безопасно, а POST — нет.

Задача 2. CRUD в памяти: как отвечает json-server ★★☆ практика

Без Express и без сети напишите функцию handle(method, path, body?) для ресурса /employees, которая возвращает { status, body }. Поведение — как в таблице раздела: список, один элемент, создание (новый id, ответ 201), полная замена PUT, частичная PATCH, удаление (204 без тела). Неизвестный id — 404. Хранилище — Map, который передаётся в createHandler(store).

Зачем: если отделить логику ресурса от HTTP-обвязки, её можно проверить обычными тестами за миллисекунды. Заодно в одном месте видно, чем PUT отличается от PATCH и какой код ответа у каждой операции.

Подсказка

Путь разбейте на сегменты: ["employees"] — коллекция, ["employees", "2"] — один элемент. При PUT сохраните id из адреса, даже если в теле пришёл другой.

Решение и разбор
export interface Employee {
  id: string;
  name: string;
  role: string;
}
type Body = Omit<Employee, 'id'>;
export interface Reply {
  status: number;
  body?: unknown;
}

export function createHandler(store: Map<string, Employee>) {
  let nextId = store.size + 1;
  return function handle(method: string, path: string, body?: Partial<Body>): Reply {
    const [resource, id, ...rest] = path.split('/').filter(Boolean);
    if (resource !== 'employees' || rest.length > 0) return { status: 404 };

    if (id === undefined) {
      if (method === 'GET') return { status: 200, body: [...store.values()] };
      if (method === 'POST') {
        const created: Employee = { name: '', role: '', ...body, id: String(nextId++) };
        store.set(created.id, created);
        return { status: 201, body: created };
      }
      return { status: 405 };
    }

    const current = store.get(id);
    if (!current) return { status: 404 };
    switch (method) {
      case 'GET':
        return { status: 200, body: current };
      case 'PUT': {
        const replaced: Employee = { name: '', role: '', ...body, id };
        store.set(id, replaced);
        return { status: 200, body: replaced };
      }
      case 'PATCH': {
        const patched: Employee = { ...current, ...body, id };
        store.set(id, patched);
        return { status: 200, body: patched };
      }
      case 'DELETE':
        store.delete(id);
        return { status: 204 };
      default:
        return { status: 405 };
    }
  };
}

Главная разница PUT и PATCH видна в двух строках. PUT строит объект заново из тела: чего нет в теле, того не будет. PATCH берёт текущий объект и накладывает изменения. id всегда берётся из адреса: ресурс определяется путём, а не телом, иначе клиент мог бы «переименовать» запись. 405 Method Not Allowed — честный ответ на DELETE /employees: адрес существует, но такое действие с ним запрещено. Проверки полей здесь намеренно нет, она появится в последней задаче.

Задача 3. Тест на идемпотентность ★★☆ практика

Возьмите createHandler из прошлой задачи и напишите тесты, которые проверяют определение из раздела: повтор PUT и DELETE оставляет данные в том же состоянии, а повтор POST создаёт вторую запись. Сравнивайте состояние хранилища, а не ответы: второй DELETE вернёт 404, и это нормально.

// handler.ts
export interface Employee { id: string; name: string; role: string }
export function createHandler(store: Map<string, Employee>) {
  let nextId = store.size + 1;
  return function handle(method: string, path: string, body?: Partial<Omit<Employee, 'id'>>): { status: number; body?: unknown } {
    const [, id] = path.split('/').filter(Boolean);
    if (id === undefined && method === 'POST') { const c = { name: '', role: '', ...body, id: String(nextId++) }; store.set(c.id, c); return { status: 201, body: c }; }
    if (id === undefined) return { status: 200, body: [...store.values()] };
    if (!store.has(id)) return { status: 404 };
    if (method === 'PUT') { const r = { name: '', role: '', ...body, id }; store.set(id, r); return { status: 200, body: r }; }
    if (method === 'DELETE') { store.delete(id); return { status: 204 }; }
    return { status: 200, body: store.get(id) };
  };
}

Зачем: идемпотентность — это про итоговое состояние сервера, а не про одинаковые ответы. На этом свойстве держатся повторы запросов при обрыве связи: клиент может спокойно повторить PUT, но повтор POST создаст дубль заказа.

Решение и разбор
// idempotent.test.ts
import { expect, it } from 'vitest';
import { createHandler, type Employee } from './handler.js';

const setup = () => {
  const store = new Map<string, Employee>([['1', { id: '1', name: 'Аня', role: 'dev' }]]);
  return { store, handle: createHandler(store) };
};
const snapshot = (store: Map<string, Employee>) => structuredClone([...store.entries()]);

it('PUT идемпотентен', () => {
  const { store, handle } = setup();
  handle('PUT', '/employees/1', { name: 'Анна', role: 'lead' });
  const once = snapshot(store);
  handle('PUT', '/employees/1', { name: 'Анна', role: 'lead' });
  expect(snapshot(store)).toEqual(once);
});

it('DELETE идемпотентен по состоянию', () => {
  const { store, handle } = setup();
  handle('DELETE', '/employees/1');
  const once = snapshot(store);
  const second = handle('DELETE', '/employees/1');
  expect(snapshot(store)).toEqual(once);
  expect(second.status).toBe(404);
});

it('POST не идемпотентен', () => {
  const { store, handle } = setup();
  handle('POST', '/employees', { name: 'Вася', role: 'dev' });
  handle('POST', '/employees', { name: 'Вася', role: 'dev' });
  expect(store.size).toBe(3);
});

structuredClone делает глубокую копию: без неё «снимок» указывал бы на те же объекты, и сравнение было бы бессмысленным. Второй DELETE отвечает 404, но данные те же. Поэтому тест сравнивает хранилище, а статус проверяет отдельно, чтобы зафиксировать и это поведение. Мутант ниже «добавляет» сотрудника при PUT вместо замены. Тест его ловит, хотя код ответа остаётся 200.

Заголовки

Самые важные для REST — Content-Type (в каком формате тело запроса или ответа) и Accept (какой формат клиент хочет получить). Лектор подчёркивает: Postman ставит Content-Type: application/json сам, а в своём коде его нужно указывать, иначе сервер может неправильно понять данные. Проверка на json-server 0.17: POST с JSON в теле, но с Content-Type: text/plain, вернул 201, а запись создалась пустой — только с id. Сервер молча проигнорировал тело. Версия 1.0 в той же ситуации разобрала JSON — на это нельзя полагаться с другими серверами.

Ещё заголовки со слайдов: Access-Control-* (CORS), Cache-Control, Set-Cookie, Authorization для токена (урок «JWT-авторизация»).

Задача 4. Заголовки только там, где нужны ★☆☆ разминка

Напишите buildInit(method, body?), которая собирает объект настроек для fetch. Accept: application/json ставится всегда. Content-Type и body — только если тело передано, и тогда тело превращается в JSON.

Зачем: Content-Type описывает тело запроса. У GET тела нет, и заголовок там вводит в заблуждение. Хуже того, в браузере он делает запрос «непростым» и вызывает лишний предварительный запрос CORS. А Accept говорит, какой ответ клиент готов прочитать.

Решение и разбор
export function buildInit(method: string, body?: unknown): RequestInit {
  const headers: Record<string, string> = { Accept: 'application/json' };
  if (body === undefined) return { method, headers };
  headers['Content-Type'] = 'application/json';
  return { method, headers, body: JSON.stringify(body) };
}

Проверка именно === undefined: тело null или 0 — допустимый JSON, его надо отправить. Про «предварительный запрос»: браузер перед запросом на другой адрес с Content-Type: application/json сначала спрашивает сервер методом OPTIONS, можно ли. Подробнее — в уроке «Клиент и сервер» (из общих знаний: правила CORS).

Данные в JSON

{
  "name": "John Doe",
  "age": 33,
  "active": true,
  "city": null
}

Правила JSON из лекции: ключи и строки — только в двойных кавычках, числа, true, false и null пишутся как есть, после последнего элемента запятая не ставится. Чего в JSON нет: undefined, функций, NaN, дат. Проверка: JSON.stringify({ a: undefined, b: null, c: NaN, d: () => 1, e: new Date(0) }) дало {"b":null,"c":null,"e":"1970-01-01T00:00:00.000Z"} — undefined и функция исчезли, NaN стал null, дата превратилась в строку.

Задача 5. Что теряется в JSON ★★☆ практика

Заказ содержит дату (Date), набор тегов (Set) и необязательный комментарий. Узнайте, что с ними сделает JSON.stringify, и напишите пару функций: toWire(order) → объект, который переживёт JSON без потерь, и fromWire(raw) → обратно Order. Проверьте полный круг fromWire(JSON.parse(JSON.stringify(toWire(o)))).

export interface Order {
  id: string;
  createdAt: Date;
  tags: Set<string>;
  comment?: string;
}

Зачем: JSON знает только строки, числа, булевы значения, null, массивы и объекты. Date молча станет строкой, Set — пустым объектом {}, а undefined исчезнет. Ошибки не будет, данные просто испортятся.

Решение и разбор
export interface Order {
  id: string;
  createdAt: Date;
  tags: Set<string>;
  comment?: string;
}
export interface WireOrder {
  id: string;
  createdAt: string;
  tags: string[];
  comment: string | null;
}

export function toWire(o: Order): WireOrder {
  return { id: o.id, createdAt: o.createdAt.toISOString(), tags: [...o.tags], comment: o.comment ?? null };
}

export function fromWire(w: WireOrder): Order {
  const order: Order = { id: w.id, createdAt: new Date(w.createdAt), tags: new Set(w.tags) };
  if (w.comment !== null) order.comment = w.comment;
  return order;
}

Два типа — «как в программе» и «как в сети» — это нормальная практика: формат передачи описан явно и не зависит от того, какие классы удобны внутри. Дату передают строкой ISO 8601 (2026-11-19T08:00:00.000Z): она однозначна, содержит часовой пояс и сортируется как строка. Отсутствующий комментарий стал null: так клиент видит поле в ответе и знает, что оно пустое, а не забыто.

Коды ответов

Статья tutsplus (на русском) выделяет главные: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 500 Internal Server Error. Хороший REST-API отвечает точным кодом и понятным сообщением в теле. Полный разбор — в разделе «Коды состояния».

Задача 6. Какой код ответа ★☆☆ разминка

Напишите statusFor(outcome) для исходов операции: "ok", "created", "deleted", "invalid", "no-token", "not-allowed", "not-found", "duplicate", "crash". Используйте Record, чтобы новый исход нельзя было забыть.

Зачем: код ответа — первое, что читает клиент. По нему он решает, показать ошибку поля, отправить на страницу входа или повторить запрос. Перепутанные 401 и 403 приводят к выходу из аккаунта вместо сообщения «нет прав».

Решение и разбор
export type Outcome = 'ok' | 'created' | 'deleted' | 'invalid' | 'no-token' | 'not-allowed' | 'not-found' | 'duplicate' | 'crash';

const CODES: Record<Outcome, number> = {
  ok: 200,
  created: 201,
  deleted: 204,
  invalid: 400,
  'no-token': 401,
  'not-allowed': 403,
  'not-found': 404,
  duplicate: 409,
  crash: 500,
};

export const statusFor = (outcome: Outcome): number => CODES[outcome];

401 Unauthorized, несмотря на название, означает «не знаю, кто вы»: токена нет или он просрочен. Лечится входом. 403 Forbidden — «знаю, кто вы, но нельзя». Повторный вход не поможет. 409 Conflict — запрос корректен, но противоречит текущему состоянию, например email уже занят. Коды 4xx — ошибка клиента, повторять тот же запрос бессмысленно. Коды 5xx — ошибка сервера, повтор может помочь.
