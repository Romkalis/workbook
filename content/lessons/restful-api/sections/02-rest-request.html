Анатомия запроса

На слайдах лекции запрос состоит из четырёх частей: адрес (endpoint), метод, заголовки и данные. Подробно HTTP разобран в уроке «Клиент-серверное взаимодействие», здесь — то, что важно именно для REST.

Адрес (endpoint)

https://domain.com/user/1/articles?page=3&published=true
└──────┬─────────┘└──────┬───────┘└──────────┬──────────┘
   домен (+ порт)       путь           строка запроса

Путь указывает ресурс: «статьи пользователя 1». Строка запроса после ? уточняет выборку: третья страница, только опубликованные. Пары разделяются &. Порт по умолчанию — 443 для HTTPS и 80 для HTTP; при локальной разработке его пишут явно: localhost:3000.

Методы и CRUD

Почти любое действие с данными сводится к четырём операциям — CRUD: Create, Read, Update, Delete. В REST каждой соответствует метод HTTP:

ОперацияМетодПримерУспешный ответ
Read — прочитать списокGETGET /employees200 + массив
Read — прочитать одинGETGET /employees/2200 или 404
Create — создатьPOSTPOST /employees + JSON201 + созданный объект
Update — заменитьPUTPUT /employees/2 + полный объект200
Update — изменить частьPATCHPATCH /employees/2 + изменённые поля200
Delete — удалитьDELETEDELETE /employees/2200 или 204

Лектор признаётся, что «особой разницы между PUT и PATCH не видит», и тут же на демо показывает её: PUT с телом {"role": "developer"} стёр все остальные поля пользователя. Проверено на json-server: после PUT /employees/1 с {"role":"lead"} от записи осталось только {"role":"lead","id":"1"}, а PATCH /employees/2 с {"salary":3000} поменял только зарплату. PUT — замена ресурса целиком, PATCH — частичное изменение.

Важное свойство — идемпотентность: повтор запроса даёт тот же итог. GET, PUT и DELETE идемпотентны (удалить уже удалённое — всё равно «удалено»), POST нет: три одинаковых POST создадут три записи. Поэтому при обрыве связи повторить PUT безопасно, а POST — нет.

Заголовки

Самые важные для REST — Content-Type (в каком формате тело запроса или ответа) и Accept (какой формат клиент хочет получить). Лектор подчёркивает: Postman ставит Content-Type: application/json сам, а в своём коде его нужно указывать, иначе сервер может неправильно понять данные. Проверка на json-server 0.17: POST с JSON в теле, но с Content-Type: text/plain, вернул 201, а запись создалась пустой — только с id. Сервер молча проигнорировал тело. Версия 1.0 в той же ситуации разобрала JSON — на это нельзя полагаться с другими серверами.

Ещё заголовки со слайдов: Access-Control-* (CORS), Cache-Control, Set-Cookie, Authorization для токена (урок «JWT-авторизация»).

Данные в JSON

{
  "name": "John Doe",
  "age": 33,
  "active": true,
  "city": null
}

Правила JSON из лекции: ключи и строки — только в двойных кавычках, числа, true, false и null пишутся как есть, после последнего элемента запятая не ставится. Чего в JSON нет: undefined, функций, NaN, дат. Проверка: JSON.stringify({ a: undefined, b: null, c: NaN, d: () => 1, e: new Date(0) }) дало {"b":null,"c":null,"e":"1970-01-01T00:00:00.000Z"} — undefined и функция исчезли, NaN стал null, дата превратилась в строку.

Коды ответов

Статья tutsplus (на русском) выделяет главные: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 500 Internal Server Error. Хороший REST-API отвечает точным кодом и понятным сообщением в теле. Полный разбор — в разделе «Коды состояния».
