Клиент для REST-API на fetch

Во второй половине лекции методы API пишутся в коде. Хорошая практика, которую показывает лектор: собрать все обращения к серверу в отдельный модуль (часто api.js), а в остальном коде импортировать готовые функции. Тогда базовый адрес, заголовки и обработка ошибок живут в одном месте. Версия ниже доработана: добавлена проверка статуса, которой в лекции нет (без неё fetch не заметит 404, урок «Клиент-серверное взаимодействие»).

const BASE_URL = 'http://localhost:3000';
const EMPLOYEES = `${BASE_URL}/employees`;

async function request(url, options = {}) {
  const response = await fetch(url, {
    ...options,
    headers: { 'Content-Type': 'application/json', ...options.headers },
  });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.status === 204 ? null : response.json();
}

export const getEmployees = (params = {}) =>
  request(`${EMPLOYEES}?${new URLSearchParams(params)}`);
export const getEmployee = (id) => request(`${EMPLOYEES}/${id}`);
export const createEmployee = (data) =>
  request(EMPLOYEES, { method: 'POST', body: JSON.stringify(data) });
export const updateEmployee = (id, patch) =>
  request(`${EMPLOYEES}/${id}`, { method: 'PATCH', body: JSON.stringify(patch) });
export const deleteEmployee = (id) => request(`${EMPLOYEES}/${id}`, { method: 'DELETE' });
  • URLSearchParams собирает строку запроса из объекта и кодирует спецсимволы: { role: 'developer' } → role=developer. Лектор собирает её вручную через map и join('&') — это работает, но забывает про кодирование пробелов и кириллицы.
  • Тело запроса — строка: объект превращают в JSON через JSON.stringify. Лектор на демо забыл это и получил ошибку — частая ошибка новичков.
  • Ответ 204 не имеет тела, и response.json() на нём упал бы, поэтому для него возвращаем null.

Модуль запущен в Node.js 22 против обеих версий json-server. getEmployees({ role: 'developer' }) вернул Аню и Петю; createEmployee создал запись со строковым id; updateEmployee поменял роль; после deleteEmployee запрос этой записи бросил HTTP 404.

Пагинация с общим числом записей

Чтобы нарисовать кнопки страниц, нужно знать, сколько их. В json-server 0.x число записей приходит в заголовке X-Total-Count. Лектор показывает, что console.log(response.headers) выводит пустой с виду объект: заголовки читают методом get, а значение всегда строка.

// json-server 0.16–0.17
async function getPage(page, limit) {
  const response = await fetch(`${EMPLOYEES}?${new URLSearchParams({ _page: page, _limit: limit })}`);
  const total = Number(response.headers.get('X-Total-Count'));
  return { items: await response.json(), total, pages: Math.ceil(total / limit) };
}
// getPage(2, 3) → { items: [Оля], total: 4, pages: 2 }

// json-server 1.0: всё в теле ответа
const page = await getEmployees({ _page: 2, _per_page: 3 });
// page.pages = 2, page.items = 4, page.data = [Оля]

Если фронтенд и json-server работают на разных портах, браузеру понадобятся заголовки CORS. json-server отдаёт их сам, поэтому учебные запросы с localhost:5173 на localhost:3000 проходят. Чужой заголовок вроде X-Total-Count браузер даёт прочитать только если сервер перечислил его в Access-Control-Expose-Headers — json-server 0.17 делает и это: проверка запросом с заголовком Origin показала Access-Control-Expose-Headers: X-Total-Count, Link. Версия 1.0 отвечает Access-Control-Allow-Origin: *, а число записей отдаёт в теле, так что заголовок ей не нужен (раздел «Заголовки CORS»).
