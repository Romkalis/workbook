Задача 14. Свой ресурс на Express вместо json-server ★★★ с подвохом

Соберите на Express то, что json-server делал сам, для /api/employees: список, один, создание, PATCH, удаление. Требования:

  • POST проверяет тело (name — непустая строка, salary — неотрицательное целое) и отвечает 400 с текстом ошибки;
  • успешный POST — 201, созданный объект и заголовок Location: /api/employees/<id>;
  • DELETE — 204 без тела; повторный DELETE — 404;
  • все ошибки — JSON вида { "message": "…" }.

Зачем: json-server удобен, пока не нужны правила: он сохранит сотрудника с зарплатой "много". Своя реализация показывает, какую работу на самом деле делает бэкенд. Дальше по этой же схеме строится проект в уроке Express + TypeScript.

Решение и разбор
// app.ts
import express, { type Request, type Response } from 'express';

interface Employee {
  id: string;
  name: string;
  salary: number;
}
type Input = Omit<Employee, 'id'>;

function parseInput(body: unknown, partial: boolean): Partial<Input> | string {
  if (typeof body !== 'object' || body === null) return 'Тело должно быть объектом';
  const out: Partial<Input> = {};
  if ('name' in body) {
    if (typeof body.name !== 'string' || body.name.trim() === '') return 'name: непустая строка';
    out.name = body.name.trim();
  } else if (!partial) return 'name: обязательное поле';
  if ('salary' in body) {
    if (!Number.isInteger(body.salary) || (body.salary as number) < 0) return 'salary: неотрицательное целое';
    out.salary = body.salary as number;
  } else if (!partial) return 'salary: обязательное поле';
  return out;
}

export function createApp() {
  const store = new Map<string, Employee>();
  let nextId = 1;
  const app = express();
  app.use(express.json());
  const notFound = (res: Response) => res.status(404).json({ message: 'Сотрудник не найден' });

  app.get('/api/employees', (_req, res) => {
    res.json([...store.values()]);
  });
  app.get('/api/employees/:id', (req: Request<{ id: string }>, res) => {
    const e = store.get(req.params.id);
    return e ? res.json(e) : notFound(res);
  });
  app.post('/api/employees', (req, res) => {
    const input = parseInput(req.body, false);
    if (typeof input === 'string') return res.status(400).json({ message: input });
    const created = { ...(input as Input), id: String(nextId++) };
    store.set(created.id, created);
    res.status(201).location(`/api/employees/${created.id}`).json(created);
  });
  app.patch('/api/employees/:id', (req: Request<{ id: string }>, res) => {
    const current = store.get(req.params.id);
    if (!current) return notFound(res);
    const input = parseInput(req.body, true);
    if (typeof input === 'string') return res.status(400).json({ message: input });
    const updated = { ...current, ...input };
    store.set(current.id, updated);
    res.json(updated);
  });
  app.delete('/api/employees/:id', (req: Request<{ id: string }>, res) => {
    if (!store.delete(req.params.id)) return notFound(res);
    res.status(204).end();
  });
  return app;
}

Одна функция проверки обслуживает и POST, и PATCH. Отличается только флаг «обязательны ли поля»: для PATCH отсутствие поля нормально. Map.delete возвращает true, если элемент был, и это сразу даёт ветку 404. Заголовок Location говорит клиенту, где теперь живёт созданный ресурс. Это часть смысла кода 201. Хранилище создаётся внутри createApp, поэтому каждый тест получает чистые данные. Ручная проверка здесь громоздкая. В уроке Zod она заменяется схемой в несколько строк.

Вопросы

Чем REST отличается от HTTP?

HTTP — протокол передачи. REST — архитектурный стиль, набор правил, как проектировать API поверх HTTP: ресурсы с адресами, действия через методы, отсутствие состояния на сервере.

Почему /deleteUser?id=5 — плохой адрес?

Действие выражено в адресе, а не методом, и для удаления используется GET, который не должен менять данные. Правильно: DELETE /users/5.

Почему повторить POST опаснее, чем PUT?

POST не идемпотентен: повтор создаст ещё одну запись. PUT заменяет ресурс тем же содержимым, повтор ничего не меняет.

Когда нужно повышать версию API?

При ломающих изменениях: изменился формат ответа или тип поля, удалена часть API. Новые поля и адреса добавляют без смены версии.
