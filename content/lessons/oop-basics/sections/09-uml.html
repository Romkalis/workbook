Начните с одного прямоугольника класса: имя, поля, методы. Затем прочитайте подпись у линии и найдите её конец: треугольник направлен к родителю или интерфейсу, ромб стоит у целого. Не пытайтесь выучить все диаграммы сразу — для примеров этого урока важнее диаграмма классов.

UML (Unified Modeling Language) это стандартный графический язык для описания устройства программ. Им рисуют схемы до написания кода, чтобы обсудить дизайн, и после, чтобы объяснить уже существующий. UML не язык программирования и не требует строгого следования: чаще всего рисуют только то, что помогает общению. Схема отвечает на вопрос «из чего это состоит и как части связаны», а не «как это работает по строкам».

Виды диаграмм

Для знакомства удобно выделить три группы; при этом диаграммы взаимодействия относятся к поведенческим: структура (из чего система состоит), поведение (что она делает) и взаимодействие (кто с кем и в каком порядке общается).

Для первого этапа самая нужная это диаграмма классов: она напрямую отражает ООП. Вторая по полезности, пожалуй, диаграмма последовательности.

Диаграмма классов: как читать

Что можно показать внутри класса

Класс это прямоугольник. Обычно в нём три отсека, но подробность зависит от задачи: можно нарисовать только имя, а можно всё. Пустой отсек не значит, что членов нет: класс просто могли не расписывать. Многоточие ... в конце списка говорит, что есть и другие члены.

Не путайте #

В UML # означает защищённый (виден классу и потомкам). В JavaScript #name это приватное поле, потомкам оно тоже недоступно. Защищённых членов в языке нет, их заменяет договорённость вроде _name. Переводя схему в код, - превращайте в #name, а # в _name с комментарием.

Связи между классами

Классы редко живут поодиночке. Связи показывают, как они друг с другом соотносятся. Вот шесть распространённых видов связей. Это разные отношения, а не универсальная шкала от «сильной» связи к «слабой».

РеализацияКласс выполняет контракт интерфейса.Пунктир с пустым треугольником у интерфейса.Circle → Shape

Что скрывается за каждой связью

  • Наследование. Класс без родителей называют корневым (базовым), без потомков листовым. Один родитель это одиночное наследование, несколько множественное. В JavaScript разрешено только одиночное, множественное заменяют примесями (mixin).
  • Реализация. Это что-то среднее между наследованием и зависимостью: класс не получает код, а обещает набор операций. В JavaScript интерфейсов нет, их роль играют договорённости и утиная типизация (в TypeScript есть interface).
  • Композиция против агрегации. Проверочный вопрос: «если удалить целое, части исчезнут?». Двигатель, спроектированный только для этой машины, исчезнет вместе с ней, это композиция. Игрок, из которого собрана команда, переживёт её расформирование, это агрегация. На практике разница тонкая, и многие обходятся простой ассоциацией, когда сомневаются.
  • Ассоциация. У неё три уточнения. Имя (глагол над линией, например «посещает», иногда с треугольником направления чтения). Роль: как называется участник на своём конце (преподаватель, студент). Кратность: сколько объектов с одной стороны приходится на один объект с другой.
  • Зависимость. Самая слабая связь и самая частая: класс упомянут в параметрах метода или создаётся внутри него. Её можно подписать именем или стереотипом.

Кратность

Кратность записывают у конца связи. Читать надо «сколько объектов на этом конце приходится на один объект на другом».

ЗаписьЗначит
1Ровно один.
0..1Ни одного или один (необязательный).
0..* или *Сколько угодно, включая ноль.
1..*Минимум один, верхней границы нет.
3Ровно три.
0..1, 3..4, 6..*Список диапазонов: допустимо любое значение из перечисленных.

Пример чтения: между Customer и Order стоит 1 у клиента и 0..* у заказа. Значит, у заказа ровно один клиент, а у клиента может быть сколько угодно заказов, в том числе ни одного.

Как схема превращается в код

Каждая связь имеет привычное выражение в JavaScript. Это не строгое правило, а типичные шаблоны, но на практических заданиях их достаточно.

// Наследование: Manager ──▷ Employee
class Employee { constructor(name) { this.name = name; } }
class Manager extends Employee {}

// Композиция: Car ◆── Engine
// Двигатель создаётся самим автомобилем и снаружи не нужен
class Car {
  #engine = new Engine();
  start() { this.#engine.run(); }
}

// Агрегация: Team ◇── Person
// Люди существуют сами по себе, команда лишь получает их
class Team {
  #members = [];
  add(person) { this.#members.push(person); }
}

// Ассоциация: Student ── Course (0..*)
class Student {
  courses = [];                       // кратность 0..*
  enroll(course) { this.courses.push(course); }
}

// Зависимость: Report ⇢ Printer
// Принтер нужен только на время вызова
class Report {
  print(printer) { printer.print(this); }
}

// Реализация: Circle ┄▷ Shape
// В JS контракт держится на соглашении, а не на ключевом слове
class Shape {
  area() { throw new Error('не реализовано'); }
}
class Circle extends Shape {
  constructor(r) { super(); this.r = r; }
  area() { return Math.PI * this.r ** 2; }
}

Главное отличие композиции от агрегации видно в коде: композитный объект сам создаёт часть (new Engine() внутри класса), а агрегатор получает уже существующие объекты снаружи (add(person)).

Расширения: стереотипы, значения, ограничения, заметки

Расширения нужны, чтобы подстроить язык под предметную область.

  • Стереотип создаёт новый вид элемента: «interface», «enumeration», или класс-исключение «exception» для Overflow.
  • Помеченное значение добавляет свойство элемента: у класса EventQueue можно записать {version = 3.2, author = "Ира"}.
  • Ограничение добавляет или меняет правило, записанное в фигурных скобках: например, элементы в очередь добавляются по порядку, {ordered}.
  • Заметка это прямоугольник с загнутым углом, прикреплённый пунктиром к элементу. В ней пишут комментарий или условие.

Как рисовать хорошую диаграмму классов

Правила из руководства по UML, которые полезно держать в голове при подготовке к практике и собеседованию:

  • Каждый класс должен соответствовать понятию из задачи или из решения. Не рисуйте классы «на всякий случай».
  • Показывайте только те свойства, которые нужны для понимания схемы в этом контексте. Остальное опускайте.
  • Длинные списки атрибутов и операций группируйте по смыслу (можно стереотипами).
  • Связанные классы держите на одной диаграмме, а большую систему делите на несколько.
  • Обязанности распределяйте равномерно: класс, который делает всё, и класс, который не делает ничего, сигналят о плохом дизайне.
  • Избегайте пересекающихся линий и произвольной раскладки: схему должно быть легко прочесть.

Две диаграммы поведения коротко

Диаграмма последовательности. Участники стоят в ряд сверху, от каждого вниз идёт пунктирная «линия жизни». Стрелки между линиями это сообщения (вызовы методов) в порядке сверху вниз. Сплошная стрелка запрос, пунктирная ответ. Узкий прямоугольник на линии показывает, что объект сейчас занят обработкой. Такая диаграмма хороша, чтобы показать один сценарий: «клиент нажал Оплатить → корзина → платёжный сервис → банк».

Диаграмма прецедентов (use case). Человечки (акторы) снаружи, овалы (сценарии использования) внутри прямоугольника системы, линии показывают, кто что делает. Она описывает систему глазами пользователя и ничего не говорит про классы.
