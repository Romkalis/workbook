Шаг 2. Как работать по TDD в этом задании

Для каждой из пяти обязательных функций в истории должны быть два соседних коммита. Проверяющий открывает вкладку Commits и смотрит, что тест появился раньше реализации и что в «красном» коммите тесты действительно падают.

Заглушка нужна, чтобы тесты падали по делу, на проверке значения, а не из-за того, что нечего импортировать. Падение на «модуль не найден» тоже падение, но заглушка нагляднее для проверяющего:

// src/game.ts — красный коммит
export const createDigitValidator =
  (_base: number) =>
  (_char: string): boolean => {
    throw new Error('Not implemented');
  };

Перед коммитом обязательно запустите npm test и убедитесь, что тесты красные. Затем:

git add src/game.ts src/game.test.ts
git commit -m "test: add failing tests for createDigitValidator"
# пишем реализацию, npm test зелёный
git commit -am "feat: implement createDigitValidator"
git push -u origin bulls-and-cows

Тесты по FIRST

Подробнее о принципах — в разделе FIRST урока о тестировании, о цикле — в разделе TDD.

  • Fast. Чистые функции проверяются за миллисекунды, никакого DOM и таймеров.
  • Independent. Тесты не делят состояние: каждый создаёт свои данные сам, порядок запуска не важен.
  • Repeatable. Никакого настоящего Math.random и Date.now в проверках. Случайность и время передаются параметром.
  • Self-validating. Результат — expect, а не console.log, который надо читать глазами.
  • Timely. Тесты написаны до кода. Это видно по коммитам.

Порядок функций я выбрал от простой к сложной и так, чтобы следующая могла опираться на предыдущую: isValidGuess использует createDigitValidator. Исправить уже отправленную историю можно только через rebase и push --force, лучше до этого не доводить.
