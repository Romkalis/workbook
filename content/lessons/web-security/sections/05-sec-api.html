Задача 5. Чужой заказ по номеру ★★☆ практика

Маршрут GET /api/orders/:id отдаёт заказ по номеру. Пользователь уже определён middleware и лежит в res.locals.userId (в задаче его ставит заглушка по заголовку X-User). Сделайте так, чтобы чужой заказ был неотличим от несуществующего: в обоих случаях 404. Администратор (role: "admin") видит все заказы.

Зачем: это первое место в OWASP API Top 10. Аутентификация есть, токен проверен, а заказ 1053 отдаётся кому угодно, кто поменял число в адресе. Проверка владельца должна стоять в каждом маршруте, который работает с объектом по id.

Решение и разбор
// app.ts
import express, { type Request } from 'express';

export interface Order {
  id: string;
  ownerId: string;
  total: number;
}
export interface User {
  id: string;
  role: 'user' | 'admin';
}

export function createApp(orders: Order[], users: User[]) {
  const app = express();
  app.use((req, res, next) => {
    res.locals.user = users.find((u) => u.id === req.header('X-User'));
    if (!res.locals.user) return res.status(401).json({ message: 'Нужен вход' });
    next();
  });
  app.get('/api/orders/:id', (req: Request<{ id: string }>, res) => {
    const user = res.locals.user as User;
    const order = orders.find((o) => o.id === req.params.id);
    const allowed = order && (order.ownerId === user.id || user.role === 'admin');
    if (!allowed) return res.status(404).json({ message: 'Заказ не найден' });
    res.json(order);
  });
  return app;
}

Почему 404, а не 403? Ответ 403 подтверждает, что заказ с таким номером существует, а это уже утечка: по ней можно оценить число заказов магазина. Для собственных объектов пользователя 404 честнее. Ещё надёжнее искать сразу с условием владельца: WHERE id = ? AND owner_id = ?. Тогда забыть проверку невозможно. Предсказуемые номера (1052, 1053) упрощают перебор, поэтому внешние id часто делают случайными (UUID), но это дополнение к проверке, а не замена.

Ограничение частоты запросов

Rate limiting защищает от перебора паролей, от ботов и от случайной перегрузки. Сервер считает запросы с одного ключа (IP, пользователь, токен) за окно времени и при превышении отвечает 429 Too Many Requests с заголовком Retry-After. Алгоритмы:

  • Фиксированное окно — счётчик на минуту; просто, но на границе окон можно сделать двойную пачку.
  • Скользящее окно — учитываются запросы за последние N секунд.
  • Token bucket («ведро жетонов») — ведро пополняется с постоянной скоростью, каждый запрос забирает жетон; разрешает короткие всплески, ограничивая среднюю скорость.

Для входа лимит строже, чем для чтения каталога: 5 попыток в минуту на аккаунт против сотен запросов на страницы.

Задача 6. Лимит: фиксированное окно ★★☆ практика

Напишите createFixedWindow({ limit, windowMs, now }) с методом hit(key), который возвращает { allowed: boolean; retryAfterMs: number }. В каждом окне длиной windowMs для одного ключа разрешено не больше limit запросов. Окно отсчитывается от первого запроса ключа.

Зачем: самый простой лимитер, и с него удобно начать: понятно, что считается, где хранится и когда сбрасывается. Его слабость — двойная пачка на стыке окон — станет мотивацией для следующей задачи.

Решение и разбор
export function createFixedWindow({ limit, windowMs, now = Date.now }: { limit: number; windowMs: number; now?: () => number }) {
  const windows = new Map<string, { start: number; count: number }>();
  return {
    hit(key: string): { allowed: boolean; retryAfterMs: number } {
      const t = now();
      let w = windows.get(key);
      if (!w || t - w.start >= windowMs) {
        w = { start: t, count: 0 };
        windows.set(key, w);
      }
      if (w.count < limit) {
        w.count++;
        return { allowed: true, retryAfterMs: 0 };
      }
      return { allowed: false, retryAfterMs: w.start + windowMs - t };
    },
  };
}

Отклонённый запрос не увеличивает счётчик: иначе настойчивый клиент сам продлевал бы себе блокировку, хотя срок окна от этого не меняется. Map в памяти работает, пока сервер один. Если серверов несколько, счётчики хранят в общем хранилище, обычно Redis (из общих знаний). Старые ключи здесь не удаляются. В рабочем коде их чистят по таймеру, иначе память растёт с каждым новым IP.

Задача 7. Лимит: ведро жетонов ★★★ с подвохом

Напишите createTokenBucket({ capacity, refillPerSec, now }) с методом take(key), возвращающим boolean. Новое ведро полное. Жетоны пополняются непрерывно (дробно) со скоростью refillPerSec, но не выше capacity. Таймеры не используйте: пополнение считается в момент запроса.

Зачем: ведро жетонов разрешает короткий всплеск (пользователь открыл страницу, и ушло десять запросов), но держит среднюю скорость. Ленивое пополнение «при запросе» — инженерный приём: миллион ключей не требует миллиона таймеров.

Решение и разбор
export function createTokenBucket({ capacity, refillPerSec, now = Date.now }: { capacity: number; refillPerSec: number; now?: () => number }) {
  const buckets = new Map<string, { tokens: number; updatedAt: number }>();
  return {
    take(key: string): boolean {
      const t = now();
      const b = buckets.get(key) ?? { tokens: capacity, updatedAt: t };
      b.tokens = Math.min(capacity, b.tokens + ((t - b.updatedAt) / 1000) * refillPerSec);
      b.updatedAt = t;
      buckets.set(key, b);
      if (b.tokens < 1) return false;
      b.tokens -= 1;
      return true;
    },
  };
}

Пополнение — это просто «сколько прошло времени × скорость», ограниченное сверху ёмкостью. Дробные жетоны важны: при скорости 2 в секунду через 250 мс накопится полжетона, и ещё через 250 мс запрос пройдёт. Если округлять, медленные клиенты никогда бы не получили жетон. Сравните с фиксированным окном: там на стыке окон можно сделать 2 × limit запросов подряд, а здесь всплеск не больше ёмкости ведра.

Задача 8. Middleware 429 для входа ★★☆ практика

Напишите middleware rateLimit(limiter, keyFn) для Express, где limiter.hit(key) — из задачи про фиксированное окно. При отказе ответ 429, заголовок Retry-After в секундах (округление вверх) и JSON { message }. Подключите к POST /api/login с ключом «IP + email»: 3 попытки за минуту.

// window.ts
export function createFixedWindow({ limit, windowMs, now = Date.now }: { limit: number; windowMs: number; now?: () => number }) {
  const w = new Map<string, { start: number; count: number }>();
  return { hit(key: string) { const t = now(); let x = w.get(key); if (!x || t - x.start >= windowMs) { x = { start: t, count: 0 }; w.set(key, x); }
    if (x.count < limit) { x.count++; return { allowed: true, retryAfterMs: 0 }; } return { allowed: false, retryAfterMs: x.start + windowMs - t }; } };
}

Зачем: перебор паролей — первая атака на любую форму входа. Ключ «IP + email» не даёт одному адресу перебирать пароль к одному аккаунту и при этом не блокирует весь офис за общим IP. Retry-After подсказывает честному клиенту, когда повторить.

Решение и разбор
// app.ts
import express, { type Request, type RequestHandler } from 'express';
import { createFixedWindow } from './window.js';

type Limiter = { hit(key: string): { allowed: boolean; retryAfterMs: number } };

export function rateLimit(limiter: Limiter, keyFn: (req: Request) => string): RequestHandler {
  return (req, res, next) => {
    const { allowed, retryAfterMs } = limiter.hit(keyFn(req));
    if (allowed) return next();
    res.set('Retry-After', String(Math.ceil(retryAfterMs / 1000)));
    res.status(429).json({ message: 'Слишком много попыток, попробуйте позже' });
  };
}

export function createApp(now?: () => number) {
  const app = express();
  app.use(express.json());
  const loginLimiter = createFixedWindow({ limit: 3, windowMs: 60_000, now });
  const byIpAndEmail = (req: Request) => `${req.ip}|${String(req.body?.email ?? '').toLowerCase()}`;
  app.post('/api/login', rateLimit(loginLimiter, byIpAndEmail), (_req, res) => {
    res.status(401).json({ message: 'Неверный email или пароль' });
  });
  return app;
}

Лимитер стоит до проверки пароля, поэтому заблокированные попытки не тратят дорогой bcrypt. Email приводится к нижнему регистру: иначе Anna@ и anna@ дали бы два счётчика. За прокси (nginx, облако) req.ip — адрес прокси. Express нужно сказать app.set('trust proxy', 1), иначе все пользователи окажутся под одним ключом (из общих знаний). В рабочих проектах берут готовый пакет express-rate-limit, но устроен он так же.

Безопасные ошибки

Ответ с ошибкой не должен раскрывать устройство системы: стек вызовов, текст SQL, версии библиотек, пути к файлам. Клиенту — общий текст и код, в логи — подробности с идентификатором запроса, чтобы найти их по жалобе. Сообщения входа одинаковые для «нет такого email» и «неверный пароль» (разбор — в задачах урока JWT).

Задача 9. Обработчик ошибок без утечек ★★☆ практика

Напишите обработчик ошибок Express (четыре параметра). Ошибка класса HttpError (со status и безопасным message) отдаётся как есть. Любая другая — 500 с текстом «Внутренняя ошибка» и requestId, а подробности (сообщение, стек) уходят в функцию log с тем же requestId. В ответе не должно быть стека и исходного текста ошибки.

Зачем: стек вызовов и текст вроде duplicate key in collection users рассказывают атакующему, какая у вас база, библиотеки и структура файлов (API8 в OWASP). А requestId позволяет по жалобе пользователя найти точную запись в логах.

Решение и разбор
// app.ts
import { randomUUID } from 'node:crypto';
import express, { type ErrorRequestHandler } from 'express';

export class HttpError extends Error {
  constructor(
    readonly status: number,
    message: string,
  ) {
    super(message);
  }
}

export function errorHandler(log: (entry: object) => void): ErrorRequestHandler {
  return (err, _req, res, _next) => {
    if (err instanceof HttpError) return res.status(err.status).json({ message: err.message });
    const requestId = randomUUID();
    log({ requestId, message: err instanceof Error ? err.message : String(err), stack: err instanceof Error ? err.stack : undefined });
    res.status(500).json({ message: 'Внутренняя ошибка', requestId });
  };
}

export function createApp(log: (entry: object) => void) {
  const app = express();
  app.get('/known', () => {
    throw new HttpError(404, 'Товар не найден');
  });
  app.get('/boom', async () => {
    throw new Error('duplicate key users.email_1 at /srv/app/db.js:42');
  });
  app.use(errorHandler(log));
  return app;
}

Express отличает обработчик ошибок по числу параметров, поэтому неиспользуемый _next обязателен. В Express 5 ошибка из async-обработчика сама попадает сюда. В Express 4 для этого нужна обёртка или next(err). Разделение «известная ошибка с безопасным текстом» и «всё остальное» — тот же подход, что в уроке Error handling: свои классы для ожидаемых ситуаций, общий ответ для непредвиденных.
