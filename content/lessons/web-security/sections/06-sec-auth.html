Способы аутентификации

Basic и Bearer

Basic — заголовок Authorization: Basic base64(логин:пароль). Base64 — не шифрование: пароль читается любым, кто видит запрос, и отправляется с каждым запросом. Допустим только по HTTPS и для служебных инструментов. Bearer — Authorization: Bearer <токен>: «кто предъявил — тот и владелец». Токен заменяет пароль, поэтому должен быть коротко живущим и передаваться только по HTTPS.

Задача 10. Разбор Basic-аутентификации ★★☆ практика

Напишите parseBasic(header): из "Basic YW5uYTpwOnc=" получается { user: "anna", pass: "p:w" }, для неверного заголовка — null. Двоеточие в пароле допустимо, в имени — нет. Строка в UTF-8. Затем checkBasic(header, expectedUser, expectedPass) со сравнением, не зависящим по времени от совпадающего префикса.

Зачем: разобрав Basic вручную, видишь главное: пароль в заголовке просто закодирован, и любой, кто видит трафик без HTTPS, читает его за секунду. Basic до сих пор используют для служебных панелей и вебхуков, поэтому разбирать его правильно полезно.

Решение и разбор
import { createHash, timingSafeEqual } from 'node:crypto';

export function parseBasic(header: string | undefined): { user: string; pass: string } | null {
  const match = /^Basic ([A-Za-z0-9+/=]+)$/.exec(header ?? '');
  if (!match) return null;
  const decoded = Buffer.from(match[1]!, 'base64').toString('utf8');
  const colon = decoded.indexOf(':');
  if (colon <= 0) return null;
  return { user: decoded.slice(0, colon), pass: decoded.slice(colon + 1) };
}

const digest = (s: string) => createHash('sha256').update(s).digest();

export function checkBasic(header: string | undefined, user: string, pass: string): boolean {
  const creds = parseBasic(header);
  if (!creds) return false;
  const userOk = timingSafeEqual(digest(creds.user), digest(user));
  const passOk = timingSafeEqual(digest(creds.pass), digest(pass));
  return userOk && passOk;
}

Делим по первому двоеточию: стандарт запрещает его в имени, а в пароле оно может быть. timingSafeEqual требует буферы одной длины. Сравнение хешей SHA-256 решает это и заодно не раскрывает длину пароля. Обе проверки выполняются всегда, без раннего выхода на неверном имени. Для паролей пользователей в базе нужен bcrypt. Здесь сравнивается служебный пароль из конфигурации, и быстрого хеша достаточно.

JWT

JSON Web Token — подписанный токен с данными (id, срок). Подпись гарантирует, что данные не подделаны, но не скрывает их. Устройство, выдача и проверка — в уроке JWT-авторизация.

OAuth 2.0

OAuth — протокол делегирования доступа: пользователь разрешает приложению действовать от его имени в другом сервисе, не отдавая пароль. Кнопка «Войти через GitHub» — это OAuth (точнее, OpenID Connect поверх него). Роли: владелец ресурса (пользователь), клиент (ваше приложение), сервер авторизации (страница входа GitHub), сервер ресурсов (API GitHub).

Основной поток — Authorization Code:

  1. Приложение отправляет пользователя на сервер авторизации с client_id, redirect_uri, нужными scope и случайным state.
  2. Пользователь входит и соглашается.
  3. Сервер возвращает его на redirect_uri с одноразовым code и тем же state.
  4. Приложение проверяет state (защита от CSRF) и меняет code на access-токен запросом с сервера.

Для приложений без бэкенда (SPA, мобильные) добавляется PKCE: клиент придумывает секрет code_verifier, отправляет в шаге 1 его хеш, а в шаге 4 — сам секрет. Перехваченный code без секрета бесполезен. Устаревший поток Implicit (токен сразу в адресе) больше не рекомендуется.

Задача 11. OAuth: state и PKCE ★★★ с подвохом

Напишите клиентскую часть Authorization Code с PKCE:

  • createPkce() → { verifier, challenge }: verifier — 32 случайных байта в base64url, challenge — base64url от SHA-256 этого verifier;
  • buildAuthorizeUrl({ authorizeUrl, clientId, redirectUri, scope, state, challenge }) с response_type=code и code_challenge_method=S256;
  • readCallback(url, expectedState) → code, или ошибка, если state не совпал или сервер вернул error.

Используйте Web Crypto (crypto.subtle): он есть и в браузере, и в Node.

Зачем: OAuth чаще всего ломают на клиенте: забытая проверка state (CSRF при входе) или отсутствие PKCE в SPA, где нет секрета клиента. Задача собирает поток из шагов раздела, а тест сверяет хеш с контрольным примером из RFC 7636.

Решение и разбор
const b64url = (bytes: Uint8Array) => Buffer.from(bytes).toString('base64url');

export async function challengeFor(verifier: string): Promise<string> {
  const hash = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
  return b64url(new Uint8Array(hash));
}

export async function createPkce(): Promise<{ verifier: string; challenge: string }> {
  const verifier = b64url(crypto.getRandomValues(new Uint8Array(32)));
  return { verifier, challenge: await challengeFor(verifier) };
}

export function buildAuthorizeUrl(o: { authorizeUrl: string; clientId: string; redirectUri: string; scope: string[]; state: string; challenge: string }): string {
  const url = new URL(o.authorizeUrl);
  url.search = new URLSearchParams({
    response_type: 'code',
    client_id: o.clientId,
    redirect_uri: o.redirectUri,
    scope: o.scope.join(' '),
    state: o.state,
    code_challenge: o.challenge,
    code_challenge_method: 'S256',
  }).toString();
  return url.href;
}

export function readCallback(callbackUrl: string, expectedState: string): string {
  const params = new URL(callbackUrl).searchParams;
  if (params.get('state') !== expectedState) throw new Error('state не совпал: возможна атака CSRF');
  const error = params.get('error');
  if (error) throw new Error(`Отказ авторизации: ${error}`);
  const code = params.get('code');
  if (!code) throw new Error('В ответе нет code');
  return code;
}

Проверка state идёт первой: если ответ не наш, его содержимое не важно, даже ошибка. verifier и state до возврата пользователя хранят в sessionStorage: они нужны только этой вкладке и только на время входа. Тест сверяет challengeFor с примером из RFC 7636 (приложение B). Обмен code на токен (POST на token endpoint с code_verifier) в задачу не входит: для него нужен настоящий сервер авторизации.

Пароли

  • Хранить только хеш медленной функцией с солью: bcrypt, scrypt, Argon2. Никогда — открытым текстом или быстрым хешем вроде SHA-256 без соли.
  • Длина важнее правил «заглавная + цифра»: OWASP советует минимум 8 символов при 2FA и разрешать длинные пароли, пробелы и любые символы. Проверять по списку утёкших паролей.
  • Ограничение попыток входа и, где можно, второй фактор.
  • Сброс пароля — одноразовой ссылкой с коротким сроком, без раскрытия, есть ли такой email.

Задача 12. Проверка пароля по рекомендациям OWASP ★☆☆ разминка

Напишите passwordProblems(password, { leaked, email }), которая возвращает список проблем: короче 8 символов, длиннее 128, есть в списке утёкших (без учёта регистра), совпадает с email или его частью до @. Никаких требований «заглавная + цифра + спецсимвол». Длину считайте в символах Юникода, а не в единицах UTF-16.

Зачем: правила состава заставляют людей писать Password1!. Он формально проходит, а в словарях взлома стоит в первой сотне. Современные рекомендации проще и сильнее: длинный пароль, которого нет в утечках. А длина в символах важна, потому что эмодзи — это два «символа» для .length.

Решение и разбор
export function passwordProblems(password: string, { leaked, email }: { leaked: ReadonlySet<string>; email: string }): string[] {
  const problems: string[] = [];
  const length = [...password].length;
  if (length < 8) problems.push('Минимум 8 символов');
  if (length > 128) problems.push('Максимум 128 символов');
  const lower = password.toLowerCase();
  if (leaked.has(lower)) problems.push('Этот пароль встречался в утечках');
  const local = email.toLowerCase().split('@')[0] ?? '';
  if (lower === email.toLowerCase() || (local.length > 0 && lower === local)) problems.push('Пароль не должен совпадать с email');
  return problems;
}

[...password].length считает кодовые точки: '🔑'.length равно 2, а [...'🔑'].length — 1. Верхний предел нужен не для безопасности, а против отказа в обслуживании: хеширование мегабайтного «пароля» дорого, а bcrypt вообще учитывает только первые 72 байта (из общих знаний). Список утечек в реальности огромный, и его проверяют через сервис Have I Been Pwned по первым символам хеша, не отправляя сам пароль.
