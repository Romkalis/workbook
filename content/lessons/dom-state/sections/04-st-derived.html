Производные данные не храним

Сумма корзины, число товаров в бейдже, отфильтрованный каталог — всё это вычисляется из состояния. Если хранить их отдельно (state.total), их придётся обновлять при каждом изменении, и однажды забудут. Храните минимум, остальное считайте функциями-селекторами: cartTotal(state), visibleProducts(state). Пересчёт суммы на сотне строк занимает микросекунды; оптимизировать стоит, только когда профилировщик покажет проблему.

Хорошая проверка: можно ли получить это значение из других полей состояния? Если да — это не состояние, а селектор.

Задача 9. Селекторы корзины ★☆☆ разминка

Напишите селекторы cartCount(state) (сумма количеств) и cartTotal(state) (сумма цена × количество) и уберите из состояния корзины поля count и total, которые сейчас обновляются вручную в каждом действии.

interface Cart {
  lines: Line[];
  count: number; // обновляется в addLine, removeLine, setQuantity...
  total: number; // ...и иногда забывается
}

Зачем: каждое хранимое производное значение — обязанность всех действий его обновлять. Селектор не может «забыть», потому что всегда считает заново из правды.

Решение и разбор
// selectors.ts
export interface Line {
  id: string;
  price: number;
  quantity: number;
}
export interface Cart {
  lines: Line[];
}

export const cartCount = (s: Cart): number => s.lines.reduce((n, l) => n + l.quantity, 0);
export const cartTotal = (s: Cart): number => s.lines.reduce((sum, l) => sum + l.price * l.quantity, 0);

После правки действия стали короче (меньше полей обновлять), а тип Cart — честнее: в нём только то, что нельзя вычислить. Селекторы используют и render, и бейдж в шапке, и кнопка «Оформить» (неактивна при cartCount === 0), и все они согласованы по построению.

Задача 10. Видимый каталог из состояния ★★☆ практика

Состояние каталога: { products, filters: { q, category }, sort: 'default' | 'price-asc' | 'price-desc' }. Напишите селектор visibleProducts(state), который применяет поиск (без учёта регистра), категорию и сортировку, не меняя исходный массив.

Зачем: список на экране — функция от трёх частей состояния. Если хранить «отфильтрованный список» отдельно, придётся пересчитывать его при изменении любой из них, и где-то это забудут. Один селектор — одно место правды.

Решение и разбор
// visible.ts
export interface Product {
  id: string;
  title: string;
  category: string;
  price: number;
}
export interface CatalogState {
  products: Product[];
  filters: { q: string; category: string | null };
  sort: 'default' | 'price-asc' | 'price-desc';
}

export function visibleProducts(s: CatalogState): Product[] {
  const q = s.filters.q.trim().toLowerCase();
  const filtered = s.products.filter(
    (p) => (q === '' || p.title.toLowerCase().includes(q)) && (s.filters.category === null || p.category === s.filters.category),
  );
  if (s.sort === 'default') return filtered;
  const sign = s.sort === 'price-asc' ? 1 : -1;
  return [...filtered].sort((a, b) => sign * (a.price - b.price));
}

Сначала фильтр, потом сортировка: сортировать меньший массив дешевле. filter уже вернул новый массив, но копия перед sort всё равно сделана: при пустых фильтрах filter мог бы быть оптимизирован до возврата исходного массива, и sort испортил бы данные состояния. Защитное копирование стоит дёшево.

Задача 11. Запомнить результат селектора ★★★ с подвохом

Селектор visibleProducts вызывается при каждой перерисовке, даже если товары и фильтры не менялись. Напишите memoizeOne(fn): обёртка запоминает последние аргументы и результат и, если все аргументы равны предыдущим по Object.is, возвращает сохранённый результат без вызова fn.

Зачем: это прямое следствие иммутабельности: раз неизменённые части состояния — те же объекты, сравнение ссылкой дешёвое и надёжное. По тому же принципу работают useMemo в React и createSelector в Redux (из общих знаний). При мутациях на месте такое запоминание выдавало бы устаревший результат.

Решение и разбор
// memo.ts
export function memoizeOne<A extends unknown[], R>(fn: (...args: A) => R): (...args: A) => R {
  let lastArgs: A | null = null;
  let lastResult: R;
  return (...args: A): R => {
    if (lastArgs && args.length === lastArgs.length && args.every((a, i) => Object.is(a, lastArgs![i]))) {
      return lastResult;
    }
    lastArgs = args;
    lastResult = fn(...args);
    return lastResult;
  };
}

Запоминается только последний вызов, а не все: селектору на экране нужен именно последний набор данных, а кеш всех вызовов рос бы без конца. Важный побочный эффект: при тех же аргументах возвращается тот же массив, и следующий слой (например, syncList) может тоже сравнить ссылкой и ничего не делать. Аргументы селектора стоит передавать частями (products, filters, sort), а не целым состоянием: иначе изменение корзины, которое к каталогу не относится, сбросит кеш.
