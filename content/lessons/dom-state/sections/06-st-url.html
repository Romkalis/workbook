Состояние в адресе страницы

Часть состояния принадлежит адресу: фильтры каталога, номер страницы, открытый товар. Тогда ссылкой можно поделиться, кнопка «назад» работает, а перезагрузка не сбрасывает выбор.

export interface Filters {
  q: string;
  category: string | null;
}

export function filtersFromSearch(search: string): Filters {
  const params = new URLSearchParams(search);
  return { q: params.get('q') ?? '', category: params.get('category') };
}

export function filtersToSearch(f: Filters): string {
  const params = new URLSearchParams();
  if (f.q) params.set('q', f.q);
  if (f.category) params.set('category', f.category);
  const s = params.toString();
  return s ? `?${s}` : '';
}

URLSearchParams сам кодирует пробелы и русские буквы. Пустые значения не пишем, чтобы адрес оставался чистым. Обновление адреса: history.pushState(null, '', url) добавляет запись в историю (кнопка «назад» вернёт прошлые фильтры), history.replaceState заменяет текущую — для живого поиска, чтобы каждая буква не становилась шагом назад. При нажатии «назад» браузер генерирует событие popstate: в обработчике читаем фильтры из location.search и кладём в стор.

Маршрутизация по хешу (#/cart) — тот же принцип для «страниц» одностраничного приложения: она разобрана в уроке Team Project и работает на любом статическом хостинге.

Задача 15. Фильтры туда и обратно ★☆☆ разминка

Расширьте filtersToSearch/filtersFromSearch из раздела полями sort (по умолчанию 'default', неизвестное значение тоже даёт 'default') и page (целое от 1, по умолчанию 1). Значения по умолчанию в адрес не пишутся. Проверьте свойство «туда и обратно»: fromSearch(toSearch(f)) равно f.

Зачем: адрес — внешние данные: его правят руками, присылают в мессенджере с опечатками. Разбор с безопасными значениями по умолчанию не даст странице упасть на ?page=abc. Свойство «туда и обратно» — удобная и сильная проверка для любой пары «записать/прочитать».

Решение и разбор
// url.ts
const SORTS = ['default', 'price-asc', 'price-desc'] as const;
type Sort = (typeof SORTS)[number];

export interface Filters {
  q: string;
  category: string | null;
  sort: Sort;
  page: number;
}

export function filtersFromSearch(search: string): Filters {
  const p = new URLSearchParams(search);
  const sort = p.get('sort');
  const page = Number(p.get('page'));
  return {
    q: p.get('q') ?? '',
    category: p.get('category'),
    sort: (SORTS as readonly string[]).includes(sort ?? '') ? (sort as Sort) : 'default',
    page: Number.isInteger(page) && page >= 1 ? page : 1,
  };
}

export function filtersToSearch(f: Filters): string {
  const p = new URLSearchParams();
  if (f.q) p.set('q', f.q);
  if (f.category) p.set('category', f.category);
  if (f.sort !== 'default') p.set('sort', f.sort);
  if (f.page !== 1) p.set('page', String(f.page));
  const s = p.toString();
  return s ? `?${s}` : '';
}

Number(null) равно 0, поэтому отсутствующая страница отсекается той же проверкой «целое от 1». Значения по умолчанию не попадают в адрес: ссылка на первую страницу каталога остаётся просто /catalog. Утверждение sort as Sort безопасно сразу после проверки по массиву.

Задача 16. Синхронизация стора и адреса ★★☆ практика

Напишите syncWithUrl(store) для стора с состоянием { filters }: при изменении фильтров записывает их в адрес через pushState (если строка адреса действительно изменилась), а на popstate читает фильтры из location.search и кладёт в стор. Используйте функции из прошлой задачи в упрощённом виде (q и category).

// store.ts
export function createStore<S>(initial: S) {
  let state = initial;
  const listeners = new Set<(s: S, p: S) => void>();
  return {
    getState: (): S => state,
    setState(update: (prev: S) => S): void {
      const prev = state;
      const next = update(prev);
      if (Object.is(next, prev)) return;
      state = next;
      listeners.forEach((l) => l(state, prev));
    },
    subscribe(l: (s: S, p: S) => void) {
      listeners.add(l);
      return () => listeners.delete(l);
    },
  };
}

Зачем: двусторонняя связь «стор ↔ адрес» легко зацикливается: стор меняет адрес, адрес меняет стор, стор снова пишет адрес. Проверка «не изменилось — не пишем» разрывает цикл, а кнопка «назад» начинает вести себя так, как ожидает пользователь.

Решение и разбор
// sync.ts
import type { createStore } from './store.js';

export interface Filters {
  q: string;
  category: string | null;
}
type Store = ReturnType<typeof createStore<{ filters: Filters }>>;

const fromSearch = (s: string): Filters => {
  const p = new URLSearchParams(s);
  return { q: p.get('q') ?? '', category: p.get('category') };
};
const toSearch = (f: Filters): string => {
  const p = new URLSearchParams();
  if (f.q) p.set('q', f.q);
  if (f.category) p.set('category', f.category);
  const s = p.toString();
  return s ? `?${s}` : '';
};

export function syncWithUrl(store: Store): () => void {
  const offStore = store.subscribe((state, prev) => {
    if (state.filters === prev.filters) return;
    const search = toSearch(state.filters);
    if (search !== location.search) history.pushState(null, '', search || location.pathname);
  });
  const onPop = () => store.setState((s) => ({ ...s, filters: fromSearch(location.search) }));
  window.addEventListener('popstate', onPop);
  return () => {
    offStore();
    window.removeEventListener('popstate', onPop);
  };
}

Два «предохранителя» от цикла. Подписчик пропускает изменения, не затронувшие фильтры: сравнение ссылкой работает благодаря иммутабельности. И не пишет адрес, если строка уже такая: после popstate стор обновился из адреса, и запись обратно была бы лишним шагом в истории. Пустые фильтры дают location.pathname, чтобы в адресе не остался одинокий ?. Тип стора выведен из createStore через ReturnType, без ручного дублирования.

Задача 17. Маршрутизатор на хеше с параметром ★★☆ практика

Напишите parseRoute(hash) для маршрутов #/ (каталог), #/cart (корзина) и #/product/<id> (страница товара). Результат — размеченное объединение { name: 'catalog' } | { name: 'cart' } | { name: 'product'; id }, неизвестный адрес даёт { name: 'notFound' }. И renderRoute(root, route) с switch и проверкой полноты.

Зачем: маршрут — тоже состояние, и размеченное объединение описывает его точно: у страницы товара есть id, у корзины нет. Новый маршрут без отрисовки компилятор не пропустит.

Решение и разбор
// router.ts
export type Route = { name: 'catalog' } | { name: 'cart' } | { name: 'product'; id: string } | { name: 'notFound' };

export function parseRoute(hash: string): Route {
  const parts = hash.replace(/^#\/?/, '').split('/').filter(Boolean);
  if (parts.length === 0) return { name: 'catalog' };
  if (parts.length === 1 && parts[0] === 'cart') return { name: 'cart' };
  if (parts.length === 2 && parts[0] === 'product' && parts[1]) return { name: 'product', id: decodeURIComponent(parts[1]) };
  return { name: 'notFound' };
}

export function renderRoute(root: HTMLElement, route: Route): void {
  const h1 = document.createElement('h1');
  switch (route.name) {
    case 'catalog':
      h1.textContent = 'Каталог';
      break;
    case 'cart':
      h1.textContent = 'Корзина';
      break;
    case 'product':
      h1.textContent = `Товар ${route.id}`;
      break;
    case 'notFound':
      h1.textContent = 'Страница не найдена';
      break;
    default: {
      const unreachable: never = route;
      throw new Error(`Неизвестный маршрут: ${JSON.stringify(unreachable)}`);
    }
  }
  root.replaceChildren(h1);
}

Разбор — чистая функция без location, её проверяет таблица случаев. id декодируется (decodeURIComponent), потому что в адресе пробелы и русские буквы закодированы. id показывается через textContent: адрес — тоже пользовательский ввод, его присылают ссылкой. Подключение к браузеру — две строки: addEventListener('hashchange', ...) и первый вызов при загрузке.
