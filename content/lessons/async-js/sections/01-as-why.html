Зачем асинхронность

JavaScript выполняет код в одном потоке: пока работает одна функция, никакая другая не начнётся. Если бы запрос к серверу занимал поток на всё время ожидания, страница бы «замерзала»: кнопки не нажимаются, анимация стоит, прокрутка дёргается. Поэтому долгие операции (сеть, таймеры, чтение файлов в Node) выполняет окружение — браузер или Node.js, а JavaScript получает уведомление, когда результат готов.

export function order(): string[] {
  const log: string[] = [];
  log.push('1: начали');
  setTimeout(() => log.push('3: таймер'), 0);
  log.push('2: закончили синхронную часть');
  return log; // ['1: начали', '2: закончили синхронную часть'] — таймер ещё не сработал
}

Даже с задержкой 0 колбэк таймера выполнится после всего синхронного кода. Как именно устроена очередь, разбирает урок Event Loop & Animation. Здесь достаточно правила: асинхронный колбэк никогда не прерывает текущий код, он ждёт, пока стек вызовов опустеет.

Колбэки и почему от них ушли

Первый способ получить результат позже — передать функцию, которую вызовут, когда всё готово. Так устроены setTimeout, addEventListener и старый API Node (fs.readFile(path, (err, data) => …)). Пока шаг один, это удобно. Когда шаги зависят друг от друга, код уходит вправо лесенкой («callback hell»), а обработку ошибок приходится повторять на каждом уровне:

getUser(id, (err, user) => {
  if (err) return show(err);
  getOrders(user, (err, orders) => {
    if (err) return show(err);
    getDelivery(orders[0], (err, delivery) => {
      if (err) return show(err);
      render(delivery);
    });
  });
});

Есть и менее заметная проблема: колбэк отдаётся чужому коду, и ничто не гарантирует, что его вызовут ровно один раз. Промисы решают обе проблемы.

Задача 1. Предскажите порядок ★☆☆ разминка

Не запуская код, запишите, в каком порядке появятся строки. Потом проверьте в консоли браузера.

console.log('A');
setTimeout(() => console.log('B'), 0);
for (let i = 0; i < 1e8; i++) {} // ~100 мс работы
console.log('C');
setTimeout(() => console.log('D'), 0);

Зачем: если понимать, что колбэк таймера ждёт окончания всего синхронного кода, перестают удивлять «таймер на 0 мс сработал через 100». Это база для всех следующих задач.

Решение и разбор
// ответ.txt
A
C
B
D

Цикл занимает поток, и таймер B не может выполниться, хотя его задержка давно прошла: он стоит в очереди. После C синхронный код закончился, и очередь разбирается в порядке постановки: сначала B, потом D. Задержка 0 означает «как можно скорее после текущего кода», а не «немедленно».

Задача 2. Колбэк ровно один раз ★★☆ практика

Чужая библиотека иногда вызывает колбэк дважды: сначала с ошибкой тайм-аута, потом с поздним ответом. Напишите обёртку once(cb): первый вызов проходит, остальные игнорируются. Обёртка возвращает функцию с той же сигнатурой.

Зачем: это та самая проблема доверия к колбэкам из раздела. Промис решает её встроенно: resolve срабатывает один раз. Если написать once руками, становится понятно, какую гарантию промис даёт бесплатно.

Решение и разбор
export function once<A extends unknown[]>(cb: (...args: A) => void): (...args: A) => void {
  let called = false;
  return (...args) => {
    if (called) return;
    called = true;
    cb(...args);
  };
}

Флаг called живёт в замыкании: у каждой обёртки он свой. Флаг ставится до вызова cb, и это важно. Если cb бросит ошибку или сам вызовет обёртку повторно, второй вызов всё равно будет отброшен. Generic A сохраняет типы аргументов, поэтому обёртка подходит к любому колбэку.
