fetch и XMLHttpRequest

fetch(url, options) возвращает промис ответа. Важная деталь: промис отклоняется только при сетевой ошибке (нет соединения, CORS, отмена). Ответ 404 или 500 — это успешно полученный ответ, и проверять response.ok нужно самим. Тело читается отдельным асинхронным шагом: response.json(), response.text(). Подробно с клиентом и состояниями загрузки — урок Данные с сервера в интерфейсе.

const response = await fetch('/api/products');
if (!response.ok) throw new Error(`HTTP ${response.status}`);
const products: unknown = await response.json();

XMLHttpRequest (XHR) — старший предшественник fetch на событиях. В новом коде его почти не пишут, но он встречается в старых проектах и умеет то, чего fetch долго не умел: событие progress для загрузки файлов на сервер.

const xhr = new XMLHttpRequest();
xhr.open('GET', '/api/products');
xhr.responseType = 'json';
xhr.onload = () => (xhr.status < 400 ? render(xhr.response) : showError(xhr.status));
xhr.onerror = () => showError('сеть');
xhr.send();

Отмена запроса и тайм-аут

AbortController создаёт сигнал, который передают в fetch. После controller.abort() промис запроса отклоняется ошибкой AbortError. Для тайм-аута есть готовый AbortSignal.timeout(ms) (из общих знаний: в материалах модуля его нет; поддерживается всеми современными браузерами и Node 18+).

const response = await fetch('/api/slow', { signal: AbortSignal.timeout(5000) });

Задача 19. getJson с проверкой статуса ★★☆ практика

Напишите getJson(url): при ответе с ok === false бросает Error("HTTP 404 /api/x"). Если сервер вернул не JSON (например, HTML-страницу ошибки прокси), бросает Error("Ожидался JSON"). Проверяйте заголовок Content-Type, а не ловите ошибку разбора.

Зачем: fetch считает 404 успехом, а response.json() на HTML падает с невнятным Unexpected token <. Проверка статуса и типа содержимого превращает загадочную ошибку в понятную.

Решение и разбор
export async function getJson(url: string): Promise<unknown> {
  const response = await fetch(url, { headers: { Accept: 'application/json' } });
  if (!response.ok) throw new Error(`HTTP ${response.status} ${url}`);
  const type = response.headers.get('Content-Type') ?? '';
  if (!type.includes('application/json')) throw new Error('Ожидался JSON');
  return response.json();
}

includes, а не точное сравнение: сервер обычно присылает application/json; charset=utf-8. Результат unknown — проверку формы делает вызывающий код. Полная версия клиента с классом ошибки и запасным текстом — в задачах урока RESTful API.

Задача 20. XMLHttpRequest в промисе ★★★ с подвохом

Оберните XHR в промис: xhrJson(url, Xhr = XMLHttpRequest). Статус 400 и выше — отклонение с Error("HTTP <код>"), событие error — отклонение Error("Сеть"). Класс передаётся параметром, чтобы в тесте подставить заглушку: в Node настоящего XHR нет.

Зачем: в старых проектах встречается XHR, а остальной код уже на промисах. Обёртка на границе — тот же приём, что с колбэками. Внедрение класса через параметр делает код проверяемым без браузера.

Решение и разбор
export interface XhrLike {
  open(method: string, url: string): void;
  send(): void;
  responseType: XMLHttpRequestResponseType;
  status: number;
  response: unknown;
  onload: (() => void) | null;
  onerror: (() => void) | null;
}

export function xhrJson(url: string, Xhr: new () => XhrLike = XMLHttpRequest as unknown as new () => XhrLike): Promise<unknown> {
  return new Promise((resolve, reject) => {
    const xhr = new Xhr();
    xhr.open('GET', url);
    xhr.responseType = 'json';
    xhr.onload = () => (xhr.status < 400 ? resolve(xhr.response) : reject(new Error(`HTTP ${xhr.status}`)));
    xhr.onerror = () => reject(new Error('Сеть'));
    xhr.send();
  });
}

Интерфейс XhrLike описывает только то, чем пользуется функция. Настоящий XMLHttpRequest ему соответствует, и заглушке в тесте не нужно реализовывать десятки остальных свойств. Обработчики назначаются до send(): иначе быстрый ответ из кеша мог бы прийти раньше, чем их назначили. Значение по умолчанию вычисляется при вызове, поэтому в Node без XHR функция работает, если класс передан явно.

Задача 21. Только последний запрос ★★★ с подвохом

Пользователь быстро печатает в поиске, и ответы на старые запросы приходят позже новых. Напишите createLatest(fetcher), где fetcher(query, signal) возвращает промис. Каждый новый вызов отменяет предыдущий через AbortController. Результат отменённого вызова — null, а не ошибка.

Зачем: это гонка запросов из урока «Данные с сервера в интерфейсе», решённая отменой. В отличие от простой проверки «мой ли это запрос», отмена ещё и экономит трафик: сервер перестаёт отправлять ненужный ответ.

Решение и разбор
export function createLatest<T>(fetcher: (query: string, signal: AbortSignal) => Promise<T>) {
  let current: AbortController | null = null;
  return async (query: string): Promise<T | null> => {
    current?.abort();
    const controller = new AbortController();
    current = controller;
    try {
      return await fetcher(query, controller.signal);
    } catch (err) {
      if (controller.signal.aborted) return null;
      throw err;
    }
  };
}

Отмену определяет controller.signal.aborted, а не имя ошибки. Это надёжнее: разные реализации fetch и заглушки бросают разные ошибки, а флаг сигнала один. Настоящие ошибки (сеть, 500) по-прежнему пробрасываются. null вместо отклонения означает, что вызывающему коду не нужно отличать «отменён» от «сломался» в каждом catch: он просто ничего не рисует.
