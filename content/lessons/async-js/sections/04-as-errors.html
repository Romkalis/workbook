Отклонения и их обработка

Ошибка в любом шаге цепочки — throw внутри then или отклонённый промис — пропускает все следующие then и попадает в ближайший catch. Это аналог try...catch для асинхронного кода.

export function recover(): Promise<string> {
  return Promise.reject(new Error('сеть'))
    .then(() => 'не выполнится')
    .catch((err: unknown) => `запасной вариант: ${err instanceof Error ? err.message : 'неизвестно'}`)
    .then((text) => text.toUpperCase());
}
// 'ЗАПАСНОЙ ВАРИАНТ: СЕТЬ'

После catch цепочка снова «здорова»: то, что вернул обработчик, идёт дальше как обычное значение. Если обработать ошибку нельзя, бросьте её снова внутри catch, и она уйдёт к следующему обработчику.

Отклонённый промис без обработчика — unhandled rejection. Браузер пишет ошибку в консоль и вызывает событие unhandledrejection, а Node.js начиная с 15 версии завершает процесс. Подробно про глобальные обработчики — в уроке Error handling.

Где ставить catch

catch ловит ошибки всех шагов выше себя. Поэтому обычно он один, в конце цепочки. Обработчики посередине цепочки нужны, только если после ошибки шаги должны продолжиться с запасным значением. Второй аргумент then(ok, fail) не ловит ошибку из самого ok, и это частая ловушка: then(ok).catch(fail) и then(ok, fail) не равны.

Задача 8. Запасной источник данных ★★☆ практика

Напишите loadWithFallback(primary, fallback): обе функции возвращают промисы. Если основной источник отклонился, берём запасной. Если отклонились оба, функция отклоняется ошибкой "Нет данных", а исходные ошибки лежат в её cause (массив из двух).

Зачем: catch посередине цепочки нужен именно для таких случаев: ошибка превращается в план Б, а не в падение. cause сохраняет исходные причины для логов, а пользователь видит одно понятное сообщение.

Решение и разбор
export function loadWithFallback<T>(primary: () => Promise<T>, fallback: () => Promise<T>): Promise<T> {
  return primary().catch((first: unknown) =>
    fallback().catch((second: unknown) => {
      throw new Error('Нет данных', { cause: [first, second] });
    }),
  );
}

Обработчик основного источника возвращает промис запасного. Если запасной выполнится, вся цепочка выполнится его значением. Вложенный catch здесь оправдан: внутри него видна первая ошибка. Запасной источник вызывается лениво, только при сбое. Поэтому параметры — функции, а не готовые промисы: промис уже запущенной операции нельзя «не запускать».

Задача 9. Обработчик, который не ловит ★★☆ практика

Код должен показывать «Ошибка: …» при любой проблеме, но падение внутри render уходит в unhandled rejection. Исправьте и объясните, почему так вышло.

export function show(load: () => Promise<string[]>, render: (items: string[]) => string): Promise<string> {
  return load().then(
    (items) => render(items),
    (err: Error) => `Ошибка: ${err.message}`,
  );
}

Зачем: второй аргумент then видит только ошибки до этого then. Ошибку в первом аргументе того же вызова он не ловит. Поэтому catch в конце цепочки надёжнее: он видит всё, что выше.

Решение и разбор
export function show(load: () => Promise<string[]>, render: (items: string[]) => string): Promise<string> {
  return load()
    .then((items) => render(items))
    .catch((err: unknown) => `Ошибка: ${err instanceof Error ? err.message : String(err)}`);
}

Тип параметра в catch сменился с Error на unknown: отклонить промис можно чем угодно, и TypeScript честно не обещает Error. Вариант с двумя аргументами иногда нужен намеренно: «обработай ошибку загрузки, а ошибку рендера пусть ловят выше». Но это редкий случай, и его стоит подписать комментарием.
