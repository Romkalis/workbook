then, catch, finally и цепочки

promise.then(onFulfilled) регистрирует реакцию на успех и возвращает новый промис. Его результат — то, что вернула реакция. Отсюда цепочки: каждый шаг получает результат предыдущего.

export function chain(): Promise<number> {
  return Promise.resolve(2)
    .then((x) => x * 10) // вернули число — следующий then получит 20
    .then((x) => Promise.resolve(x + 1)) // вернули промис — цепочка дождётся его: 21
    .finally(() => {
      // finally не получает значение и не меняет его
    });
}

Три правила, на которых держатся цепочки:

  • Вернули из then обычное значение — следующий шаг получит его.
  • Вернули промис — цепочка дождётся его и передаст результат дальше. Так последовательные запросы пишутся без вложенности.
  • Ничего не вернули — следующий шаг получит undefined, и, что хуже, не будет ждать запущенную внутри операцию. Забытый return — самая частая ошибка с промисами.

catch(onRejected) — то же, что then(undefined, onRejected). finally(fn) выполняется при любом исходе и подходит для «снять индикатор загрузки». Если finally вернёт значение, оно игнорируется. Но если бросит ошибку, цепочка станет отклонённой с ней.

Зачем then возвращает новый промис, а не тот же?

Чтобы у каждого шага был свой результат. Если бы then менял исходный промис, два независимых обработчика одного запроса мешали бы друг другу.

Задача 6. Лесенка в цепочку ★☆☆ разминка

Перепишите «лесенку» из раздела про колбэки на промисах. Функции getUser, getOrders, getDelivery уже возвращают промисы. showDelivery(id) должна вернуть промис со статусом доставки первого заказа, без вложенных then.

// api.ts
export const getUser = async (id: string) => ({ id, name: 'Аня' });
export const getOrders = async (user: { id: string }) => [{ id: `o-${user.id}` }];
export const getDelivery = async (order: { id: string }) => ({ order: order.id, status: 'в пути' });

Зачем: плоская цепочка — главный выигрыш промисов. Каждый шаг возвращает промис следующего запроса, и обработка ошибок пишется один раз в конце, а не на каждом уровне.

Решение и разбор
import { getDelivery, getOrders, getUser } from './api.js';

export function showDelivery(id: string): Promise<string> {
  return getUser(id)
    .then((user) => getOrders(user))
    .then((orders) => {
      const first = orders[0];
      if (!first) throw new Error('Заказов нет');
      return getDelivery(first);
    })
    .then((delivery) => delivery.status);
}

Каждый then возвращает промис следующего шага, и цепочка его дожидается. Вложенность исчезает. Пустой список заказов превращён в ошибку: она пройдёт мимо следующих then к тому catch, который поставит вызывающий код. .then((user) => getOrders(user)) можно сократить до .then(getOrders), но с передачей методов так легко потерять this.

Задача 7. Забытый return ★★☆ практика

Функция должна сохранить товар и только потом вернуть обновлённый список. Иногда список приходит без нового товара. Найдите ошибку.

export function addAndList(api: { save(t: string): Promise<void>; list(): Promise<string[]> }, title: string) {
  return Promise.resolve()
    .then(() => {
      api.save(title);
    })
    .then(() => api.list());
}

Зачем: забытый return не даёт ошибки компиляции и иногда даже работает, если сохранение быстрое. Такие плавающие баги находят неделями, поэтому правило «каждый промис внутри then возвращается» стоит довести до автоматизма.

Решение и разбор
export function addAndList(api: { save(t: string): Promise<void>; list(): Promise<string[]> }, title: string) {
  return Promise.resolve()
    .then(() => api.save(title))
    .then(() => api.list());
}

В фигурных скобках стрелки нужен явный return, без скобок значение возвращается само. Без return следующий шаг не ждёт save: список читается раньше записи. Есть и вторая беда: если save отклонится, ошибку никто не обработает. Правило линтера @typescript-eslint/no-floating-promises находит такие места автоматически (из общих знаний).
