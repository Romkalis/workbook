Scrum

Scrum описан в Scrum Guide — 13 страниц, последняя редакция ноября 2020 года. Работа идёт спринтами: отрезками фиксированной длины до месяца (чаще 1–2 недели). Каждый спринт заканчивается инкрементом — готовой к использованию частью продукта.

Ответственности

Scrum Team — до 10 человек, без иерархии и подкоманд. В руководстве 2020 года роли называются ответственностями (accountabilities):

КтоЗа что отвечает
Product Owner (владелец продукта)ценность продукта: ведёт и упорядочивает Product Backlog, формулирует Product Goal. Один человек, не комитет
Scrum Masterэффективность команды: помогает понять Scrum, убирает препятствия, учит команду самоорганизации. Не начальник и не секретарь
Developers (разработчики)создание инкремента каждый спринт: план спринта, качество, Definition of Done. Сюда входят все, кто делает работу, — и тестировщики, и дизайнеры

События

СобытиеДлительность (для спринта в месяц)Зачем
Sprintдо 1 месяцаконтейнер для всех остальных событий
Sprint Planningдо 8 часовпочему ценен спринт (Sprint Goal), что сделать, как сделать

Для коротких спринтов события обычно короче. Daily Scrum — не отчёт начальнику: популярные «три вопроса» (что сделал, что сделаю, что мешает) руководство 2020 года больше не требует, формат выбирают разработчики.

Артефакты и обязательства

У каждого артефакта есть обязательство (commitment), которое делает прогресс измеримым:

АртефактЧто этоОбязательство
Product Backlogупорядоченный список всего, что может понадобиться продуктуProduct Goal — долгосрочная цель продукта
Sprint Backlogцель спринта, выбранные элементы и план их выполненияSprint Goal — единственная цель спринта
Incrementпроверенный, готовый к использованию шаг к цели продуктаDefinition of Done — общее для команды определение «сделано»

Definition of Done — например: код прошёл ревью, тесты зелёные, работает на мобильной ширине, задеплоено на стенд. Если элемент не соответствует DoD, он не попадает в инкремент и возвращается в Product Backlog, даже если «почти готово».

Задача 2. Definition of Done как проверка ★★☆ практика

Definition of Done команды: есть PR с одобрением ревьюера, CI зелёный, есть тесты (покрытие изменённых файлов не ниже 80%), проверено на мобильной ширине. Напишите checkDone(task), которая возвращает список невыполненных пунктов человеческим языком, и sprintIncrement(tasks), которая делит задачи спринта на done и backToBacklog.

Зачем: «почти готово» — самая опасная оценка в разработке: последние 10% работы занимают половину времени. DoD в виде проверяемых правил убирает спор «готово или нет» и не даёт незаконченным задачам попасть в инкремент.

Решение и разбор
export interface Task {
  id: string;
  prApproved: boolean;
  ciGreen: boolean;
  coverage: number | null;
  mobileChecked: boolean;
}

const RULES: [string, (t: Task) => boolean][] = [
  ['нет одобренного PR', (t) => t.prApproved],
  ['CI не зелёный', (t) => t.ciGreen],
  ['покрытие тестами ниже 80%', (t) => t.coverage !== null && t.coverage >= 80],
  ['не проверено на мобильной ширине', (t) => t.mobileChecked],
];

export const checkDone = (task: Task): string[] => RULES.filter(([, ok]) => !ok(task)).map(([text]) => text);

export function sprintIncrement(tasks: readonly Task[]) {
  return {
    done: tasks.filter((t) => checkDone(t).length === 0).map((t) => t.id),
    backToBacklog: tasks.filter((t) => checkDone(t).length > 0).map((t) => t.id),
  };
}

Правила лежат в данных, в массиве RULES, а не в цепочке if. Команда меняет DoD на ретроспективе, и в коде добавляется одна строка. Отсутствие данных о покрытии (null) считается невыполнением: «не знаем» не равно «хорошо». Задачи, не прошедшие DoD, по Scrum Guide не входят в инкремент и возвращаются в Product Backlog. Делить их на «готово на 80%» нельзя.

Оценка: story points и скорость

Команды часто оценивают задачи не в часах, а в story points — относительных единицах сложности: «эта задача примерно вдвое сложнее той». Для оценки используют planning poker: каждый одновременно показывает карту с числом из ряда, похожего на Фибоначчи (1, 2, 3, 5, 8, 13, 21…). Если оценки сильно разошлись, крайние объясняют свои причины, и голосуют снова. Растущие промежутки в ряду отражают растущую неопределённость больших задач. Задачу больше 13 обычно дробят.

Скорость (velocity) — сколько очков команда закрывает за спринт. Её считают по нескольким прошлым спринтам и используют для прогноза («что успеем»). Это метрика команды для планирования, а не оценка работы людей. Сравнивать скорость разных команд бессмысленно: у них разная шкала очков.

Burndown-график показывает, сколько работы осталось в спринте по дням. Идеальная линия идёт от полного объёма к нулю. Если фактическая линия выше идеальной, команда отстаёт.

Story points, planning poker, velocity и burndown — популярные практики, но в самом Scrum Guide их нет (из общих знаний: руководство сознательно не предписывает способ оценки).

Задача 3. Прогноз по скорости команды ★☆☆ разминка

Напишите forecast(history, backlog). history — очки, закрытые в прошлых спринтах, backlog — оценки оставшихся задач. Скорость — среднее по последним трём спринтам (или по всем, если их меньше трёх), округлённое вниз. Верните { velocity, sprints }, где sprints — сколько спринтов нужно на весь бэклог (с округлением вверх). Без истории функция бросает ошибку: прогнозировать не на чем.

Зачем: скорость используют для честного ответа на вопрос «когда будет готово». Берут несколько последних спринтов, потому что команда меняется. Округление вниз осторожнее: лучше пообещать меньше. А отказ прогнозировать без данных — тоже инженерная честность.

Решение и разбор
export function forecast(history: readonly number[], backlog: readonly number[]): { velocity: number; sprints: number } {
  if (history.length === 0) throw new Error('Нет завершённых спринтов — прогноз невозможен');
  const recent = history.slice(-3);
  const velocity = Math.floor(recent.reduce((a, b) => a + b, 0) / recent.length);
  if (velocity === 0) throw new Error('Нулевая скорость — прогноз невозможен');
  const remaining = backlog.reduce((a, b) => a + b, 0);
  return { velocity, sprints: Math.ceil(remaining / velocity) };
}

slice(-3) берёт последние три элемента, а для коротких массивов — сколько есть. Деление на ноль скорости ловится отдельно: Infinity спринтов — не прогноз. В реальности прогноз дают диапазоном: по худшему и лучшему спринтам из последних. Одно число создаёт ложное ощущение точности.

Задача 4. Данные для burndown-графика ★★☆ практика

Напишите burndown(total, days, done). total — очки в спринте, days — его длина в рабочих днях, done — массив закрытых очков по прошедшим дням. Верните массив { day, ideal, actual } для дней от 0 до days: ideal равномерно убывает от total до 0 (два знака после запятой), actual — остаток работы, а для будущих дней null. Добавьте isBehind(points): отстаёт ли команда в последний известный день.

Зачем: график — способ увидеть проблему на третий день спринта, а не на последний. Расчёт данных отделён от рисования, поэтому одну функцию можно проверить тестом, а нарисовать хоть в canvas, хоть в SVG.

Решение и разбор
export interface Point {
  day: number;
  ideal: number;
  actual: number | null;
}

export function burndown(total: number, days: number, done: readonly number[]): Point[] {
  let remaining = total;
  return Array.from({ length: days + 1 }, (_, day) => {
    if (day > 0 && day <= done.length) remaining -= done[day - 1]!;
    return {
      day,
      ideal: Math.round((total - (total * day) / days) * 100) / 100,
      actual: day <= done.length ? remaining : null,
    };
  });
}

export function isBehind(points: readonly Point[]): boolean {
  const known = points.filter((p) => p.actual !== null);
  const last = known.at(-1);
  return last !== undefined && last.actual! > last.ideal;
}

День 0 — начало спринта, остаток равен всему объёму. null для будущих дней честнее нуля: библиотеки графиков рисуют разрыв, а не падение до нуля. Округление идеальной линии через Math.round(x * 100) / 100 убирает хвосты вроде 26.666666666666668. Если фактическая линия идёт горизонтально несколько дней, это сигнал для Daily Scrum: задачи застряли, а не «почти готовы».

Задача 5. Раунд planning poker ★★☆ практика

Напишите pokerRound(votes), где votes — объект «участник → карта» из ряда 1, 2, 3, 5, 8, 13, 21 или "?" (не знаю). Правила: если все числовые голоса совпали, это консенсус — { status: "agreed", points }. Если крайние голоса отличаются больше чем на одну ступень ряда, это обсуждение — { status: "discuss", ask: [имена с минимальной и максимальной оценкой] }. Иначе берётся большая из соседних оценок — { status: "agreed", points }. Голоса "?" не учитываются, но если «не знают» все, верните { status: "split" }. Карта не из ряда — ошибка.

Зачем: смысл покера — не число, а разговор: разброс «2 и 13» означает, что люди по-разному понимают задачу. Правило «объясняют крайние» превращает голосование в способ найти недопонимание до начала работы.

Решение и разбор
export const DECK = [1, 2, 3, 5, 8, 13, 21] as const;
export type Card = (typeof DECK)[number] | '?';
export type Round = { status: 'agreed'; points: number } | { status: 'discuss'; ask: string[] } | { status: 'split' };

export function pokerRound(votes: Record<string, Card>): Round {
  const numeric = Object.entries(votes).filter((e): e is [string, Exclude<Card, '?'>] => e[1] !== '?');
  for (const [name, card] of numeric) {
    if (!(DECK as readonly number[]).includes(card)) throw new RangeError(`${name}: карты ${card} нет в колоде`);
  }
  if (numeric.length === 0) return { status: 'split' };
  const steps = numeric.map(([, c]) => DECK.indexOf(c));
  const min = Math.min(...steps);
  const max = Math.max(...steps);
  if (max - min > 1) {
    const ask = numeric.filter(([, c]) => DECK.indexOf(c) === min || DECK.indexOf(c) === max).map(([n]) => n);
    return { status: 'discuss', ask };
  }
  return { status: 'agreed', points: DECK[max]! };
}

Расстояние считается в ступенях ряда, а не в числах: 13 и 21 — соседние карты, хотя разница 8. А 2 и 5 — уже обсуждение, хотя разница 3. При соседних оценках берётся большая: недооценка опаснее переоценки. Правило «ступень в одну — соглашаемся» — договорённость команды, а не стандарт (из общих знаний). Многие команды требуют полного совпадения.
