Kanban

Kanban пришёл из производственной системы Toyota: «канбан» по-японски — «карточка, вывеска». Ритма и ролей у него нет. Есть способ сделать работу видимой и управлять её потоком.

Доска и вытягивание

Работа изображается карточками на доске с колонками-этапами: «Бэклог → В работе → Ревью → Тестирование → Готово». Главное правило — вытягивание (pull): карточку берут в следующую колонку, когда там освободилось место, а не «толкают» туда по указанию. Правила перехода (например, «в Ревью — только с открытым PR и зелёным CI») записывают явно прямо на доске.

Лимит незавершённой работы

WIP-лимит (work in progress) — максимум карточек в колонке. Если в «Ревью» лимит 3 и там уже 3 карточки, новую задачу туда не двигают. Вместо этого разработчик идёт помогать с ревью. Звучит как потеря скорости, но работает наоборот: меньше переключений между задачами, задачи быстрее доходят до конца, узкие места видны сразу — это колонка, которая всегда заполнена до лимита.

Задача 6. Kanban-доска с WIP-лимитами ★★☆ практика

Напишите класс Board с колонками и лимитами (new Board([{ name: "todo" }, { name: "doing", limit: 2 }, { name: "review", limit: 1 }, { name: "done" }])). Методы: add(id) кладёт карточку в первую колонку; pull(id) переносит карточку в следующую колонку, если там есть место по лимиту, иначе бросает ошибку с названием колонки; column(name) возвращает карточки колонки; bottleneck() — первая колонка, заполненная до лимита, или null.

Зачем: лимит работает, только если его нельзя нарушить «на минуточку». В коде, как и на хорошей доске, правило проверяется в момент перемещения. Метод bottleneck переводит вопрос «где у нас затор» в данные.

Решение и разбор
export interface ColumnDef {
  name: string;
  limit?: number;
}

export class Board {
  private readonly cards = new Map<string, number>(); // id карточки → индекс колонки

  constructor(private readonly columns: readonly ColumnDef[]) {
    if (columns.length < 2) throw new Error('Нужно хотя бы две колонки');
  }

  private count(index: number): number {
    return [...this.cards.values()].filter((i) => i === index).length;
  }

  add(id: string): void {
    if (this.cards.has(id)) throw new Error(`Карточка ${id} уже на доске`);
    const first = this.columns[0]!;
    if (first.limit !== undefined && this.count(0) >= first.limit) throw new Error(`Колонка ${first.name} заполнена`);
    this.cards.set(id, 0);
  }

  pull(id: string): void {
    const from = this.cards.get(id);
    if (from === undefined) throw new Error(`Нет карточки ${id}`);
    const to = from + 1;
    const target = this.columns[to];
    if (!target) throw new Error(`Карточка ${id} уже в последней колонке`);
    if (target.limit !== undefined && this.count(to) >= target.limit) {
      throw new Error(`WIP-лимит колонки ${target.name}: ${target.limit}`);
    }
    this.cards.set(id, to);
  }

  column(name: string): string[] {
    const index = this.columns.findIndex((c) => c.name === name);
    return [...this.cards].filter(([, i]) => i === index).map(([id]) => id);
  }

  bottleneck(): string | null {
    const full = this.columns.find((c, i) => c.limit !== undefined && this.count(i) >= c.limit);
    return full?.name ?? null;
  }
}

Карточка хранит индекс колонки, а не имя. Тогда «следующая колонка» — это +1, и переименование колонки ничего не ломает. Перемещение только на одну колонку вперёд — упрощение: на настоящих досках карточки возвращают назад (ревью не прошло), и для этого нужен отдельный метод со своими правилами. Ошибка называет колонку и лимит, поэтому интерфейс доски может показать понятное сообщение, а не просто «нельзя».

Метрики потока

  • Lead time — от появления задачи на доске до «Готово»: сколько ждал заказчик.
  • Cycle time — от начала работы до «Готово»: сколько делала команда.
  • Throughput (пропускная способность) — сколько задач завершается за период.
  • Cumulative Flow Diagram — график числа карточек в каждой колонке по дням. Расширяющаяся полоса — узкое место.

Их связывает закон Литтла: среднее время в работе = среднее число задач в работе / пропускная способность. Отсюда главный вывод Kanban: чтобы задачи проходили быстрее, нужно уменьшить число одновременно начатых задач, а не начать больше (из общих знаний: закон сформулирован в теории очередей, в материалах модуля его нет).

Задача 7. Lead time, cycle time и throughput ★★☆ практика

У каждой карточки есть история: { id, created, started, finished } (даты ISO, started и finished могут быть null). Напишите flowMetrics(cards, from, to): для карточек, завершённых в интервале [from, to), посчитайте средние lead time и cycle time в днях (один знак после запятой) и throughput — число завершённых. Если завершённых нет, средние — null.

Зачем: это объективные данные для ретроспективы. Разница между lead time и cycle time — время, которое задача пролежала в бэклоге. Если она велика, проблема не в скорости разработки, а в приоритизации.

Решение и разбор
export interface Card {
  id: string;
  created: string;
  started: string | null;
  finished: string | null;
}
const DAY = 24 * 60 * 60 * 1000;
const avg = (xs: number[]) => (xs.length ? Math.round((xs.reduce((a, b) => a + b, 0) / xs.length) * 10) / 10 : null);

export function flowMetrics(cards: readonly Card[], from: string, to: string) {
  const start = Date.parse(from);
  const end = Date.parse(to);
  const finished = cards.filter((c): c is Card & { finished: string } => {
    if (c.finished === null) return false;
    const t = Date.parse(c.finished);
    return t >= start && t < end;
  });
  const days = (a: string, b: string) => (Date.parse(b) - Date.parse(a)) / DAY;
  return {
    throughput: finished.length,
    leadTime: avg(finished.map((c) => days(c.created, c.finished))),
    cycleTime: avg(finished.filter((c) => c.started !== null).map((c) => days(c.started!, c.finished))),
  };
}

Интервал полуоткрытый, [from, to): карточка, завершённая ровно в полночь начала следующей недели, попадёт в следующую неделю, а не в обе. Так соседние периоды не пересекаются. Карточка без started (сразу из бэклога в «готово») учитывается в lead time, но не в cycle time. В реальных отчётах вместо среднего часто берут 85-й перцентиль: он устойчивее к одной задаче, которая висела месяц (из общих знаний).

Задача 8. Закон Литтла на практике ★☆☆ разминка

Команда закрывает в среднем 10 задач в неделю, и в работе одновременно 30 задач. Напишите avgTimeInSystem(wip, throughput) и wipForTarget(targetTime, throughput). Посчитайте: сколько сейчас в среднем идёт задача и каким должен быть WIP, чтобы задача проходила за полнедели.

Зачем: это самый короткий аргумент для разговора «давайте возьмём ещё задач, чтобы успеть». Формула показывает, что при той же пропускной способности больше начатых задач значит только больше ожидания.

Решение и разбор
export function avgTimeInSystem(wip: number, throughput: number): number {
  if (throughput <= 0) throw new RangeError('Пропускная способность должна быть больше нуля');
  return wip / throughput;
}

export const wipForTarget = (targetTime: number, throughput: number): number => Math.floor(targetTime * throughput);

// 30 задач / 10 в неделю = 3 недели на задачу.
// Чтобы проходить за 0,5 недели при тех же 10 в неделю: WIP = 5.

Единицы должны совпадать: задачи в неделю дают время в неделях. Закон описывает средние значения устойчивой системы, а не отдельную задачу. Если в бэклог постоянно добавляют больше, чем команда закрывает, никакой WIP-лимит не поможет: очередь будет расти. Math.floor в лимите — снова осторожная сторона: лимит 5,5 задачи на практике значит 5.
