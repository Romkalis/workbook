Что часто путают

  • Токен не хранится на сервере. Поэтому «выгнать» пользователя до истечения срока сложно: сервер не может забыть токен, которого не помнит. Остаётся ждать exp или вести чёрный список отозванных токенов в базе или Redis. По этой же причине срок жизни делают коротким.
  • Payload читает каждый. Вставьте токен на jwt.io — и увидите id. Пароли и личные данные туда не кладут.
  • jwt.verify бросает исключение. Нужен try/catch, а не if (!decoded).
  • exp добавляется сам. Достаточно передать expiresIn в jwt.sign.
  • Сменили JWT_SECRET — все выйдут. Все выданные токены станут недействительными: их подписи считались старым секретом. Иногда этим пользуются намеренно, чтобы разлогинить всех.
  • Refresh-токены — следующий шаг. В рабочих системах выдают пару: короткий access-токен (минуты) и долгий refresh-токен, которым можно получить новый access без повторного ввода пароля. Для учебного проекта пока не обязательно.

Задача 15. Выйти на всех устройствах ★★★ с подвохом

Токен нельзя отозвать, но можно сделать устаревшим. Добавьте пользователю поле tokenVersion (число). При входе версия кладётся в токен, requireAuth сверяет её с хранилищем, а POST /api/auth/logout-all увеличивает версию. После этого все ранее выданные токены перестают работать, а новый вход снова работает.

Зачем: это компромисс между «сервер ничего не хранит» и «нужно уметь выгнать пользователя». Мы храним одно число на пользователя, а не список токенов. Цена — одно чтение из хранилища на запрос, и мы его уже делаем, когда берём профиль.

Решение и разбор
// app.ts
import express, { type RequestHandler } from 'express';
import jwt from 'jsonwebtoken';

export interface User {
  id: string;
  tokenVersion: number;
}

export function createApp(secret: string, users: Map<string, User>) {
  const app = express();
  app.use(express.json());

  const issue = (user: User) => jwt.sign({ sub: user.id, ver: user.tokenVersion }, secret, { expiresIn: '1h' });

  const requireAuth: RequestHandler = (req, res, next) => {
    const [scheme, token] = (req.headers.authorization ?? '').split(' ');
    try {
      if (scheme !== 'Bearer' || !token) throw new Error('no token');
      const p = jwt.verify(token, secret, { algorithms: ['HS256'] });
      if (typeof p === 'string' || typeof p.sub !== 'string') throw new Error('payload');
      const user = users.get(p.sub);
      if (!user || p.ver !== user.tokenVersion) throw new Error('revoked');
      res.locals.user = user;
      next();
    } catch {
      res.status(401).json({ message: 'Нужен вход' });
    }
  };

  app.post('/api/auth/login', (req, res) => {
    const user = users.get(String(req.body.userId));
    if (!user) return res.status(401).json({ message: 'Нужен вход' });
    res.json({ token: issue(user) });
  });
  app.get('/api/me', requireAuth, (_req, res) => {
    res.json({ id: (res.locals.user as User).id });
  });
  app.post('/api/auth/logout-all', requireAuth, (_req, res) => {
    const user = res.locals.user as User;
    users.set(user.id, { ...user, tokenVersion: user.tokenVersion + 1 });
    res.status(204).end();
  });
  return app;
}

Тот же механизм пригодится при смене пароля: увеличили версию, и украденные токены перестали работать. Альтернатива — «чёрный список» отозванных токенов. Но его нужно хранить до истечения каждого токена, и он растёт. В рабочих системах обычно комбинируют короткий access-токен и refresh-токен, который хранится на сервере и отзывается (раздел «Что часто путают»).
