Из чего состоит JWT

Токен — это одна строка из трёх частей, разделённых точками:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9                                  ← header
.eyJpZCI6IjY2NGYyYSIsImlhdCI6MTc5MzY4ODY3MywiZXhwIjoxNzkzNzc1MDczfQ   ← payload
.L3Vp…                                                                ← signature

Здесь токен разбит на строки для наглядности, на деле это одна строка без пробелов.

  1. Header (заголовок) — служебные данные: каким алгоритмом подписан токен. Например, {"alg":"HS256","typ":"JWT"}.
  2. Payload (полезная нагрузка) — то, что сервер положил в токен. Например, {"id":"664f2a","iat":1793688673,"exp":1793775073}. Поле iat — когда выдан, exp — когда истекает (в секундах с 1970 года).
  3. Signature (подпись) — строка, которую сервер вычислил из первых двух частей и своего секретного ключа.

Первые две части — это обычный JSON, записанный в кодировке base64url. Кодировка — не шифр: её может раскодировать кто угодно. Проверьте сами в Node.js:

const payload = token.split('.')[1];
console.log(Buffer.from(payload, 'base64url').toString());
// {"id":"664f2a","iat":1793688673,"exp":1793775073}

Подпись — не шифрование

Это главное, что нужно понять про JWT. Данные в токене не спрятаны, их видит любой, у кого есть токен. Защищены они от другого — от изменения.

Представьте открытку с печатью. Текст на ней читает каждый почтальон. Но если кто-то исправит текст, печать перестанет совпадать, и это сразу будет видно.

Отсюда два правила:

  • не кладите в токен пароли и другие секреты — их прочитают;
  • доверять данным из токена можно, только если сервер проверил подпись.

Фраза «я шифрую id пользователя в JWT» поэтому неточна: id не шифруют, а подписывают. Зашифрованные JWT тоже существуют (стандарт JWE), но в учебных и большинстве рабочих проектов токены только подписывают.

Задача 1. Прочитать токен без библиотеки ★☆☆ разминка

Задачи урока решаются на TypeScript с ES-модулями, как в уроке Express + TypeScript. Код урока написан на CommonJS, но идеи те же.

Напишите readPayload(token: string): unknown, которая раскодирует вторую часть токена. Если частей не три или это не JSON, бросьте TypeError. Проверьте на токене, подписанном jwt.sign.

Зачем: так своими руками проверяется главная мысль урока: содержимое токена читает любой, секрет для этого не нужен. После этой задачи мысль «положу в токен пароль» уже не появится.

Решение и разбор
export function readPayload(token: string): unknown {
  const parts = token.split('.');
  if (parts.length !== 3 || parts[1] === undefined) throw new TypeError('JWT состоит из трёх частей');
  try {
    return JSON.parse(Buffer.from(parts[1], 'base64url').toString('utf8'));
  } catch {
    throw new TypeError('Payload не является JSON');
  }
}

Результат — unknown, и это честно. Функция ничего не проверяет: подделанный токен она прочитает так же охотно, как настоящий. Поэтому на сервере её использовать для решений нельзя, только jwt.verify. На клиенте такое чтение уместно, например чтобы заранее узнать exp и обновить токен до истечения. Кодировка base64url отличается от обычной base64 заменой +/ на -_ и отсутствием = в конце, чтобы токен можно было передать в адресе.

Задача 2. Подпись HS256 своими руками ★★★ с подвохом

Повторите jwt.sign и jwt.verify для алгоритма HS256 на модуле node:crypto: sign(payload, secret) и verify(token, secret). Шаги перечислены в разделе «Что делает jwt.sign». Ваш токен должна принять библиотека jsonwebtoken, а ваш verify — отвергнуть токен с изменённым payload. Сроки (exp) пока не проверяйте.

Зачем: когда подпись собрана руками, исчезает магия: становится видно, что это HMAC от двух первых частей и что без секрета её не пересчитать. В рабочем коде пишите jsonwebtoken, а не свою версию: там учтены алгоритмы, сроки и десятки пограничных случаев.

Подсказка

createHmac("sha256", secret).update(${h}.${p}).digest("base64url"). Подписи сравнивайте через timingSafeEqual из того же модуля, предварительно сравнив длины.

Решение и разбор
import { createHmac, timingSafeEqual } from 'node:crypto';

const encode = (value: object) => Buffer.from(JSON.stringify(value)).toString('base64url');
const hmac = (data: string, secret: string) => createHmac('sha256', secret).update(data).digest('base64url');

export function sign(payload: object, secret: string): string {
  const head = encode({ alg: 'HS256', typ: 'JWT' });
  const body = encode({ ...payload, iat: Math.floor(Date.now() / 1000) });
  return `${head}.${body}.${hmac(`${head}.${body}`, secret)}`;
}

export function verify(token: string, secret: string): Record<string, unknown> {
  const [head, body, signature, ...rest] = token.split('.');
  if (!head || !body || !signature || rest.length > 0) throw new Error('jwt malformed');
  const header: unknown = JSON.parse(Buffer.from(head, 'base64url').toString());
  if (typeof header !== 'object' || header === null || !('alg' in header) || header.alg !== 'HS256') {
    throw new Error('invalid algorithm');
  }
  const expected = Buffer.from(hmac(`${head}.${body}`, secret));
  const actual = Buffer.from(signature);
  if (expected.length !== actual.length || !timingSafeEqual(expected, actual)) throw new Error('invalid signature');
  return JSON.parse(Buffer.from(body, 'base64url').toString()) as Record<string, unknown>;
}

Почему не ===? Обычное сравнение строк останавливается на первом несовпавшем символе. Замеряя время ответа, можно в теории подбирать подпись по символу. timingSafeEqual всегда сравнивает всё. Проверка alg — защита от известной атаки: токен с заголовком "alg": "none" и пустой подписью. Если сервер берёт алгоритм из самого токена, он принимает подделку. Ровно поэтому в уроке у jwt.verify указано algorithms: ['HS256'].

Задача 3. Тест, который ловит доверие к decode ★★☆ практика

Функция userIdFrom(token, secret) должна возвращать id из проверенного токена. Напишите тесты, которые падают, если внутри кто-то заменил jwt.verify на jwt.decode: подделанный payload, чужой секрет, просроченный токен.

// user-id.ts
import jwt from 'jsonwebtoken';
export function userIdFrom(token: string, secret: string): string {
  const payload = jwt.verify(token, secret, { algorithms: ['HS256'] });
  if (typeof payload !== 'object' || typeof payload.id !== 'string') throw new Error('invalid payload');
  return payload.id;
}

Зачем: jwt.decode и jwt.verify возвращают одно и то же на правильном токене. Разница видна только на неправильном. Если тесты проверяют только счастливый путь, такая замена пройдёт ревью и откроет вход под любым пользователем.

Решение и разбор
// user-id.test.ts
import jwt from 'jsonwebtoken';
import { expect, it } from 'vitest';
import { userIdFrom } from './user-id.js';

const SECRET = 's'.repeat(32);

it('принимает свой токен', () => {
  expect(userIdFrom(jwt.sign({ id: 'u1' }, SECRET), SECRET)).toBe('u1');
});

it('отвергает изменённый payload', () => {
  const [head, , sig] = jwt.sign({ id: 'u1' }, SECRET).split('.');
  const forged = Buffer.from(JSON.stringify({ id: 'admin' })).toString('base64url');
  expect(() => userIdFrom(`${head}.${forged}.${sig}`, SECRET)).toThrow();
});

it('отвергает токен с чужим секретом', () => {
  expect(() => userIdFrom(jwt.sign({ id: 'u1' }, 'чужой'), SECRET)).toThrow();
});

it('отвергает просроченный токен', () => {
  const old = jwt.sign({ id: 'u1', exp: Math.floor(Date.now() / 1000) - 10 }, SECRET);
  expect(() => userIdFrom(old, SECRET)).toThrow('jwt expired');
});

Просроченный токен делается без ожидания: exp можно передать прямо в payload, задав время в прошлом. Это быстрее и надёжнее, чем подменять часы. Каждый тест проверяет одну причину отказа. Если упадёт, по названию сразу видно, какая защита пропала. Попробуйте сами: замените в функции verify на decode, и три теста из четырёх покраснеют.
