Модель пользователя и хеш пароля

// models/User.js
const mongoose = require('mongoose');
const bcrypt = require('bcrypt');

const userSchema = new mongoose.Schema({
  email: { type: String, required: true, unique: true },
  password: { type: String, required: true }, // здесь будет хеш, а не сам пароль
});

// Перед сохранением хешируем пароль, если он новый или изменился
userSchema.pre('save', async function () {
  if (!this.isModified('password')) return;
  this.password = await bcrypt.hash(this.password, 10);
});

// Проверка пароля при входе
userSchema.methods.comparePassword = function (candidate) {
  return bcrypt.compare(candidate, this.password);
};

module.exports = mongoose.model('User', userSchema);

Что такое хеш

Пароль никогда не хранится как есть. bcrypt.hash превращает "1234" в строку вида $2b$10$N9qo8uLOickgx2ZMRZoMy… длиной 60 символов. Обратно из неё пароль получить нельзя.

Как же тогда проверить пароль при входе? Не расшифровкой, а сравнением: введённый пароль хешируется заново тем же способом, и результаты сравниваются. Это делает bcrypt.compare. Число 10 — «стоимость» хеширования: чем больше, тем медленнее подбирать пароли перебором.

Даже если базу украдут, злоумышленник получит хеши, а не пароли.

Задача 5. Хеш с солью ★☆☆ разминка

С пакетом bcryptjs (замена bcrypt на чистом JavaScript, API тот же) напишите hashPassword(plain) и checkPassword(plain, hash). Убедитесь тестом, что два хеша одного пароля разные, но оба проходят проверку.

Зачем: разные хеши одного пароля — это соль: случайная добавка, которая хранится прямо в строке хеша. Без соли одинаковые пароли давали бы одинаковые хеши, и утёкшую базу можно было бы расшифровать заранее подготовленной таблицей.

Решение и разбор
import bcrypt from 'bcryptjs';

const COST = 10;

export const hashPassword = (plain: string): Promise<string> => bcrypt.hash(plain, COST);
export const checkPassword = (plain: string, hash: string): Promise<boolean> => bcrypt.compare(plain, hash);

Хеш вида $2b$10$<22 символа соли><31 символ хеша> содержит всё нужное для проверки: алгоритм, стоимость и соль. Поэтому compare не нужна отдельная соль. COST = 10 означает 210 раундов. Каждая единица удваивает время, и для злоумышленника перебор становится дорогим. В тестах ради скорости можно брать 4, минимум для bcrypt.

Почему function, а не стрелка

Внутри хука this — это документ, который сохраняется. У стрелочной функции своего this нет, поэтому здесь нужна обычная function.

this.isModified('password') защищает от двойного хеширования: если пользователь поменял только email, пароль уже хранится как хеш, и хешировать его снова нельзя, иначе войти больше не получится.

Отличие от исходного материала

В исходнике хук написан как async function (next) с вызовами next(). Для асинхронной функции next не нужен: Mongoose сам ждёт, пока завершится Promise. Мы проверили оба варианта. В mongoose 8 работают оба. В mongoose 9 в хук больше не передаётся next, и код из исходника падает с ошибкой «next is not a function». Вариант без next работает в обеих версиях.

Задача 6. Не захешировать хеш ★★☆ практика

Без MongoDB повторите смысл хука pre('save') с isModified. Напишите репозиторий в памяти: create(email, password) хеширует пароль, changeEmail(id, email) меняет только почту, changePassword(id, password) хеширует новый пароль. Проверка: после смены почты старый пароль подходит.

Зачем: если хешировать пароль при каждом сохранении, после смены почты в базе окажется хеш от хеша, и пользователь больше не войдёт. Это самая частая ошибка с хуком pre('save'). Здесь она воспроизводится без базы, и видно, почему нужна проверка «пароль изменился».

Решение и разбор
import bcrypt from 'bcryptjs';

export interface StoredUser {
  id: string;
  email: string;
  passwordHash: string;
}

export function createUserRepo(cost = 4) {
  const users = new Map<string, StoredUser>();
  let next = 1;

  return {
    async create(email: string, password: string): Promise<StoredUser> {
      const user = { id: String(next++), email, passwordHash: await bcrypt.hash(password, cost) };
      users.set(user.id, user);
      return user;
    },
    changeEmail(id: string, email: string): void {
      const user = users.get(id);
      if (user) users.set(id, { ...user, email });
    },
    async changePassword(id: string, password: string): Promise<void> {
      const user = users.get(id);
      if (user) users.set(id, { ...user, passwordHash: await bcrypt.hash(password, cost) });
    },
    async login(email: string, password: string): Promise<StoredUser | null> {
      const user = [...users.values()].find((u) => u.email === email);
      return user && (await bcrypt.compare(password, user.passwordHash)) ? user : null;
    },
  };
}

Поле называется passwordHash, а не password, и это тоже защита: по имени видно, что внутри не пароль, и никто не положит туда открытый текст. Хеширование происходит только в двух методах, которые получают новый пароль. В Mongoose ту же гарантию даёт isModified('password'). Явные методы, как здесь, проще проверить, но о них нужно помнить при каждом новом сценарии изменения.
