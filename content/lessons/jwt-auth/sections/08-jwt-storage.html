Где хранить токен на клиенте

Сервер отдал токен. Теперь клиент должен его где-то сохранить и прикладывать к запросам. Основных вариантов два.

localStorage и заголовок Authorization

// после входа
localStorage.setItem('token', data.token);

// при каждом запросе
fetch('/api/user/profile', {
  headers: { Authorization: `Bearer ${localStorage.getItem('token')}` },
});

Просто и понятно. Минус: любой JavaScript на странице может прочитать localStorage. Если злоумышленник сумеет внедрить свой скрипт (такая атака называется XSS), он украдёт токен.

httpOnly cookie

// на сервере при входе вместо res.json({ token })
res.cookie('token', token, {
  httpOnly: true,                                  // JavaScript страницы cookie не видит
  secure: process.env.NODE_ENV === 'production',   // только по HTTPS
  sameSite: 'strict',                              // не отправлять с чужих сайтов
  maxAge: 24 * 60 * 60 * 1000,                     // сутки, как у токена
});
res.json({ ok: true });

Браузер сам прикладывает cookie к запросам, а скрипты на странице прочитать её не могут. Это безопаснее при XSS. Но middleware теперь должен брать токен не из заголовка, а из cookie. Вот что нужно изменить, этого шага в исходном материале нет:

// app.js
app.use(require('cookie-parser')());

// middleware/auth.js — вместо разбора заголовка
const token = req.cookies.token;
if (!token) return res.status(401).json({ message: 'Токен не предоставлен' });

Если фронтенд и сервер живут на разных адресах, понадобится настройка CORS с credentials: true на сервере и credentials: 'include' в fetch. Cookie отправляются автоматически, поэтому появляется риск другой атаки, CSRF: чужой сайт заставляет браузер отправить запрос с вашей cookie. sameSite: 'strict' во многом его закрывает.

Для учебного проекта начните с localStorage и заголовка: так проще увидеть, что происходит. В рабочем проекте чаще выбирают httpOnly cookie.
