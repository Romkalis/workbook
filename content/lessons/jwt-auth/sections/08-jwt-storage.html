Где хранить токен на клиенте

Сервер отдал токен. Теперь клиент должен его где-то сохранить и прикладывать к запросам. Основных вариантов два.

localStorage и заголовок Authorization

// после входа
localStorage.setItem('token', data.token);

// при каждом запросе
fetch('/api/user/profile', {
  headers: { Authorization: `Bearer ${localStorage.getItem('token')}` },
});

Просто и понятно. Минус: любой JavaScript на странице может прочитать localStorage. Если злоумышленник сумеет внедрить свой скрипт (такая атака называется XSS), он украдёт токен.

Задача 13. Клиент: токен в каждом запросе и выход по 401 ★★☆ практика

Напишите на клиенте createAuthClient(storage, onLogout) с методами login(token), logout() и fetch(url, init?). fetch добавляет Authorization, если токен есть, и сохраняет заголовки, переданные вызывающим. При ответе 401 токен удаляется и вызывается onLogout. storage — объект с интерфейсом localStorage, чтобы в тесте подставить заглушку.

Зачем: если вручную дописывать заголовок в каждом fetch, его обязательно где-то забудут. Одна обёртка — одно место, где живут правила авторизации: как прикладывать токен и что делать, когда он перестал действовать.

Решение и разбор
type TokenStorage = Pick<Storage, 'getItem' | 'setItem' | 'removeItem'>;
const KEY = 'token';

export function createAuthClient(storage: TokenStorage, onLogout: () => void) {
  const logout = () => {
    storage.removeItem(KEY);
    onLogout();
  };
  return {
    login(token: string) {
      storage.setItem(KEY, token);
    },
    logout,
    async fetch(url: string, init: RequestInit = {}): Promise<Response> {
      const headers = new Headers(init.headers);
      const token = storage.getItem(KEY);
      if (token) headers.set('Authorization', `Bearer ${token}`);
      const response = await fetch(url, { ...init, headers });
      if (response.status === 401) logout();
      return response;
    },
  };
}

new Headers(init.headers) принимает любую форму заголовков: объект, массив пар или другой Headers. Если просто написать { ...init.headers, Authorization }, это сломается, когда вызывающий передал Headers: spread его не раскрывает. Pick<Storage, …> описывает ровно то, что нужно, и в тесте хватает маленькой заглушки на Map. 403 не разлогинивает: пользователь известен, просто действие запрещено.

httpOnly cookie

// на сервере при входе вместо res.json({ token })
res.cookie('token', token, {
  httpOnly: true,                                  // JavaScript страницы cookie не видит
  secure: process.env.NODE_ENV === 'production',   // только по HTTPS
  sameSite: 'strict',                              // не отправлять с чужих сайтов
  maxAge: 24 * 60 * 60 * 1000,                     // сутки, как у токена
});
res.json({ ok: true });

Браузер сам прикладывает cookie к запросам, а скрипты на странице прочитать её не могут. Это безопаснее при XSS. Но middleware теперь должен брать токен не из заголовка, а из cookie. Вот что нужно изменить, этого шага в исходном материале нет:

// app.js
app.use(require('cookie-parser')());

// middleware/auth.js — вместо разбора заголовка
const token = req.cookies.token;
if (!token) return res.status(401).json({ message: 'Токен не предоставлен' });

Если фронтенд и сервер живут на разных адресах, понадобится настройка CORS с credentials: true на сервере и credentials: 'include' в fetch. Cookie отправляются автоматически, поэтому появляется риск другой атаки, CSRF: чужой сайт заставляет браузер отправить запрос с вашей cookie. sameSite: 'strict' во многом его закрывает.

Задача 14. Токен в httpOnly cookie ★★☆ практика

Переделайте вход на cookie. POST /api/auth/login ставит cookie token с флагами HttpOnly, SameSite=Strict, Path=/ и сроком час, а в теле отвечает { ok: true }. GET /api/me читает токен из cookie. POST /api/auth/logout удаляет cookie. Пароли проверять не нужно: вход принимает { userId }, нас интересует только транспорт токена.

Зачем: cookie с HttpOnly недоступна JavaScript страницы, и XSS не сможет украсть токен. Выход здесь — это удаление cookie на сервере: клиентский код до неё не дотянется, даже если захочет.

Решение и разбор
// app.ts
import cookieParser from 'cookie-parser';
import express from 'express';
import jwt from 'jsonwebtoken';

const COOKIE = { httpOnly: true, sameSite: 'strict', path: '/', secure: process.env.NODE_ENV === 'production' } as const;

export function createApp(secret: string) {
  const app = express();
  app.use(express.json());
  app.use(cookieParser());

  app.post('/api/auth/login', (req, res) => {
    const token = jwt.sign({ sub: String(req.body.userId) }, secret, { expiresIn: '1h' });
    res.cookie('token', token, { ...COOKIE, maxAge: 60 * 60 * 1000 }).json({ ok: true });
  });

  app.get('/api/me', (req, res) => {
    const token: unknown = req.cookies.token;
    if (typeof token !== 'string') return res.status(401).json({ message: 'Нужен вход' });
    try {
      const p = jwt.verify(token, secret, { algorithms: ['HS256'] });
      if (typeof p === 'string') throw new Error('payload');
      res.json({ userId: p.sub });
    } catch {
      res.status(401).json({ message: 'Нужен вход' });
    }
  });

  app.post('/api/auth/logout', (_req, res) => {
    res.clearCookie('token', COOKIE).json({ ok: true });
  });
  return app;
}

clearCookie должен получить те же path и sameSite, что и при установке. Иначе браузер посчитает это другой cookie и не удалит исходную. Поэтому параметры вынесены в общую константу. maxAge задаётся в миллисекундах, а в заголовке превращается в секунды (Max-Age=3600). Токен остаётся действительным до exp, даже после удаления cookie. Если его успели скопировать, выход его не отзовёт, и это ограничение JWT из раздела «Что часто путают».
