Защищённые маршруты: middleware

Middleware в Express — функция, которая выполняется до обработчика маршрута. Она может пропустить запрос дальше (next()) или сразу ответить сама. Для авторизации это идеальное место: проверяем токен один раз и подключаем проверку к нужным маршрутам.

// middleware/auth.js
const jwt = require('jsonwebtoken');

module.exports = function authMiddleware(req, res, next) {
  // 1. Достаём токен из заголовка "Authorization: Bearer xxx.yyy.zzz"
  const authHeader = req.headers.authorization;
  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({ message: 'Токен не предоставлен' });
  }
  const token = authHeader.split(' ')[1];

  try {
    // 2. Проверяем подпись и срок
    const decoded = jwt.verify(token, process.env.JWT_SECRET, { algorithms: ['HS256'] });
    // decoded: { id: '664f2a', iat: ..., exp: ... }

    // 3. Кладём id в req, чтобы обработчик маршрута мог им пользоваться
    req.userId = decoded.id;
    next();
  } catch (err) {
    // подпись не совпала или срок истёк
    return res.status(401).json({ message: 'Невалидный или просроченный токен' });
  }
};

Что делает jwt.verify

  1. Разбивает токен на три части.
  2. Сам заново считает подпись от первых двух частей своим секретом.
  3. Сравнивает её с подписью в токене. Не совпала — ошибка invalid signature.
  4. Смотрит на exp. Срок прошёл — ошибка jwt expired.
  5. Если всё в порядке, возвращает payload как обычный объект.

Важная деталь: при неудаче jwt.verify выбрасывает исключение, а не возвращает false. Поэтому нужен try/catch, а не if.

Опция algorithms: ['HS256'] говорит библиотеке принимать только наш алгоритм. Её нет в исходном материале, но её советует документация jsonwebtoken: так сервер не примет токен, подписанный другим способом.

Задача 10. requireAuth на TypeScript ★★☆ практика

Напишите middleware requireAuth(secret): достаёт токен из Authorization: Bearer …, проверяет его только с алгоритмом HS256 и кладёт id пользователя (sub) в res.locals.userId. Отказы — 401 с разными текстами: нет заголовка, неверный формат, просрочен, подпись неверна. Подключите к GET /api/me, который отвечает { userId }.

Зачем: в уроке id кладётся в req.userId, а TypeScript такого поля не знает. res.locals — предусмотренное Express место для данных одного запроса. Разные тексты отказов помогают клиенту: на «просрочен» можно тихо обновить токен, а на «подпись неверна» — выйти из аккаунта.

Решение и разбор
// app.ts
import express, { type RequestHandler } from 'express';
import jwt from 'jsonwebtoken';

export function requireAuth(secret: string): RequestHandler {
  return (req, res, next) => {
    const header = req.headers.authorization;
    if (!header) return res.status(401).json({ message: 'Токен не предоставлен' });
    const [scheme, token, ...rest] = header.split(' ');
    if (scheme !== 'Bearer' || !token || rest.length > 0) {
      return res.status(401).json({ message: 'Ожидался заголовок Authorization: Bearer <token>' });
    }
    try {
      const payload = jwt.verify(token, secret, { algorithms: ['HS256'] });
      if (typeof payload === 'string' || typeof payload.sub !== 'string') {
        return res.status(401).json({ message: 'Неверное содержимое токена' });
      }
      res.locals.userId = payload.sub;
      next();
    } catch (err) {
      const expired = err instanceof jwt.TokenExpiredError;
      res.status(401).json({ message: expired ? 'Токен просрочен' : 'Невалидный токен' });
    }
  };
}

export function createApp(secret: string) {
  const app = express();
  app.get('/api/me', requireAuth(secret), (_req, res) => {
    res.json({ userId: res.locals.userId });
  });
  return app;
}

jwt.verify возвращает string | JwtPayload: строкой payload бывает, если подписали строку, а не объект. Поэтому проверка формы нужна и после проверки подписи. Подпись говорит «это выпустили мы», но не «внутри то, что мы ждём». TokenExpiredError — класс из библиотеки, его различают через instanceof, а не по тексту сообщения. Тексты могут поменяться в новой версии. Фабрика requireAuth(secret) получает секрет параметром, без чтения process.env внутри. Так её легко тестировать.

Подключаем к маршруту

// routes/user.js
const router = require('express').Router();
const authMiddleware = require('../middleware/auth');
const User = require('../models/User');

router.get('/profile', authMiddleware, async (req, res) => {
  try {
    // req.userId положил authMiddleware
    const user = await User.findById(req.userId).select('-password');
    if (!user) return res.status(404).json({ message: 'Пользователь не найден' });
    res.json(user);
  } catch (err) {
    res.status(500).json({ message: 'Ошибка сервера' });
  }
});

module.exports = router;

.select('-password') убирает хеш пароля из ответа. Пользователя всё равно ищем в базе: токен говорит, кто пришёл, но актуальные данные профиля лежат в базе. Пользователя могли удалить уже после того, как токен был выдан, — для этого и проверка на 404.

Задача 11. Профиль удалённого пользователя ★★☆ практика

Сделайте GET /api/profile поверх requireAuth из прошлой задачи. Профиль берётся из хранилища по id из токена. Отдельно обработайте случай, когда токен действителен, а пользователя уже удалили. В ответе нет passwordHash.

// auth.ts
import type { RequestHandler } from 'express';
import jwt from 'jsonwebtoken';
export function requireAuth(secret: string): RequestHandler {
  return (req, res, next) => {
    const [scheme, token] = (req.headers.authorization ?? '').split(' ');
    if (scheme !== 'Bearer' || !token) return res.status(401).json({ message: 'Токен не предоставлен' });
    try {
      const p = jwt.verify(token, secret, { algorithms: ['HS256'] });
      if (typeof p === 'string' || typeof p.sub !== 'string') throw new Error('payload');
      res.locals.userId = p.sub;
      next();
    } catch {
      res.status(401).json({ message: 'Невалидный токен' });
    }
  };
}

Зачем: токен живёт своей жизнью: сервер его не хранит и не может отозвать. Пока не истёк срок, токен удалённого или заблокированного пользователя проходит проверку подписи. Поэтому данные пользователя всегда читаются из базы, а не из токена.

Решение и разбор
// app.ts
import express from 'express';
import { requireAuth } from './auth.js';

export interface User {
  id: string;
  email: string;
  passwordHash: string;
}

export function createApp(secret: string, users: Map<string, User>) {
  const app = express();
  app.get('/api/profile', requireAuth(secret), (_req, res) => {
    const user = users.get(res.locals.userId as string);
    if (!user) return res.status(401).json({ message: 'Пользователь больше не существует' });
    res.json({ id: user.id, email: user.email });
  });
  return app;
}

В уроке на этот случай отвечают 404. Здесь выбран 401, и это сознательное решение: «профиль не найден» звучит как ошибка адреса, а на деле не действует сама сессия. Клиент, получив 401, отправит на вход. Оба варианта встречаются, главное — договориться и быть последовательным. res.locals имеет тип Record<string, any>, поэтому приведение к string — это документация того, что положил middleware.

Задача 12. 401 или 403: проверка роли ★★★ с подвохом

Добавьте middleware requireRole("admin"), который ставится после requireAuth. Роль берите из хранилища пользователей, а не из токена. Маршрут DELETE /api/users/:id доступен только администратору. Без токена — 401, с токеном обычного пользователя — 403, администратор — 204.

Зачем: разделение «кто вы» (аутентификация) и «что вам можно» (авторизация) — основа любой системы прав. Роль в токене удобна, но после понижения прав старый токен ещё час будет пускать бывшего администратора. Чтение из базы стоит один запрос, зато права меняются сразу.

Решение и разбор
// app.ts
import express, { type Request, type RequestHandler } from 'express';
import jwt from 'jsonwebtoken';

export interface User {
  id: string;
  role: 'user' | 'admin';
}

export function createApp(secret: string, users: Map<string, User>) {
  const requireAuth: RequestHandler = (req, res, next) => {
    const [scheme, token] = (req.headers.authorization ?? '').split(' ');
    try {
      if (scheme !== 'Bearer' || !token) throw new Error('no token');
      const p = jwt.verify(token, secret, { algorithms: ['HS256'] });
      if (typeof p === 'string' || typeof p.sub !== 'string') throw new Error('payload');
      res.locals.userId = p.sub;
      next();
    } catch {
      res.status(401).json({ message: 'Нужен вход' });
    }
  };

  const requireRole =
    (role: User['role']): RequestHandler =>
    (_req, res, next) => {
      const user = users.get(res.locals.userId as string);
      if (!user) return res.status(401).json({ message: 'Нужен вход' });
      if (user.role !== role) return res.status(403).json({ message: 'Недостаточно прав' });
      next();
    };

  const app = express();
  app.delete('/api/users/:id', requireAuth, requireRole('admin'), (req: Request<{ id: string }>, res) => {
    users.delete(req.params.id);
    res.status(204).end();
  });
  return app;
}

Цепочка middleware читается слева направо, как охрана на входе: сначала «покажите пропуск», потом «есть ли допуск в этот зал». Порядок важен: requireRole опирается на res.locals.userId, который кладёт requireAuth. Тест с понижением роли показывает, зачем роль читать из хранилища: тот же токен перестаёт давать права сразу.

Собираем приложение

// app.js
require('dotenv').config();
const express = require('express');
const mongoose = require('mongoose');

const app = express();
app.use(express.json()); // без этого req.body будет undefined
app.use('/api/auth', require('./routes/auth'));
app.use('/api/user', require('./routes/user'));

mongoose.connect(process.env.MONGO_URI)
  .then(() => app.listen(3000, () => console.log('Server on :3000')))
  .catch(console.error);

dotenv подключается первой строкой: переменные из .env должны появиться раньше, чем их прочитает остальной код.
