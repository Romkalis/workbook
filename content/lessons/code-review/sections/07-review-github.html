Инструменты и решения в GitHub

Из общих знаний и документации GitHub: во вкладке Files changed виден diff, возле строки можно оставить комментарий или предложение правки. Несколько замечаний удобно собрать в одно ревью, затем отправить вместе с общим выводом.

Comment, Approve, Request changes

  • Comment — обратная связь без явного одобрения и запроса обязательных исправлений.
  • Approve — рецензент считает изменение готовым к слиянию.
  • Request changes — есть замечания, которые нужно исправить до слияния.

Фактическая возможность слияния зависит от правил репозитория, прав доступа и настроек защиты ветки. Зелёный CI и одобрение — разные сигналы. CI проверяет настроенные команды; ревью оценивает то, что эти команды не охватывают.

Что поручить автоматике

У каждого инструмента своя узкая работа:

  • форматтер (Prettier) расставляет отступы и кавычки одинаково;
  • линтер (ESLint) находит подозрительные места по списку правил, например неиспользуемую переменную;
  • проверка типов (TypeScript) ловит, когда строку передали туда, где ждут число;
  • тесты проверяют те сценарии, которые вы для них написали.

Ни один из них не скажет, делает ли новая функция то, что нужно пользователю. Это остаётся на человеке, который проводит ревью.

У GitLab merge requests, Bitbucket pull requests и специализированных систем похожая задача, но набор функций и правила различаются. Для школьного задания достаточно освоить площадку, где находится репозиторий; устанавливать отдельный инструмент ради этого конспекта не нужно.

Как завершить ревью

Кратко укажите, что проверено, какие обязательные замечания остались и что остаётся непроверенным. Пример: «Проверил расчёт скидки, границы 0/100 и сохранность входа. До слияния нужно отклонять percent = NaN. Отображение корзины в браузере не проверял». Такой вывод точнее безусловного «всё хорошо».
