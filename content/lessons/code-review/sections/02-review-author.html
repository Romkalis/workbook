Как автору подготовить Pull Request

Рецензенту нужны цель, границы изменения и способ его проверить. Если эти сведения приходится угадывать по десяткам файлов, часть времени уйдёт на восстановление контекста вместо анализа.

Одно законченное изменение

Хороший PR решает одну понятную задачу и включает связанные проверки. Не смешивайте новую функцию, массовое форматирование и переименование всего проекта: это затрудняет сравнение. Размер определяйте смыслом и возможностью разобраться, а не обязательным лимитом строк.

Перед отправкой прочитайте собственный diff. Уберите случайные логи, временные файлы и секреты, проверьте требования проекта. Если меняется интерфейс, приложите результат на узком и широком экране. Если затронуто поведение при ошибке, опишите, как его воспроизвести.

Пример описания PR

Поиск больше не запрашивает пустую строку

После удаления текста поле поиска оставляло запрос с пустым параметром. Теперь пробелы по краям убираются, а пустой запрос завершает поиск без обращения к API. Проверено: обычный текст, только пробелы, очистка поля после успешного поиска. Ошибка API показывается сообщением с возможностью повторить запрос.

Такое описание объясняет изменение поведения и даёт проверяемые сценарии. Фраза «пофиксил баги и улучшил код» этого не делает. Отдельно назовите существенное ограничение: например, отмена предыдущего запроса будет в другой задаче, если текущие требования позволяют такой объём.

Когда просить ревью

Для законченного PR должны проходить необходимые проверки и быть понятен способ ручной проверки. Draft PR полезен для раннего обсуждения направления: прямо укажите, какую обратную связь ждёте и какие части ещё не готовы.
