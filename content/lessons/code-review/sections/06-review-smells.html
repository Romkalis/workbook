Запахи кода и производительность

Одна из целей модуля — научиться замечать баги, code smells и проблемы производительности. «Запах» (code smell) — это не ошибка, а признак, что код будет трудно менять. Сам по себе запах не повод блокировать PR. Повод — конкретный риск, который вы можете назвать.

Частые запахи — из общих знаний

Длинная функция
Делает несколько дел сразу: загружает, преобразует и рисует. Любую часть трудно проверить отдельно.
Дублирование
Одна и та же логика в двух местах. Исправите баг в одном месте и забудете про другое.
Магические числа и строки
if (status === 3) не говорит, что такое 3. Помогает именованная константа.
Длинный список параметров
Пять аргументов подряд легко перепутать местами. Часто лучше передать объект.
Флаг-параметр
render(true) прячет смысл. Обычно это две разные функции.
Глубокая вложенность
Четыре уровня if. Ранний return часто выпрямляет поток.
Мёртвый и закомментированный код
Читатель тратит время, чтобы понять, что код не работает. История и так хранится в git.
Неясные имена
data, tmp, handle2. Имя должно говорить, что лежит в переменной или что делает функция.

Производительность: сначала сценарий

Замечание о скорости полезно, когда вы можете описать вход, на котором будет медленно. Пример: список фильмов надо пометить избранными. В PR для каждого фильма вызывается includes по массиву избранного, то есть работа растёт как произведение двух длин.

// Версия из PR
function markFavoritesSlow(movies, favoriteIds) {
  return movies.map((m) => ({ ...m, favorite: favoriteIds.includes(m.id) }));
}

// Предложение рецензента
function markFavorites(movies, favoriteIds) {
  const ids = new Set(favoriteIds);
  return movies.map((m) => ({ ...m, favorite: ids.has(m.id) }));
}

На 20 000 фильмах и 20 000 избранных первая версия в Node.js 22 работала около 56 мс, вторая около 3 мс, результат одинаковый. Но если в избранном не больше десятка фильмов, разница незаметна. Хорошее замечание звучит так: «Если избранного может быть тысячи, includes внутри map даёт квадратичную работу. Set сохраняет поведение и проверяет за постоянное время. Не блокирую, если список заведомо маленький».

Что ещё искать во фронтенде — из общих знаний

  • Запрос в цикле вместо одного запроса со списком.
  • Обработчик scroll или input без троттлинга, который каждый раз перестраивает DOM.
  • Подписка или таймер без отписки: утечка памяти и повторные вызовы.
  • Огромная картинка там, где показывается миниатюра.

Если нет сценария, лучше задать вопрос, чем требовать оптимизацию. Без измерений «быстрый» код часто оказывается просто менее понятным.
