Как рецензенту читать изменение

Начните с описания задачи и поведения до/после. Потом посмотрите список файлов и основные точки входа. Чтение с первой изменённой строки не всегда помогает понять, что вообще должно происходить.

Три прохода по PR

Сначала проверьте общий замысел: где находятся обязанности и как движутся данные. Затем пройдите пользовательский сценарий с краевыми случаями. В конце оцените названия, локальную структуру и пояснения. Так замечание о запятой не отвлечёт от потери данных.

Читайте за пределами diff

Изменённая функция может нарушить ожидания вызывающего кода. Найдите её вызовы, типы аргументов и соседние тесты. Проверьте контракты: что считается пустым результатом, какие ошибки выбрасываются, меняются ли переданные объекты.

Для UI полезно запустить приложение и пройти сценарий руками: diff не показывает фактический фокус, перенос текста и состояние загрузки. Для сложной логики выпишите маленький вход и проследите значения переменных. Если контекста не хватает, сформулируйте вопрос, а не объявляйте код ошибочным.

Объём замечаний

Связывайте замечания с текущим изменением. Старую проблему стоит блокирующе поднимать, если новый код делает её опаснее или без исправления задача некорректна. Независимое улучшение можно вынести в отдельную задачу. Ревью не требует переписать весь проект по вкусу рецензента.
