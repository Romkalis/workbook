Хеши, ссылки и HEAD

Объекты и SHA-1

Всё, что Git сохраняет, лежит в папке .git/objects в виде объектов трёх основных видов:

  • blob — содержимое одного файла (без имени);
  • tree — папка: список имён файлов и подпапок со ссылками на их blob и tree;
  • commit — снимок: ссылка на корневой tree, на родительский коммит, автор, дата и сообщение.

Имя каждого объекта — его хеш SHA-1: 40 шестнадцатеричных символов, вычисленных из содержимого. Хеш — это «отпечаток»: одинаковое содержимое всегда даёт одинаковый хеш, а малейшее изменение — совсем другой. Поэтому Git замечает любую порчу данных, а одинаковые файлы хранит один раз. Заглянем внутрь коммита:

$ git rev-parse HEAD
6c3b002fc003d62e76bc6ccf11c57cebc160e5bf
$ git cat-file -t HEAD
commit
$ git cat-file -p HEAD
tree f04539bd79d42651f63a3a0c7d6c02e47eb9a9c1
author Аня <a@example.com> 1794659582 +0100
committer Аня <a@example.com> 1794659582 +0100

Первый коммит
$ git cat-file -p HEAD^{tree}
100644 blob d0f56e135b2282bfdd87b1cae5d0238b6a193ab5	hello.txt
$ echo "привет" | git hash-object --stdin
d0f56e135b2282bfdd87b1cae5d0238b6a193ab5

Последняя команда посчитала хеш строки «привет» и получила тот же хеш, что у blob файла hello.txt: имя объекта действительно зависит только от содержимого. В хеш коммита входят хеш дерева, родитель, автор и время, поэтому изменить что угодно в старом коммите, не поменяв хеши всех следующих, невозможно. Шестнадцатеричные символы — это цифры 0–9 и буквы a–f. Обычно хватает первых 7 символов: 6c3b002. В новых версиях Git можно включить SHA-256 вместо SHA-1, но по умолчанию пока используется SHA-1 (из общих знаний).

Ссылки

Помнить хеши неудобно, поэтому есть ссылки (refs) — файлы с человеческими именами, внутри которых записан хеш (руководство Atlassian «Refs and the reflog»):

  • ветка main — файл .git/refs/heads/main с хешем последнего коммита ветки. Ветка — это просто подвижный указатель на коммит, а не копия файлов;
  • теги — .git/refs/tags/, неподвижные метки вроде v1.0.0;
  • ветки сервера — .git/refs/remotes/origin/main.

Иногда ссылки упакованы в один файл .git/packed-refs для экономии места — поэтому файла ветки в refs/heads может не быть.

HEAD

HEAD — особая ссылка «где я сейчас». Обычно она указывает не на коммит, а на ветку:

$ cat .git/HEAD
ref: refs/heads/main
$ cat .git/refs/heads/main
6c3b002fc003d62e76bc6ccf11c57cebc160e5bf

При коммите Git создаёт новый коммит и сдвигает ветку, на которую указывает HEAD. Если же переключиться прямо на коммит, HEAD будет указывать на хеш напрямую — это detached HEAD («отсоединённая голова»):

$ git switch --detach HEAD~1
$ git status
HEAD detached at ccd1dc7

В этом состоянии можно смотреть старый код и даже коммитить, но новые коммиты не принадлежат ни одной ветке: после переключения их легко потерять. Если хотите сохранить работу — создайте ветку: git switch -c fix-old-bug. Вернуться — git switch main. Старая команда git checkout <хеш> делает то же самое.

Относительные ссылки

  • HEAD~1 — родитель HEAD, HEAD~2 — «дедушка» и так далее назад по истории.
  • HEAD^ — первый родитель, то же, что HEAD~1. У коммита слияния два родителя, второй — HEAD^2.
  • Работает с любой ссылкой: main~3, origin/main^.

Reflog — журнал перемещений

Git записывает каждое перемещение HEAD и веток: коммиты, переключения, reset, слияния. Этот журнал — reflog, и он спасает «потерянные» коммиты:

$ git reset --hard HEAD~1        # «потеряли» коммит «Версия 3»
$ git reflog
ccd1dc7 HEAD@{0}: reset: moving to HEAD~1
aad07a7 HEAD@{1}: reset: moving to HEAD
...
$ git reset --hard HEAD@{1}      # вернулись туда, где были шагом раньше
$ git log --oneline -1
aad07a7 Версия 3

HEAD@{1} значит «где был HEAD одно перемещение назад». Reflog локальный (на сервер не отправляется) и хранится ограниченное время, по умолчанию около 90 дней. Коммит, на который не ссылается ни одна ветка, не исчезает сразу — его со временем удаляет сборщик мусора git gc. Пока он не удалён, reflog помогает его найти.
