GitHub Actions

GitHub Actions — встроенная в GitHub система CI/CD. Словарь:

  • Workflow — YAML-файл в .github/workflows/. Описывает, когда и что запускать.
  • Event (on) — что запускает workflow: push, pull_request, ручной запуск, расписание.
  • Job — набор шагов на одной виртуальной машине (runner). Задания по умолчанию идут параллельно.
  • Step — команда (run) или готовое действие (uses).
  • Action — переиспользуемый шаг, например actions/checkout скачивает код репозитория.
name: CI
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test
      - run: npm run build

Каждый шаг выполняется в новом процессе оболочки. Если команда завершилась с ненулевым кодом, задание падает, следующие шаги не выполняются, а у коммита в GitHub появляется красный крестик. cache: npm у setup-node сохраняет скачанные пакеты между запусками, и npm ci идёт быстрее. Версии действий (@v7) актуальны на ноябрь 2026, свежие указаны на странице каждого действия.

События

on:
  push:
    branches: [main]
    paths-ignore: ['**.md']     # не запускать, если поменялась только документация
  pull_request:                 # каждый PR и каждый новый коммит в нём
  workflow_dispatch:            # кнопка «Run workflow» в интерфейсе
  schedule:
    - cron: '0 3 * * 1'         # каждый понедельник в 03:00 UTC

pull_request проверяет результат слияния PR с целевой веткой, а не только саму ветку, поэтому ловит конфликты логики.

Задача 3. Не гонять CI из-за README ★☆☆ разминка

Измените события из прошлой задачи: push в main и PR не запускают workflow, если изменились только файлы *.md и папка docs/. Добавьте ручной запуск и ночную проверку каждый день в 02:00 UTC (она ловит поломки из-за обновившихся внешних сервисов).

Зачем: бесплатные минуты CI ограничены, и очередь из ненужных запусков задерживает нужные. Фильтр по путям — дешёвая оптимизация. А ночной запуск ловит то, что ломается без изменений в коде: просроченный сертификат, изменившийся внешний API.

Решение и разбор
// ci.yml
name: CI
on:
  push:
    branches: [main]
    paths-ignore: ['**.md', 'docs/**']
  pull_request:
    paths-ignore: ['**.md', 'docs/**']
  workflow_dispatch:
  schedule:
    - cron: '0 2 * * *'

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run check

Cron пишется пятью полями: минута, час, день месяца, месяц, день недели, время — UTC. Расписание в GitHub не точное: при нагрузке запуск может опоздать (из общих знаний). Осторожно с paths-ignore и обязательными проверками: если PR меняет только README, проверка не запустится, и обязательный статус будет висеть в ожидании. Для таких репозиториев фильтр ставят на шаги или используют отдельный «пустой» workflow с тем же именем задания.

Задания, зависимости и матрица

Задания связывают через needs: deploy с needs: check стартует только после успешного check. Условие if пропускает задание или шаг: if: github.ref == 'refs/heads/main' — только для main. Матрица запускает одно задание с разными параметрами:

strategy:
  matrix:
    node: [20, 22, 24]
runs-on: ubuntu-latest
steps:
  - uses: actions/setup-node@v7
    with:
      node-version: ${{ matrix.node }}

Три задания пойдут параллельно. Это нужно библиотеке, которая обещает работать на нескольких версиях Node. Приложению обычно хватает одной версии, той же, что на сервере.

Задача 4. Параллельные задания и сборка после них ★★☆ практика

Разбейте проверку на три задания: lint (линтер и форматирование), types и test, которые идут параллельно, и build, который запускается только после успеха всех трёх. Повторяющиеся шаги установки оставьте в каждом задании: задания работают на разных машинах.

Зачем: три параллельных задания по минуте быстрее одного на три минуты, а в интерфейсе PR сразу видно, что сломалось: «types» красный, остальные зелёные. Понимание, что каждое задание — отдельная чистая машина, объясняет, почему npm ci повторяется.

Решение и разбор
// ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm run format:check
  types:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run typecheck
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm test
  build:
    needs: [lint, types, test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run build

Повторение шагов — цена параллельности. Когда его становится слишком много, повторяющиеся шаги выносят в собственное составное действие (.github/actions/setup/action.yml с runs: using: composite) или в переиспользуемый workflow (workflow_call). Запись with: { ... } — обычный YAML-объект в одну строку. Он короче, но читается хуже, если ключей много.

Задача 5. Матрица для библиотеки ★★☆ практика

Библиотека обещает работать на Node 20, 22 и 24, на Linux и Windows. Напишите задание test с матрицей по версии Node и ОС. Падение одной комбинации не должно отменять остальные: важно увидеть все сломанные сразу. Исключите комбинацию Node 20 + Windows (её не поддерживаете).

Зачем: «у меня работает» на одной версии и одной ОС ничего не гарантирует пользователям библиотеки. Переводы строк, разделители путей и регистр имён файлов на Windows ломают код, который на Linux проходит. Матрица проверяет обещание из README автоматически.

Решение и разбор
// ci.yml
name: Test matrix
on:
  pull_request:

permissions:
  contents: read

jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        node: [20, 22, 24]
        os: [ubuntu-latest, windows-latest]
        exclude:
          - node: 20
            os: windows-latest
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm test

Матрица 3 × 2 даёт шесть заданий, exclude убирает одно — остаётся пять. По умолчанию fail-fast: true: первое падение отменяет остальные задания матрицы. Это экономит минуты, но прячет полную картину. Минуты на Windows в приватных репозиториях тарифицируются дороже Linux (из общих знаний), поэтому Windows часто оставляют только для одной версии Node.

Секреты, переменные и окружения

Токены и пароли хранят в Secrets (Settings → Secrets and variables → Actions) и читают как ${{ secrets.DEPLOY_TOKEN }}. GitHub маскирует их в логах звёздочками, но маскировка ловит только точное значение: закодированный или разрезанный секрет в лог попадёт. Поэтому секреты передают через env и никогда не выводят. Environments (окружения: staging, production) позволяют завести отдельные секреты для каждого и требовать ручного подтверждения перед выкладкой. Это и есть граница между Delivery и Deployment.

Задача 2. Первый workflow ★☆☆ разминка

Напишите .github/workflows/ci.yml: запускается на каждый PR и на push в main, работает на ubuntu-latest с Node 22 и кешем npm, ставит зависимости через npm ci и запускает npm run check из прошлой задачи, затем npm run build. Права токена — только чтение кода.

Зачем: это минимальный CI, который стоит добавить в любой учебный проект в первый же день. Дальше каждый PR получает зелёную или красную отметку, и ревьюер не тратит время на код, который даже не собирается.

Решение и разбор
// ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run check
      - run: npm run build

Push в любую ветку не запускает проверку: ветки проверяются через PR, иначе каждый коммит в PR запускал бы workflow дважды. pull_request: без параметров означает «все PR во все ветки». После первого успешного запуска в настройках защиты main отметьте задание check как обязательное (Require status checks). Тогда кнопка Merge будет заблокирована, пока проверка не пройдёт.

Задача 6. Секрет для выкладки ★★☆ практика

Задание deploy отправляет сборку на хостинг командой npx some-host deploy dist, которая читает токен из переменной окружения HOST_TOKEN. Напишите задание: только для push в main, после задания check, в окружении production (с ручным подтверждением, настроенным в GitHub), токен — из секрета, без вывода в лог.

Зачем: секрет в YAML-файле виден всем, у кого есть доступ к репозиторию, навсегда — история Git помнит. Окружение с подтверждением превращает Deployment в Delivery: всё готово, но последнее слово за человеком.

Решение и разбор
// deploy.yml
name: Deploy
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run check
  deploy:
    needs: check
    if: github.ref == 'refs/heads/main'
    environment: production
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run build
      - run: npx some-host deploy dist
        env:
          HOST_TOKEN: ${{ secrets.HOST_TOKEN }}

Секрет передаётся через env только тому шагу, которому он нужен, а не всему заданию. Остальные шаги (npm ci со сторонними скриптами установки) его не видят. Условие if дублирует фильтр события, и это намеренно: если позже кто-то добавит workflow_dispatch, выкладка из случайной ветки всё равно не произойдёт. Ручное подтверждение и список допущенных людей настраиваются в Settings → Environments → production → Required reviewers.
