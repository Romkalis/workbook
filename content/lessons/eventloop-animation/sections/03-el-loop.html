Цикл событий: задачи, микрозадачи, отрисовка

Упрощённый алгоритм одного оборота цикла в браузере:

  1. Взять одну задачу (macrotask) из очереди задач и выполнить её целиком: скрипт страницы, колбэк таймера, обработчик события.
  2. Выполнить все микрозадачи, включая те, что добавились по ходу.
  3. Если пора, обновить экран: колбэки requestAnimationFrame, стили, раскладка, отрисовка.
  4. Повторить.
export function order(): Promise<string[]> {
  const log: string[] = [];
  log.push('script');
  setTimeout(() => log.push('timeout'), 0);
  Promise.resolve().then(() => log.push('promise'));
  queueMicrotask(() => log.push('microtask'));
  log.push('script end');
  return new Promise((r) => setTimeout(() => r(log), 5));
}
// ['script', 'script end', 'promise', 'microtask', 'timeout']

Синхронный код скрипта — это первая задача. После неё выполняются все микрозадачи в порядке постановки, и только в следующем обороте — колбэк таймера.

Микрозадачи

Микрозадачи — реакции промисов (then, catch, finally, продолжение после await), queueMicrotask(fn) и колбэки MutationObserver. Они выполняются сразу после текущей задачи, до отрисовки и до следующего таймера. Поэтому результат промиса нельзя «увидеть на экране между» двумя микрозадачами.

Цена этой скорости: если микрозадачи всё время ставят новые микрозадачи, очередь никогда не опустеет, и браузер не дойдёт ни до таймеров, ни до отрисовки. Страница зависнет так же, как от бесконечного цикла, только без явного while.

export async function awaitOrder(): Promise<string[]> {
  const log: string[] = [];
  async function inner() {
    log.push('inner start');
    await null;
    log.push('inner after await');
  }
  log.push('start');
  const p = inner();
  log.push('after call');
  await p;
  return log; // ['start', 'inner start', 'after call', 'inner after await']
}

Async-функция выполняется синхронно до первого await, а остаток уходит в микрозадачу. Поэтому after call печатается раньше продолжения inner.

Задача 3. Зависание без бесконечного цикла ★★★ с подвохом

Функция обрабатывает очередь сообщений: после каждого сообщения «уступает» циклу событий через await Promise.resolve(). Но индикатор прогресса (таймер) не обновляется до конца обработки. Объясните почему и исправьте yieldNow так, чтобы таймеры успевали срабатывать между сообщениями.

const yieldNow = () => Promise.resolve();
export async function drain(queue: string[], handle: (m: string) => void) {
  while (queue.length) {
    handle(queue.shift()!);
    await yieldNow();
  }
}

Зачем: «уступить» через промис — частое заблуждение. Продолжение после await — микрозадача, а цикл не перейдёт к таймерам и отрисовке, пока микрозадачи не кончатся. Получается тот же длинный блок, только разрезанный на невидимые для браузера кусочки.

Решение и разбор
const yieldNow = () => new Promise<void>((resolve) => setTimeout(resolve, 0));

export async function drain(queue: string[], handle: (m: string) => void): Promise<void> {
  while (queue.length) {
    handle(queue.shift()!);
    await yieldNow();
  }
}

Таймер ставит продолжение в очередь задач, и между двумя сообщениями браузер успевает выполнить другие задачи и отрисовать кадр. Цена — минимальная задержка таймера, после пяти вложенных вызовов около 4 мс. Поэтому уступать после каждого маленького сообщения расточительно. Лучше обрабатывать пачку в течение нескольких миллисекунд и уступать после неё, как processInChunks из раздела.

Долгие задачи и как их дробить

Задача дольше 50 мс считается долгой (long task): за это время пользователь замечает задержку реакции на клик. Тяжёлую работу дробят на порции и между порциями возвращают управление циклу, чтобы браузер успел отрисовать кадр и обработать события. Вернуть управление можно новой задачей (setTimeout), а не микрозадачей: микрозадачи выполнятся до отрисовки.

const yieldToLoop = () => new Promise<void>((r) => setTimeout(r, 0));

export async function processInChunks<T>(items: readonly T[], fn: (item: T) => void, chunk = 500): Promise<void> {
  for (let i = 0; i < items.length; i += chunk) {
    items.slice(i, i + chunk).forEach(fn);
    await yieldToLoop();
  }
}

В Chromium есть специальный scheduler.yield() для той же цели (из общих знаний: поддерживается не всеми браузерами, поэтому setTimeout остаётся запасным вариантом). Работу, которой не нужен DOM, можно вообще увести в Web Worker — отдельный поток.

Задача 2. Порядок вывода ★☆☆ разминка

Запишите, в каком порядке появятся буквы. Затем проверьте в консоли и на JS Visualizer 9000.

setTimeout(() => console.log('A'), 0);
Promise.resolve().then(() => {

  queueMicrotask(() => console.log('D'));
});
console.log('E');
setTimeout(() => Promise.resolve().then(() => console.log('F')), 0);
// trace.ts
export function trace(): Promise<string[]> {
  const log: string[] = [];
  setTimeout(() => log.push('A'), 0);
  Promise.resolve().then(() => {
    log.push('B');
    setTimeout(() => log.push('C'), 0);
    queueMicrotask(() => log.push('D'));
  });
  log.push('E');
  setTimeout(() => Promise.resolve().then(() => log.push('F')), 0);
  return new Promise((r) => setTimeout(() => r(log), 10));
}

Зачем: задачи на порядок вывода любят на собеседованиях и в автотестах. Решаются они не угадыванием, а прогоном алгоритма из раздела: задача целиком, все микрозадачи, следующая задача.

Решение и разбор
// ответ.txt
E B D A F C

Задача 1 (скрипт): печатает E, ставит таймеры A и F и микрозадачу. Микрозадачи: B, внутри ставится таймер C (в конец очереди задач) и микрозадача D, она выполнится в этом же опустошении. Дальше задачи по очереди: A; таймер F ставит микрозадачу, которая выполняется сразу после него, до C. Последний — C. Скрытая проверка прогоняет этот же код в Node и подтверждает ответ.

Задача 4. Порции по времени, а не по количеству ★★☆ практика

Размер порции в processInChunks подобран на глаз: на мощном компьютере 500 элементов занимают 2 мс, на старом телефоне — 60. Напишите processWithBudget(items, fn, budgetMs = 8, now = performance.now): обрабатывает элементы, пока не истёк бюджет времени, затем уступает циклу через setTimeout и продолжает.

Зачем: кадр на экране 60 Гц длится около 16 мс, и браузеру нужно время на отрисовку. Бюджет по времени сам подстраивается под устройство: быстрый компьютер сделает больше за один заход, медленный — меньше, но интерфейс не будет дёргаться ни там, ни там.

Решение и разбор
const yieldToLoop = () => new Promise<void>((r) => setTimeout(r, 0));

export async function processWithBudget<T>(
  items: readonly T[],
  fn: (item: T) => void,
  budgetMs = 8,
  now: () => number = () => performance.now(),
): Promise<number> {
  let i = 0;
  let slices = 0;
  while (i < items.length) {
    const start = now();
    do {
      fn(items[i]!);
      i++;
    } while (i < items.length && now() - start < budgetMs);
    slices++;
    if (i < items.length) await yieldToLoop();
  }
  return slices;
}

do...while гарантирует, что за один заход обработается хотя бы один элемент, даже если он сам дольше бюджета. Иначе цикл бы застрял. Функция возвращает число заходов: это пригодится для замеров. Часы now передаются параметром, и тест управляет временем без реальных задержек. Такой же приём был с clock в задаче про DI в уроке Design Patterns.
