Utility types для объектов

Utility types — встроенные вспомогательные типы. Они позволяют получить новый тип из существующего, например сделать поля профиля необязательными для формы редактирования. Они меняют статический контракт, не копируют, не фильтруют и не замораживают реальные объекты. Формулы этих типов можно прочитать в lib.es5.d.ts установленного компилятора.

Partial, Required и Readonly

interface Profile { id: string; name: string; bio?: string }
const patch: Partial<Profile> = { name: "Анна" };
const full: Required<Profile> = { id: "u1", name: "Анна", bio: "Учусь" };
const view: Readonly<Profile> = full;
console.log(patch.name, view.bio);
if (false) {
  // @ts-expect-error: readonly запрещает запись через view
  view.name = "Лев";
}

В примере patch — частичное обновление профиля: менять имя можно, передавать все остальные поля не требуется. Full — полностью заполненный профиль. View ссылается на тот же объект, но его тип разрешает только чтение. Partial делает свойства необязательными, Required убирает знак ?, Readonly запрещает присваивание через этот тип. Они работают на первом уровне: Readonly<{ meta: { title: string } }> не делает meta.title неизменяемым. Для обновления профиля безопаснее Partial<Pick<Profile, "name" | "bio">>, чтобы не разрешать менять id.

Задача 11. Неизменяемое обновление статьи ★☆☆ разминка

Напишите updateArticle(article, patch). Статья приходит как Readonly<Article>, патч может содержать любые поля, кроме id. Функция возвращает новый объект и не меняет исходный. Попытку передать id в патче покажите строкой с @ts-expect-error.

export interface Article {
  id: string;
  title: string;
  description?: string;
}

Зачем: тип параметра — это документация, которую проверяет компилятор. Readonly обещает вызывающему, что его объект не тронут. Partial<Omit<…>> отвечает на вопрос «что разрешено менять» без отдельного интерфейса, который забудут обновить.

Решение и разбор
export interface Article {
  id: string;
  title: string;
  description?: string;
}
export type ArticlePatch = Partial<Omit<Article, 'id'>>;

export function updateArticle(article: Readonly<Article>, patch: ArticlePatch): Article {
  return { ...article, ...patch };
}

const a: Article = { id: 'a1', title: 'TS' };
updateArticle(a, { title: 'TS Advanced' });
if (false) {
  // @ts-expect-error: id менять нельзя
  updateArticle(a, { id: 'other' });
}

Утилиты читаются изнутри наружу: Omit убирает id, Partial делает остальное необязательным. Добавится поле tags — и патч узнает о нём сам. Оговорка: { title: undefined } тип пропустит и затрёт название. Как это закрыть, разбирается в задаче про exactOptionalPropertyTypes ниже.

Задача 12. Значения по умолчанию и коварный undefined ★★★ с подвохом

Напишите withDefaults(options: SearchOptions): Required<SearchOptions>, где все поля необязательны, а значения по умолчанию: pageSize = 20, sort = "new", query = "". Очевидное решение { ...DEFAULTS, ...options } проходит проверку типов. Найдите вызов, на котором оно ломается, и напишите правильное.

export interface SearchOptions {
  pageSize?: number;
  sort?: 'new' | 'popular';
  query?: string;
}

Зачем: опции часто собирают из формы или адреса страницы, и там легко получить { pageSize: undefined }. Spread копирует ключ вместе с undefined и затирает значение по умолчанию, а тип Required уверяет, что там число. Это пример того, как типы и реальность расходятся.

Подсказка

Попробуйте withDefaults({ pageSize: undefined }).pageSize. Затем соберите результат по полям через ??.

Решение и разбор
export interface SearchOptions {
  pageSize?: number;
  sort?: 'new' | 'popular';
  query?: string;
}

export function withDefaults(options: SearchOptions): Required<SearchOptions> {
  return {
    pageSize: options.pageSize ?? 20,
    sort: options.sort ?? 'new',
    query: options.query ?? '',
  };
}

При обычных настройках pageSize?: number означает number | undefined, поэтому явный undefined разрешён, и spread его копирует. Сборка по полям надёжнее: каждое значение по умолчанию стоит рядом с полем, и компилятор не даст забыть новое поле, ведь результат обязан быть Required. Второе решение — флаг exactOptionalPropertyTypes: с ним { pageSize: undefined } вообще не скомпилируется.

Pick, Omit и Record

interface Article { id: string; title: string; secret: string }
type Card = Pick<Article, "id" | "title">;
type PublicArticle = Omit<Article, "secret">;
const original: Article = { id: "a1", title: "TS", secret: "hidden" };
const typed: PublicArticle = original; // ссылка всё ещё содержит secret
const card: Card = { id: original.id, title: original.title };
const labels: Record<"loading" | "ready", string> = {
  loading: "Загрузка", ready: "Готово"
};
console.log("secret" in typed, "secret" in card, labels.ready); // true false Готово

Pick выбирает ключи, Omit исключает, Record описывает значения по набору ключей. Omit не удалил secret во время выполнения; для публичного ответа сформируйте новый объект из нужных полей. Record с конечным union требует все перечисленные ключи; произвольный строковый словарь не гарантирует существование каждого ключа.

ТипКогда полезен
Partial<T>Частичное обновление разрешённых полей
Required<T>Полная конфигурация после заполнения пропусков
Readonly<T>Контракт чтения без присваиваний
Pick<T, K>Узкое представление с выбранными полями
Omit<T, K>Контракт без перечисленных полей
Record<K, V>Словарь значений V по ключам K

Задача 13. Omit не удаляет поле ★★☆ практика

Есть пользователь с passwordHash. Напишите toPublicUser(user: User): PublicUser, где PublicUser = Omit<User, "passwordHash">. Вариант return user компилируется. Объясните, почему он опасен, и напишите функцию, которая действительно убирает поле.

export interface User {
  id: string;
  email: string;
  passwordHash: string;
}

Зачем: типы стираются при сборке. Omit лишь запрещает обращаться к полю в коде, а res.json(user) отправит хеш пароля клиенту. Эта ошибка встречается в учебных проектах с JWT-авторизацией постоянно.

Решение и разбор
export interface User {
  id: string;
  email: string;
  passwordHash: string;
}
export type PublicUser = Omit<User, 'passwordHash'>;

export function toPublicUser(user: User): PublicUser {
  const { passwordHash: _hidden, ...rest } = user;
  return rest;
}

Деструктуризация с остатком создаёт новый объект без поля, и тип rest компилятор выводит сам: ровно Omit<User, 'passwordHash'>. Подчёркивание в имени _hidden — соглашение «переменная не используется намеренно». Ещё надёжнее белый список: { id: user.id, email: user.email }. При нём новое секретное поле в User не утечёт само по себе.

Задача 14. Подписи, которые нельзя забыть ★☆☆ разминка

Есть тип Status = "draft" | "published" | "archived". Опишите объект подписей через Record и функцию statusLabel(s). Затем добавьте в Status вариант "review" и посмотрите, где компилятор потребует правку.

Зачем: словарь через Record<Status, string> обязан содержать все ключи. Новый статус не останется без подписи: ошибка появится в момент добавления, а не когда пользователь увидит undefined на экране.

Решение и разбор
export type Status = 'draft' | 'published' | 'archived';

const LABELS: Record<Status, string> = {
  draft: 'Черновик',
  published: 'Опубликована',
  archived: 'В архиве',
};

export function statusLabel(status: Status): string {
  return LABELS[status];
}

if (false) {
  // @ts-expect-error: нет подписи для archived
  const partial: Record<Status, string> = { draft: 'Черновик', published: 'Опубликована' };
}

Сравните с { [key: string]: string }: такой словарь примет любой набор ключей и ничего не потребует. Record с конечным union работает как чек-лист. Проверка лишних ключей тоже есть: опечатка publised будет ошибкой.
