Встроенные type guards и анализ потока

Type guard, или проверка типа, помогает уточнить, какое значение перед нами. Например, переменная имеет тип string | number. После проверки typeof value === "string" внутри этой ветки можно вызывать строковые методы. Такое уточнение называется сужением типа (narrowing). Компилятор учитывает условия, выход из функции через return и новые присваивания.

typeof и равенство

function text(value: string | number | null): string {
  if (value === null) return "нет значения";
  return typeof value === "number" ? value.toFixed(1) : value.toUpperCase();
}
function common(a: string | number, b: string | boolean): string {
  if (a === b) return a.toUpperCase(); // общий возможный тип — string
  return "разные";
}
console.log(text(2), text(null), common("ts", "ts"));

В text(2) выбирается числовая ветка и получается "2.0"; для null функция сразу возвращает "нет значения". Теперь common. a бывает строкой или числом, b — строкой или boolean. Если a === b, значения одинаковые, а значит, и типы одинаковые. Общий тип у них только один — string. TypeScript делает тот же вывод, поэтому внутри if у a можно вызвать toUpperCase(). typeof полезен для примитивов, но typeof null равно "object"; для объекта сначала исключайте null. Проверка value != null намеренно исключает и null, и undefined; строгое сравнение исключает только указанное значение.

Задача 1. Подпись для значения любого типа ★☆☆ разминка

Напишите label(value: string | number | boolean | null): string. Правила: null → "—", число → два знака после точки, true/false → "да"/"нет", строка → как есть. Не используйте as: каждая ветка должна получить уже суженный тип.

Зачем: когда компилятор сам сужает тип после проверки, ветки не могут перепутаться: toFixed просто не вызовется на строке. А as выключает эту защиту и превращает ошибку в падение у пользователя.

Решение и разбор
export function label(value: string | number | boolean | null): string {
  if (value === null) return '—';
  if (typeof value === 'number') return value.toFixed(2);
  if (typeof value === 'boolean') return value ? 'да' : 'нет';
  return value;
}

После каждого return компилятор вычёркивает проверенный вариант. К последней строке остаётся только string, поэтому return value проходит без приведения. Порядок важен лишь для читаемости: null первым, потому что typeof null равно "object", и проверка через typeof его бы не поймала.

Проверка if (value): пустое значение тоже может быть данными

function length(value: string | undefined): number | undefined {
  if (value === undefined) return undefined;
  return value.length;
}
console.log(length(""), length(undefined)); // 0 undefined

JavaScript преобразует условие if в boolean. Такая проверка называется truthiness — проверкой того, считается ли значение истинным. Условие if (value) отсекает не только отсутствие, но и пустую строку, ноль, false и другие falsy-значения. Выбирайте проверку по смыслу данных. Для пустого текста длина 0 может быть корректным результатом.

Задача 2. Ноль — тоже данные ★☆☆ разминка

Функция показывает число комментариев, но для статьи без комментариев пишет «нет данных». Найдите причину и исправьте так, чтобы 0 давал "0 комментариев", а «нет данных» появлялось только для undefined.

export function commentsLabel(count: number | undefined): string {
  if (!count) return 'нет данных';
  return `${count} комментариев`;
}

Зачем: проверка if (!x) сразу отсеивает 0, "" и NaN. Для чисел и строк это почти всегда ошибка: «пусто» и «нет значения» — разные состояния, и интерфейс должен их различать.

Решение и разбор
export function commentsLabel(count: number | undefined): string {
  if (count === undefined) return 'нет данных';
  return `${count} комментариев`;
}

TypeScript в обоих вариантах сужает тип до number, поэтому компилятор ошибку не покажет: это логическая ошибка, а не ошибка типов. Явное сравнение с undefined говорит ровно то, что имелось в виду. Если бы допускался и null, подошло бы count == null: нестрогое равенство с null ловит оба пустых значения и только их.

instanceof, in и размеченный union

class Video { constructor(readonly minutes: number) {} }
function duration(value: Video | { words: number }): number {
  if (value instanceof Video) return value.minutes;
  return Math.ceil(value.words / 200);
}
type Result = { kind: "ok"; title: string } | { kind: "error"; message: string };
function render(result: Result): string {
  if ("message" in result) return result.message;
  return result.title;
}
console.log(duration(new Video(5)), render({ kind: "ok", title: "TS" }));

instanceof использует существующий конструктор, а не interface: интерфейсы стираются. In проверяет наличие свойства, но ещё не его содержимое; если свойство необязательное, его наличие не всегда позволяет однозначно выбрать один вариант объединения. Для сложных состояний удобно общее поле kind с литеральными значениями.

В примере duration(new Video(5)) возвращает 5. В render проверка "message" in result выбирает вариант ошибки; вместо неё здесь можно проверить result.kind === "error". Общее поле kind называется дискриминантом: его конкретное значение показывает, с каким вариантом мы работаем.

Задача 3. Текст из любой ошибки ★★☆ практика

В catch приходит unknown: бросить можно что угодно. Напишите errorMessage(error: unknown): string:

  • экземпляр Error → его message;
  • строка → она сама;
  • объект со строковым полем message (так выглядят ошибки многих API) → это поле;
  • всё остальное → "Неизвестная ошибка".

Зачем: эта функция пригодится в каждом проекте: в обработчике ошибок Express, в API-клиенте, в интерфейсе. Она учит не верить catch: error.message без проверки упадёт, если кто-то бросил строку или null.

Подсказка

in проверяет только наличие свойства. Тип самого свойства нужно проверить отдельно: typeof error.message === "string".

Решение и разбор
export function errorMessage(error: unknown): string {
  if (error instanceof Error) return error.message;
  if (typeof error === 'string') return error;
  if (typeof error === 'object' && error !== null && 'message' in error && typeof error.message === 'string') {
    return error.message;
  }
  return 'Неизвестная ошибка';
}

Цепочка проверок идёт от точной к общей. instanceof работает с классами, которые существуют во время выполнения. Для объекта из JSON его недостаточно: такой объект не создан через new Error. После 'message' in error TypeScript знает, что поле есть, но его тип пока unknown. Поэтому нужна вторая проверка, typeof. Без неё объект { message: 42 } вернул бы число там, где обещана строка.
