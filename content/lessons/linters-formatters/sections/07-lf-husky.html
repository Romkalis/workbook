Git-хуки, Husky и lint-staged

Настройки редактора помогают, но не гарантируют: кто-то пишет в другом редакторе, кто-то отключил расширение. Последний рубеж — проверка в момент коммита.

Git-хуки

Хук (hook, «крючок») — скрипт, который git запускает сам при определённом событии (Pro Git: хуки). pre-commit — перед созданием коммита, commit-msg — после ввода сообщения, pre-push — перед отправкой на сервер. Если хук завершился с ненулевым кодом, git отменяет действие. Хуки лежат в папке .git/hooks, которая не попадает в репозиторий, поэтому без помощника их не раздать команде.

Husky

Husky хранит хуки в папке .husky в самом проекте (она коммитится) и настраивает git так, чтобы он брал хуки оттуда. Установка в проекте, где уже есть git-репозиторий:

npm install -D husky
npx husky init

husky init делает две вещи: создаёт файл .husky/pre-commit с командой npm test и добавляет в package.json скрипт "prepare": "husky". Скрипт prepare npm запускает автоматически после npm install, поэтому у каждого, кто склонирует проект и установит зависимости, хуки включатся сами. Файл хука — обычный shell-скрипт (набор команд для терминала): какие команды в нём написаны, те и выполнятся.

lint-staged: проверять только изменённое

Запускать ESLint по всему проекту на каждый коммит долго, и падать он будет из-за чужих старых файлов. lint-staged запускает команды только для файлов, добавленных в коммит (git add, «staged»), а исправленные файлы сам возвращает в коммит.

npm install -D lint-staged

Файл .husky/pre-commit:

npx lint-staged

Настройка в package.json:

"lint-staged": {
  "*.js": ["eslint --fix", "prettier --write"],
  "*.{css,md,json,html}": ["prettier --write"]
}

Проверено в учебном репозитории. Коммит с файлом из раздела про ESLint не прошёл: lint-staged показал те же пять проблем, Husky вывел «pre-commit script failed (code 1)», и коммит не создался. После исправления ошибок код без точек с запятой и с двойными кавычками закоммитился, а в репозиторий попала уже отформатированная Prettier версия.

Старая настройка из видео и статьи

В видео модуля о Husky хуки описаны прямо в package.json полем "husky": { "hooks": { "pre-commit": "lint-staged" } }, а в списке команд lint-staged последней стоит git add. Это Husky 4 и lint-staged до 10-й версии. Сейчас поле "husky" в package.json игнорируется (хуки живут в папке .husky), а git add писать не нужно: lint-staged добавляет изменения сам. Статья Bits and Pieces о Husky из теории модуля больше недоступна — адрес ведёт на главную блога.

Обойти и подстраховать

Хук можно пропустить флагом git commit --no-verify (проверено: коммит создаётся без проверок). Это нужно в редких случаях, например для коммита с заведомо незаконченной работой в свою ветку. Поэтому хуки — удобство для разработчика, а не защита: окончательную проверку делают в CI (например, GitHub Actions — встроенный в GitHub сервис автоматических проверок — запускает npm run lint и prettier --check . на каждый пул-реквест) — из общих знаний.

Ещё один популярный хук — commit-msg с commitlint (пакет для проверки сообщений коммитов): он проверяет, что сообщение коммита соответствует соглашению, например feat: добавить поиск. Сообщения коммитов в RS School часто требуют оформлять именно так.
