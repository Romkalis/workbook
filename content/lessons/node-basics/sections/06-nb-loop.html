Цикл событий и неблокирующий ввод-вывод

Ваш JavaScript в Node.js выполняется в одном потоке: в каждый момент времени работает одна функция. Как тогда один сервер обслуживает тысячи пользователей? Секрет в том, что почти всё время сервер не считает, а ждёт: ответа базы данных, чтения файла, сети. Это ожидание называется вводом-выводом (I/O).

Node.js не ждёт сам. Он передаёт операцию libuv и операционной системе («прочитай файл, скажи, когда будет готово») и идёт обслуживать следующий запрос. Когда данные готовы, колбэк или промис ставится в очередь, и цикл событий (event loop) выполняет его, как только поток освободится. Аналогия: официант принимает заказ, отдаёт его на кухню и идёт к следующему столику, а не стоит у плиты.

Как заблокировать сервер

Обратная сторона: если ваш код долго считает, ждут все. Цикл на миллиард итераций, синхронное чтение большого файла (readFileSync), тяжёлое шифрование в главном потоке — пока это выполняется, сервер не отвечает ни одному пользователю. Правило: не блокируйте цикл событий. Тяжёлые вычисления выносят в worker threads (дополнительные потоки Node.js) или отдельный сервис (из общих знаний).

Если тяжёлую работу можно разбить на части, есть простой приём без дополнительных потоков: обработать порцию, отдать управление циклу событий через setImmediate и продолжить. Между порциями успеют выполниться таймеры и запросы других пользователей:

const yieldToLoop = () => new Promise((resolve) => setImmediate(resolve));

async function sumInChunks(items, chunkSize = 10000) {
  let sum = 0;
  for (let i = 0; i < items.length; i += chunkSize) {
    for (let j = i; j < Math.min(i + chunkSize, items.length); j++) sum += items[j];
    await yieldToLoop(); // пауза: цикл событий обслуживает остальных
  }
  return sum;
}

Именно setImmediate, а не await Promise.resolve(): промисы — микрозадачи, они выполняются раньше таймеров и ввода-вывода, и цикл событий так и не получил бы управление. Общее время подсчёта немного вырастет, зато сервер не замирает.

Задача 17. Длинный подсчёт, который не вешает сервер ★★★ с подвохом

Функция считает сумму по миллиону заказов одним циклом, и всё это время сервер никому не отвечает. Напишите sumInChunks(items, chunkSize): она возвращает Promise с суммой и после каждой порции из chunkSize элементов отдаёт управление циклу событий через setImmediate. Докажите, что таймер, поставленный до начала подсчёта, срабатывает раньше конца подсчёта.

Зачем: одна тяжёлая синхронная операция останавливает обслуживание всех пользователей. Дробление работы — самый простой способ быть «вежливым» к циклу событий, пока вы не дошли до worker threads.

Подсказка

Обработайте порцию, затем await new Promise((r) => setImmediate(r)). Между порциями успеют выполниться таймеры и запросы.

Решение и разбор
// chunks.mjs
const yieldToLoop = () => new Promise((resolve) => setImmediate(resolve));

export async function sumInChunks(items, chunkSize = 10000) {
  let sum = 0;
  for (let i = 0; i < items.length; i += chunkSize) {
    const end = Math.min(i + chunkSize, items.length);
    for (let j = i; j < end; j++) sum += items[j];
    await yieldToLoop();
  }
  return sum;
}

Почему setImmediate, а не Promise.resolve(): промисы — микрозадачи, они выполняются до таймеров и ввода-вывода, и цикл событий так и не получил бы управление. setImmediate ставит продолжение в фазу цикла, после которой обрабатываются и новые события. Плата — общее время подсчёта чуть больше. Размер порции — компромисс между отзывчивостью и скоростью.

Порядок выполнения

setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
console.log('sync');

В Node.js 22 вывелось: sync, nextTick, promise, immediate, timeout. Сначала весь синхронный код, затем очередь process.nextTick, затем микрозадачи промисов (колбэки .then и продолжения после await), и только потом фазы цикла событий с таймерами и setImmediate. Порядок последних двух в главном файле не гарантирован и может меняться от запуска к запуску — на него не полагаются. Подробности в статье «The Node.js Event Loop».

Этот порядок верен для CommonJS. Пример выше запускался как файл .js без "type": "module". Если сохранить тот же код как order.mjs, Node.js 22 выведет sync, promise, nextTick, … Промис оказался раньше nextTick, потому что тело ES-модуля само выполняется внутри асинхронной задачи, и накопленные промисы срабатывают до очереди nextTick. Внутри колбэков (таймера, чтения файла, запроса) порядок «сначала nextTick, потом промисы» одинаков в обеих системах. Вывод тот же, что и для таймеров: не стройте логику на тонкостях порядка очередей.

Задача 18. Предскажите и проверьте порядок ★☆☆ разминка

Напишите файл order.cjs (CommonJS), который выводит буквы строго в порядке A B C D E. Каждую букву выведите из своего механизма: синхронный код, process.nextTick, промис, setImmediate внутри колбэка fs.readFile и setTimeout внутри того же колбэка. Порядок вызовов в файле — любой, порядок вывода — правильный.

Зачем: понимание очередей отвечает на практические вопросы: почему колбэк промиса уже выполнился, а таймер нет, или почему nextTick в цикле может заморить ввод-вывод. Задача заставляет предсказать порядок, а не подбирать его.

Подсказка

Внутри колбэка ввода-вывода (после чтения файла) setImmediate гарантированно выполняется раньше setTimeout(..., 0). В главном файле этот порядок не гарантирован.

Решение и разбор
// order.cjs
const { readFile } = require('node:fs');

readFile(__filename, () => {
  setTimeout(() => console.log('E'), 0);
  setImmediate(() => console.log('D'));
});
Promise.resolve().then(() => console.log('C'));
process.nextTick(() => console.log('B'));
console.log('A');

A — синхронный код выполняется первым. B — очередь nextTick разбирается до промисов. C — микрозадача промиса. Чтение файла завершается позже, а внутри его колбэка цикл событий находится в фазе ввода-вывода: следующей идёт фаза check (setImmediate) и только потом снова таймеры. Поэтому D раньше E, и это гарантировано документацией Node.js о цикле событий.

Почему файл .cjs: переименуйте его в .mjs (и замените require на import), и вывод станет A C B D E. Мы проверили это в Node.js 22. Тело ES-модуля само выполняется как асинхронная задача, и накопленные промисы срабатывают раньше очереди nextTick. Внутри колбэков порядок «nextTick, затем промис» одинаков в обеих системах модулей.
