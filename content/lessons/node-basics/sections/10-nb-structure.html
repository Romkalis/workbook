Структура проекта и путь к JWT

Пока всё в одном файле, проект легко читать. Когда маршрутов и моделей становится больше, код раскладывают по папкам по ролям. Единого стандарта нет, частый вариант:

todo-api/
  .env              секреты, не в git
  .env.example      список переменных без значений
  .gitignore        node_modules, .env
  package.json
  src/
    server.js       подключиться к базе и запустить app.listen
    app.js          создать app, подключить middleware и роутеры
    routes/         какие URL есть (todos.js, auth.js)
    controllers/    что делать на каждый URL
    models/         схемы Mongoose (Todo.js, User.js)
    middleware/     свои middleware (requireAuth.js, errorHandler.js)

Разделение app.js и server.js полезно для тестов: приложение можно импортировать и проверять запросами, не запуская сервер на порту.

// src/server.js
require('dotenv').config();
const mongoose = require('mongoose');
const app = require('./app');

const PORT = Number(process.env.PORT) || 3000;

async function start() {
  try {
    await mongoose.connect(process.env.MONGO_URI);
    app.listen(PORT, () => console.log(`http://localhost:${PORT}`));
  } catch (error) {
    console.error('Не удалось запустить сервер', error);
    process.exit(1);
  }
}

start();

Сервер сначала подключается к базе и только потом начинает принимать запросы. Если база недоступна, процесс завершается с кодом 1, а не работает «наполовину».

Как фронтенд обращается к своему серверу

Фронтенд на Vite (localhost:5173) и сервер (localhost:3000) — разные origin, поэтому браузер применит CORS. Два решения из урока о клиенте и сервере: подключить на сервере пакет cors с вашим origin (app.use(cors({ origin: 'http://localhost:5173' }))) или настроить прокси в dev-сервере Vite.

Что дальше

Теперь в уроке «JWT-авторизация» знакомо всё, на что он опирается: require, npm и .env, Express-маршруты и middleware, модели Mongoose. К этому добавятся модель пользователя с хешем пароля, выдача токена при входе и middleware, которое проверяет токен перед защищёнными маршрутами.

Задача 30. app отдельно от server и первый тест API ★★☆ практика

Разделите проект на app.mjs (создаёт приложение, ничего не слушает) и server.mjs (читает порт из окружения и вызывает listen). Напишите тест app.test.mjs на node:test с библиотекой supertest: GET /api/health отвечает { ok: true }, неизвестный путь — 404.

Зачем: приложение, которое не занимает порт при импорте, тестируется без запуска сервера: быстро, параллельно и без конфликтов с npm run dev. Это главный архитектурный шаг перед тем, как проект начнёт расти.

Решение и разбор
// app.mjs
import express from 'express';

export function createApp() {
  const app = express();
  app.get('/api/health', (req, res) => res.json({ ok: true }));
  app.use((req, res) => res.status(404).json({ error: 'Маршрут не найден' }));
  return app;
}
// server.mjs
import { createApp } from './app.mjs';

const port = Number(process.env.PORT) || 3000;
createApp().listen(port, () => console.log(`http://localhost:${port}`));
// app.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import request from 'supertest';
import { createApp } from './app.mjs';

test('health', async () => {
  const res = await request(createApp()).get('/api/health');
  assert.equal(res.status, 200);
  assert.deepEqual(res.body, { ok: true });
});

test('неизвестный путь — 404', async () => {
  assert.equal((await request(createApp()).get('/nope')).status, 404);
});

supertest принимает приложение и сам поднимает его на временном порту на время запроса. Ставится как dev-зависимость: npm i -D supertest. В server.mjs остались только «грязные» вещи: окружение и порт. Его почти нечего тестировать, и в этом смысл разделения. Продолжение с TypeScript, проверкой данных и CORS — в уроке Express на TypeScript.
