process, .env, файлы, пути и события

process

Глобальный объект process описывает запущенную программу:

  • process.argv — аргументы командной строки. node app.js --port 4000 даёт массив, где первые два элемента — путь к node и к файлу, дальше ваши аргументы.
  • process.env — переменные окружения (следующий подраздел).
  • process.exit(1) — завершить программу. Код 0 означает успех, любой другой — ошибку; по нему скрипты и CI понимают, что что-то пошло не так.
  • process.cwd() — папка, из которой запустили программу (не обязательно папка файла).
  • process.version, process.platform — версия Node.js и система: у нас вывело v22.23.2 darwin.

Задача 7. Разбор аргументов командной строки ★★☆ практика

Напишите parseArgs(argv): из массива вроде ['--category', 'books', '--limit', '2', '--json'] получает объект { category: 'books', limit: '2', json: true } (флаг без значения — true). Используйте его в list.mjs: скрипт печатает названия товаров из products.json с фильтром по категории и ограничением количества.

// products.json
[
  { "id": 1, "title": "Чистый код", "category": "books", "price": 150000 },
  { "id": 2, "title": "Каркассон", "category": "games", "price": 249000 },
  { "id": 3, "title": "Грокаем алгоритмы", "category": "books", "price": 99000 }
]

Зачем: разбор аргументов отдельно от действия — то же разделение, что «чистая функция + тонкий внешний слой». parseArgs легко протестировать на массивах, а скрипт только склеивает части.

Подсказка

Аргументы программы начинаются с индекса 2: process.argv.slice(2). Флаг без значения — это когда следующий элемент отсутствует или тоже начинается с --.

Решение и разбор
// args.mjs
export function parseArgs(argv) {
  const result = {};
  for (let i = 0; i < argv.length; i++) {
    const arg = argv[i];
    if (!arg.startsWith('--')) continue;
    const next = argv[i + 1];
    if (next === undefined || next.startsWith('--')) {
      result[arg.slice(2)] = true;
    } else {
      result[arg.slice(2)] = next;
      i++;
    }
  }
  return result;
}
// list.mjs
import { readFile } from 'node:fs/promises';
import path from 'node:path';
import { parseArgs } from './args.mjs';

const args = parseArgs(process.argv.slice(2));
const products = JSON.parse(await readFile(path.join(import.meta.dirname, 'products.json'), 'utf8'));

const limit = args.limit === undefined ? Infinity : Number(args.limit);
const found = products.filter((p) => !args.category || p.category === args.category).slice(0, limit);
console.log(found.map((p) => p.title).join('\n'));

Значения остаются строками, превращает их в числа тот, кто знает смысл (Number(args.limit)). parseArgs не знает, что limit — число. В Node есть встроенный util.parseArgs с описанием опций (из общих знаний), но написать свой простой разбор полезно хотя бы раз, чтобы понимать, что там внутри.

Задача 8. Код выхода и поток ошибок ★☆☆ разминка

Доработайте list.mjs: если передана неизвестная категория, скрипт пишет сообщение в поток ошибок (console.error) и завершается с кодом 1. Проверьте в терминале: node list.mjs --category toys; echo $?.

// products.json
[
  { "id": 1, "title": "Чистый код", "category": "books", "price": 150000 },
  { "id": 2, "title": "Каркассон", "category": "games", "price": 249000 }
]

Зачем: скрипты запускают другие скрипты, CI и git-хуки. Им нужен не текст, а код выхода. Сообщения об ошибках идут в отдельный поток, чтобы node list.mjs > out.txt не смешал результат с ошибками.

Решение и разбор
// list.mjs
import { readFile } from 'node:fs/promises';
import path from 'node:path';

const category = process.argv[2];
const products = JSON.parse(await readFile(path.join(import.meta.dirname, 'products.json'), 'utf8'));
const known = new Set(products.map((p) => p.category));

if (category && !known.has(category)) {
  console.error(`Неизвестная категория «${category}». Есть: ${[...known].join(', ')}`);
  process.exit(1);
}

const found = products.filter((p) => !category || p.category === category);
console.log(found.map((p) => p.title).join('\n'));

Сообщение помогает исправить ошибку: в нём перечислены существующие категории. Здесь подходит process.exit(1): после ошибки делать больше нечего. В задаче про проверки в уроке тестирования мы выбирали process.exitCode, потому что там нужно было продолжить работу. Список категорий взят из данных, а не написан руками, поэтому новая категория не потребует правки скрипта.

Переменные окружения и .env

Переменные окружения — настройки, которые передаются программе снаружи, а не пишутся в коде: порт, адрес базы данных, секретные ключи. Один и тот же код запускают на ноутбуке и на сервере с разными значениями. А секреты не попадают в git (документация).

Локально их удобно держать в файле .env в корне проекта:

PORT=4000
MONGO_URI=mongodb://localhost:27017/todo
JWT_SECRET=длинная-случайная-строка

Прочитать его можно двумя способами:

  • Встроенный флаг (Node.js 20.6+): node --env-file=.env app.js.
  • Пакет dotenv, как в уроке о JWT: require('dotenv').config() в самом начале программы.

Проверка: node --env-file=.env -e "console.log(process.env.PORT, typeof process.env.PORT)" вывела 4000 string. Все значения в process.env — строки, числа и логические значения нужно преобразовать: Number(process.env.PORT) || 3000. Файл .env всегда добавляют в .gitignore, а в репозиторий кладут .env.example — файл-образец с названиями переменных без настоящих значений.

Задача 9. Конфигурация из окружения ★★☆ практика

Напишите loadConfig(env = process.env), которая возвращает { port, nodeEnv, apiKey }. Правила: PORT по умолчанию 3000, должен быть целым числом от 1 до 65535, иначе ошибка с названием переменной. NODE_ENV по умолчанию 'development'. API_KEY обязателен только при NODE_ENV=production.

Зачем: неверная настройка должна ронять сервер сразу при старте с понятным текстом («PORT должен быть числом, получено "abc"»), а не через час странным поведением. Параметр env делает функцию чистой: тесты передают объект, а не меняют process.env.

Решение и разбор
// config.mjs
export function loadConfig(env = process.env) {
  const port = env.PORT === undefined ? 3000 : Number(env.PORT);
  if (!Number.isInteger(port) || port < 1 || port > 65535) {
    throw new Error(`PORT должен быть целым числом от 1 до 65535, получено "${env.PORT}"`);
  }

  const nodeEnv = env.NODE_ENV ?? 'development';
  const apiKey = env.API_KEY;
  if (nodeEnv === 'production' && !apiKey) {
    throw new Error('API_KEY обязателен в production');
  }

  return { port, nodeEnv, apiKey };
}

Все значения в окружении — строки, поэтому Number и проверка. Конфигурацию читают в одном месте, при запуске, и дальше передают готовый объект. Тогда в коде нет разбросанных process.env.X, и сразу видно, какие настройки есть у приложения. Ключ необязателен в разработке, чтобы новичку не нужно было добывать секрет ради запуска на своём компьютере.

Задача 10. .env и .env.example ★☆☆ разминка

Подключите loadConfig из прошлой задачи в server.mjs, который просто печатает итоговую конфигурацию без ключа. Создайте .env с PORT=4000 и .env.example с пустыми значениями. Запустите с --env-file. Добавьте .env в .gitignore.

Зачем: .env.example — документация «какие настройки нужны», которая живёт в репозитории, а секреты остаются у каждого свои. Без него новичок узнаёт о переменной, только когда сервер упадёт.

Решение и разбор
// server.mjs
import { loadConfig } from './config.mjs';

const { port, nodeEnv } = loadConfig();
console.log(`Сервер: порт ${port}, режим ${nodeEnv}`);
// config.mjs
export function loadConfig(env = process.env) {
  const port = env.PORT === undefined ? 3000 : Number(env.PORT);
  if (!Number.isInteger(port) || port < 1 || port > 65535) throw new Error(`PORT неверный: "${env.PORT}"`);
  const nodeEnv = env.NODE_ENV ?? 'development';
  if (nodeEnv === 'production' && !env.API_KEY) throw new Error('API_KEY обязателен в production');
  return { port, nodeEnv, apiKey: env.API_KEY };
}
// .env.example
PORT=
NODE_ENV=
API_KEY=

Команда: node --env-file=.env server.mjs выведет «порт 4000». В .gitignore строка .env, а .env.example коммитится. Ключ намеренно не печатается: логи часто попадают туда, где их читают многие.

Файлы: fs

Модуль fs (file system) работает с файлами. У большинства функций три вида: с колбэком (fs.readFile), синхронный (fs.readFileSync) и на промисах (fs/promises). В новом коде берите промисы, а синхронные — только в коротких скриптах: пока файл читается синхронно, сервер не отвечает никому.

import { readFile, writeFile } from 'node:fs/promises';
import path from 'node:path';

const file = path.join(import.meta.dirname, 'notes.txt');
await writeFile(file, 'первая строка\n', 'utf8');
console.log(await readFile(file, 'utf8')); // первая строка

try {
  await readFile(path.join(import.meta.dirname, 'nope.txt'), 'utf8');
} catch (error) {
  console.log(error.code); // ENOENT — такого файла нет
}

Без второго аргумента 'utf8' readFile вернёт не строку, а Buffer — набор байтов. Ошибки Node.js имеют свойство code: ENOENT (нет файла), EACCES (нет прав), EADDRINUSE (порт занят) — по нему удобно ветвиться, как учил урок об обработке ошибок.

Задача 11. Сколько строк в файле ★☆☆ разминка

Упражнение из урока: count.mjs получает имя файла из аргументов, читает его через fs/promises и печатает число строк. Если файла нет — понятное сообщение и код 1. Если аргумента нет — подсказка, как запускать, и код 1.

Зачем: это скелет любой утилиты: аргументы → чтение → результат, а ошибки — понятными словами. Обработка по error.code отделяет ожидаемую ситуацию («нет файла») от настоящей поломки.

Решение и разбор
// count.mjs
import { readFile } from 'node:fs/promises';

const file = process.argv[2];
if (!file) {
  console.error('Использование: node count.mjs <файл>');
  process.exit(1);
}

try {
  const text = await readFile(file, 'utf8');
  const lines = text === '' ? 0 : text.split('\n').length - (text.endsWith('\n') ? 1 : 0);
  console.log(lines);
} catch (error) {
  if (error.code !== 'ENOENT') throw error;
  console.error(`Файл не найден: ${file}`);
  process.exit(1);
}

Файл "a\nb\n" — это две строки, а не три: завершающий перенос не начинает новую строку. Это граничный случай, о котором стоит подумать. Ошибки, кроме ENOENT, пробрасываются дальше. Если нет прав (EACCES), честнее упасть с настоящей причиной, чем соврать «не найден».

Задача 12. JSON-хранилище с значением по умолчанию ★★☆ практика

Напишите модуль store.mjs с двумя функциями. readJson(file, fallback) возвращает разобранный JSON, а если файла нет — fallback. Любая другая ошибка, включая битый JSON, пробрасывается. writeJson(file, data) сохраняет с отступом 2 и переносом строки в конце.

Зачем: это будет «база данных» каталога до Mongo. Важное решение: отсутствующий файл — нормальная ситуация (первый запуск), а битый файл — авария, которую нельзя молча заменить пустым массивом, иначе следующая запись сотрёт все данные.

Решение и разбор
// store.mjs
import { readFile, writeFile } from 'node:fs/promises';

export async function readJson(file, fallback) {
  try {
    return JSON.parse(await readFile(file, 'utf8'));
  } catch (error) {
    if (error.code === 'ENOENT') return fallback;
    throw error;
  }
}

export async function writeJson(file, data) {
  await writeFile(file, JSON.stringify(data, null, 2) + '\n', 'utf8');
}

У ошибки JSON.parse нет code, поэтому она пробрасывается. Посмотрите, что случилось бы с «удобным» catch { return fallback }: файл повредился → прочитали [] → добавили товар → записали массив из одного товара. Остальные данные потеряны без единой ошибки в логе.

Задача 13. Запись, которую нельзя оборвать на середине ★★★ с подвохом

Если процесс упадёт посреди writeFile, на диске останется половина JSON. Сделайте writeJsonAtomic(file, data): сначала пишет во временный файл рядом (file + '.tmp'), затем переименовывает его в нужное имя через rename из fs/promises.

Зачем: переименование файла в пределах одного диска выполняется целиком или никак (из общих знаний об операционных системах), поэтому читатель видит либо старую, либо новую версию, но не обрывок. Так же поступают редакторы и базы данных. Это пример инженерного мышления: думать не только о том, как должно работать, но и о том, как это может сломаться.

Решение и разбор
// atomic.mjs
import { writeFile, rename } from 'node:fs/promises';

export async function writeJsonAtomic(file, data) {
  const tmp = `${file}.tmp`;
  await writeFile(tmp, JSON.stringify(data, null, 2) + '\n', 'utf8');
  await rename(tmp, file);
}

Временный файл лежит в той же папке: при переименовании между разными дисками атомарность не гарантирована. Ограничение решения: два одновременных вызова запишут один и тот же .tmp. Для учебного каталога это допустимо, а настоящая база данных решает и эту задачу. Это одна из причин, почему данные в итоге переезжают в базу.

Пути: path

Пути в Windows пишутся через \, в macOS и Linux через /. Модуль path собирает их правильно для любой системы, поэтому строки руками не склеивают:

  • path.join('src', 'routes', 'todos.js') → src/routes/todos.js.
  • path.resolve('public') → абсолютный путь от папки запуска.
  • path.extname('photo.final.jpg') → .jpg; path.basename(file) → имя файла.

Относительные пути в readFile('data.json') считаются от process.cwd(), а не от файла с кодом. Запустили из другой папки — файл «пропал». Надёжнее строить путь от import.meta.dirname или __dirname.

Пути от пользователя. Если часть пути приходит из запроса (имя картинки, файла для скачивания), просто склеить её с папкой опасно: path.join('public', '../../.env') выйдет за пределы public. Эта уязвимость называется path traversal. Защита: получить итоговый путь через path.resolve(root, userPath) и проверить, что он начинается с path.resolve(root) + path.sep. Готовый express.static такие проверки делает сам.

Задача 14. Путь к данным от файла, а не от терминала ★☆☆ разминка

Скрипт ниже работает, только если запускать его из папки проекта. Исправьте его так, чтобы data/products.json находился при запуске из любой папки. Строки путей руками не склеивайте.

// starter.mjs
import { readFile } from 'node:fs/promises';
const products = JSON.parse(await readFile('data/products.json', 'utf8'));
console.log(products.length);
// data/products.json
[{ "id": 1 }, { "id": 2 }]

Зачем: сервер на хостинге запускают из какой угодно папки, а cron-задачи — вообще из домашней. Код, который зависит от того, откуда его запустили, однажды не найдёт свои файлы в самый неудобный момент.

Решение и разбор
// count-products.mjs
import { readFile } from 'node:fs/promises';
import path from 'node:path';

const file = path.join(import.meta.dirname, 'data', 'products.json');
const products = JSON.parse(await readFile(file, 'utf8'));
console.log(products.length);

Относительный путь в readFile считается от process.cwd(). path.join соберёт путь с правильным разделителем для Windows и Unix. Каждая часть передаётся отдельным аргументом, без '/' в строках.

Задача 15. Не выпустить пользователя из папки ★★★ с подвохом

Сервер отдаёт картинки товаров по имени из адреса: /images/lamp.jpg. Напишите safeResolve(root, userPath): возвращает абсолютный путь внутри root или бросает ошибку, если путь выходит за её пределы (../../etc/passwd, абсолютный /etc/passwd).

Зачем: это уязвимость path traversal: склеив папку с именем из запроса, сервер отдаст любой файл, до которого дотянется, вплоть до .env с секретами. Проверять нужно итоговый путь после разрешения всех .., а не искать в строке «плохие» символы.

Подсказка

path.resolve(root, userPath) сам разрешит все ... Затем проверьте, что результат начинается с root + path.sep.

Решение и разбор
// safe.mjs
import path from 'node:path';

export function safeResolve(root, userPath) {
  const base = path.resolve(root);
  const full = path.resolve(base, userPath);
  if (!full.startsWith(base + path.sep)) {
    throw new Error('Путь вне разрешённой папки');
  }
  return full;
}

Проверяется результат resolve: так ловится любая форма обхода, включая абсолютный путь, который resolve просто подставит вместо базы. Разделитель в конце (base + path.sep) важен: без него папка /srv/images-secret «начиналась бы» с /srv/images. Сама папка root тоже отклоняется, ведь отдать нужно файл внутри неё. Готовый express.static такие проверки уже делает. Собственный код нужен, когда вы читаете файлы по имени из запроса вручную.

События: EventEmitter

Многие объекты Node.js (сервер, потоки, процесс) сообщают о происходящем через события, как кнопки в браузере. Основа — класс EventEmitter:

const { EventEmitter } = require('node:events');

const shop = new EventEmitter();
shop.on('order', (id) => console.log('новый заказ', id));
shop.emit('order', 42);
console.log('после emit');
// новый заказ 42
// после emit

on подписывается, emit вызывает всех подписчиков — синхронно, сразу. Если у эмиттера случилось событие 'error', а подписчика на него нет, программа упадёт, поэтому на 'error' подписываются всегда.

Задача 16. Магазин на событиях ★★☆ практика

Сделайте класс Shop extends EventEmitter с методом placeOrder(items): для непустого заказа генерирует событие 'order' с объектом { id, total } (id растёт с 1), для пустого — событие 'error' с Error. Подпишите два обработчика на 'order': «письмо» и «лог», и один на 'error'.

Зачем: события развязывают части программы: магазин не знает, кто реагирует на заказ. Завтра добавится аналитика, и для этого понадобится новый подписчик, а не правка placeOrder. Подписка на 'error' обязательна, иначе ошибка уронит процесс.

Решение и разбор
// shop.mjs
import { EventEmitter } from 'node:events';

export class Shop extends EventEmitter {
  #nextId = 1;

  placeOrder(items) {
    if (items.length === 0) {
      this.emit('error', new Error('Пустой заказ'));
      return;
    }
    const total = items.reduce((sum, i) => sum + i.price * i.quantity, 0);
    this.emit('order', { id: this.#nextId++, total });
  }
}

const shop = new Shop();
shop.on('order', (o) => console.log(`письмо: заказ №${o.id}`));
shop.on('order', (o) => console.log(`лог: ${o.total}`));
shop.on('error', (e) => console.log(`ошибка: ${e.message}`));

emit вызывает подписчиков синхронно и по порядку подписки, поэтому «письмо» всегда раньше «лога». Без подписчика на 'error' emit('error') бросает ошибку прямо из placeOrder. Проверочный тест это показывает.
