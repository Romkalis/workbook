as, non-null assertion, as const и satisfies

Утверждение типа — просьба компилятору считать значение известным автору типом. Оно не проверяет данные. Сравните три задачи: Number(value) преобразует значение, typeof value проверяет его во время выполнения, а value as number лишь меняет представление для проверки типов.

Эти конструкции похожи внешне, но решают разные задачи. Различайте проверку контракта и просьбу поверить программисту.

Утверждение as не проверяет значение

const raw: unknown = "42";
const asserted = raw as number;
const converted = Number(raw);
console.log(typeof asserted, typeof converted); // string number

as number не преобразовало строку в число. Для преобразования нужен Number, а для безопасности ещё и проверка результата, например Number.isFinite. Утверждения разрешаются при достаточном пересечении типов; двойное as unknown as T позволяет обойти ограничение и часто скрывает ошибку. Предпочитайте сужение проверкой, если форма данных заранее неизвестна.

Задача 26. Замените as на настоящее преобразование ★☆☆ разминка

Код ниже компилируется, но считает сумму неправильно. Найдите причину и исправьте без as: значения из формы должны стать числами, а нечисловые — давать ошибку.

const fromForm: unknown[] = ['100', '250'];
const prices = fromForm as number[];
const sum = prices.reduce((a, b) => a + b, 0);
console.log(sum); // "0100250" вместо 350

Зачем: as не меняет данные, он только просит компилятор замолчать. Поэтому ошибка тут не видна ни компилятору, ни в редакторе, а + склеивает строки. Это классика: «TypeScript же проверил!» — нет, вы попросили его не проверять.

Решение и разбор
export function toPrices(values: unknown[]): number[] {
  return values.map((v) => {
    const n = typeof v === 'number' ? v : Number(v);
    if (!Number.isFinite(n)) throw new TypeError(`Не число: ${String(v)}`);
    return n;
  });
}

const sum = toPrices(['100', '250']).reduce((a, b) => a + b, 0);
console.log(sum); // 350

Number(v) действительно преобразует значение, а Number.isFinite отсекает NaN от "abc". Функция возвращает number[] честно, без утверждений. Правило: если хочется написать as для внешних данных, на его месте должна быть проверка или преобразование.

Оператор !: ответственность на авторе

function size(value: string | null): number {
  if (value === null) return 0;
  return value.length;
}
const maybe: string | null = "TS";
console.log(maybe!.length, size(null)); // 2 0

! после выражения (input!.value) — это обещание компилятору: «здесь точно не null». TypeScript поверит на слово и ничего не проверит. Если обещание окажется ложным, программа упадёт при запуске, как в обычном JavaScript. Для DOM безопаснее проверить результат querySelector и при необходимости instanceof HTMLInputElement. value?.length безопасно возвращает undefined при отсутствии значения; это исполняемая операция, в отличие от утверждения !. Префиксный !value — обычное логическое отрицание JS.

Задача 27. Уберите опасный ! ★☆☆ разминка

Функция падает с TypeError, если товара нет в каталоге. Перепишите её без !: для отсутствующего товара возвращайте null и отразите это в типе результата.

const catalog = new Map<number, { title: string; price: number }>([[1, { title: 'A', price: 100 }]]);
export function priceOf(id: number): number {
  return catalog.get(id)!.price;
}

Зачем: ! переносит проверку из компилятора в вашу голову. Когда id приходит из адреса страницы или из корзины в localStorage, товара может уже не быть. Тип number | null заставит каждого вызывающего подумать, что показывать в этом случае.

Решение и разбор
const catalog = new Map<number, { title: string; price: number }>([[1, { title: 'A', price: 100 }]]);

export function priceOf(id: number): number | null {
  const product = catalog.get(id);
  return product ? product.price : null;
}

Map.get возвращает T | undefined — это правда о данных. Одна проверка сужает тип, и ! не нужен. Можно и короче: catalog.get(id)?.price ?? null. Оператор ?. — исполняемая проверка, а не обещание.

as const сохраняет литералы

const options = { mode: "read", size: 2 } as const;
const directions = ["up", "down"] as const;
type Direction = typeof directions[number]; // "up" | "down"
const direction: Direction = "up";
console.log(options.mode, direction);
if (false) {
  // @ts-expect-error: свойство стало readonly
  options.size = 3;
}

Без as const запись const roles = ["admin", "user"] получает тип string[]: просто какие-то строки. С as const тип становится readonly ["admin", "user"]: TypeScript запоминает точные значения и запрещает менять массив. Как и readonly, это работает только при проверке типов. Заморозить объект в работающей программе может только Object.freeze.

Задача 28. Категории: массив, тип и проверка ★★☆ практика

Объявите CATEGORIES = ['books', 'games', 'toys'] as const, выведите из него тип Category и напишите предикат isCategory(value: string): value is Category. Используйте его, чтобы безопасно разобрать категорию из адреса ?category=games.

Зачем: один источник правды: список категорий для меню и тип для проверок берутся из одного массива. Добавили категорию в массив — и меню, и тип, и проверка обновились сами.

Решение и разбор
export const CATEGORIES = ['books', 'games', 'toys'] as const;
export type Category = (typeof CATEGORIES)[number]; // 'books' | 'games' | 'toys'

export function isCategory(value: string): value is Category {
  return (CATEGORIES as readonly string[]).includes(value);
}

export function categoryFromQuery(search: string): Category | null {
  const value = new URLSearchParams(search).get('category');
  return value !== null && isCategory(value) ? value : null;
}

Без as const массив был бы string[], и тип Category выродился бы в string. С ним массив становится readonly ['books', 'games', 'toys'], а [number] берёт union элементов. Внутри isCategory расширяем массив до readonly string[], потому что includes у узкого кортежа принимает только известные строки. Это безопасное расширение, а не утверждение о неизвестных данных.

satisfies проверяет совместимость

type Channels = "success" | "error";
const colors = {
  success: [0, 128, 0],
  error: "red"
} satisfies Record<Channels, string | [number, number, number]>;
console.log(colors.error.toUpperCase(), colors.success[1]);

При аннотации : Record<...> чтение каждого значения дало бы широкий union. satisfies проверяет контракт, сохраняя полезную конкретику выражения: error остаётся строкой, success — кортежем. Контекст может влиять на вывод, поэтому это не обещание «тип никогда не меняется». Оператор появился в TS 4.9; в видео 2021 года его не будет.

ЗаписьЗадачаПроверка в runtime
: TЗадать тип и проверить присваиваниеНет
as T и !Утвердить то, что автор считает известнымНет
as constСохранить литеральность и readonlyНет
satisfies TПроверить контракт выраженияНет
typeof, instanceofПроверить реальное значение и сузить типДа

Задача 29. Промокоды через satisfies ★★☆ практика

Объявите словарь промокодов { SALE10: 10, SALE20: 20 } так, чтобы: 1) компилятор проверил, что все значения — числа; 2) тип PromoCode был 'SALE10' | 'SALE20', а не string. Напишите discountFor(code: PromoCode): number.

Зачем: аннотация Record<string, number> проверит значения, но сотрёт ключи: keyof станет string. satisfies проверяет контракт и оставляет конкретику, и это единственный способ получить и то и другое.

Решение и разбор
export const PROMO_CODES = {
  SALE10: 10,
  SALE20: 20,
} satisfies Record<string, number>;

export type PromoCode = keyof typeof PROMO_CODES; // 'SALE10' | 'SALE20'

export function discountFor(code: PromoCode): number {
  return PROMO_CODES[code];
}

if (false) {
  // @ts-expect-error: такого промокода нет
  discountFor('FREE');
}

Попробуйте написать SALE30: '30': satisfies сообщит, что строка не число. При этом тип PROMO_CODES остался точным, и keyof даёт union реальных ключей. Сравните с аннотацией const PROMO_CODES: Record<string, number>: тогда discountFor('FREE') скомпилируется и вернёт undefined во время работы.
