Generics и keyof: сохраняем связь типов

В identity буква T — место для конкретного типа. При вызове identity(42) компилятор подставляет числовой тип и сохраняет его в результате. Запись K extends keyof T читается как «K должен быть одним из ключей T», а T[K] — «тип значения по этому ключу».

Generic — параметр типа. Он нужен, когда несколько мест сигнатуры должны зависеть от одного выбранного типа. Замена всех типов на any эту связь теряет.

Функция и контейнер с параметром типа

function identity<T>(value: T): T { return value; }
interface Box<T> { value: T }
const box: Box<string> = { value: "TypeScript" };
const count = identity(42); // тип выведен из аргумента
const title = identity<string>(box.value); // тип задан явно
function first<T>(items: readonly T[]): T | undefined { return items[0]; }
console.log(count, title.toUpperCase(), first<number>([]));

В identity<T> один и тот же T описывает вход и выход. Компилятор чаще всего выводит его сам. Сигнатура first учитывает пустой массив: обещание просто T было бы неверным. Внутри generic-функции нельзя считать, что у любого T есть length.

Задача 22. Обобщённые last и uniqueBy ★★☆ практика

Напишите last<T>(items: readonly T[]): T | undefined и uniqueBy<T>(items, key), где key: (item: T) => string | number: оставляет первый элемент с каждым ключом. Проверьте, что last([1, 2]) имеет тип number | undefined, а не unknown или any.

Зачем: одна функция для товаров, заказов и пользователей без потери типа. С any вы бы получили функцию для всего, но после её вызова компилятор перестал бы помогать.

Решение и разбор
export function last<T>(items: readonly T[]): T | undefined {
  return items[items.length - 1];
}

export function uniqueBy<T>(items: readonly T[], key: (item: T) => string | number): T[] {
  const seen = new Set<string | number>();
  return items.filter((item) => {
    const k = key(item);
    if (seen.has(k)) return false;
    seen.add(k);
    return true;
  });
}

const n = last([1, 2]); // number | undefined
const products = uniqueBy([{ id: 1, t: 'a' }, { id: 1, t: 'b' }], (p) => p.id); // { id: number; t: string }[]
console.log(n, products);

T связывает вход и выход: какой массив передали, элементы такого типа и вернутся. T | undefined у last обязателен, ведь массив может быть пустым. В uniqueBy тип p в колбэке выводится из массива, хотя мы его нигде не писали. Set проверяет наличие за O(1), в отличие от поиска по массиву.

Ограничение extends

function lengthOf<T extends { length: number }>(value: T): number {
  return value.length;
}
console.log(lengthOf("TS"), lengthOf([1, 2, 3]));
if (false) {
  // @ts-expect-error: у числа нет свойства length
  lengthOf(42);
}

extends здесь задаёт минимальный контракт, а не наследование класса. Если нужно только прочитать length и нигде не сохранить T, достаточно параметра { length: number }. Generic полезен, когда связь типов реально используется.

Задача 23. Ограничение: «что-то с длиной» ★★☆ практика

Напишите longest<T extends { length: number }>(a: T, b: T): T: возвращает более длинное значение (при равенстве — первое). Проверьте на строках и массивах, а вызов с числами пометьте @ts-expect-error.

Зачем: extends в generic задаёт минимальное требование: «мне неважно, что это, лишь бы была длина». Без ограничения внутри функции нельзя прочитать .length, а с конкретным типом string функция потеряла бы массивы.

Решение и разбор
export function longest<T extends { length: number }>(a: T, b: T): T {
  return b.length > a.length ? b : a;
}

const word = longest('кот', 'собака'); // string
const list = longest([1], [1, 2]); // number[]
console.log(word, list);
if (false) {
  // @ts-expect-error: у number нет length
  longest(1, 2);
}

Почему generic, а не параметр { length: number }? Здесь T возвращается, и вызывающий получает string или number[], а не безликое «что-то с длиной». Если бы функция возвращала только число (длину), generic был бы не нужен: правило из раздела «generic полезен, когда связь типов реально используется».

keyof и доступ к типу свойства

function get<T, K extends keyof T>(object: T, key: K): T[K] {
  return object[key];
}
const student = { name: "Маша", score: 95 };
type StudentKey = keyof typeof student; // "name" | "score"
const key: StudentKey = "score";
console.log(get(student, key).toFixed(0), get(student, "name").toUpperCase());
if (false) {
  // @ts-expect-error: такого ключа нет
  get(student, "age");
}

typeof student в позиции типа получает тип переменной, keyof — объединение ключей этого типа, T[K] — тип выбранного свойства. В JS-выражении typeof по-прежнему возвращает строку. У числовой индексной сигнатуры keyof будет number; у строковой — string | number, потому что числовые ключи JS-объекта преобразуются в строки.

Задача 24. pluck и sortBy по ключу ★★☆ практика

Напишите pluck(items, key): собирает значения одного поля, тип результата — массив значений этого поля. И sortBy(items, key), где key — ключ, значение которого число; функция не меняет исходный массив. Неверный ключ должен быть ошибкой компиляции.

Зачем: keyof и T[K] позволяют написать функцию «по имени поля» без строк, которые никто не проверяет. Переименовали поле в типе — компилятор покажет все вызовы со старым именем.

Подсказка

Для sortBy ограничьте ключ: K extends keyof T, а значение по нему должно быть числом: T extends Record<K, number>.

Решение и разбор
export function pluck<T, K extends keyof T>(items: readonly T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}

export function sortBy<K extends PropertyKey, T extends Record<K, number>>(items: readonly T[], key: K): T[] {
  return [...items].sort((a, b) => a[key] - b[key]);
}

const products = [{ title: 'B', price: 200 }, { title: 'A', price: 100 }];
const titles = pluck(products, 'title'); // string[]
const cheapFirst = sortBy(products, 'price');
console.log(titles, cheapFirst);
if (false) {
  // @ts-expect-error: нет такого поля
  pluck(products, 'cost');
  // @ts-expect-error: title — не число, по нему так сортировать нельзя
  sortBy(products, 'title');
}

В pluck тип T[K][] означает «массив значений поля K»: для 'title' получится string[]. В sortBy ограничение записано через Record<K, number>: объект должен иметь числовое поле K, иначе вычитание a[key] - b[key] не имело бы смысла. Копия [...items] — потому что sort меняет массив на месте.

Готовые преобразования типов

Дополнение из общих знаний, сверяемое со справочником TypeScript: Partial<T> делает свойства необязательными, Required<T> — обязательными, Readonly<T> — доступными только для чтения. Pick<T, K> оставляет выбранные ключи, Omit<T, K> исключает их. Это изменения типов, не преобразования объектов во время выполнения.

interface Profile { id: number; name: string; bio?: string }
const patch: Partial<Profile> = { name: "Анна" };
const card: Pick<Profile, "id" | "name"> = { id: 1, name: "Маша" };
console.log({ ...card, ...patch });

Задача 25. Частичное обновление товара ★★☆ практика

Напишите updateProduct(product, patch), где patch может содержать любые поля товара, кроме id. Функция возвращает новый объект. Также опишите ProductPreview — только id и title — через утилитарный тип.

Зачем: форма редактирования отправляет только изменённые поля, но менять идентификатор нельзя. Это правило бизнес-логики, и его можно выразить типом Partial<Omit<...>>, а не комментарием.

Решение и разбор
export interface Product { id: number; title: string; price: number; description?: string }

export type ProductPatch = Partial<Omit<Product, 'id'>>;
export type ProductPreview = Pick<Product, 'id' | 'title'>;

export function updateProduct(product: Product, patch: ProductPatch): Product {
  return { ...product, ...patch };
}

if (false) {
  const p: Product = { id: 1, title: 'A', price: 1 };
  // @ts-expect-error: id нельзя менять патчем
  updateProduct(p, { id: 2 });
}

Утилиты собираются как конструктор: Omit убирает id, Partial делает остальное необязательным. Возвращается новый объект, исходный не меняется: так проще отследить изменения (например, сравнить «до» и «после»). Утилитарные типы работают только при проверке: Omit не удалит id из реального объекта, если он придёт через any.
