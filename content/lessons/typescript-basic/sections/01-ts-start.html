TypeScript и JavaScript: что меняется

Компилятор TypeScript — программа tsc: она проверяет код и может получить из .ts JavaScript-файлы .js. Тип описывает допустимые значения, аннотация — явная запись вроде : number, контракт — договорённость об аргументах и результате. «Во время выполнения» означает, что JavaScript уже запущен, а большая часть TS-записей удалена.

TypeScript помогает проверить договорённости о данных до запуска программы. Если функция ждёт число, редактор укажет на переданную строку. При этом арифметика, объекты, прототипы и обработка событий остаются JavaScript. Чтобы учиться по этому уроку, уже нужно понимать переменные, функции, массивы и классы JS.

Работайте в два прохода: сначала прочитайте пример и предскажите результат, затем запустите его и объясните типы. В уроке есть намеренные ошибки: строки с @ts-expect-error должны отклоняться компилятором. Директива нужна только для проверки учебных примеров; исправлять ею прикладной код не следует.

Типы до запуска, значения во время выполнения

function double(value: number): number {
  return value * 2;
}
console.log(double(21)); // 42
if (false) {
  // @ts-expect-error: строка не является числом
  double("21");
}

В записи value: number после двоеточия описан параметр, а после скобок — результат функции. Эти аннотации исчезнут из выпущенного JS. Если проверку обойти и передать строку, поведение определит JavaScript, а не аннотация. TypeScript не добавляет автоматическую проверку ответа сервера. Большинство типов стирается, но обычные классы и enum создают код выполнения.

Задача 1. Контракт функции цены ★☆☆ разминка

Напишите функцию formatPrice: она принимает цену в копейках (число) и возвращает строку вида "1500.00 ₽". Добавьте аннотации параметра и результата. Ниже вызова с числом напишите вызов со строкой "1500" и пометьте его // @ts-expect-error: компилятор должен его отклонить.

Зачем: аннотация на границе функции — это договор. Тот, кто вызывает функцию, видит, что передавать, а ошибка «передал строку» ловится в редакторе, а не у пользователя.

Подсказка

Копейки в рубли: деление на 100. Два знака после точки даёт toFixed(2).

Решение и разбор
export function formatPrice(kopecks: number): string {
  return `${(kopecks / 100).toFixed(2)} ₽`;
}

console.log(formatPrice(150000)); // 1500.00 ₽

if (false) {
  // @ts-expect-error: строка не число
  formatPrice('1500');
}

Аннотации : number и : string исчезнут после компиляции, но до запуска они не дадут передать строку. Результат тоже аннотирован: если кто-то потом поменяет тело так, что функция вернёт число, ошибка появится в самой функции, а не у всех, кто её вызывает. @ts-expect-error — способ доказать, что неверный вызов запрещён: если ошибки вдруг не будет, компилятор пожалуется на лишнюю директиву.

Задача 2. Типы не защищают во время работы ★★☆ практика

Функция ниже типизирована, но её вызывает JavaScript-код, который прислал строку. Не меняя сигнатуру, добавьте проверку во время выполнения: если пришло не конечное число, бросьте TypeError с понятным сообщением.

export function applyDiscount(price: number, percent: number): number {
  return price - (price * percent) / 100;
}
// где-то в JS: applyDiscount("1000", 10) → "1000" - 100 = 900? А "1000" * 10 ...

Зачем: типы стираются при сборке. Всё, что приходит из JS-кода, формы, сети или localStorage, может оказаться чем угодно. Аннотация описывает намерение, а проверка защищает от реальности.

Подсказка

Number.isFinite(x) возвращает true только для обычного числа: не для строки, NaN или Infinity.

Решение и разбор
export function applyDiscount(price: number, percent: number): number {
  if (!Number.isFinite(price) || !Number.isFinite(percent)) {
    throw new TypeError(`applyDiscount: ожидались числа, получено ${typeof price} и ${typeof percent}`);
  }
  return price - (price * percent) / 100;
}

В типах ничего не поменялось: внутри TypeScript-кода проверка выглядит лишней, ведь price уже number. Но она нужна на границе, там, где в код попадают данные снаружи. Внутри доверяем типам, на краях проверяем. Number.isFinite, в отличие от глобального isFinite, не приводит строку к числу, поэтому "1000" не пройдёт.

Первый запуск и настройки

Самый короткий путь — открыть TypeScript Playground, включить Strict и сравнить вкладки TypeScript и JavaScript. Для отдельного учебного проекта установите локальный компилятор. Команды ниже выполняются в новой папке, где установлен Node.js; src/index.ts содержит первый пример.

npm init -y
npm install --save-dev typescript
npx tsc --init
npx tsc --project tsconfig.json
node dist/index.js
Какая версия поставится

Сейчас эта команда ставит TypeScript 7 — компилятор, переписанный на Go: tsc в нём работает как раньше. Но ts-loader для Webpack и typescript-eslint пока требуют TypeScript 5.x. Если они нужны в проекте, ставьте typescript@5.9 (подробности — в уроке TypeScript Advanced).

Замените созданный конфиг следующим минимальным вариантом. Здесь target задаёт уровень выходного JS, module — формат модулей, outDir — папку результата. Это вариант для небольших упражнений в Node.js, а настройки приложения с бандлером могут отличаться.

{
  "compilerOptions": {
    "target": "ES2020",
    "module": "CommonJS",
    "strict": true,
    "noEmitOnError": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src/**/*.ts"]
}

strict включает семейство строгих проверок, в том числе noImplicitAny и strictNullChecks. noEmitOnError запрещает выпуск JS при ошибках; без этой опции диагностика и выпуск кода — разные процессы. tsc --noEmit только проверяет типы. Не передавайте имя файла вместе с ожиданием, что автоматически применится ваш tsconfig: используйте --project.

Практический совет из общих знаний: сохраните конфигурацию, исходники и lock-файл зависимостей вместе. Так другой студент сможет повторить запуск с той же версией компилятора.

Создайте отдельную папку для упражнения, откройте в ней терминал, затем выполните команды установки. Перед сборкой создайте папку src, файл src/index.ts с первым примером и tsconfig.json из блока ниже. Команды npx tsc и node dist/index.js выполняйте только после создания этих файлов. В Playground включите strict и выберите target ES2020: это важно для примера с bigint.

Задача 3. Проект, который не собирается с ошибкой ★☆☆ разминка

Создайте учебный проект по разделу выше. Добавьте в package.json два скрипта: check только проверяет типы, build собирает в dist. Затем намеренно сделайте ошибку типа в src/index.ts и убедитесь, что npm run build завершается с ошибкой и не создаёт файлы в dist.

Зачем: проверка, которую надо помнить запустить, рано или поздно не запустится. Скрипты в package.json — общий язык команды и CI. noEmitOnError гарантирует, что сломанный код не уедет дальше.

Подсказка

Перед проверкой удалите старую папку dist, иначе увидите файлы прошлой сборки.

Решение и разбор
{
  "scripts": {
    "check": "tsc --noEmit --project tsconfig.json",
    "build": "tsc --project tsconfig.json"
  }
}

С "noEmitOnError": true из конфигурации раздела tsc печатает ошибку и не пишет ни одного файла, а код выхода ненулевой: CI тоже увидит провал. Без этого флага TypeScript выпустил бы JavaScript, несмотря на ошибку. Проверка типов и выпуск кода — разные процессы. Скрипт check быстрее: он ничего не записывает, его удобно гонять перед коммитом.
